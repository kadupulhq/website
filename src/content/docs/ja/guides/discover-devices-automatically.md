ソースは利用可能ですが、サポートされている Kadupul のリリースや移行パスはありません。これらに依存する前に、バックアップを用意した隔離環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。

自動化は混同しやすい2つの独立した仕組みで構成されています。検出（Discovery）はアドレスの範囲を走査して何がデバイスであるかを判断します。ルール（Rules）は、デバイスが存在した後に何を作成するかを決定します。どちらか一方を単独で実行することもできますが、自動化によって発生する問題の多くは、両方を同時にオンにして後から気づくことに起因します。

## 範囲を定義する

ネットワーク範囲はカンマ区切りのリストです。各エントリは次の3つの形式のいずれかです。

| 形式 | 例 | 備考 |
|---|---|---|
| CIDR | `192.168.1.0/24` | ドット区切りのマスク `192.168.1.0/255.255.255.0` も受け入れます |
| ワイルドカード | `192.168.*.*` | 内部で同等の CIDR に変換されます |
| 単一アドレス | `192.168.1.10` | そのアドレスのみをスキャンします |

`192.168.1.10-192.168.1.50` のように記述された開始から終了までの範囲はエラーで拒否されます。これらはサポートされていません。

同時に実行される可能性のあるネットワーク間を含め、重複しない範囲を使用してください。作業テーブルには IP アドレスに対するグローバル一意キーがあります。重複があると挿入バッチ全体が拒否され、そのバッチ内の他のアドレスが除外される可能性があります。[イシュー #207](https://github.com/kadupulhq/kadupul/issues/207) を参照してください。

すべて IPv4 です。範囲の計算には全体を通して 32 ビット整数の変換が使用されるため、ここには IPv6 のパスはありません。

ネットワークアドレスとブロードキャストアドレスは除外されます。`/24` は `.1` から `.254` までの 254 アドレスをスキャンします。単一アドレスエントリは1つをスキャンします。最後のオクテットが 255 のアドレスもスキャン中にスキップされます。

スキャンが開始される前に、範囲内のすべてのアドレスが作業テーブルに1アドレスにつき1行として書き込まれ、スレッドがそこから行を取得します。`/16` では、最初の ping の前に 65534 行が書き込まれます。これは実際のコストであり、応答がない場合でも大規模な疎な範囲のスキャンが遅くなる理由です。

各範囲に SNMP オプションセットをアタッチします。マスターモードでは、SNMP セット ID がゼロの範囲はエラーをログに記録してスキップします。対象を絞った実行ではその同一のガードが適用されません。直接開始しても、欠落している SNMP オプションが使用可能になるわけではありません。

## スキャンのペースを調整する

| 設定 | 動作 | デフォルト |
|---|---|---|
| 検出スレッド数 | アドレスを取得する並行ワーカー | 1 |
| 実行制限 | 検出はこの時間を経過すると終了します | 20 分 |
| スケジュールタイプ | 手動、毎日、毎週、毎月、または指定日 | 手動 |
| Ping メソッド | ICMP、TCP、TCP closed、UDP、または SNMP | グローバル設定から取得 |
| Ping リトライ、タイムアウト | アドレスごとの障害コスト | グローバル設定から取得 |

スレッドと実行制限は、慎重に考慮しないと競合を引き起こします。侵入検知システムから見れば、`/16` に対する 50 スレッドはポートスキャンとみなされます。同じ範囲に対して 1 スレッドで実行すると、実行制限に達して途中で強制終了され、完全な結果に見える部分的な結果が残ります。

ネットワークが許容できるスレッド数で、制限時間内にスキャンが終了するように範囲のサイズを設定します。小さな範囲を複数設定する方が大きな範囲を1つ設定するよりも優れています。それぞれに独自のスケジュールと制限が適用されるためです。

## スキャンがアドレスごとに実行する処理

1. 名前を解決します。代替 DNS サーバーを空白区切りのリストとして指定できます。設定されていない場合は、ポーラー自身のレゾルバが使用されます。DNS が何も返さない場合、NetBIOS ルックアップはオプションのフォールバックとなります。
2. そのアドレスまたは名前がすでにデバイスであるかどうかを確認します。デバイスである場合、アドレスは完了としてマークされます。これにより、これらの値によって見つかった既存のデバイスが抑制されます。これは、同時作成や異なるエイリアスに対する保証ではありません。
3. 設定された方法を使用して ping を実行します。SNMP メソッドは個別の ping をバイパスします。
4. ping に応答がある場合、または SNMP メソッドが選択されている場合は、SNMP を試行し、`sysDescr`、`sysObjectID`、`sysName`、`sysLocation`、`sysContact`、および稼働時間を収集します。
5. 収集したシステムデータをデバイスルールと照合します。

ping に応答するが SNMP に応答しないアドレスは、検出され生存しているものとして記録されます。SNMP に応答するがどのデバイスルールにも一致しないアドレスは、システムデータとともに検出されたものとして記録され、何も作成されません。両方とも検出されたデバイスのリストに登録されます。

重複の抑制はデフォルトでオンになっています。このネットワークの保存された検出レコードにおいて、別のアドレスですでに `sysName` が確認されている場合、または異なるホスト名を持つデバイス上に存在する場合、そのアドレスはスキップされます。これは多数のアドレス指定されたインターフェースを持つルーターには適したデフォルトですが、別個の NAT アドレスの背後にある同一アプライアンスには適していません。同一 sysName オプションは、この挙動をオフにするために存在します。

既存のデバイスは、スキャン中にデータクエリを再実行できます。これはデフォルトでオフになっており、アップまたは回復中として記録されているデバイスに適用されます。検出はこの決定に保存されたステータスを使用し、既存のデバイスを新たにプローブすることはありません。

## デバイスルールによるテンプレートの決定

デバイスルールはシステムデータをデバイステンプレートにマッピングします。各ルールには、`sysDescr`、`sysObjectID`、および `sysName` のパターンが含まれます。マッチャーは、デバイスが空でない値として返した各システムフィールドに対してフィルタリングを行います。空白のルールパターンは任意の値に一致します。ルールは順序に従って評価され、最初の一致が優先されます。

単純なリテラル部分文字列を使用し、検出結果で選択されたテンプレートを確認してください。現在の SQL マッチャーは正規表現パターンをリテラル `/` 文字でラップするため、`^Linux.*fixture$` のようなアンカー付きパターンは、データベースの正規表現演算子が直接一致する場合でも失敗します。部分文字列フォールバックはそのケースを修復しません。[イシュー #206](https://github.com/kadupulhq/kadupul/issues/206) を参照してください。SQL `LIKE` も `%` と `_` をワイルドカードとして扱います。

一致しない場合はデバイスが作成されません。アドレスは収集されたシステムデータとともに検出されたデバイスのリストに記録され、そのリストこそが不足していたルールを作成する場所となります。

汎用ルールの前に特定のルールを配置します。ベンダーのルールの上に部分文字列 `Linux` に一致するルールを配置すると、説明に Linux が記載されているすべての機器がその対象になってしまいます。

## 作成を有効にする前に検出をプレビューする

新しい範囲のデバイス作成スイッチはデフォルトでオフになっています。最初のパスではオフのままにし、既存デバイスのデータクエリを再実行するオプションを無効にします。このパスでも検出レコード、スキャン統計、ログは更新され、設定された通知を送信できます。グラフやツリーのルールの実行はプレビューされません。

スキャンを実行し、検出されたデバイスのリストを確認します。そこには、記録された検出、収集された SNMP データ、および利用可能な場合は一致したテンプレートが表示されます。既存のデバイス、抑制された重複、スキップされたアドレスはそこに表示される必要はありません。リストとともに、アドレスごとのデバッグ出力も確認してください。

スケジュールを待たずにコマンドラインからスキャンを強制実行します。

```bash
php poller_automation.php --network=3 --force --debug
```

デバッグフラグは、アドレスごとの判定が発生したときにリアルタイムで出力します。スケジュールが到来した有効な範囲を起動するマスタープロセスは、別のモードです。

```bash
php poller_automation.php -M
```

対象を絞った `--force` コマンドは、無効化されたネットワークも実行します。マスターモードに `--force` を追加すると、スケジュールチェックがバイパスされ、無効化されたネットワークも起動できます。1つの範囲を検証する場合は、対象を絞った形式を使用してください。

作成をオンにする前に、結果で次の3点を確認してください。

- デバイス数が予想どおりであること。資産リストよりも大幅に多いカウントは、通常、範囲が思っていたよりも広いことを意味します。
- 選択されたテンプレートが適切であること。すべてに同じ汎用テンプレートの列が表示される場合は、ルールが一致していないことを意味します。
- 重要なものが欠落していないこと。見つからないデバイスについては、範囲の展開、ワーカーの完了、既存デバイスおよび重複の抑制、ping ポリシー、SNMP の結果を確認してください。リストにないことだけでは、到達不能であると判断できません。

## グラフおよびツリールール

デバイスが存在すると、グラフルールとツリールールによってその上に何が構築されるかが決定されます。検出はデバイスの作成後にこの自動化を呼び出すことができ、CLI は既存のデバイスにそれを適用できます。個別のグラフおよびツリールールを有効にする必要があります。グローバルなグラフ/ツリー自動化スイッチは特定の作成フックを制御するものであり、明示的な CLI 自動化を全面的に禁止するものではありません。

グラフルールには3つの部分があります。どのデバイスに適用されるか、データクエリ内のどの検出されたインデックスに適用されるか、そしてどのグラフタイプを作成するかです。どちらのマッチング部分もルール項目から構築され、ルール項目はフィールド、演算子、パターンで構成され、括弧付きの `AND` または `OR` で結合されます。

| 演算子グループ | メンバー |
|---|---|
| 部分文字列 | contains, does not contain, begins with, does not begin with, ends with, does not end with |
| 完全一致 | matches, is not equal to |
| 数値 | is less than, less than or equal, greater than, greater than or equal |
| 存在 | is unknown, is not unknown, is empty, is not empty |
| パターン | matches regular expression, does not match regular expression |

これらは SQL の `WHERE` 句になります。正規表現演算子は PCRE ではなくデータベースの正規表現方言であるため、`preg_match` で機能するパターンがここでも機能するとは限りません。数値パターンに対する数値比較は引用符なしで渡され、その他のすべては引用符で囲まれ、データベースはその型変換規則を適用します。実際にキャッシュされた値に対して数値フィルターをテストしてください。これらの値は通常テキストとして保存されます。部分文字列演算子は SQL `LIKE` を使用し、`%` と `_` はワイルドカードの意味を持ちます。

何もしないルールをデバッグする前に、知っておく価値のある2つの動作があります。

**空のデバイス/オブジェクトフィルターは何にも一致しませんが、空のインデックスフィルターはキャッシュされたすべてのインデックスに一致します。** デバイス選択フィルターは、一致する項目がない場合、false 条件にフォールバックします。ただし、グラフルールがデバイスに一致すると、そのグラフインデックス条件をすべて削除してもデータクエリはフィルターされないままになります。たとえば、`ifDescr = eth0` 条件を削除すると、`lo` に対してもグラフが作成される可能性があります。インデックス条件を編集する間は、ルールを無効にしてください。

**デバイスが検出していないフィールドを参照するルールは破棄されます。** ルールがそのデバイスのキャッシュにないデータクエリフィールドをフィルタリングする場合、実行時にそのフィールドを挙げた警告がログに記録され、そのデバイスに対するそのルールの処理が停止します。一般的な原因は、あるデータクエリに対して記述されたルールが、異なるフィールドセットを返したデバイス上で評価されることです。

ルール編集ページには、候補となるオブジェクトとグラフが一覧表示されます。ルールを有効にする前や編集した後に、これらのリストを確認してください。これらは選択のプレビューであり、完全なドライラン実行ではありません。データソースのチェック、既存グラフの検出、作成フック、ツリーへの挿入は、実行中に依然として発生します。CLI にはドライランオプションはありません。

ツリールールには個別のデバイスリーフとグラフリーフのタイプがあり、選択された宛先ツリーと親を持ちます。ヘッダーステップでは、固定文字列またはデバイス/グラフフィールドの値を使用できます。フィールドから派生したヘッダーには、大文字と小文字を区別しない PHP 正規表現の置換が適用されます。結果に含まれるリテラル `\n` シーケンスによって、連続するネストされたヘッダーに分割されます。この置換構文は、オブジェクトのマッチングに使用される SQL 正規表現とは異なります。既存のヘッダーとリーフは、同じツリーおよび親で再利用されます。パスを変更すると、古い配置を削除せずに別の配置を追加できます。

## すでに存在するデバイスにルールを適用する

検出だけが唯一の入口ではありません。ID、ホスト名、または説明によって選択された、システム内にすでに存在するデバイスに対してルールを実行できます。

```bash
php cli/apply_automation_rules.php --ids="12 13 14" --debug
php cli/apply_automation_rules.php --hostname="^edge-" --debug
php cli/apply_automation_rules.php --description="branch office"
```

値が有効な場合、ホスト名と説明は正規表現として照合され、常に部分文字列としても照合されます。3つのうち少なくとも1つが必要です。セレクターなしで呼び出すとエラーで終了します。セレクターを組み合わせると、`AND` で結合されます。絞り込みにはスペース区切りの正のデバイス ID を使用します。カンマ区切りの ID はサポートされていません。パターンは依然として広範に指定でき、SQL `LIKE` フォールバックは `%` と `_` をワイルドカードとして扱います。

セレクタークエリは無効化されたデバイスを自動的に除外しません。`--debug` は診断情報を追加しますが、作成は実行されます。一致するデバイスがない場合は正常な何もしない処理となるため、終了ステータスだけでは何かが作成されたことを証明できません。

一致するデバイスごとに、実行は次の3つの処理を順番に行います。

1. テンプレートの適合性とデータソースのチェックを条件として、デバイス上にグラフがないアタッチされたグラフテンプレートの作成を試みます。
2. 保存されたインデックスキャッシュを使用して、アタッチされたデータクエリに対して有効化されたグラフルールを実行します。このステップ自体は検出を再実行しません。キャッシュが見つからないか古い場合は、まずデータクエリを更新してください。
3. 有効化されたデバイスリーフのツリールールを適用します。

グローバルツリー自動化が有効になっている場合、新しいグラフの作成によってグラフリーフのツリールールが呼び出されることがあります。CLI は、すでに作成されているグラフに対してこれらのルールを再適用しません。したがって、新しいまたは変更されたグラフリーフルールは、CLI を再実行したからといって既存のグラフに自動的に適用されるわけではありません。[イシュー #211](https://github.com/kadupulhq/kadupul/issues/211) を参照してください。それらの配置は個別に検証してください。作成フックをトリガーするためだけに過去のグラフを削除して再作成しないでください。

繰り返しの実行では、デバイスとグラフテンプレートによって既存の非インデックスグラフが抑制されます。インデックス付きグラフは、デバイス、データクエリ、グラフタイプ、およびインデックスによってチェックされます。これにより、順次実行における重複作成が防止されます。これは同時実行の保証ではありません。実行後にグラフリストとツリーを確認し、スキップされたグラフ、無効なデータ、または作成の失敗に関する `AUTOM8` ログメッセージを確認してください。

混乱を招くほど静かにスキップされる点が1つあります。上書き可能とマークされ、デフォルト値を持たないフィールドを持つグラフテンプレートは、自動化の対象になりません。実行ログには、上書き可能なフィールドにデフォルト値がないため追加されなかったことが記録され、処理は次に進みます。期待するテンプレートが表示されない場合は、まずそれを確認してください。上書き可能なフィールドの詳細については、[テンプレート](/ja/concepts/templates/) を参照してください。

## 注意点

**ルールを無効にしても、その作業は元に戻りません。** すでに作成されたグラフやツリーのエントリは削除されません。デバイスの削除には個別のグラフおよびデータソースのクリーンアップ動作があります。デバイスを削除する前に削除オプションを確認してください。

**強制終了されたスキャンは正常終了したように見えます。** 実行制限により、どこまで到達していても検出は終了します。記録される合計は終了した作業の合計であり、結果が部分的であることを示すマークはありません。スキャンされたアドレス数を範囲のサイズと比較してください。

**ルールはデバイスではなく、データクエリのキャッシュに対して実行されます。** 何にも一致しないグラフルールは、多くの場合、データクエリが一度も実行されなかったか、実行されたもののインデックスが見つからなかったことを意味します。ルールを書き直す前に、検出されたインデックステーブルを確認してください。

**通知メールには既存の検出と新しい検出の両方が含まれます。** 範囲のスキャン完了時にメールを送信でき、各 IP がスキャン前のスナップショットに存在していたかどうかに基づいて、記録された検出をグループ化します。これは、要求されたすべてのアドレスがスキャンされたことの証明にはなりません。

## 障害モード

| 現象 | 一般的な原因 |
|---|---|
| アドレスが存在する範囲でスキャンが何も見つけない | Ping のブロック、SNMP の失敗、除外設定、または重複の抑制 |
| 範囲のスキャンが拒否され、ログにエラーが記録される | SNMP オプションセットがアタッチされていない |
| デバイスは見つかったが何も作成されない | 作成スイッチがオフ、またはデバイスルールが一致しない |
| すべてに同じ汎用テンプレートが適用される | ルールの順序の問題で、汎用ルールが特定ルールの上にある |
| 一部のアドレスしかスキャンされない | 実行制限に達したか、重複する範囲によってアドレスバッチが拒否された |
| インターフェースごとではなくルーターごとに1台、またはその逆 | 同一 sysName の重複抑制設定 |
