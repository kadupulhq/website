:::caution[상속된 RRDtool proxy 동작]
Kadupul에서는 RRDtool proxy 배포를 지원하지 않습니다. 로컬 RRDtool 스토리지
(`storage_location = 0`)를 사용하세요. 이 페이지의 proxy 설정, 프로토콜 설명 및
워크플로는 상속된 동작을 기록한 문서일 뿐이며 지원되는 배포나 마이그레이션 경로를
나타내지 않습니다. [RRDtool proxy](/ko/reference/rrdproxy/)를 참조하세요.
:::

:::caution[사용 전 검증]
소스를 사용할 수 있지만 지원되는 Kadupul 릴리스 또는 마이그레이션 경로는 아직
없습니다. 시스템에 의존하기 전에 백업이 포함된 격리된 사본에서 이 절차를
테스트하세요. [프로젝트 상태](/ko/project/status/)를 참조하세요.
:::

마이그레이션은 백업이 생성된 원본 머신과 다른 머신에 복원하는 작업입니다.
[백업 및 복원](/ko/guides/back-up-and-restore/)의 모든 지침이 여기에도 적용되며, 이 페이지는
대상 시스템이 원본 시스템과 다르기 때문에 발생하는 차이점만을 다룹니다.

세 가지 차이점이 존재하며, 각각 고유한 장애 유형을 유발합니다.

| 차이점 | 발생하는 장애 |
|---|---|
| 파일 경로 차이 | 데이터베이스 및 폴러 캐시에 저장된 파일 경로 훼손 |
| 사용자 및 그룹 ID 차이 | 파일 접근 권한 및 스토리지 신뢰 검사 실패 |
| 런타임 버전 차이 | 확장 모듈, 데이터베이스 동작 및 RRD 호환성 불일치 |

## 설정을 변경하기 전에

먼저 대상 머신을 구축하여 클린 설치가 정상 작동할 수 있는 상태로 준비하세요. 데이터베이스 서버 실행,
필수 PHP 확장 모듈 설치, RRDtool 준비, 선택한 수집기 사용 가능 상태, Web 서버 구성 완료 등이 포함됩니다.
이 단계에서는 폴러, 예약된 작업, 원격 복제 및 외부 알림을 모두 비활성화해 두세요. 설치 프로그램을
실행하지 마세요. 데이터베이스를 통째로 교체할 것이므로 어설프게 설치된 스키마는 빈 스키마보다 원인 분석이 훨씬 어렵습니다.

로컬 수정 사항 및 플러그인을 포함하여 애플리케이션 버전 및 종속성을 완벽히 일치시키세요. 데이터베이스의
`version` 테이블은 스키마 버전을 기록할 뿐 모든 소스 변경 사항을 기록하지 않으므로, 이 값만 일치시키는 것으로는
불충분합니다. 설치 프로그램으로 리디렉션되는 현상은 스키마 불일치나 불완전한 복원을 의미할 수 있습니다.
이전할 시스템과 정확히 동일한 코드를 대상 시스템에 설치하고, 마이그레이션을 수행하여 정상 작동을 확인한 다음,
[안전한 업그레이드](/ko/guides/upgrade-safely/)에 따라 별도의 작업으로 업그레이드를 진행하세요.

지금 설치 경로를 확정하세요. 두 머신에서 설치 경로를 동일하게 유지하면 아래 작업의 대부분을 생략할 수 있습니다.
동일하게 유지할 수 없다면 시작하기 전에 경로 섹션을 주의 깊게 읽어보세요.

## 작업 순서

각 단계는 이전 단계의 결과를 검증하므로 순서를 임의로 변경하지 마세요.

1. **원본 및 대상 머신의 모든 데이터 생성 프로세스를 중지합니다.** 예약된 수집, 원격 수집, Web 트리거 수집, 수동 수집 및 유지 관리 작업을 중지하고 진행 중인 실행을 완료시킵니다. 지연된 쓰기 플러시는 생성 프로세스가 중지된 후에만 수행하세요. 확인되지 않은 큐 행은 일치하는 데이터베이스 및 RRD 백업과 함께 보존하고 truncate 등으로 삭제하지 마세요.
2. **백업을 수행합니다.** 데이터베이스, RRD 디렉터리 트리, 구성 파일을 동시에 수집합니다. [백업 및 복원](/ko/guides/back-up-and-restore/)의 일관성 규칙을 준수하는 것이 이 작업의 핵심입니다.
3. **RRD 트리를 이전합니다.** 세부 절차는 아래를 참조하세요.
4. **데이터베이스를 이전합니다.**
5. **코드, 구성 및 구성이 가리키는 모든 리소스를 이전합니다.** 여기에는 `plugins/`, `scripts/`, `resource/` 및 데이터 입력 방법이 호출하는 모든 로컬 파일이 포함됩니다.
6. **최종 복원 후 대상 시스템 구성을 다시 적용합니다.** 경로, 데이터베이스 엔드포인트, 서비스 소유권 및 숫자 기반 스토리지 신뢰 설정을 수정합니다.
7. **폴러 캐시를 재구축합니다.**
8. **모든 서비스 계정으로 스토리지 검사를 실행한 후 대상 시스템에서만 수집을 시작합니다.** 대표 파일들과 보류된 큐의 깊이를 모니터링하세요.

## RRD 트리 이전

RRD 파일은 생성된 시스템 환경에 따라 내부 구조가 달라지는 바이너리 파일입니다. 바이너리 직접 복사는
완벽히 호환되는 아키텍처와 RRDtool 형식을 필요로 합니다. OS 이름이나 워드 크기가 일치한다는 사실만으로는
호환성을 보장할 수 없습니다. 호환되지 않는 환경에서는 읽기 오류가 발생합니다. 대상 머신의 RRDtool을
사용하여 복사된 파일들을 검증하세요.

두 환경이 완벽히 일치하는지 확신할 수 없다면 직접 복사 대신 변환을 수행하세요. RRDtool의 자체 dump 및
restore 명령은 이식성이 뛰어난 텍스트 형태(XML)를 생성합니다. Kadupul 역시 아카이브를 재작성해야 할 때
내부적으로 이 명령어 쌍을 사용합니다.

원본 머신에서 쓰기 작업을 중지한 상태로 격리된 새 임시 스테이징 디렉터리를 사용하세요.

```sh
set -eu
umask 077
rrdtool dump /path/to/source/file.rrd > /private/staging/file.xml.partial
mv /private/staging/file.xml.partial /private/staging/file.xml
```

완료된 XML 파일을 안전하게 전송합니다. 대상 머신에서 새 후보 파일로 복원합니다.

```sh
set -eu
umask 077
rrdtool restore /private/staging/file.xml /private/staging/file.candidate.rrd
rrdtool info /private/staging/file.candidate.rrd
```

변환이 필요한 모든 파일에 대해 이 과정을 반복하고 각 명령의 종료 상태를 확인하세요. 불완전한 덤프나
검증되지 않은 후보 파일을 설치하지 마세요. RRDtool은 XML을 [이기종 아키텍처 간 전송 형식](https://oss.oetiker.ch/rrdtool/doc/rrddump.en.html)으로
공식 문서화하고 있습니다.

시간이 오래 걸리는 전체 변환을 진행하기 전에 사전 확인을 거치세요. 단일 파일을 복사하고 대상 머신에서
`rrdtool info`를 실행하여 step, 아카이브 구조, 마지막 업데이트 시간, 데이터 소스 이름을 비교하세요.
데이터가 채워진 것으로 알려진 구간에 대해 `fetch` 쿼리 결과도 대조하세요. 전체 트리를 이전하기 전에
대표적인 아카이브 구조들에 대해 이 확인을 반복한 다음 전체 파일 목록을 검증하세요. 후보 검증 기준 및 소유권
요건은 [RRD 복구](/ko/guides/recover-a-corrupted-rrd/)를 참조하세요.

어떤 방식을 선택하든 디렉터리 계층 구조를 그대로 보존하세요. RRA 디렉터리 아래의 중첩된 서브디렉터리는
단순한 정돈용이 아닙니다. 각 파일의 경로는 데이터 소스별로 기록되어 있으므로 디렉터리 구조를 평탄화하면
모든 데이터 소스 연결이 파손됩니다.

## 데이터베이스 이전

덤프 및 임포트 단계입니다. 대상 서버에서 확인해야 할 두 가지 사항이 있습니다.

서버 전역 기본값뿐만 아니라 복원된 테이블의 문자 집합, 콜레이션(collation), 스토리지 엔진을 검사하세요.
전환 전에 원본 정의를 유지하고 대상 데이터베이스 버전과의 호환성을 검증하세요.

**수집기 큐는 일회용 캐시가 아닙니다.** 현재의 `poller_output` 큐는 반드시 InnoDB를 사용해야 합니다.
스토리지 사전 검사는 MEMORY 큐를 거부합니다. 샘플이 정상 기록되었음이 확인될 때까지 해당 행들과 boost 및
realtime 큐를 보존하세요. RRD 백업에는 해당 측정값이 아직 포함되지 않았을 수 있습니다. 복원된 MEMORY 테이블이
비어 있을 것이라고 지레짐작하지 마세요. 논리적 덤프 파일 내에 테이블을 다시 채우는 insert 문이 포함되어 있을 수 있습니다.

쓰기 작업을 중지하고 백업을 확보한 상태라면 상속된 비 InnoDB 큐를 명시적으로 변환할 수 있습니다.

```sh
php cli/upgrade_database.php --migrate-poller-queue
php cli/upgrade_database.php --check-rrd-storage
```

실제 Web 및 폴러 서비스 계정으로 각각 스토리지 검사를 실행하세요. 로컬 스토리지 접근 권한과 선택된 큐를
확인합니다. root 권한으로 성공했다고 해서 서비스 계정의 접근이 보장되는 것은 아닙니다. 온라인 원격 수집기는
일반적으로 메인 큐를 대상으로 합니다. 로컬 큐를 의도적으로 테스트할 때만 `--local`을 사용하세요.
기타 런타임/캐시 테이블도 명확한 보존 또는 재구축 계획이 필요합니다. [스토리지 요구 사항](/ko/reference/requirements/)을
참조하세요.

## 대상 시스템에서의 경로 수정

첫 수집이 실행될 때까지 대부분의 오류가 드러나지 않기 때문에 마이그레이션이 실패하기 가장 쉬운 단계입니다.

**RRA 경로.** 표준 데이터 소스 경로는 `<path_rra>` 토큰을 사용합니다. 이 리비전에서 부트스트랩은
애플리케이션 디렉터리에 `/rra`를 더하여 `$config['rra_path']`를 도출합니다. 이는 임의의 로컬 디렉터리를
자유롭게 선택할 수 있는 일반 데이터베이스 설정이 아닙니다. 파일을 이동하기 전에 실제 유효 경로를 확인하세요.
수동으로 지정된 절대 경로는 개별적으로 확인하고 수정해야 합니다. 중첩된 디렉터리 구조를 유지하세요.

**폴러 캐시는 절대 경로를 보관합니다.** 캐시가 생성될 때 토큰이 확장되어 전체 절대 경로가 캐시 행에 기록됩니다.
RRA 디렉터리를 변경하더라도 캐시는 여전히 이전 위치를 가리킵니다. 폴러는 계속 실행되지만 찾을 수 있는 파일은
아무것도 생성되지 않습니다. 캐시를 재구축하세요.

```sh
php cli/rebuild_poller_cache.php
```

**경로를 보관하는 설정 항목들.** 이들은 데이터베이스에 저장되어 있으므로 이전 시스템의 디렉터리 구조를
가리키는 상태로 이전됩니다. 첫 실행 전에 모두 점검하세요. RRDtool 바이너리, 수집기 바이너리 및 구성 파일,
PHP 바이너리, SNMP 도구, 로그 경로, 기본 글꼴, 스파이크 제거 백업 디렉터리 등입니다. 또한 구성 파일,
서비스 유닛 파일, cron 작업 및 Web 서버 내의 경로와 환경 변수도 함께 검토하세요.

**데이터 입력 방법에 포함된 명령줄.** 설치 루트를 나타내는 토큰을 사용하므로 경로 구조가 동일한 이전이라면
수정할 필요가 없습니다. 구조가 변경된 이전이라면 각 항목을 일일이 확인해야 합니다. 데이터 쿼리 배후에 있는
리소스 XML 파일도 마찬가지입니다.

**원격 수집기는 자체 구성 파일을 갖습니다.** 자체 데이터베이스 자격 증명과 수집기 ID를 보관하고 있습니다.
이들은 중앙 덤프에 포함되지 않습니다. 중앙 데이터베이스 주소가 변경되었다면 관련 엔드포인트를 업데이트하고
각 수집기의 연결을 검증하세요. 전체 복제는 독립된 작업이며, 활성화된 원격 수집기가 구성되어 있을 때만 메인
수집기에서 실행됩니다.

```sh
php cli/poller_replicate.php
```

활성화된 원격 수집기가 없으면 이 명령은 오류를 내며 종료됩니다. 단일 수집기 마이그레이션에서 이 명령을 필수
성공 확인 단계로 추가하지 마세요. 원격 수집 재개를 허용하기 전에 원격 구성과 복제를 검증하세요.

## 소유권 및 파일 권한

폴러는 이를 실행하는 시스템 계정 권한으로 RRD 파일을 작성합니다. Web 인터페이스는 Web 서버 계정 권한으로
해당 파일들을 읽습니다. `/etc/passwd` 항목이 서로 다른 머신 간에 숫자 ID를 그대로 유지한 채 파일을 복사하면
잘못된 계정이 소유한 파일이 생성됩니다.

마이그레이션 직후 그래프가 중단된다면 권한, 오래된 경로, 수집 누락, 타임스탬프 오류 또는 거부된 샘플을 나타낼 수
있습니다. 조치를 취하기 전에 폴러 로그와 보류된 큐를 먼저 점검하세요. 그래프만으로는 원인을 파악할 수 없습니다.

샘플 파일 하나뿐만 아니라 RRA 디렉터리 자체와 중첩된 하위 디렉터리들의 소유권을 확인하세요. 수집 중에 해당
디렉터리 내에 새 파일이 생성되므로, 폴러가 쓸 수 없는 디렉터리는 기존 파일이 정상이더라도 마이그레이션 이후에
생성된 데이터 소스에 대해 실패하게 됩니다. `include/config.php`의 `rrd_maintenance_trusted_uids` 및
`rrd_maintenance_trusted_gids`를 대상 시스템의 실제 숫자 ID로 다시 매핑하고 신뢰할 수 있는 상위 디렉터리를
확인하세요. [스토리지 요구 사항](/ko/reference/requirements/)을 참조하세요.

## 데이터 손실을 최소화하는 전환

RRD 파일은 마지막 업데이트 타임스탬프 이전이나 동일한 시점의 업데이트를 거부합니다. 이는 데이터 재처리에
제약을 주지만, 모든 마이그레이션이 반드시 데이터를 유실해야 함을 의미하지는 않습니다. 공백의 크기는 샘플링 주기,
다운타임, 큐에 저장된 측정값 중 보존된 데이터에 따라 달라집니다. 이 절차는 단일 수집 책임자를 사용하며
리허설 중 독립적으로 수집된 기록을 최종 아카이브 세트에 병합하지 않습니다.

1. 전날 백업을 활용하여 사전 전체 리허설을 수행합니다. 모든 데이터를 복제하고, 모든 경로를 수정하며, 알림을 비활성화한 상태에서 격리된 테스트 장치들을 대상으로 업데이트를 테스트합니다. 대상 시스템에서의 변경 사항을 재현 가능한 절차로 기록합니다. 테스트 완료 후 리허설 작성 프로세스를 중지합니다.
2. 리허설 환경을 완전히 격리된 상태로 유지합니다. 해당 데이터베이스와 RRD를 최종 일치 백업으로 완전히 교체합니다. 리허설 행이나 큐의 샘플을 정식 복원 작업에 혼합하지 마세요.
3. 전환 시점: 원본 생성 프로세스를 중지하고 보류된 샘플을 플러시하거나 보존한 다음 최종 백업을 캡처하여 전송합니다. 대상 시스템 재정의 구성을 다시 적용합니다. 데이터베이스를 복원하면 `settings` 테이블에 원본 경로가 다시 복구되며, 구성 파일을 복원하면 리허설 엔드포인트와 신뢰 설정이 덮어써질 수 있기 때문입니다.
4. 폴러 캐시를 재구축하고, 스토리지 검사를 실행하며, 파일 목록을 검증한 후, 이러한 점검이 완료된 이후에만 대상 시스템에서 수집을 활성화합니다.

리허설 소요 시간을 측정하고 검증 및 롤백을 위한 여유 시간을 확보하세요. 전환이 완료되거나 제어된 롤백을 통해
원본 시스템이 다시 수집 주체로 재지정될 때까지 원본 시스템을 중지 상태로 유지하세요.

## 점검 순서

1. 설치 프로그램으로의 리디렉션 없이 Web 인터페이스가 정상 로드되는지 확인합니다. 리디렉션되는 경우 코드/스키마 불일치, DB 연결 실패 또는 불완전한 복원을 조사합니다.
2. 테스트 장치가 새 수집 시도에 응답하는지 확인합니다. 복원된 "up" 상태값 자체는 중지 이전의 낡은 데이터일 수 있습니다.
3. 첫 번째 수집 주기 완료 후 RRD 파일의 최종 수정 시간이 갱신되는지 확인합니다. 화면의 그래프가 아니라 디스크의 실제 파일을 확인하세요.
4. 최근 1시간 동안 그려진 그래프가 공백 없이 연속된 선으로 나타나는지 확인합니다.

3단계가 실패하면 경로, 권한, 스토리지 사전 검사, 큐 깊이 및 RRDtool 오류를 점검하세요. 4단계가 실패하면 보존된 값,
그래프 정의, 선택된 시간 범위 및 Web 계정의 접근 권한을 점검하세요. 단일 파일의 성공이 모든 장치, 데이터 입력 방법
또는 원격 수집기의 정상 작동을 보장하지는 않습니다.

## 주의해야 할 함정

**두 시스템을 동일한 RRD 디렉터리 트리에서 동시에 가동하지 마세요.** 두 폴러가 동일한 파일에 쓰기를 시도하면
데이터가 병합되는 것이 아니라 업데이트가 거부되고 그래프에 구멍이 발생합니다.

**더 최신 데이터베이스 위에 더 오래된 RRD 트리를 복원하지 마세요.** 파일이 소급하여 채워지지는 않습니다. 수집은
현재 시점부터 재개되며 둘 사이의 간격은 영구적인 결측 구간으로 남습니다.

**백업에는 장치 자격 증명이 일반 텍스트로 포함되어 있습니다.** 하드웨어를 이전한다는 것은 자격 증명이 네트워크를
통해 이동하고 두 머신에 동시에 보관됨을 의미합니다. 백업 접근을 제한하고 전송 경로를 암호화하세요. 정식 인수 검수가
완료되고 보존 정책에 따라 폐기가 허용될 때까지 보호된 롤백 사본을 유지하세요. 전환 작업 중에 삭제하지 마세요.

**플러그인 테이블은 데이터베이스에 있지만 플러그인 코드는 그렇지 않습니다.** 일치하는 플러그인 코드와 종속성 없이
데이터베이스만 복원하면 플러그인 페이지, 훅(hook) 또는 작업이 중단될 수 있습니다. 필요한 각 플러그인을 개별적으로 확인하세요.

**기존 proxy 스토리지는 본 마이그레이션 절차의 적용 대상이 아닙니다.** proxy 배포는 지원되지 않습니다. 실제 RRD 파일을
찾아 백업한 후 격리된 환경에서 로컬 스토리지로의 별도 이전을 검증하세요. 로컬 `rra/` 디렉터리에는 찌꺼기 파일만 남아 있을 수 있습니다.

**이전 머신의 폐기는 가장 마지막에 수행하며, 결코 전환 당일에 진행하지 마세요.** 전원을 끄거나 모든 데이터 생성 프로세스를
비활성화한 상태로 유지하고, 새 시스템의 수집, 그래프, 원격 수집기 및 플러그인 검증이 완전히 통과될 때까지 일치하는 백업을
보존하세요. 워크로드와 롤백 정책에 따라 관찰 기간을 설정하세요. 가장 짧은 단 한 번의 아카이브 주기가 정상 완료되었다고 해서
모든 하위 시스템이 정상 작동함을 의미하지는 않습니다.
