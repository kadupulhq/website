:::caution[사용 전 검증]
소스를 사용할 수 있지만 지원되는 Kadupul 릴리스 또는 마이그레이션 경로는 아직
없습니다. 시스템에 의존하기 전에 백업이 포함된 격리된 사본에서 이 절차를
테스트하세요. [프로젝트 상태](/ko/project/status/)를 참조하세요.
:::

폴러를 확장하는 것은 단 하나의 질문으로 귀결됩니다. 바로 한 번의 수집 실행이 다음 실행이 시작되기
전에 끝나는가 하는 점입니다. 아래의 모든 내용은 이 질문에 답하고, 그 답을 다시 ‘예’로 되돌리는 데 목적이 있습니다.

수집을 담당하는 구성 요소가 명확하지 않다면 먼저 [아키텍처](/ko/concepts/architecture/)를 읽어보세요.

## 두 개의 시계

시스템에는 두 가지 주기가 있으며, 이 둘은 서로 다른 설정 항목입니다.

| | 항목 설명 | 허용되는 값 |
|---|---|---|
| 실행기 주기 | 운영체제가 cron 또는 `cactid` 서비스를 통해 수집기를 시작하는 주기 | 60초 또는 300초 |
| 폴러 주기 | 기본 수집 주기. 개별 데이터 소스 단계는 이보다 길 수 있음 | 10, 15, 20, 30, 60 또는 300초 |

폴러 주기가 실행기 주기보다 짧은 경우, 한 번의 실행 내에서 루프를 돌며 여러 차례의 수집 단계를 수행합니다.
수집 패스 횟수는 실행기 주기를 폴러 주기로 나눈 값입니다.

전체 실행에 할당되는 시간 예산은 이 두 수치로부터 도출됩니다. 즉, 패스 횟수에 폴러 주기를 곱한 값에서
2초를 뺀 시간입니다. 이것이 바로 실행 시간을 측정하는 실제 기준 시계가 됩니다.

## 주기가 초과되었을 때 발생하는 현상

세 가지 서로 다른 현상이 발생하며, 각기 다른 로그 행을 생성합니다.

**실행이 강제 차단됩니다.** 경과 시간이 예산을 초과하면 폴러는 최대 실행 시간을 초과했다는 로그를 남기고,
통계치를 기록한 뒤 종료됩니다. 샘플을 생성하지 못한 작업은 공백을 남길 수 있습니다. 지속성 큐에 이미 수락된
샘플은 나중에 성공적으로 RRD에 기록될 수 있도록 보류 상태로 남을 수 있습니다. 초과가 발생했다고 해서
플러시되지 않은 모든 측정값이 버려지는 것은 아닙니다. 그래프와 함께 큐의 깊이 및 로그를 점검하고, 다음 실행이
깨끗하게 보이도록 하려는 목적으로 보존된 행을 임의로 삭제하지 마세요.

**다음 실행이 남겨진 비정상 상태를 감지합니다.** 시작 시 폴러는 정상적으로 닫히지 않은 프로세스 행을 계산하고,
프로세스가 폴링 주기를 초과한 것으로 감지되었다는 경고를 출력합니다. 완료되지 않았거나 오래된 프로세스 레코드
및 실제로 실행 중인 자식 프로세스를 조사하세요. 경고만으로는 병목 지점을 특정할 수 없습니다.

**시계의 동기화가 어긋납니다.** 이전 실행 이후 예산에서 허용하는 것보다 많은 시간이 경과한 경우, 폴러는
실행기가 폴러 주기와 동기화되지 않았다고 경고합니다. 이 문제는 보통 폴러가 아니라 실행기 쪽의 문제입니다.
cron 항목의 빈도 오류, 중지된 서비스 또는 절전 모드에 들어갔던 호스트 등이 원인입니다.

이러한 경로들은 관리자 알림 헬퍼를 호출합니다. 알림 전달 여부는 구성된 수신자, 알림 제어 설정 및 정상 작동하는
메일 전송 환경에 따라 달라집니다. 로그의 경고만으로 이메일이 도착했음을 입증할 수는 없습니다.
[이메일 알림](/ko/guides/send-email-notifications/)을 참조하세요.

주기 초과가 아닌 네 번째 사례도 있습니다. 폴러가 예상보다 일찍 다시 시작되면, 실행 빈도가 너무 높게 구성되었다는
로그를 남기고 수집 없이 종료됩니다. `--force`는 이러한 시간 확인을 건너뜁니다. 예약된 실행 및 기타 수동 실행이
중지된 통제된 진단 중에만 이 옵션을 사용하세요. 이 옵션이 처리 용량을 늘려주거나 중복 수집을 안전하게 만들어 주지는 않습니다.

## 통계 행

완료된 각 실행은 로그에 한 줄의 통계 행을 기록합니다. 여기에는 경과 시간, 수집 방식, 프로세스 및 스레드 수,
장치 수, 프로세스당 장치 수, 데이터 소스 수, 처리된 RRD 파일 수가 포함됩니다.

경과 시간, 테일 레이턴시(tail latency), 큐 깊이 및 업데이트 실패 추세를 추적하세요. 공백을 유발한다면
예산에 근접한 단발성 실행이라도 조사해야 합니다. 지속적인 증가는 용량이나 수집 동작을 변경해야 할 시점을
파악하는 데 도움이 됩니다.

## 프로세스와 스레드

서로 다른 역할을 수행하는 두 가지 조절 항목입니다.

| 조절 항목 | 분할하는 작업 단위 | 사용하는 수집기 |
|---|---|---|
| 프로세스 | 장치(연속된 장치 ID 범위로 분할) | 둘 다 |
| 스레드 | 단일 장치 내부의 항목들 | Spine 전용 |

그 결과 많은 이들이 혼란을 겪는 핵심적인 특성이 나타납니다. 즉, **프로세스에는 장치 단위 전체가 할당된다는 점입니다.**
5,000개의 데이터 소스를 가진 단일 장치를 여러 프로세스에 걸쳐 분산할 수 없습니다. 해당 장치는 하나의 프로세스에
할당되며 그 프로세스는 필요한 만큼의 시간을 소모합니다. 프로세스를 더 추가하더라도 이 장치의 처리 시간은 단축되지 않습니다.

두 값은 전역적이 아니라 데이터 수집기별로 유지됩니다. 설정 페이지의 값은 새 데이터 수집기가 생성될 때 적용되는
사전 설정입니다. 사전 설정을 변경하더라도 기존 수집기의 설정이 변경되지는 않습니다.

또한 대규모 장치 하나를 분할하는 방법인 장치당 스레드 수 설정도 존재합니다. 이 설정은 C 수집기에만 적용됩니다.

Balance Process Load는 누적된 항목 수를 사용하여 장치 ID 순서대로 전체 장치 간의 경계를 선택합니다. 이 기능은
단일 장치를 분할하거나 동일한 항목 수를 보장하지 않으며, 항목 수가 곧 실행 시간을 의미하지는 않습니다. 격리된
대표 워크로드에서 이 기능을 활성화하기 전과 후의 프로세스별 소요 시간을 비교하세요.

## PHP 수집기와 C 수집기 비교

PHP 수집기인 `cmd.php`는 애플리케이션과 함께 기본 제공됩니다. Kadupul은 Spine 포크를 유지 관리할 계획이지만,
해당 소스 위치와 검증된 빌드는 아직 문서화되지 않았습니다. 해당 검증 자료가 확보될 때까지는 PHP를 사용하세요.
아래의 Spine 비교, 스레드 설정 및 명령어는 상속된 동작을 설명하는 것이며, 사용 가능하거나 지원되는 Kadupul 배포를
의미하지 않습니다.

| | PHP 수집기 | Spine |
|---|---|---|
| 병렬 모델 | 프로세스 전용 | 프로세스 및 스레드 |
| 스레드 설정 | 구성과 관계없이 1로 강제됨 | 설정 반영 |
| 스크립트 서버 | 프로세스당 1개(구성 불가) | 프로세스당 1~15개(구성 가능) |
| 스크립트 제한 시간 | 적용되지 않음 | 적용됨(기본값 25초) |
| 설치 방식 | 코드에 기본 포함 | 포크 계획 중(검증된 빌드 문서화 없음) |

강제 스레드 수 제한은 명확히 짚고 넘어갈 가치가 있습니다. 수집기가 PHP로 설정된 경우 런타임 스레드 변수는
1로 고정되며, 이것이 저장된 수집기 스레드 설정을 덮어쓰지는 않습니다. PHP 수집기를 확장하려면 더 많은 프로세스가
필요할 수 있으며, 소스 코드의 지침은 CPU 코어 수의 2배 이하를 유지할 것을 권장합니다.

Spine 구성과 명령어 동작은 평가 대상 바이너리와 일치하는지 검증해야 합니다. PHP 애플리케이션 소스 코드만으로는
구성 검색 순서, 스레드 동작 또는 부작용을 확정할 수 없습니다.

격리된 Spine 평가를 위한 상속된 예시(검증된 Kadupul 명령어가 아님):

```sh
spine --first=42 --last=42 --threads=1 --verbosity=HIGH --stdout
spine --hostlist='42,43,51' --readonly
```

`--readonly`는 결과 저장을 방지하기 위한 옵션입니다. 하지만 여전히 장치에 연결하고 수집 스크립트를 실행하므로,
먼저 격리된 테스트 환경에서 그 부작용을 검증하세요.

## 데이터베이스 연결

스레드는 비용이 들지 않는 자원이 아닙니다. 각 Spine 스레드는 자체 데이터베이스 연결을 유지하며, 각 스크립트 서버도 마찬가지입니다.

```
estimated worker connections = processes * (threads + script_servers)
```

이것은 애플리케이션 설정 도움말에 제공된 추정치이며, 측정된 상한선이 아닙니다. 수집기 전체에 걸쳐 이 값을 합산하고
폴러 부모 프로세스, 웹 요청, 유지 관리 및 기타 클라이언트를 위한 여유 용량을 추가하세요. 데이터베이스 한도를
설정하기 전에 실제 최대 연결 수와 거부된 연결 수를 측정하세요. 한도를 높이면 시스템 자원도 함께 소모됩니다.

연결이 고갈되면 샘플이 누락될 수 있지만, 순환하며 발생하는 공백이 고갈만의 유일한 징후는 아닙니다. 데이터베이스 연결
지표와 애플리케이션 오류를 통해 이를 교차 확인하세요.

## 지연된 RRD 쓰기

폴러가 매 주기마다 RRD 파일에 직접 쓰는 것을 방지하는 모드가 존재합니다. 결과는 데이터베이스 테이블에 누적되며
타이머에 따라 또는 그래프가 파일을 요청할 때 일괄적으로 플러시됩니다. 이를 통해 수많은 소규모 쓰기 작업을 적은 수의
대규모 쓰기 작업으로 전환합니다.

운영상 중요한 두 가지 사실이 있습니다.

- 원격 데이터 수집기를 사용하는 경우 이 모드는 필수입니다. 이는 단순한 권장 사항이 아니라 소프트웨어가 요구하는 조건입니다.
- 버퍼 테이블은 메모리가 아닌 영구 스토리지에 저장되므로 플러시되지 않은 샘플도 재시작 후 유지됩니다. 이는 RRD 파일의
  기록이 데이터베이스보다 뒤처진다는 뜻이기도 합니다. 스냅샷을 생성하기 전에 [백업 및 복원](/ko/guides/back-up-and-restore/)을
  참조하세요.

이 리비전에서 처리 중인 메인 큐 `poller_output` 역시 InnoDB를 사용합니다. 스토리지 사전 검사는 MEMORY 큐를 거부하며,
힙 테이블 제한을 늘려도 이 거부를 해결할 수 없습니다. 데이터 생성 프로세스를 중지하고 일치하는 백업을 유지한 상태에서,
상속된 부적절한 큐를 명시적으로 변환한 후 각 서비스 계정으로 스토리지를 확인하세요.

```sh
php cli/upgrade_database.php --migrate-poller-queue
php cli/upgrade_database.php --check-rrd-storage
```

이들은 서로 독립된 작업입니다. 보류 중인 행을 유지하고 행 수뿐만 아니라 데이터베이스 디스크 공간과 큐의 대기 시간을 모니터링하세요.
큐 선택, 서비스 계정 신뢰 검사 및 재시작 전제 조건은 [안전한 업그레이드](/ko/guides/upgrade-safely/)를 참조하세요.

## 원격 수집기로 전환해야 하는 시점

원격 데이터 수집기는 동일한 코드를 다른 수집기 ID로 실행하면서 장치의 일부를 폴링하고 결과를 중앙 데이터베이스에
다시 기록하는 두 번째 머신입니다.

병목 현상이 스토리지 측면이 아니라 수집 측면에 있을 때 원격 수집기로 전환하세요.

- 폴러 호스트의 CPU가 실행 중에는 포화 상태이고 실행 사이에는 유휴 상태일 때.
- 특정 장치 그룹에 대한 왕복 지연 시간이 실행 시간의 대부분을 차지하고 해당 장치들이 단일 링크 뒤에 있을 때.
- 직접 폴링하고 싶지 않은 원격 WAN 끝단에 사이트가 위치해 있을 때.
- 격리된 사이트에서의 수집이 필요하며, 시스템에 의존하기 전에 해당 수집기에 대한 오프라인 버퍼링 및 복구를 검증했을 때.

원격 수집기가 중앙 데이터베이스나 RRD 쓰기 제한을 없애주지는 않습니다. 수집 처리량을 늘리기 전에 중앙의 수신 및 플러시
용량을 측정하세요. 생성 프로세스를 추가하면 기존의 처리 지연이 오히려 가중될 수 있습니다.

각 수집기는 자체 프로세스 및 스레드 수, 자체 데이터베이스 자격 증명, 기본 2시간인 동기화 주기를 갖습니다. 대기하지 않고
전체 동기화를 강제 실행하는 명령줄 도구가 제공됩니다.

중앙 설치 환경은 웹 사이트 및 플러그인 코드를 원격 수집기로 복제하여 스스로 업데이트되도록 할 수 있습니다. 다른 방식으로
코드를 배포하는 경우 이 복제 기능을 비활성화할 수 있습니다.

## 어떤 한계에 도달했는가

이 표를 참조하여 가설을 세운 다음, 로그와 측정 지표를 통해 검증하세요. 여러 한계가 동시에 나타날 수도 있습니다.
Spine 옵션은 여기에서 아직 검증되지 않았습니다.

| 관찰 결과 | 도달한 한계 | 변경 조치 사항 |
|---|---|---|
| 실행기 비동기화 경고 발생, 폴러 자체는 빠름 | 예약 지연, 이전 실행 초과 또는 호스트 중단 | 실행 기록 및 프로세스 상태 점검 |
| 실행 시간은 일정하나 한 장치가 항상 지연됨 | 느린 응답, 무거운 스크립트 또는 집중된 작업 부하 | 입력 방식을 측정하고 타임아웃/재시도 동작 검토 |
| 장치 수에 비례하여 실행 시간 증가, CPU 포화 | 수집기 CPU 부하 과다 | 프로세스 추가가 유효한지 측정. 수집기 분산 배치 고려 |
| 장치 수에 비례하여 실행 시간 증가, CPU 유휴 | 네트워크, 스크립트 또는 DB 대기 지연 | 동시성을 변경하기 전에 대기 원인 측정 |
| 여러 장치에서 샘플이 번갈아 누락됨 | 연결 고갈, 타임아웃 또는 기타 수집 실패 | 오류 로그, 연결 지표 및 보류된 큐 점검 |
| 실행 시간은 양호하나 RRD 쓰기가 느리고 디스크 바쁨 | 스토리지 I/O 한계 | 지연된 RRD 쓰기 적용 또는 더 빠른 디스크 도입 |
| 웹 인터페이스를 포함하여 모든 동작이 느림 | 데이터베이스 처리 한계 | 버퍼 풀 크기 조정, 이후 DB 서버 사양 증설 |

주의해야 할 두 가지 함정.

**기본 주기를 변경하는 것이 모든 데이터 소스 단계를 변경하는 것과 같지는 않습니다.**
프로필, 캐시된 항목 단계, RRD의 heartbeat/step 정의를 일치시키세요. 캐시를 재구축하더라도 기존 RRD 파일의 구조가
자동으로 재조정되지는 않습니다. [데이터 보존](/ko/guides/manage-data-retention/) 및
[시간과 주기](/ko/concepts/time-and-intervals/)를 참조하세요.

**주기를 단축하면 모든 부하가 곱절로 늘어납니다.** 주기를 300초에서 60초로 변경한다고 해서 작업량이 5분의 1로 줄어들지는
않습니다. 더 빠른 주기로 구성된 소스는 더 자주 수집되며, 더 긴 단계를 유지하는 소스는 매 기본 패스마다 실행될 필요가 없습니다.
모든 패스에 동일한 작업이 소요된다고 가정하지 말고 실제 발생하는 부하를 측정하세요.
