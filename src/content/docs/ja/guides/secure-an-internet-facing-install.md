:::caution[使用前に検証してください]
ソースコードは公開されていますが、サポートされている Kadupul のリリースや移行
パスはまだ存在しません。本運用で依存する前に、バックアップを備えた隔離された
環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

率直な結論から申し上げます。本システムは VPN の背後に配置してください。Kadupul は監視対象のすべての
デバイスの SNMP 認証情報を平文で保持しており、通常の運用の一環として自身のホスト上でコマンドを実行します。
パブリックなインターネット上にそのまま公開することを推奨できる設定は存在しません。

以下のチェック項目は、隔離された環境を評価するための指標です。これらはサポートされた安全なパブリック
デプロイを保証するものではありません。結果を解釈する際は、上記のプロジェクトステータスに関する制約を念頭に置いてください。

## TLS

TLS の終端は Web サーバーまたはその前段のリバースプロキシで行ってください。Kadupul 自体は独自のソケットをリスンしません。

次に、平文の HTTP リクエストを HTTPS にリダイレクトする設定を有効にしてください。この設定はデフォルトではオフ（`off`）
になっています。この設定が無効な場合、ログインフォームが HTTP で配信され、他のあらゆる保護対策が機能する前にパスワードが
平文のままネットワーク上を流れることになります。

PHP が `off` 以外の空でない `$_SERVER['HTTPS']` の値を受信すると、アプリケーションはセッション Cookie に Secure 属性を付与します。
TLS 終端プロキシの背後では、信頼できる Web サーバーまたは FastCGI 層が HTTPS を正しく通知するように構成し、ブラウザ側で
生成された `Set-Cookie` ヘッダーを確認してください。

`$proxy_headers` はクライアントのアドレス解決を制御します。この設定は HTTPS サーバー変数を定義するものではなく、
Secure Cookie を有効化するものでもありません。プロキシが設定したアドレスヘッダーのみを信頼し、クライアントから送られてくる
ヘッダーを破棄して、バックエンドへの直接アクセスを遮断してください。認証情報が送信される前に、公開プロキシ側で HTTP から HTTPS への
リダイレクトを強制してください。

アプリケーションはセッション Cookie に HttpOnly および SameSite=Strict を設定します。デプロイの境界において、実際の
Cookie とリダイレクトの動作を確認してください。これらの属性が存在するからといって、他のすべての Cookie が同一の設定を
共有していることの証明にはなりません。[PHP セッション設定リファレンス](https://www.php.net/manual/en/session.configuration.php)を参照してください。

## デフォルトの認証情報

提供されるスキーマには、パスワードハッシュが文字列 `admin` の MD5 値である `admin` という名前の管理者アカウントが1つ含まれています。
このアカウントは初回ログイン時にパスワードの変更を要求するようフラグが立てられています。変更が確実に行われたことを、推測ではなく
実際に確認してください。Web Basic 認証下では、Web サーバー側ですでにユーザーが特定されているため、この変更を強制する画面はスキップされます。

次に、ユーザーアカウント以外の認証情報を確認してください。

- 付属の設定テンプレートにおいて、データベースアカウントはデフォルトで `cactiuser`、パスワードも `cactiuser` に設定されています。
- 自動化サブシステムには、コミュニティ名 `public` および `private` を含むデフォルトの SNMP オプションと、SNMPv3 のユーザー名/パスワードのペアが付属しています。これらは探索用のデフォルト値であり、個別のデバイス設定ではありませんが、ディスカバリー機能が最初に試行する文字列となります。

パスワードポリシーは変更可能です。デフォルトの要件は8文字以上かつ大文字・小文字の混在です。有効期限および連続失敗後の
アカウントロックアウトは両方とも利用可能ですが、初期状態ではどちらも無効になっています。インターネットに接続する環境では、ロックアウトを有効にしてください。

## データベース権限

インストールのサンプルでは、データベーススコープの権限に加えてタイムゾーンテーブルへのアクセス権を使用しています。
以下の例示的なアカウント名やデータベース名を置き換え、実際のデプロイおよびメンテナンス作業に合わせて付与権限を精査してください。

```sql
GRANT ALL ON kadupul.* TO 'someuser'@'localhost';
GRANT SELECT ON mysql.time_zone_name TO 'someuser'@'localhost';
```

2つ目の権限付与は必須です。タイムゾーン処理はこのテーブルを読み取り、インストーラーはアクセス権と登録済みタイムゾーンデータの
有無をチェックします。安易に削除する前に、実際の保守作業およびコレクターの要件と照らし合わせて追加権限を検討してください。
この例は、すべての環境で全く同じ権限が必要であることを示すものではありません。

留意すべきスコープ上の重要事項：

- データベースは localhost またはプライベートインターフェースにバインドし、Web サーバーがリクエストに応答する公開アドレスにはバインドしないでください。
- 各リモートデータコレクターには専用のデータベースアカウントを割り当ててください。それらの認証情報は中央データベースおよび各自の設定ファイルに格納されるため、アカウントを分けることで追跡性と失効処理が向上します。ただし、コレクターのアカウント権限が中央への書き込みを許可している場合、侵害されたコレクター自体をアカウント分離だけで完全に隔離できるわけではありません。
- 接続は TLS をサポートしており、設定ファイル内の秘密鍵、証明書、および CA パスによって構成されます。データベースが別ホストに存在する場合は必ず TLS を使用してください。
- 設定ファイルは Web サーバーの実行ユーザーから読み取り可能とし、通常の運用中は Web サービスユーザーおよびポーラーサービスユーザーのいずれからも書き込みできないように設定してください。ファイルの所有権は管理者アカウントに保持させてください。リモートポーラーのセットアップ処理では設定ファイルを更新できるかが具体的に確認されます。プライマリサーバーのすべての環境で同様の一時的な書き込み権限が必要であると早合点しないでください。
- CSRF シークレットはデータベースの代わりにファイルに保存することができます。このオプションを使用する場合、ファイルはドキュメントルートの外部に配置しなければなりません。これは単なる提案ではなく、必須要件として定められています。

## データディレクトリをドキュメントルートから除外する

リポジトリルートをそのまま公開するデプロイでは、プライベートデータやソースコードのディレクトリが公開ルートの下層に配置される
場合があります。いくつかのディレクトリには `.htaccess` によるアクセス拒否ルールが配置されていますが、すべてのパスが保護されていると
過信せず、実際のチェックアウト内容とサーバー構成を精査してください。現在進行中の部分的なフレームワーク移行の観点からも、従来のルーティングを
考慮せずにサイト全体を `public/` に切り替えるだけでは、完全なデプロイ手順とは言えません。

これらの設定ファイルは Apache 上で、かつ該当ディレクトリでの設定の上書きが許可されている場合にのみ機能します。Nginx 上では
完全に無効です。誤った設定の Apache 上でも機能しません。ログディレクトリの前にある拒否設定が機能していなければ、デバイス名、
ユーザー名、クエリ文字列、エラー詳細が記録されたアプリケーションログを誰でも閲覧できてしまいます。Apache は必要な上書きの動作について
[`.htaccess` ガイド](https://httpd.apache.org/docs/2.4/howto/htaccess.html)で解説しています。

以下の両方の対策を実施してください。

**データを移動する前にストレージパスを検証する。** ログの出力先は変更可能ですが、`include/global.php` は RRA のベースパスを
インストール環境内の `rra` ディレクトリに固定しています。UI 上に RRA ディレクトリを変更するための一般的な設定画面は存在しません。
個別にマウントされたストレージ構成によって期待されるパスを維持することは可能ですが、ファイルシステム上の配置だけで、公開ディレクトリや
シンボリックリンク経由の HTTP アクセスを防ぐことはできません。既存のデータソースパス、サービス権限、バックアップ、および HTTP での
アクセス拒否を併せて確認してください。ファイルがどのように解決されるかを検証せずにキャッシュツリーを移動しないでください。
[新しいハードウェアへの移行](/ja/guides/migrate-to-new-hardware/)および[安全なアップグレード](/ja/guides/upgrade-safely/)を参照してください。

**Web サーバー側でプライベートパスへのアクセスを拒否する。** ソースコードに含まれる
[リポジトリルート用 Nginx 設定例](https://github.com/kadupulhq/kadupul/blob/661a57ff43ebf275e6b07211d4284dd727103959/tests/e2e/nginx.conf)
を実際の URL プレフィックスとサーバー環境に合わせて調整してください。アクセス拒否ルールは一般的な PHP 処理よりも優先される必要があります。
以下のリストは棚卸しのための参考資料であり、そのまま適用できるサーバー設定ではありません。

| ディレクトリ | 拒否すべき理由 |
|---|---|
| `rra/` | 測定データファイル |
| `log/` | クエリやエラーの詳細を含むアプリケーションログ |
| `cache/` | 意図したアセットアクセスを精査し、キャッシュパス内での PHP 実行を遮断 |
| `scripts/` | 収集コードは HTTP 経由で直接配信または呼び出しを行ってはならない |
| `cli/` | HTTP 経由でアクセスされることを意図していないコマンドラインツール群 |
| `mibs/`、`contrib/`、`docs/` | 内部リソースおよびドキュメント |
| `src/`、`config/`、`templates/`、`var/`、`lib/`、`bin/`、`tests/`、`tools/` | アプリケーションの内部構造、状態データ、およびツール類 |
| ドットファイル、依存関係マニフェスト、内部の include/bootstrap PHP | リポジトリのメタデータおよび内部エントリーポイント |

`include/js` や `include/themes` などの必須の公開アセットは保護してください。include 全体を無差別にブロックすると UI が破損します。
安全なテストパスを用いて拒否設定を検証し、レスポンスにソースコードやファイルの中身が露出していないことを確認してください。
本物の秘密情報をターミナルやログに出力させてテストを行わないでください。

また、静的アセット向けのセキュリティレスポンスヘッダーを定義したオプションファイルも用意されています。PHP のレスポンスはコード内で
独自のヘッダーを設定しますが、静的ファイルは該当ファイルを有効化するかサーバー構成に同様のディレクティブを記述しない限りヘッダーを付与しません。

コンテンツセキュリティポリシー（CSP）はカスタマイズ可能です。プラグインが依存しているため、デフォルトのスクリプトポリシーでは nonce なしの
インライン JavaScript が許可されています。設定画面に表示されるより厳格な nonce モードはレポート専用（report-only）です。
[設定画面の古いヘルプ](https://github.com/kadupulhq/kadupul/issues/265)の記載とは異なり、ヘッダー実装は `nonce` の強制適用も
受け付けます。強制適用とレポート専用モードは明確に異なります。モードを切り替える前に、ヘッダーを精査し必要なすべてのページおよびプラグインを
テストしてください。強制処理が実装されているからといって、完全な nonce 互換性が保証されているわけではありません。

## ポーラーによるコマンド実行

これはシステムの脅威モデルを根本から変化させる要因です。

データ収集は SNMP だけに留まりません。データ入力方式（Data Input Method）にはコマンドラインを定義でき、ポーラーはそれを実行します。
コマンドラインはポーラーキャッシュに格納され、コレクターの OS 実行ユーザーの権限でインターバルごとに実行されます。PHP スクリプトサーバーの
入力は、独立した常駐 PHP プロセスを使用します。外部コマンド入力とスクリプトサーバー入力は異なる経路をたどります。すべてのスクリプトがその
サーバー内で動作していると思い込んだり、本バージョンで C コレクターが検証済みであると過信したりしないでください。

以下の権限は、コード実行を伴う極めて特権的な構成インターフェースとして扱ってください。その影響は、有効化された機能や入力検証コントロールによって異なります。

| 権限項目 | 理由 |
|---|---|
| データ入力方式 | 実行されるコマンドラインを直接定義する |
| テンプレートのインポート | インポートされたテンプレートやパッケージにデータ入力方式が含まれる可能性がある |
| プラグイン管理 | プラグインコードがアプリケーション内で直接実行される |
| 設定 / ユーティリティ | 実行されるバイナリのパスを制御する |

該当ホストへのシェルアクセス権を持たないユーザーには、これらの権限を一切与えないでください。グラフを閲覧できるだけの読み取り専用ユーザーは
これらとは完全に異なる立場であり、ほぼすべてのアカウントが持つべき役割はそちらです。

2つの防御機能が存在し、両方とも活用する価値があります。

**メタ文字の制限。** データ入力コマンド文字列に含まれるシェルのメタ文字は、デフォルトでブロックされます。シェルパイプラインを
利用していた古い定義のために、それらを許可する設定項目も存在します。この設定は必ず無効のままにしてください。パイプライン処理を必要とする
定義がある場合は、scripts ディレクトリ配下のスクリプト内にパイプライン処理を移し、そのスクリプトを呼び出すようにしてください。

**入力ホワイトリスト。** 設定ファイルで指定されたファイルで、データ入力方式ごとに承認済みのコマンド文字列を保持します。このファイルが
設定されている場合、コマンド文字列がリストに存在しないデータ入力方式からグラフやデータソースを作成することはできません。承認済みコマンドを
変更すると、監査済みのホワイトリストが更新されるまで比較照合が失敗します。ホワイトリストの再生成はコマンドラインから実行する設計になっており、
これこそが肝心な点です。つまり、ブラウザ上の管理者セッションではなく、ホストへのシェルアクセスが必要となります。

このチェックはポーラーキャッシュの再構築時にも再実行されます。チェックに失敗したデータ入力はポーラー項目を生成せず、残された行は次回の
コミットを伴う再構築/フラッシュ時に削除されます。これは作成とキャッシュ格納を制限するものであり、すでに実行中の処理を即時中断する機構ではなく、
各コレクターが実行前に変更されたホワイトリストを都度再読み込みすることを保証するものでもありません。ポリシー変更後は、コミットされた
キャッシュの状態とコレクターの挙動を検証してください。

```sh
php cli/input_whitelist.php --audit
# After reviewing this data input's command; 42 is an example data-input ID.
php cli/input_whitelist.php --update --id=42
```

対象を指定しない `--update` は、現在のコマンド定義を無差別にホワイトリストに承認登録してしまいます。これをコマンド監査の省略手段として
使用しないでください。ホワイトリストファイルおよびその親ディレクトリをサービスユーザーの書き込みから保護してください。明示的に設定しない限り
この機能はオフになっています。対象の選定や出力の詳細については、[データ収集スクリプトの作成](/ja/guides/write-a-data-collection-script/)を参照してください。
これにより、ブラウザ経由の管理者アカウント侵害に対する攻撃コストを大幅に引き上げることができます。新しいコマンドを収集フローに組み込むには、
ポーラーホスト上のファイルシステム書き込み権限も必要となるためです。ただし、承認済みの既存コマンド文字列を悪用できる攻撃者は新たなコマンドを
追加する必要がないため、上表の権限保持者を制限することの代用にはなりません。

## 認証

4つの認証方式が提供されています。どれが利用可能かはインストールされている PHP 拡張モジュールに依存します。

| 方式 | ユーザー検証の実施場所 | 備考 |
|---|---|---|
| 内蔵（Built-in） | ローカルデータベース | パスワード、ポリシー、ロックアウトをすべてローカルで処理 |
| Web Basic 認証 | Web サーバー | サーバーが伝達するユーザー識別子を全面的に信頼 |
| LDAP | 単一のディレクトリ | PHP LDAP 拡張モジュールが必須 |
| 複数 LDAP/AD ドメイン | 複数のディレクトリ | 同様に拡張モジュールが必須 |

設定画面のセレクターには、従来の認証なしモード（モードゼロ）を除外したこれらの認証方式が表示されます。認証のブートストラップ処理は、
古い認証なしの設定をローカル認証に移行させようと試みますが、低レベルの認可ヘルパーには依然としてモードゼロ用の分岐コードが残存しています。
画面上に選択肢が存在しないことだけを安全性の根拠とせず、保存されている方式、設定された識別子、および実際に保護されているルーティングを確認してください。

確認すべき要点：

- **Web Basic 認証は本人確認を外部に委ねる。** このモードを選択すると、Kadupul はサーバーで認証された識別変数を読み取りますが、アカウントのマッピング、有効化状態、および認可ルールは引き続き適用されます。識別情報が欠落しているからといって自動的に管理者になるわけではありません。想定されるすべてのルートを認証するようにサーバーを構成し、クライアントから信頼済み識別変数が持ち込まれるのを阻止してください。画像出力やエクスポートのルート、および意図的なゲストの挙動は個別に検証してください。
- **「ログイン状態を保持する」のサポート**はデフォルトで有効になっています。永続トークンは、ユーザーが認証後にそのオプションを選択した際に作成されるものであり、すべてのセッションで無差別に生成されるわけではありません。このトークンは90日間使用されないと失効します。インターネットに公開する環境では、この機能を有効にしておくべきか慎重に判断してください。
- **ゲストユーザーは nobody（未割り当て）に設定する。** 匿名でのグラフ閲覧を明示的に許可したい場合を除き、デフォルトはユーザー未割り当てとなっており、これが適切な設定です。初期セットアップ中に変更されていないか確認してください。
- **システム全体の前段に多要素認証（MFA）を導入する。** アプリケーション自体には MFA 機能は含まれていません。アイデンティティ認識型プロキシや SSO ゲートウェイを前段に配置して対応してください。

## リモートデータコレクターのエンドポイント

リモートコレクターを運用している場合、中央サーバーはそれらのコレクターが通信するためのエンドポイントを公開します。
このエンドポイントはユーザーセッションによる認証は行いません。呼び出し元のアドレスを名前解決し、登録済みコレクターの
ホスト名と照合することで認可を行い、失敗した場合はセキュリティカテゴリのログを出力します。

これには2つの運用上の注意点があります。第1に、そのエンドポイントはパブリックなインターネットからアクセスできてはなりません。
Web サーバー側でアクセス元をコレクターのアドレスのみに制限してください。第2に、照合されるクライアントアドレスはリクエストから
抽出されたものであるため、前述した転送ヘッダー（forwarded-header）の信頼設定がここでも適用されます。管理下にないヘッダーを
信頼してしまうと、攻撃者がコレクターのアドレスを偽装できてしまいます。

また、中央サーバーがコレクターと通信する際に、自己署名証明書やホスト名の不一致を許容する設定がデフォルトで有効になっています。
コレクター向けに正規の証明書を発行し、この許容設定をオフにしてください。

## 最低限のチェックリスト

1. TLS を終端し、ログイン前に HTTP をリダイレクトし、信頼できるサーバー経由で PHP の HTTPS 状態を構成し、Secure Cookie を確認する。クライアントアドレス用ヘッダーは、プロキシが設定・検証するもののみに限定する。
2. デフォルトの admin パスワードを変更し、確認する。アカウントロックアウトを有効にする。
3. インストール、メンテナンス、およびコレクターの役割に合わせてデータベース権限を精査する。タイムゾーンへのアクセス権を確認し、データベースへのネットワークアクセスを必要なクライアントのみに制限する。
4. ストレージパスを検証し、非公開ディレクトリとメタデータへのアクセスを Web サーバーで拒否し、必要な静的アセットが正常に動作することを確認する。
5. 設定ファイルを実行時に書き込み不可にする。CSRF シークレットファイルを使用する場合は、ドキュメントルートの外部に配置する。
6. 「データ入力方式」、「テンプレートのインポート」、「プラグイン管理」の各権限を、ポーラーホストのシェル権限を持たないユーザーに付与しない。メタ文字制限を有効にする。入力ホワイトリストを構成する。
7. リモートコレクターのエンドポイントを接続元アドレスで制限する。厳格な証明書検証を有効にする。
8. システム全体の前段に配置したプロキシで MFA を強制する。
