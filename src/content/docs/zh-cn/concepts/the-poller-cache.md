[架构](/zh-cn/concepts/architecture/)用一句话介绍了轮询器缓存：
工作列表是预先计算好的，收集器读取该列表，而不是在每个周期重新解析
您的配置。本页将探讨这一设计决策在实践中的实际意义。

## 收集器原本需要做些什么

要确定为单个值收集什么，需要解析整个依赖链。数据源指向一个设备和一个数据模板。
模板指向一个数据输入。数据输入包含多个字段，其中一些在每个设备上被覆盖，一些从模板继承。
如果数据源来自数据查询，则必须通过查询缓存解析当前索引。然后必须从设备获取 SNMP 凭据，
除非某个字段覆盖了它们。

对于单个值来说，这就是多次连接（join）操作。一个适度规模的安装包含数万个值，并且每五分钟运行一个周期。
如果在收集时执行这种解析，将意味着由数据库而不是网络来决定您可以监控多少台设备。

因此，解析仅在发生更改时进行一次，并将结果扁平化地记录下来。

## 缓存中存储的内容

缓存预先计算收集指令。它减少了重复的配置解析，但并没有消除连接或对实时设备状态的读取。

| 行中保存的内容 | 存在的原因 |
|---|---|
| 由哪个收集器拥有 | 每个收集器仅选择属于自己的行 |
| 操作类型：SNMP、脚本或脚本服务器 | 决定执行哪条代码路径 |
| 主机名、SNMP 版本、端口、超时、共同体名或凭据 | 缓存的连接字段；同时也会读取主机的实时状态 |
| OID 或完整的脚本命令行 | 已完成替换，可直接运行 |
| RRD 文件的路径 | 已解析完成 |
| 该文件内的字段名称以及一次完整读取包含的字段数 | 用于匹配和验证输出 |
| 步长（step）以及距离该项下次到期的倒计时 | 请参阅[时间与时间间隔](/zh-cn/concepts/time-and-intervals/) |

`cmd.php` 将 `poller_item` 与 `host` 连接，过滤掉已禁用的设备，并使用实时设备字段进行可用性和重新索引检查。
缓存的 OID、命令和 RRD 元数据仍需与目标数据源匹配。

缓存的凭据是一个快照，但通过设备 API 保存更改后的凭据通常会刷新受影响的缓存。
直接编辑数据库会绕过该路径，并可能留下过时的快照。请验证实际缓存，而不是假设每次更改凭据都需要手动重建。

RRD 路径同样是一个快照。移动文件或更改文件存放位置会使每个缓存行继续指向旧位置。

## 什么会写入它

缓存是由知道自己更改了内容的各个操作进行增量维护的。

| 操作 | 重写的行 |
|---|---|
| 保存设备 | 连接字段、收集器或禁用状态的更改会触发推送；未更改的收集字段可使用快速保存路径 |
| 保存数据源 | 该数据源的行 |
| 从模板创建图形和数据源 | 新创建的行 |
| 移动或解析了索引的数据查询运行 | 仅更改的数据源 |
| CLI 重建 | 由其工作进程处理的已启用设备；当前 `--host-id` 转发缺陷妨碍了对设备隔离的依赖 |

重写并不是盲目插入。正在重建的数据源的行首先被标记为缺席，然后写入新集合，最后删除仍标记为缺席的所有行。
这就是删除不再存在的字段对应行的方式。缓冲区清理的作用域受收集器和数据源 ID 限制。
这保护了普通定向路径中不相关的源；但这并不是对并发重建或数据库写入失败的绝对保证。
重建后请验证生成的行，在排查影响范围时可包括附近未受影响的设备。

## 从不写入的行

某些配置不会生成新的缓存行。请检查日志以及图形。

构建器会跳过已禁用的设备，但批量**禁用**操作会保留现有的缓存行，并且收集过程会将该设备过滤掉。
在禁用状态下重建可能会删除这些行。批量**启用**操作会重用已填充的缓存，或在缓存为空时进行初始化；
通常不需要额外保存设备。现有的部分或过时缓存仍需进行排查。

设备没有可用 SNMP 配置的 SNMP 项不会生成任何行。缺少版本、版本超出范围，或在版本 1 或 2 上共同体名为空，
该行都会被跳过，而不是写入一行在每个周期都会失败的记录。

当配置了输入白名单时，缺少文件或被拒绝的输入会阻止为该输入生成新行。已提交的重建仍会清理其过时的行。
在没有 `input_whitelist` 配置的情况下，此检查允许输入；它不是始终启用的保护措施。
在修改白名单之前，请检查被拒绝的命令和配置的策略。

界面仍可能显示缓存为空的数据源。其图形可能会保留旧历史记录或显示空白间隙；平直的零线并不是可靠的指标。
缺失的凭据和被拒绝的输入都是需要解决的配置问题。

## 为什么更改似乎未起作用

三种不同的机制会导致相同的症状。

**行未被重建。** 您更改了界面认为不影响收集的内容，或者您在界面外部进行了更改。
缓存中仍然保存着旧答案。在确认预期配置后，重建可以刷新缓存字段。

**行从未被构建。** 上文已作说明。重建也可以解决此问题，但前提是必须先修复底层问题；
诊断信息通常出现在日志中而不是图形上。

**值被收集后随即被丢弃。** 多值输出通过模板字段定义进行映射，未引用的字段在解析期间可能会被跳过。
检查预期的字段名称、映射和图形关联；此规则不会一概丢弃所有没有图形引用的数字样本。
缓存重建无法修复不正确的输出契约。

## 强力工具

对于单个设备，请在其传统设备页面上使用**重新填充轮询器缓存**。该操作会调用设备作用域的
`push_out_host()` 路径。之后请检查生成的行和诊断信息。

当前的 `rebuild_poller_cache.php` 父脚本接受 `--host-id`，但不会将该过滤器转发给其工作进程命令。
因此，声称针对单个设备的 CLI 重建可能会连带重建其他已启用的设备。在修复此应用程序缺陷之前，
请勿依赖该选项来实现隔离。

可以通过轮询器用户从应用程序根目录运行广泛的 CLI 重建：

```bash
php cli/rebuild_poller_cache.php
```

它会处理已启用的设备；它并不是对每个无主机或已禁用数据源的修复。此操作会写入收集表并可能需要一定时间。
避免重叠的重建操作，且不要中途中断。CLI 的 `--force` 参数会覆盖其进程注册防护，因此它不是常规的修复选项。

重建会刷新派生状态；它不能修复设备可达性，不能移动 RRD 文件，不能修复被拒绝的输入命令，也不能恢复丢失的历史记录。
在确认修复完成之前，请检查生成的缓存、日志和后续收集。

Kadupul 会记录缓存上次更改的时间，这使得系统的其他部分能够察觉并重新读取它。

## 多个收集器

当有多个收集器时，每一行都严格属于其中一个收集器，并且这些行既会被推送到该收集器自己的数据库中，
也会推送到中央数据库中。

如果您在保存更改时某个远程收集器不可达，则更改将仅保存在中央而不是远程，Kadupul 会提示这一点：
它要求在收集器恢复后进行完整同步。在该同步完成之前，远程收集器运行的工作列表比界面向您显示的要旧。
特定收集器的差异是检查复制状态、连接性以及每个收集器本地缓存的理由。

完整运行中的顺序（包括读取缓存的位置以及处理重新索引命令的时间）在
[轮询器生命周期](/zh-cn/reference/poller-lifecycle/)中有详细说明。关于扩展收集器，请参阅
[扩展轮询器](/zh-cn/guides/scale-the-poller/)。
