随附的 ESXi 软件包收集主机测量数据和客户机资产清单计数。它不提供针对每个客户机的 CPU、内存或争用度量。在选择图表之前，请验证您的虚拟机管理程序版本暴露的对象。

## 随附内容

附带了一个虚拟机管理程序设备模板：**ESXi Device**。它是一个设备软件包，因此 `install/templates/ESXi_Device.xml.gz` 包含其脚本和数据查询文件。遵循[导入和导出模板](/zh-cn/guides/import-and-export-templates/)并验证导入是否完成，包括文件部署。选择设备模板，检查发现，并显式创建所需的图表；仅导入软件包或关联设备模板不会创建它们。

| 随附项 | 用途 |
|---|---|
| `resource/snmp_queries/esxi_cpu.xml` | 发现处理器并读取单处理器负载 |
| `resource/snmp_queries/esxi_hw.xml` | 发现硬件组件并读取其状态 |
| `resource/snmp_queries/interface.xml` | 标准接口统计信息查询 |
| `resource/script_server/host_disk.xml` | 挂载的分区，通过 Host Resources 存储表 |
| `scripts/ss_esxi_vhosts.php` | 捆绑在 `install/templates/ESXi_Device.xml.gz` 内部；统计客户机数量、已开机客户机数量以及客户机工具状态 |
| `scripts/ss_multicpu_avg.php` | 将单处理器负载平均为一个数值 |
| `scripts/ss_hstats.php` | 读取 Kadupul 已为该设备保存的轮询统计信息 |
| `scripts/ss_host_disk.php` | 支持分区查询 |

在当前检出版本中，未随附针对 Hyper-V、KVM/libvirt、Xen 或 Proxmox 的专用设备软件包。通用 Linux/Windows 模板可能涵盖其代理支持的主机指标；特定于虚拟机管理程序的收集需要合适的模板和收集器。参见[编写数据收集脚本](/zh-cn/guides/write-a-data-collection-script/)。

## 首先开启代理

查看现有的代理配置并使用适合您的 ESXi 版本的说明。软件包注释包括出厂重置；这不是例行的先决条件，并且会清除现有的 SNMP 配置。对于基于共同体的设置，以下命令设置代理值；在设置共同体列表时，请替换示例并保留任何所需的现有共同体。

```bash
esxcli system snmp get
esxcli system snmp set -c YOUR_STRING
esxcli system snmp set -p 161
esxcli system snmp set -L "City, State, Country"
esxcli system snmp set -C noc@example.com
esxcli system snmp set -e yes
```

第一个命令显示配置；最后一个命令启用代理。共同体选项将替换其配置的列表。检查来自轮询器的必需防火墙访问权限，并查阅 [ESXCLI SNMP 命令参考](https://developer.broadcom.com/xapis/esxcli-command-reference/latest/namespace/esxcli_system.html)。这些命令配置基于共同体的轮询；它们不配置 SNMPv3。在添加设备之前，从运行轮询器的机器进行验证。

```bash
snmpget  -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.1.1.0
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.25.3.3.1.2
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.4.1.6876.2.1.1.6
```

如果第一个命令有效而第三个命令没有返回任何内容，请检查 SNMP 错误、访问策略和代理支持；仅凭空的 walk 无法确定原因。捆绑的客户机脚本使用 SNMPv1，因此成功的 v2c 探测不能验证其收集路径。空的客户机 walk 会产生零计数，而不一定是图表断层；参见[空结果缺陷](https://github.com/kadupulhq/kadupul/issues/245)。

## 主机暴露的内容

| 区域 | 子树 | 提供的内容 |
|---|---|---|
| 处理器 | `.1.3.6.1.2.1.25.3.3.1` | 代理暴露的每个处理器的负载 |
| 硬件组件 | `.1.3.6.1.2.1.25.3.2.1` | 组件索引、描述和状态 |
| 存储 | `.1.3.6.1.2.1.25.2.3.1` | 数据存储和本地文件系统，按代理选择报告的形式 |
| 接口 | `.1.3.6.1.2.1.2` 与 `.1.3.6.1.2.1.31` | 流量、错误、状态 |
| 客户机清单 | `.1.3.6.1.4.1.6876` | 单客户机电源状态和客户机工具状态 |

前四个是标准的 Host Resources 和接口表，与 Linux 主机响应的表相同。有关这些表的行为方式以及优先选择哪个磁盘表，请参见[监控 Linux 服务器](/zh-cn/guides/monitor-a-linux-server/)。

第五个是随附的客户机计数脚本使用的供应商子树。

## 图表模板

| 图表 | 来源 | 读取内容 |
|---|---|---|
| ESXi - CPU | 数据查询 | 单个已发现处理器的负载 |
| ESXi - MultiCPU Average | 脚本 | 所有处理器负载的均值 |
| ESXi - Hardware | 数据查询 | 单个已发现组件的状态 |
| ESXi - VHosts | 脚本 | 客户机计数和客户机工具状态 |
| Host MIB - Processes | 固定 OID | 主机上的进程计数 |
| Host MIB - Logged in Users | 固定 OID | 主机上的会话计数 |
| Device - Uptime | 脚本 | Kadupul 最后记录的正常运行时间 |
| Device - Polling Time | 脚本 | Kadupul 轮询此设备花费的时间 |
| 接口图表 | 数据查询 | 每个接口的流量、错误、数据包、状态 |

处理器查询读取每个已发现条目的负载。不要假定其行数与主机的硬件线程数相匹配：随附的索引模式仅接受一位或两位数字的索引，并拒绝 100 或更大值，即使在 CPU 很少的主机上也是如此。将发现与原始 walk 进行比较；参见 [CPU 索引缺陷](https://github.com/kadupulhq/kadupul/issues/246)。平均值脚本独立遍历处理器负载并对返回的行求均值。

Device - Uptime 和 Device - Polling Time 读取 Kadupul 存储的设备记录。正常运行时间助手返回存储的 SNMP 正常运行时间，而不推断经过的时间；轮询时间描述 Kadupul 的收集工作。旧的存储值不能证明当前的可达性。如果收集停止，这些助手不会生成新样本。

## 统计难题

这正是虚拟化与物理服务器不同的地方，并且没有一个问题可以通过图表模板来解决。

**客户机会发生移动。** 迁移到另一台主机的客户机会从第一台主机的清单中消失，并出现在第二台主机的清单中。独立计时的采样可能会暂时对该客户机进行重复计数或遗漏。仅凭计数变化并不能证明发生了迁移：请使用虚拟机管理程序清单标识和事件来解释它们。

**资源是共享的，因此单客户机归属只是一种估计。** 主机报告物理处理器负载。它不报告是由哪个客户机引起的。将主机 CPU 除以客户机数量得出的数字在算术上是正确的，但没有回答任何人提出的问题。

**超额分配使分配量与使用量成为不同的指标。** 分配的虚拟 CPU 可以故意超过物理核心数，分配的内存也可以故意超过物理内存。分配资源的图表描述的是分配而不是实测需求。将其与物理容量、配置限制和实际使用情况进行对比。

**争用不会出现在这些表中。** 告诉您客户机正处于资源匮乏状态的指标（等待物理处理器所花费的时间以及主机从其回收的内存）并不在此模板收集的内容中。一个 CPU 为 60% 且客户机严重争用的主机在此处看起来与一个 CPU 为 60% 且客户机运行良好的主机完全相同。

**客户机与主机测量回答不同的问题。** 单纯的客户机利用率可能无法解释主机调度延迟。将客户机/应用程序度量与虚拟机管理程序争用指标相关联，而不是从主机负载推导归属。

### 替代方案

| 问题 | 答案所在 |
|---|---|
| 主机是否饱和 | 来自主机的物理处理器负载 |
| 客户机是否饱和 | 在客户机内部，加上虚拟机管理程序保留的争用指标 |
| 正在运行多少客户机 | 主机客户机清单计数 |
| 环境是否超容 | 无法从这些图表中得出。它需要主机未暴露的放置数据 |
| 客户机是否移动 | 虚拟机管理程序清单标识和迁移事件；仅凭计步是不够的 |

对于与客户机相关的任何信息，将客户机作为其自身的设备进行监控，而对于与主机相关的任何信息，则监控主机。抵制根据主机级数字构建单客户机图表的做法：它们是派生出来的，看起来具有权威性，但其错误方式日后无人能察觉。

## 随附客户机计数中的陷阱

在依赖其输出之前，了解客户机清单脚本是值得的。

**它仅使用 SNMP 版本 1 和共同体字符串执行遍历。** 该版本在脚本中固定，设备上的 v3 凭据未传递。配置为 v3 的设备可以通过其他路径进行收集，而客户机收集会失败。如果该代理独立接受通过 v1 传递的存储共同体，则客户机收集可能仍会成功；在设备上选择 v3 本身并不能决定结果。空的客户机 walk 返回为零。在不降低代理安全策略以适应助手的情况下检查此协议不匹配。

**计数来自电源状态表。** 报告为客户机总数的数字是对电源状态子树进行 walk 返回的条目数，而不是来自单独的清单对象。主机列出但没有电源状态条目的客户机不会被计入。

**根据状态文本匹配已开机状态。** 修剪并转为小写后，只有 `powered on` 和 `poweredon` 会增加运行计数。其他表示形式不会；在解释零之前请对比原始代理响应。

**客户机工具分类存在已确认的缺陷。** 字面值 `not installed` 被计为正在运行，因为它的匹配从偏移量零开始。无法识别的文本也会落入正在运行的范畴。不要将该计数视为工具健康的证据；参见[工具状态缺陷](https://github.com/kadupulhq/kadupul/issues/244)。

**每次调用会遍历三次。** 它读取电源状态表两次，然后读取工具表，因此即使是它自己的计数也不是原子清单快照。在具有许多客户机的主机上，请评估该收集成本。如果轮询器很紧张，这是使用更长间隔的候选对象，而不是使用更多线程的候选对象。参见[扩展轮询器](/zh-cn/guides/scale-the-poller/)。

该脚本通常会输出所有五个命名值，包括空遍历的零。因此，失败的遍历可能会产生语法完整但具有误导性的样本。对于不完整的输出，PHP 输出处理器会检查关联数据源所需的字段，并扣留不完整的时间戳组；它不一定会立即丢弃它们。参见[轮询器缓存](/zh-cn/concepts/the-poller-cache/)。

## 其余部分的陷阱

**处理器平均值掩盖了不平衡。** 一个具有 1 个高负荷核心和 63 个空闲核心的主机其平均值很低。在重要的地方保留经过验证的单处理器图表。平均值助手在遇到空遍历时也会返回 `load:0`，这与实测的空闲 CPU 无法区分；将其与收集状态和已知的空结果缺陷联系起来。

**处理器索引是基于位置的。** 它们是通过遍历处理器表发现的。如果代理索引发生更改，在信任连续性之前请验证身份映射。随附的一位/两位数限制是一个单独的发现缺陷。

**存储条目是代理称为存储的任何内容。** 预计数据存储会与您不需要的内容混合在一起，以需要乘法的分配单位表示。这是 Host Resources 的行为，而不是 ESXi 的特例。在解释字节之前请验证缓存的分配单位；共享脚本对于无效的负样本或缺失的乘数具有[已知的转换缺陷](https://github.com/kadupulhq/kadupul/issues/243)。

**虚拟机管理程序上的接口名称在发生变化前是稳定的。** 驱动程序更新或重新配置可能会对其重新编号。有关如何选择索引及其重要性的信息，请参见[监控交换机](/zh-cn/guides/monitor-a-switch/)。

**脚本在轮询器主机上运行。** 它们自行访问虚拟机管理程序，使用由缓存命令传递的设备 ID。客户机和 CPU 平均值助手在每次调用时都会获取当前设备行；共同体更改不需要重新构建这些命令参数。其他收集器可能会在其工作项中嵌入凭据。参见[轮询器缓存](/zh-cn/concepts/the-poller-cache/)。

## 故障模式

| 现象 | 常见原因 |
|---|---|
| 除客户机计数外所有内容均能收集 | 设备配置为 SNMP v3，而客户机脚本使用 v1 |
| 客户机计数正确，开机计数为零 | 检查确切的电源状态文本以及第二次遍历是否成功 |
| 客户机计数降至零后恢复 | 检查失败/空的遍历；助手可以输出完全为零的行 |
| 硬件更改后处理器图表出现随后停止 | 检查更改的索引以及随附的限制为一位或两位数 |
| 主机 CPU 保持低平而客户机变慢 | 检查收集故障以及争用；空的平均值遍历报告为零 |
| 数据存储图表包含您未要求的分区 | 代理将其报告为存储 |
| 轮询器停机后正常运行时间图表看起来不正常 | 它报告 Kadupul 最后记录的值，而不是实时读取 |
| 维护期间跨主机的客户机总数发生跳变 | 正在迁移的客户机会短暂地被计数两次，或者根本不计数 |
