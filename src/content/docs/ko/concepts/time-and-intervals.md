데이터 수집에는 세 가지 클록이 관여합니다. 시작 관리자 실행 주기, 각 호출 내부의 폴링 간격, 그리고 RRD 스텝입니다. 이들은 서로 호환 가능한 설정을 유지해야 합니다.

| 항목 | 소속 | 사용 방식 |
|---|---|---|
| 시작 관리자 간격 | Cron, 작업 스케줄러 또는 `cactid.php` | `cron_interval` 과 일치해야 하며, `poller.php` 에 의해 60초 또는 300초로 해석됨 |
| 폴링 간격 | 수집 패스 | `poller.php` 가 시작 관리자 간격당 정수 회의 패스 수를 계산함 |
| 스텝 | RRD 파일 | 기본 정규화 간격으로, 생성 시 데이터 소스 프로필에서 설정됨 |
| 하트비트 | RRD 내부 필드 | 업데이트 간에 허용되는 최대 간격으로, 생성 시 데이터 소스 필드 정의를 읽음 |

예를 들어 60초 시작 관리자와 10초 폴링 간격은 호출당 6번의 패스를 생성합니다. 300초 시작 관리자와 300초 폴링 간격은 1번의 패스를 생성합니다. 시작 관리자 간격을 폴링 간격보다 작게 구성하지 마세요. 60/300은 패스 수를 0으로 계산합니다. 단일 스케줄러를 사용하고, 수동으로 `--force` 를 실행하기 전에 중지하세요. [설치](/ko/start/install/)를 참조하세요.

프로필을 편집해도 기존 파일이 자동으로 마이그레이션되지는 않습니다. 하트비트는 조정할 수 있으며, 스텝 변경은 설치된 RRDtool 지원 도구를 사용하여 계획된 마이그레이션이 필요합니다. 이후 데이터베이스 정의와 `rrdtool info` 출력을 모두 확인하세요.

## 값이 일치하는 경우

스텝이 폴링 간격과 같은 데이터 소스는 디바이스 상태, 캐시 내용 및 런타임 한계 내에서 각 패스마다 수집 대상이 됩니다. 기본 제공 구성에서는 둘 다 300초를 사용합니다. 대상이 된다고 해서 읽기 성공이 보장되는 것은 아닙니다.

## 스텝이 인터벌보다 긴 경우

PHP 수집기는 여러 활성 일정이 필요로 할 때 작업 목록의 각 행에서 `rrd_next_step` 을 사용합니다. 0 이하의 행을 선택한 다음 해당 수집기 및 호스트 범위에 대한 카운트다운을 업데이트합니다. 스텝이 폴링 간격과 동일한 행은 0으로 유지됩니다. 다른 행은 폴링 간격만큼 감소하며, 언더플로 발생 시 재설정 동작은 호출 모드에 따라 다릅니다. 일반 하위 시작 관리자 패스는 스텝에서 간격을 뺀 값으로 재설정되고, 시작 관리자와 폴러 간격이 동일한 경우 및 전체 호스트 경로는 전체 스텝으로 재설정됩니다. 10분 스텝이 항상 5분 호출 2회당 1회를 의미한다고 가정하지 마세요. 실제 만료 행과 업데이트 타임스탬프를 검사하세요.

**프로세스 부하 분산**이 활성화되면 캐시 구축 시 스텝과 폴링 간격을 사용하여 디바이스의 연속적인 데이터 소스에 오프셋을 할당합니다. 동일한 소스의 필드는 오프셋을 공유합니다. 이를 통해 작업을 패스 간에 분산할 수 있지만 실행 시간이 균등해지는 것은 아닙니다. 디바이스 대기 시간, 타임아웃 및 스크립트 특성이 서로 다르기 때문입니다. 시작 관리자는 데이터 소스 내에서 일치하지 않는 필드 카운트다운도 정렬합니다.

한 번의 패스에서 아무것도 생성되지 않았다고 해서 항목이 손상되었다고 결론 내리기 전에 만료 상태와 후속 패스를 확인하세요. 재구축 한계는 [폴러 캐시](/ko/concepts/the-poller-cache/)를 참조하세요.

## 스텝이 인터벌보다 짧은 경우

짧은 스텝을 설정해도 수집기가 측정하지 않은 데이터를 만들어낼 수는 없습니다. 수집 속도가 스텝에 비해 너무 느린 경우 Kadupul은 캐시 생성 중에 경고를 표시합니다. 폴링 설정을 해결하고 영향을 받는 캐시를 재구축하세요.

이러한 불일치가 반드시 빗살 모양의 그래프를 생성하는 것은 아닙니다. 하트비트가 허용하는 경우 RRDtool은 덜 빈번한 업데이트를 더 작은 스텝으로 정규화할 수 있지만, 그렇다고 누락된 측정 세부 정보가 복원되지는 않습니다.

## 하트비트가 항상 스텝의 두 배는 아님

하트비트는 입력이 알 수 없음으로 처리되기 전에 허용되는 업데이트 간의 최대 간격입니다. RRD 생성 시 데이터 소스 필드 정의에서 하트비트를 읽으며, 이는 프로필이나 템플릿 설정을 상속받을 수 있습니다. 스텝에 추가되는 유예 기간이 아닙니다. 프로필과 다를 경우 실제 필드와 파일을 검사하세요.

제공되는 기본 프로필은 일률적인 규칙을 따르지 않습니다.

| 프로필 | 스텝 | 하트비트 | 업데이트 간격 한계 |
|---|---|---|---|
| 5분 | 300 | 600 | 10분 |
| 1분 | 60 | 600 | 10분 |
| 30초 | 30 | 1200 | 20분 |

이 값들은 기본 제공 프로필 값이며 서비스 중단 감지 타이머가 아닙니다. 명시적으로 알 수 없는 입력은 하트비트가 만료되기 전에 공백을 생성할 수 있습니다. 데이터 정규화 및 아카이브 임계값은 표시되는 결과에 영향을 미칩니다. 하트비트가 클수록 유효한 업데이트 간의 더 긴 간격을 허용합니다. 정상 업데이트 간격 이하로 설정하면 지연에 대한 허용 범위가 거의 남지 않습니다.

프로필뿐만 아니라 실제 물리적 파일도 확인하세요. 기존 RRD는 수정된 데이터베이스 정의와 다를 수 있으며, 파일 감사는 이러한 드리프트를 보고합니다. 파일 변경을 계획하기 전에 [RRDtool 하트비트 정의](https://oss.oetiker.ch/rrdtool/doc/rrdcreate.en.html) 및 [튜닝 참조 문서](https://oss.oetiker.ch/rrdtool/doc/rrdtune.en.html)를 검토하세요.

## 저장되는 값은 디바이스가 응답한 값과 다름

RRDtool은 업데이트를 고정된 스텝 경계로 정규화합니다. 경계 사이의 값은 둘 이상의 기본 데이터 포인트에 기여할 수 있습니다. 하트비트, 명시적 알 수 없는 값 및 경계값은 유효한 입력에 영향을 미치며, 아카이브 통합은 자체적인 알 수 없는 데이터 임계값을 적용합니다. 스텝에 알려진 값을 유지하기 위해 별도의 원시 샘플이 포함되어야 하는 것은 아닙니다.

카운터 값은 경과 시간에 따른 속도로 변환되며, 카운터 리셋, 래핑 처리 및 경계값의 영향을 받습니다. 게이지 수치 역시 시간에 따라 정규화됩니다. 짧은 스파이크는 샘플링으로 인해 희석되거나 완전히 누락될 수 있으며, 지속적인 수치나 경계에 정렬된 업데이트는 반드시 축소되는 것은 아닙니다. 아카이브 설정으로 수집되지 않았거나 정규화 중에 손실된 세부 정보를 재구성할 수는 없습니다.

## 어느 클록이 결정하는가

일반적인 `cmd.php` 수집의 경우 배치 데이터 삽입 시 SQL `CURRENT_TIMESTAMP()` 가 출력 타임스탬프를 제공합니다. 이는 디바이스가 제공한 타임스탬프가 아니며 디바이스가 응답한 정확한 순간의 측정도 아닙니다. 기타 수집 백엔드 및 실시간 경로는 별도로 점검해야 합니다.

PHP 수집기는 결과를 버퍼에 보관하고 배치 단위로 기록하며 디바이스가 바뀌거나 버퍼가 가득 차면 플러시합니다. 타임스탬프는 배치당 한 번만 평가되므로 한 배치의 모든 값은 동일한 시간을 갖습니다.

그 결과는 명확하지 않으므로 자세히 설명할 가치가 있습니다.

**디바이스 클록은 이 SNMP 샘플에 타임스탬프를 찍지 않습니다.** 수집기는 데이터베이스 삽입 시간을 사용합니다. 스크립트나 특정 메트릭의 의미에서 디바이스 시간이 중요할 수 있으므로 이것이 클록 동기화를 무시해도 된다는 이유는 아닙니다.

**수집기 또는 데이터베이스의 잘못된 클록은 데이터를 왜곡시킵니다.** 값이 잘못된 슬롯에 기록되며, 이미 일부가 기록된 파일에서는 이전 기록보다 이후가 아닌 업데이트는 완전히 거부됩니다. 타임스탬프가 파일의 마지막 업데이트 기록 이전으로 되돌아가면 새 데이터의 타임스탬프가 그 기록을 초과할 때까지 파일을 진행시킬 수 없습니다. 데이터베이스 클록, 수집기 클록 및 파일 타임스탬프를 확인하세요. 수집기 클록만 변경한다고 해서 데이터베이스가 생성하는 타임스탬프가 반드시 바뀌지는 않습니다.

**사이클 내의 시간은 지터가 됩니다.** 긴 실행 주기의 끝부분에서 폴링된 디바이스는 동일한 주기에 속하더라도 시작 시 폴링된 디바이스보다 늦은 타임스탬프를 받습니다. 부하가 많은 수집기에서 이러한 지터는 간격의 상당 부분을 차지할 수 있으며, 하트비트를 스텝에 너무 가깝게 설정했을 때 갭이 발생하는 원인 중 하나입니다.

**데이터베이스의 시간대는 왕복 경로의 중간에 위치합니다.** 타임스탬프는 데이터베이스 타임스탬프로 기록되며 읽을 때 데이터베이스에 의해 절대 시간으로 다시 변환됩니다. 세션 시간대 처리가 일치하지 않으면 이러한 해석이 달라질 수 있습니다. 오프셋을 진단할 때 읽기/쓰기 세션 설정 및 에포크 변환을 확인하세요. 표시 시간대를 변경한 것만으로는 저장된 기록 데이터가 이동했다는 증거가 되지 않습니다.

## 판독값은 타임스탬프별로 취합됨

인바운드 바이트와 아웃바운드 바이트가 있는 인터페이스와 같이 둘 이상의 필드를 갖는 데이터 소스는 별도의 SNMP 작업 목록 항목이나 여러 명명된 값을 반환하는 스크립트를 사용할 수 있습니다. 파싱된 필드는 RRD 업데이트를 위해 데이터 소스 및 타임스탬프별로 그룹화됩니다.

불완전한 세트는 일부만 기록되는 대신 예상 필드 수가 충족될 때까지 보류됩니다. 이는 조립 유효성 검사이며 모든 필드에 올바른 숫자가 포함되어 있음을 보장하는 것은 아닙니다. 명시적으로 알 수 없는 값은 여전히 기록될 수 있습니다. 일반적으로 양쪽 모두 동일한 배치에 있어 타임스탬프를 공유하므로 이 과정은 드러나지 않습니다. 같은 초 내에 삽입된 배치도 일치할 수 있습니다. 필드가 서로 다른 타임스탬프를 받으면 그룹이 불완전한 상태로 남아 업데이트가 생성되지 않을 수 있습니다. 현재 코드는 사이클 간에 불완전한 그룹을 유지하다가 `5 * max(60, poller_interval)` 초 후에 로그를 남기고 만료시킵니다. 읽기 페이지 경계는 마지막 타임스탬프 그룹을 포함하도록 확장됩니다.

또한 파일은 마지막 업데이트보다 오래된 값을 허용하지 않으므로 업데이트는 기록 전에 시간 오름차순으로 정렬됩니다.

## 지연된 쓰기는 타임스탬프를 유지함

RRD 쓰기가 지연되어 나중에 일괄 적용될 때 기록된 타임스탬프는 값과 함께 이동하며 배치는 시간순으로 기록됩니다. 정오의 타임스탬프는 1시에 업데이트가 시도되더라도 유지되며 플러시 시간으로 대체되지 않습니다. RRDtool은 허용된 업데이트를 여전히 스텝 경계로 정규화합니다.

백로그는 파일의 마지막 업데이트보다 최신의 대기열 타임스탬프를 통해 파일을 진행시킬 수 있습니다. 그러나 해당 타임스탬프 이전의 임의의 갭을 소급하여 채울 수는 없습니다. Boost 라이터는 파일의 마지막 업데이트 시점 이전의 샘플을 필터링하므로 대기열이 비었다고 해서 모든 샘플이 적용되었음을 증명하지는 않습니다. [대용량 쓰기](/ko/concepts/high-volume-writes/) 및 [RRDtool 업데이트 참조 문서](https://oss.oetiker.ch/rrdtool/doc/rrdupdate.en.html)를 참조하세요. 지연된 쓰기는 여전히 성공적인 스토리지 저장 및 올바른 시간 순서에 의존합니다. 모든 장애로부터의 복구를 보장하지는 않습니다. 백로그가 해소되지 않을 때 보류되거나 거부된 출력을 검사하세요.

## 사이클이 완료되지 않는 경우

PHP 수집기는 작업 항목 사이의 경과 시간을 확인하고 폴링 간격을 초과하면 항목 루프를 종료하며 경고를 기록합니다. 이는 마감 시점의 강제 중단이 아닙니다. 진행 중인 작업은 해당 검사 전에 초과될 수 있습니다. 도달하지 못한 항목은 해당 사이클에서 값을 생성하지 않습니다. 하트비트와 아카이브 임계값이 허용하는 경우 유효한 업데이트 사이의 공백은 메워질 수 있습니다. 반복되는 초과는 용량, 타임아웃 및 수집 오류를 조사해야 할 증거이며 눈에 보이는 모든 공백이 동일한 원인이라는 증거는 아닙니다.

[폴러 스케일링](/ko/guides/scale-the-poller/)에서 대처 방안을 설명합니다. 실행 순서와 초과 보호 장치는 [폴러 라이프사이클](/ko/reference/poller-lifecycle/)에 설명되어 있습니다.
