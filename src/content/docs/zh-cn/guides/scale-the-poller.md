扩展轮询器归根结底是一个核心问题：一次采集运行是否在下一次开始之前完成？
下文的所有内容都旨在回答这一问题，并引导系统重回肯定的状态。

如果您不清楚具体由哪一部分负责执行数据采集，请先阅读[架构](/zh-cn/concepts/architecture/)。

## 两个时钟

系统存在两个不同的时间间隔，它们并不属于同一配置项。

| | 定义说明 | 允许的值 |
|---|---|---|
| 启动器间隔 | 操作系统通过 cron 或 `cactid` 服务启动采集器的频率 | 60 或 300 秒 |
| 轮询器间隔 | 基础采集节奏；各个数据源的采集步长可以更长 | 10、15、20、30、60 或 300 秒 |

当轮询器间隔短于启动器间隔时，单次启动会在循环中执行多轮采集。
轮数等于启动器间隔除以轮询器间隔。

整个启动任务的时间预算正是由这两个数值推导出来的：采集轮数乘以轮询器间隔，再减去两秒。
这就是衡量每次运行是否超时的真实墙上时钟。

## 当运行超时发生时

此时会发生三种不同情况，并在日志中输出三条独立的记录。

**运行被强制中断。** 当耗时超过时间预算时，轮询器会记录一条已超过最大运行时长的日志，
写入统计信息后退出。尚未产生采样数据的工作可能会留下数据空白。已经进入持久化队列的采样
仍会保留，以便在随后的 RRD 写入中成功落地；超时并不意味着所有未刷新的度量都会被丢弃。
请结合图表检查队列深度和日志，切勿为了让下一次运行看起来干净而清除保留的行。

**下一次运行发现残留残迹。** 启动时，轮询器会统计未正常关闭的进程行，并发出警告，
提示检测到进程超出了轮询周期。请调查未完成或陈旧的进程记录以及实际仍在运行的子进程；
单独的警告信息并不能直接定位瓶颈所在。

**时钟发生漂移。** 如果距离上一次运行的时间超过了预算允许的范围，轮询器会发出警告，
提示启动器与轮询器间隔失去同步。这通常是启动器的问题，而不是轮询器的问题：cron 条目的
执行频率错误、服务已停止、或者主机曾处于休眠状态。

这些路径都会调用管理员通知助手。通知是否送达取决于已配置的收件人、通知控制以及邮件传输组件
是否正常工作；日志中的警告并不证明邮件已成功送达。参见[邮件通知](/zh-cn/guides/send-email-notifications/)。

还有第四种不属于超时的情况。如果轮询器在预期时间之前再次启动，它会记录一条配置为运行过于频繁的
日志，并在不采集数据的情况下退出。`--force` 会绕过这一计时检查；仅在受控的诊断过程中、且在已停止
计划启动和手动启动的前提下使用该选项。它既不会增加系统容量，也不会让重叠的采集变得安全。

## 统计信息行

每次完成的运行都会在日志中写入一行统计信息。它包含耗时、采集方法、进程和线程数、
设备数量、每个进程的设备数、数据源数量以及处理的 RRD 文件数。

请跟踪耗时、尾部延迟、队列深度以及失败更新的趋势。即使是偶尔一次接近预算极限但导致图表留白
的运行也应予以排查；持续的增长有助于确定何时需要调整系统容量或采集行为。

## 进程与线程

这是两组用途截然不同的调节选项。

| 调节项 | 其划分的工作单元 | 适用的采集器 |
|---|---|---|
| 进程 | 设备，按连续的设备 ID 范围进行切分 | 两者皆适用 |
| 线程 | 单个设备内部的各项监控条目 | 仅 Spine |

其直接推论正是常被误解的地方：**一个进程分配到的是整台设备。** 拥有五千个数据源的单台设备
无法被拆分到多个进程中处理。它只能落入某一个进程，而该进程需要多长时间就得耗费多长时间。
盲目增加进程数对此毫无助益。

这两个数值是针对每个数据采集器单独设置的，并非全局统一。设置页面上的数值是在创建新数据采集器
时应用的预设模板。修改预设值并不会改变现有的采集器。

此外还存在单设备线程数设置，这正是对单个大型设备进行内部细分的方法。该选项仅对 C 采集器生效。

Balance Process Load 会利用累积的项目计数，按设备 ID 顺序在整台设备之间选择边界。它不会拆分
单台设备，也不保证项目数量完全相等，且项目计数并不等同于执行耗时。在隔离且具代表性的工作负载下，
对比开启前后的每个进程执行耗时。

## PHP 采集器与 C 采集器对比

PHP 采集器 `cmd.php` 随应用程序一起提供。Kadupul 计划维护一个 Spine 分支，但其源码位置和经过
验证的构建版本尚未形成文档。在获得相应验证之前，请使用 PHP 采集器。以下关于 Spine 的对比、
线程设置和命令仅描述继承自上游的行为，并非可用的或受支持的 Kadupul 部署。

| | PHP 采集器 | Spine |
|---|---|---|
| 并行模型 | 仅进程 | 进程与线程 |
| 线程设置 | 无论如何配置均强制为 1 | 遵从配置 |
| 脚本服务器 | 每个进程固定 1 个，不可配置 | 每个进程 1 至 15 个，可配置 |
| 脚本超时 | 不应用 | 应用，默认 25 秒 |
| 安装方式 | 随源码附带 | 计划分支；目前尚无经文档记录的已验证 Kadupul 构建 |

强制单线程机制有必要明确说明：如果采集器设置为 PHP，运行时线程变量会被置为 1；这不会改写已保存的
采集器线程配置。扩展 PHP 采集器可能需要增加进程数，源码中的建议是保持在 CPU 核心数的两倍或以内。

Spine 的配置与命令行为必须针对正在评估的具体二进制文件进行验证。仅凭 PHP 应用程序源码无法确定其
配置搜索顺序、线程行为或潜在副作用。

用于隔离评估 Spine 的继承示例（非经过验证的 Kadupul 命令）：

```sh
spine --first=42 --last=42 --threads=1 --verbosity=HIGH --stdout
spine --hostlist='42,43,51' --readonly
```

`--readonly` 旨在避免写入结果数据。但它依然会与设备建立通信并执行采集脚本；请先在隔离测试中验证其副作用。

## 数据库连接

线程并非零开销。每个 Spine 线程都会占用一个独立的数据库连接，每个脚本服务器也是如此。

```
estimated worker connections = processes * (threads + script_servers)
```

这是应用程序设置帮助文档中给出的估算公式，而非实测的上限。在所有采集器上累加该数值，并为轮询器
父进程、Web 请求、维护任务及其他客户端预留容量。在设定数据库连接上限之前，请实测真实的连接峰值和
被拒绝连接数；调高上限同样会消耗系统资源。

连接耗尽可能会导致采样丢失，但轮换出现的图表留白并非唯一特征。请通过数据库连接指标和应用程序错误日志进行确认。

## 延迟 RRD 写入

系统提供了一种阻止轮询器在每次采集后都立即写入 RRD 文件的运行模式。采集结果会暂存至数据库表中，
并在定时器触发或图表请求该文件时批量刷新写入。它以少量的大批量写入取代了大量的碎片化小写入。

关于该模式在运维层面的两个关键事实：

- 当拥有远程数据采集器时，该模式是强制要求的。这不是建议，而是软件明确规定的运行前提。
- 缓冲表具有持久性，并非纯内存结构，因此未刷新的采样在系统重启后依然存在。这也意味着您的 RRD 文件
  更新会滞后于数据库。在制作任何快照之前，请先阅读[备份与恢复](/zh-cn/guides/back-up-and-restore/)。

在此版本中，处理中的主队列 `poller_output` 也采用了 InnoDB 引擎。存储预检会拒绝 MEMORY 队列；
增加堆表（heap-table）上限并不能解决该拒绝。在停止数据生成并保留一致备份的前提下，显式转换继承的
不合适队列，随后以各个服务账户的身份检查存储：

```sh
php cli/upgrade_database.php --migrate-poller-queue
php cli/upgrade_database.php --check-rrd-storage
```

这些属于独立的操作。请保留挂起的行，并在关注行数的同时监控数据库磁盘空间和队列积压时间。
参见[安全升级](/zh-cn/guides/upgrade-safely/)以了解队列选择、服务账户信任检查以及重启前置条件。

## 何时采用远程采集器

远程数据采集器是指运行相同代码但配置不同采集器 ID 的第二台机器，它负责轮询一部分设备，并将采集结果写回中心数据库。

当系统瓶颈出现在采集端而非存储端时，应考虑引入远程采集器：

- 轮询器主机的 CPU 在采集运行期间达到饱和，而在各次运行之间处于空闲。
- 访问某组设备的往返延迟主导了整个运行时间，且该组设备集中在单一网络链路之后。
- 某个站点位于广域网的远端，您不希望通过跨广域网的方式直接进行轮询。
- 您需要在隔离站点进行采集，并且在依赖该采集器之前已验证了离线缓冲与恢复流程。

远程采集器并不能消除中心数据库或 RRD 写入瓶颈。在提升采集吞吐量之前，请先衡量中心的接收与刷新能力；
增加采集端可能会进一步加剧现有的积压。

每个采集器都拥有独立的进程和线程配置、独立的数据库凭据以及同步间隔（默认为两小时）。
系统提供了命令行工具来强制执行完整同步，而无需被动等待。

中心节点可以将网站和插件代码复制到远程采集器，以便它们自动更新。如果您通过其他途径分发代码，可以关闭该复制功能。

## 遇到了哪种限制

参考下表建立排查假设，然后通过日志和监控指标进行核实。多个瓶颈可能会同时出现。此处尚未对 Spine 选项进行验证。

| 观察现象 | 瓶颈类别 | 解决措施 |
|---|---|---|
| 提示启动器失去同步警告，但轮询器本身很快 | 调度延迟、先前的超时或主机中断 | 检查启动历史和进程状态 |
| 运行耗时平稳，但某台设备总是超时滞后 | 响应迟缓、脚本开销大或任务过于集中 | 测量其输入方式并检查超时/重试策略 |
| 运行时间随设备数量线性增长，CPU 饱和 | 采集器 CPU 压力过大 | 评估增加进程是否有帮助；考虑部署分布式采集器 |
| 运行时间随设备数量线性增长，CPU 空闲 | 网络、脚本或数据库等待 | 在修改并发参数前排查具体的等待源 |
| 采样在不同设备间轮换缺失 | 连接耗尽、超时或其他采集故障 | 检查错误日志、连接指标及积压队列 |
| 运行时间正常，RRD 写入缓慢，磁盘繁忙 | 存储瓶颈 | 启用延迟 RRD 写入，或更换更快的磁盘 |
| 系统全盘缓慢，包括 Web 界面 | 数据库瓶颈 | 调大缓冲池（buffer pool），进而升级数据库主机 |

有两个必须指出的常见陷阱。

**修改基础间隔并不等同于修改每个数据源的步长。**
需要协调好模板配置、已缓存的项目步长以及 RRD 的 heartbeat 和 step 定义。仅重建缓存并不能重塑现有的 RRD 文件。
参见[数据保留策略](/zh-cn/guides/manage-data-retention/)与[时间与间隔](/zh-cn/concepts/time-and-intervals/)。

**更快的间隔会带来成倍的整体开销。** 将间隔从 300 秒缩短至 60 秒并不会让每次的工作量变为五分之一。
配置为较快节奏的数据源将被更频繁地采集；保持较长步长的数据源则无需在每个基础轮次中都运行。
请实测由此产生的负载，而不是臆断每个周期的工作量都均等。
