:::caution[상속된 RRDtool 프록시 동작]
Kadupul에서는 RRDtool 프록시 배포가 지원되지 않습니다. 로컬 RRDtool 스토리지(`storage_location = 0`)를 사용하세요. 이 페이지의 프록시 설정, 프로토콜 설명 및 워크플로는 상속된 동작을 문서화한 것이며, 지원되는 배포 또는 마이그레이션 경로가 아닙니다. [RRDtool 프록시](/ko/reference/rrdproxy/)를 참조하세요.
:::

Kadupul의 웹 애플리케이션, 데이터베이스, 예약된 수집 및 RRD 스토리지는 서로 다른 역할을 수행하지만 실행 경로는 겹칩니다. 어떤 작업이 실패했는지 알면 조사 범위를 좁히는 데 도움이 됩니다. 인터페이스가 작동한다고 해서 수집이 제대로 동작한다는 의미는 아닙니다.

**웹 인터페이스**는 PHP 애플리케이션입니다. 구성을 관리하고 캐시된 그래프를 렌더링하거나 제공합니다. 실시간 그래프 요청과 같은 일부 웹 작업은 수집을 트리거하기도 하며, 일반 그래프 요청은 대기 중인 RRD 업데이트를 트리거할 수 있습니다.

**데이터베이스**는 구성, 권한, 작동 상태, 폴러 캐시 및 측정 큐를 보관합니다. 수집된 값은 RRD 쓰기나 재시도를 대기하는 동안 데이터베이스에 남아 있을 수 있습니다. 단순한 구성 저장소가 아닙니다.

**폴러**는 예약된 작업과 하위 수집기 프로세스를 조율합니다. 일반 작성기나 지연된 작성기가 RRD 파일을 업데이트하기 전에 결과는 데이터베이스 큐를 통과합니다.

**RRD 파일**은 유한한 기간의 이력 시계열을 보관합니다. 데이터 소스는 일반적으로 해당 필드를 포함하는 하나의 RRD를 가지며, 그래프 생성 시 기존 소스를 재사용할 수 있습니다. 메타데이터를 생성했다고 해서 파일이 이미 존재한다는 보장은 없습니다.

## 경계

| 경계 | 통과하는 항목 | 전송 수단 |
|---|---|---|
| 인터페이스와 데이터베이스 간 | 구성, 세션, 인가, 캐시된 작업 및 운영 데이터 | SQL, 데이터베이스가 원격일 수 있음 |
| 인터페이스와 파일 간 | 그래프 읽기, 캐시된 이미지, 적격한 온디맨드 RRD 업데이트 또는 생성 | 파일시스템 및 RRDtool |
| 폴러와 데이터베이스 간 | 작업 목록, 수집된 값, 보존된 큐, 상태 및 카운트다운 | SQL |
| 수집 프로세스와 장치 간 | SNMP, 수집 스크립트 및 도달 가능성 검사 | 네트워크 또는 로컬 명령, 웹 트리거 수집도 가능함 |
| 작성기와 파일 간 | 그룹화된 샘플, 업데이트당 여러 타임스탬프 가능 | RRDtool 명령 및 응답 파이프 |
| 데이터베이스 서버와 RRD 파일 간 | 정상적인 애플리케이션 경로에서는 직접 RRD 업데이트가 없음 | 애플리케이션 작성기 코드가 두 저장소를 조율함 |

데이터베이스 행은 데이터 소스를 장치 및 구성된 파일 경로와 연결합니다. RRDtool 파일은 시계열과 아카이브를 설명하지만 해당 애플리케이션 매핑을 대체하지는 않습니다. 네트워크 트래픽은 장치 폴링에 국한되지 않습니다. 데이터베이스 연결, 원격 수집기 및 기타 구성된 통합도 호스트 간 경계를 넘나듭니다.

데이터베이스 상태, 대기 중인 샘플 및 RRD 파일을 일관되게 백업하세요. 데이터베이스만 복원하면 과거 RRD 내용이 복원되지 않으며, 파일만 복원하면 구성과 플러시되지 않은 샘플이 누락됩니다. 경로를 조정하지 않고 파일을 이동하면 파일 누락 오류나 보존된 쓰기가 발생할 수 있습니다. 이것이 조용한 수집 실패를 보장하지는 않습니다. [백업 및 복원](/ko/guides/back-up-and-restore/) 및 [새 하드웨어로 마이그레이션](/ko/guides/migrate-to-new-hardware/)을 참조하세요.

## 장기 이력에 RRD 파일을 사용하는 이유

장기 그래프 이력은 RRD에 저장되지만 측정 큐는 데이터베이스에 있습니다. 이 리비전에서 정상적인 처리 중인 큐는 InnoDB이며, 지연된 쓰기는 Boost 테이블에 샘플을 보존합니다. 쓰기에 실패하거나 원격 전송이 지연되면 이러한 큐가 커질 수 있습니다. [대용량 쓰기](/ko/concepts/high-volume-writes/)를 참조하세요.

RRD는 선택한 해상도에 맞춰 정의된 수의 행을 할당합니다. 일반 업데이트는 이력을 무한정 추가하는 대신 해당 공간을 재사용합니다. 레이아웃이 변경되지 않는 한 파일 크기는 고정되어 있습니다. 데이터 소스를 추가하거나, 레이아웃을 변경하거나, 복구 복사본을 보관하거나, 큐가 누적되면 전체 스토리지 요구 사항이 계속 증가합니다.

장기 보존을 미리 선택하는 대신 세부 정보 손실이라는 절충이 따릅니다. 세밀한 이력이 만료되거나 통합된 후에는 나중에 레이아웃을 변경하더라도 버려진 세부 정보를 다시 만들 수 없습니다. [데이터 소스 및 라운드 로빈 아카이브](/ko/concepts/data-sources-and-rras/)를 참조하세요.

애플리케이션에 공유 업데이트와 관계형 쿼리가 필요하기 때문에 구성 및 작동 상태에는 데이터베이스를 사용합니다. 그렇다고 해서 모든 관계가 데이터베이스 외래 키로 적용되거나 행 저장소가 반드시 무한히 커진다는 의미는 아닙니다. 이는 이 애플리케이션의 책임 분담을 설명합니다.

## 두 경로가 공유하는 두 부분

일반적인 페이지 또는 그래프 요청은 일반적으로 다음 경로를 따릅니다.

1. 브라우저가 요청을 보내면 PHP가 구성을 로드하고 데이터베이스에 연결합니다.
2. 요청은 인증과 관련 영역/객체 인가를 적용합니다.
3. 콘솔 작업은 구성을 읽거나 업데이트하며 추가 작업을 트리거할 수 있습니다.
4. 그래프 요청은 보류 중인 Boost 샘플과 이미지 캐시를 확인하거나, RRDtool 명령을 구성하여 지정된 파일을 읽을 수 있습니다. [그래프 생성 방식](/ko/concepts/how-graphs-are-drawn/)을 참조하세요.
5. 실시간 그래프 요청은 실시간 수집기를 시작하고 별도의 임시 데이터를 사용할 수 있습니다. 평평한 그래프만으로는 파일이 비어 있는지 또는 수집 및 렌더링이 성공했는지를 증명하지 못합니다.

예약된 폴링은 일반적으로 다음 경로를 따릅니다.

1. 스케줄러가 폴러를 시작하고, 폴러는 활성화 상태, 타이밍 및 스토리지를 확인합니다.
2. 폴러 캐시에서 예정된 작업을 선택하고 하위 수집기 프로세스를 실행합니다.
3. 하위 프로세스는 장치를 쿼리하거나 수집 스크립트를 실행하고 데이터베이스에 결과를 스테이징합니다.
4. 해당 작성기는 그룹화된 샘플을 처리하며, 구성된 경우 지연 큐를 사용하고 재시도 가능한 실패를 보존합니다.
5. 운영 상태와 스케줄링 상태가 데이터베이스에서 업데이트됩니다.

순서 지정 및 오류 처리에 대해서는 [폴러 수명 주기](/ko/reference/poller-lifecycle/)를 참조하세요. 이러한 경로는 데이터베이스 및 스토리지 리소스를 공유하며 리소스 경합을 일으킬 수 있습니다. 웹 서버를 재시작한다고 해서 별도로 예약된 폴러가 복구되지는 않지만, 웹 요청이 수집 및 쓰기에 참여할 수 있습니다. 실제로 실패한 프로세스를 진단하세요.

## 실행 사용자 권한 구분

| 프로세스 | 실행 사용자 | 시작 주체 |
|---|---|---|
| PHP 웹 애플리케이션 | 웹 서버 또는 PHP-FPM 풀 계정 | 웹 서버 |
| 예약된 폴러 | 스케줄러에 구성된 계정 | cron, 작업 스케줄러 또는 구성된 서비스 |
| RRDtool | 일반적으로 실행 프로세스의 계정을 상속 | 웹, 폴러 또는 유지 관리 경로 |
| 수집 스크립트 | 일반적으로 수집기의 계정을 상속 | 예약된 수집 또는 웹 트리거 수집 |

모든 참여 작성기 계정은 구성된 스토리지에 대한 적절한 액세스 권한이 필요합니다. 일반적인 데이터 소스 생성은 메타데이터를 기록하며, 작성기가 필요로 할 때 나중에 RRD를 생성할 수 있습니다. 파일 누락은 경로, 신뢰, 권한 또는 생성 실패뿐만 아니라 수집이 이 지점에 도달하지 못했음을 나타낼 수도 있습니다.

root로 실행되는 일부 생성 경로는 RRA 디렉터리의 소유자와 그룹을 적용하려고 시도합니다. 이러한 시도는 실패하고 오류를 기록할 수 있습니다. 이는 서비스 계정을 올바르게 구성하는 것을 대신할 수 없습니다. root가 아닌 소유권은 디렉터리 그룹 상속 및 ACL을 포함한 운영체제 규칙을 따릅니다. 모든 웹 및 폴러 작성기 계정에서 스토리지 권한과 숫자 신뢰 UID/GID 설정을 검증하세요. [안전한 업그레이드](/ko/guides/upgrade-safely/)를 참조하세요.

검토된 PHP ICMP 구현은 운영체제의 ping 유틸리티를 호출합니다. 프로브를 전송하는 기능은 해당 유틸리티 및 운영체제 정책에 따라 달라집니다. 레거시 유효 UID 헬퍼가 존재한다고 해서 각 ICMP 프로브가 PHP 권한을 root로 승격한다는 의미는 아닙니다. 단지 ping을 활성화하기 위해 애플리케이션을 root로 실행하지 마세요. 실제 명령, 계정 및 오류 출력을 확인하세요. TCP 또는 UDP 검사는 도달 가능성 의미 체계가 서로 다릅니다.

## 사전 계산되는 작업 목록

폴러 캐시는 확인된 수집 작업을 저장하므로 매 실행마다 템플릿 관계에서 모든 명령을 파생할 필요가 없습니다. 구성 작업은 영향을 받는 항목을 다시 빌드할 수 있으며, 필요할 때 명시적인 재빌드 도구를 사용할 수 있습니다.

캐시된 필드에 표시되는 변경 사항은 수집에서 이를 사용하기 전에 해당 항목에 도달해야 합니다. 다른 설정은 별도로 읽히므로 모든 구성 변경에 수동 캐시 재빌드가 필요한 것은 아닙니다. 한 가지 원인만 가정하지 말고 캐시 내용, 수집 오류 및 원격 복제 상태를 점검하세요. [폴러 캐시](/ko/concepts/the-poller-cache/) 및 [원격 데이터 수집](/ko/concepts/remote-data-collection/)을 참조하세요.

## 주로 문제가 발생하는 지점

| 증상 | 유용한 점검 사항 |
|---|---|
| 인터페이스는 작동하지만 그래프가 평평함 | 스케줄러 실행, 수집 오류, 큐, 샘플 최신성 및 그래프 기간 |
| 폴러는 실행되지만 파일이 진행되지 않음 | 작성기 승인/오류, 스토리지 신뢰 및 권한, 지연된 백로그 |
| 하나의 데이터 소스만 평평함 | 장치 응답, 캐시 행, 파일 매핑, 알 수 없는 샘플 및 그리기 표현식 |
| 구성 변경이 적용되지 않는 것처럼 보임 | 저장 결과, 템플릿 재정의, 영향받는 캐시 항목 및 복제 |
| 규칙적인 간격 발생 | 타이밍, 하트비트, 시간 초과, 장치 가용성 및 쓰기 실패 |
| 예상치 못한 그래프 형태 | 생성된 명령, CDEF/CF 선택, 실제 파일 데이터, 이미지 캐시 및 매핑 |
| 포트 이력이 다른 인터페이스에 연결된 것처럼 보임 | 쿼리 식별자, 번호 재지정 및 재색인 결과 |
| 계정이 콘솔은 볼 수 있지만 그래프는 보이지 않음 | 그래프 페이지 영역, 객체 인가 및 요청된 그래프 식별자 |
| 수집기 간 결과가 다름 | 할당, 복제된 구성, 로컬 재정의 및 연결 상태 |
| 모든 작업이 느림 | 데이터베이스 대기, 작성기/스토리지 경합, 수집기 실행 시간 및 웹 워크로드 |
| 데이터 소스 메타데이터는 존재하지만 파일이 없음 | 첫 번째 수집/쓰기, 구성된 경로, 신뢰 및 생성 오류 |

이러한 항목은 진단 결과가 아니라 점검의 출발점입니다. 관련 경계 전반에 걸쳐 증거를 추적하고 변경 후 결과를 확인하세요. [누락된 데이터 문제 해결](/ko/guides/troubleshoot-missing-data/)을 참조하세요.
