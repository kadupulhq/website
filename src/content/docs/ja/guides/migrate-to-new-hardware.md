:::caution[継承された RRDtool proxy の挙動]
Kadupul では RRDtool proxy デプロイはサポートされていません。ローカルの RRDtool
ストレージ（`storage_location = 0`）を使用してください。このページに記載されている
proxy 設定、プロトコルの説明、およびワークフローは継承された仕様の記録であり、
サポートされたデプロイや移行手順を示すものではありません。[RRDtool proxy](/ja/reference/rrdproxy/)を参照してください。
:::

:::caution[使用前に検証してください]
ソースコードは公開されていますが、サポートされている Kadupul のリリースや移行
パスはまだ存在しません。本運用で依存する前に、バックアップを備えた隔離された
環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

移行作業とは、バックアップの取得元とは異なるマシン環境へのリストア処理です。
[バックアップと復元](/ja/guides/back-up-and-restore/)に記載されているすべての原則がここでも適用されます。
このページでは、移行先が元のマシンと異なることによって生じる差分のみを扱います。

主な差異は3点あり、それぞれ特有の障害を引き起こします。

| 相違点 | 発生する障害 |
|---|---|
| ファイルパスの違い | データベース内およびポーラーキャッシュ内に保持されているファイルパスの破損 |
| ユーザー ID およびグループ ID の違い | ファイルアクセス権やストレージ信頼チェックの失敗 |
| ランタイムバージョンの違い | 拡張モジュール、データベースの動作仕様、RRD の互換性の不一致 |

## 何かに手を加える前に

まず移行先のサーバーを構築し、新規インストールが正常に動作する段階まで環境を整備してください。
データベースサーバーが稼働し、必要な PHP 拡張モジュールが存在し、RRDtool が導入され、選択したコレクターが
利用可能で、Web サーバーが適切に構成されている状態です。この段階ではポーラー、cron などのスケジュールジョブ、
リモートレプリケーション、外部通知はすべて無効化しておいてください。インストーラーは実行しないでください。
データベースは丸ごと差し替えるため、中途半端にテーブルが作成されたスキーマは空のスキーマよりも原因調査が困難になります。

ローカルでの改修や追加プラグインを含め、アプリケーションのリビジョンおよび依存関係を完全に一致させてください。
データベースの `version` テーブルはスキーマのバージョンを記録するものであり、個々のソースコードの変更履歴を
網羅するものではありません。その値だけを一致させても不十分です。インストーラー画面にリダイレクトされる場合は、
スキーマの不一致や不完全なリストアを示唆しています。移行元の環境と全く同じコードを移行先に配置して移行を完了させ、
正常動作を確認した上で、[安全なアップグレード](/ja/guides/upgrade-safely/)に従って独立したタスクとしてバージョンアップを実施してください。

この段階でインストールパスを確定させてください。両方のマシンで全く同一のディレクトリパスを採用すれば、
後述する作業の大半を省くことができます。同一パスにできない場合は、作業を開始する前にパスに関するセクションを熟読してください。

## 作業の手順

各ステップは前段階の成否を確認しながら進めるため、順序を変更しないでください。

1. **移行元および移行先ですべてのデータ生成プロセスを停止する。** スケジュール実行、リモート、Web トリガー、手動の各収集処理およびメンテナンスを停止し、実行中の処理を完了させます。遅延書き込みのフラッシュは、生成プロセスが完全に停止した後にのみ行ってください。未確認のキュー行は、整合するデータベースおよび RRD バックアップとともに保護し、truncate などで消去しないでください。
2. **バックアップを取得する。** データベース、RRD ディレクトリツリー、設定ファイルを同時に取得します。[バックアップと復元](/ja/guides/back-up-and-restore/)に記載された整合性のルールを厳格に守ることが極めて重要です。
3. **RRD ディレクトリツリーを移行する。** 具体的な手法は後述します。
4. **データベースを移行する。**
5. **コード、設定ファイル、および設定が参照しているすべてのリソースを移行する。** これには `plugins/`、`scripts/`、`resource/`、およびデータ入力方式が呼び出すすべてのローカルファイルが含まれます。
6. **最終リストア完了後、移行先用の設定を再適用する。** ディレクトリパス、データベース接続先、サービスの実行権限、ストレージの数値信頼設定を修正します。
7. **ポーラーキャッシュを再構築する。**
8. **各サービスアカウントでストレージ検証を実行し、問題がなければ移行先でのみ収集を開始する。** 代表的なファイル群と保留キューの滞留状況を監視してください。

## RRD ツリーの移行

RRD ファイルは、作成されたシステム環境の内部アーキテクチャに依存したバイナリファイルです。バイナリの直接コピーには、
完全に互換性のある CPU アーキテクチャと RRDtool 形式が必要です。OS 名やワードサイズが一致しているだけでは十分な
証拠にはなりません。非互換な環境では読み取りエラーが発生します。移行先の RRDtool を使用して、コピーされたファイルを検証してください。

両環境の完全な互換性に確信が持てない場合は、直接コピーではなくデータ変換を行ってください。RRDtool 自身が提供する
dump および restore コマンドを使用すれば、移植性の高いテキスト形式（XML）を生成できます。Kadupul もアーカイブを
再生成する必要がある際、内部でこのコマンドペアを使用しています。

移行元サーバーで書き込みプロセスを停止した状態で、隔離された新しい作業ディレクトリを使用します。

```sh
set -eu
umask 077
rrdtool dump /path/to/source/file.rrd > /private/staging/file.xml.partial
mv /private/staging/file.xml.partial /private/staging/file.xml
```

生成された XML ファイルを安全に転送します。移行先で新しい候補ファイルとして復元します。

```sh
set -eu
umask 077
rrdtool restore /private/staging/file.xml /private/staging/file.candidate.rrd
rrdtool info /private/staging/file.candidate.rrd
```

変換が必要なすべてのファイルに対してこの処理を繰り返し、各コマンドの終了コードを確認してください。不完全なダンプや
未検証の候補ファイルを配置しないでください。RRDtool は XML を[異なるアーキテクチャ間での転送用フォーマット](https://oss.oetiker.ch/rrdtool/doc/rrddump.en.html)
として公式に文書化しています。

時間のかかる完全変換を実施する前に、必ず事前検証を行ってください。1つのファイルをコピーして移行先で `rrdtool info` を
実行し、step、アーカイブ構成、最終更新時刻、データソース名を比較します。既知のデータが存在する時間帯を対象に `fetch` の
出力結果も照合してください。ツリー全体を移行する前に代表的なアーカイブ構成でこれを繰り返し、すべてのファイル一覧を検証します。
候補の検証基準と所有権要件については、[RRD の復旧](/ja/guides/recover-a-corrupted-rrd/)を参照してください。

どの手法を選択した場合でも、ディレクトリ構造は完全に維持してください。RRA ディレクトリ配下の多層サブディレクトリは
単なる整理用のものではありません。各ファイルのパスはデータソースごとに個別に記録されており、ディレクトリをフラット化すると
すべてのデータソース参照が破損します。

## データベース

ダンプとインポートの工程です。移行先で確認すべき点が2つあります。

サーバーのデフォルト設定だけでなく、復元された各テーブルの文字セット、照合順序（collation）、およびストレージエンジンを
確認してください。元の定義を保持し、本番切り替え前に移行先のデータベースバージョンとの互換性を検証してください。

**コレクターのキューは使い捨てのキャッシュではありません。** 現在の `poller_output` キューは必ず InnoDB を使用しなければ
なりません。ストレージの事前チェックでは MEMORY キューは拒否されます。測定データがファイルに書き込まれたことが確認されるまで、
その行データおよび boost と realtime のキューを保持してください。RRD バックアップにはそれらの測定値がまだ含まれていない
可能性があるためです。復元された MEMORY テーブルが空であると思い込んではいけません。論理ダンプの中にテーブルを再充填する
insert 文が含まれている場合があります。

書き込みプロセスを停止しバックアップを確保した状態であれば、継承された非 InnoDB キューを明示的に変換できます。

```sh
php cli/upgrade_database.php --migrate-poller-queue
php cli/upgrade_database.php --check-rrd-storage
```

Web サーバーおよびポーラーの実際の各サービスアカウントでストレージチェックを実行してください。このコマンドはローカルストレージへの
アクセス権と選択されたキューを検証します。root で成功したからといって、サービスアカウントのアクセスが保証されるわけではありません。
オンラインのリモートコレクターは通常メインキューを対象とします。ローカルキューを意図的にテストする場合にのみ `--local` を
使用してください。その他のランタイムテーブルやキャッシュテーブルについても、保持または再構築の明確な計画を立ててください。
[ストレージ要件](/ja/reference/requirements/)を参照してください。

## 移行先でのパスの調整

初回収集が走るまで問題が表面化しにくいため、この工程は移行作業で最もトラブルが発生しやすいポイントです。

**RRA パス。** 標準的なデータソースパスは `<path_rra>` トークンを使用します。本リビジョンでは、ブートストラップ処理が
アプリケーションディレクトリに `/rra` を追加して `$config['rra_path']` を自動算出します。これは任意のローカルディレクトリを
自由に選択できる汎用的なデータベース設定ではありません。ファイルを移動する前に有効なパスを確認してください。手動で設定された
絶対パスは個別に精査して修正する必要があります。ネストされたディレクトリ構造を維持してください。

**ポーラーキャッシュは絶対パスを保持する。** キャッシュが生成される際、トークンは展開され、完全な絶対パスがキャッシュ行に
書き込まれます。RRA ディレクトリを変更しても、キャッシュは古いパスを参照し続けます。ポーラーは動作し続けますが、どこにもデータが
出力されなくなります。キャッシュを再構築してください。

```sh
php cli/rebuild_poller_cache.php
```

**パスを保持する設定項目。** これらの設定値はデータベース内に保存されているため、移行直後は古いマシンのディレクトリ構造を指した
状態になっています。初回の収集を実行する前にすべて確認してください。RRDtool バイナリ、コレクターバイナリとその設定ファイル、
PHP バイナリ、SNMP ツール群、ログ出力パス、デフォルトフォント、およびスパイク除去用バックアップディレクトリです。また、設定ファイル、
サービス定義ユニット、cron ジョブ、Web サーバー内の各パスと環境変数も精査してください。

**データ入力方式に含まれるコマンドライン。** これらはインストールルートを表すトークンを使用しているため、ディレクトリ構造が同一の
移行であれば修正は不要です。構造が変わる場合は、各項目の確認が必要です。データクエリの背後にあるリソース XML ファイルについても同様です。

**リモートコレクターは独自の設定ファイルを持つ。** そこには独自のデータベース認証情報とコレクター ID が記載されています。
これらは中央のダンプファイルには含まれていません。中央データベースのアドレスが変更された場合は、該当するエンドポイントを更新し、
各コレクターの接続を検証してください。完全なレプリケーションは独立した処理であり、有効化されたリモートコレクターが存在する場合にのみ
メインコレクター上で実行されます。

```sh
php cli/poller_replicate.php
```

有効なリモートコレクターが存在しない場合、このコマンドはエラー終了します。単一コレクターの移行において、このコマンドを必須の
成功判定条件として組み込まないでください。リモート収集の再開を許可する前に、リモート設定とレプリケーションを検証してください。

## 所有権とアクセス権限

ポーラーはそれを実行するシステムアカウントの権限で RRD ファイルを書き込みます。Web インターフェースは Web サーバーのアカウントで
それらを読み取ります。`/etc/passwd` の内容が異なるサーバー間で数値 ID をそのまま保持してファイルをコピーすると、誤ったアカウントに
所有されたファイル群が生成されてしまいます。

移行直後にグラフの更新が停止した場合、権限の不備、パスの不一致、収集未実行、タイムスタンプのズレ、サンプルの拒否などが考えられます。
対処を行う前にポーラーログと保持キューを確認してください。グラフを見るだけでは原因は特定できません。

個別のサンプルファイルだけでなく、RRA ディレクトリ自体および入れ子になったサブディレクトリの所有権を確認してください。
収集処理中にこれらのディレクトリ内に新しいファイルが作成されるため、既存ファイルが読み取れても、ポーラーが書き込めない
ディレクトリでは移行後に追加されたデータソースの収集に失敗します。`include/config.php` 内の `rrd_maintenance_trusted_uids`
および `rrd_maintenance_trusted_gids` を移行先の実際の数値 ID にマッピングし直し、信頼済み親ディレクトリ群を確認してください。
[ストレージ要件](/ja/reference/requirements/)を参照してください。

## データ欠落を最小限に抑える切り替え

RRD は、ファイルの最終更新時刻以前のタイムスタンプを持つ更新データを拒否します。これによりリプレイ処理には制約が課されますが、
あらゆる移行で必ずデータ欠落が起きるわけではありません。欠落の規模は、サンプリング間隔、停止時間、およびキュー内のどの未処理データが
保持されたかに依存します。本手順では収集の担当ホストを単一に保ち、リハーサル中に独自に収集された履歴を本番アーカイブに混入させることはしません。

1. 前日のバックアップを使用して、事前に完全なリハーサルを実施する。すべてのデータを複製し、各パスを修正し、通知を無効化した状態で隔離された検証用デバイスに対して更新テストを行います。移行先での調整事項を再現可能な手順書として記録します。テスト終了後はリハーサル環境の書き込み処理を停止します。
2. リハーサル環境の独立性を維持する。そのデータベースと RRD を最終的な本番バックアップで完全に置き換えます。リハーサル時のデータ行やキューに残ったサンプルを本番リストアに混入させてはなりません。
3. 本番切り替えの実施：移行元のデータ生成プロセスを停止し、未処理サンプルをフラッシュまたは保護した上で、最終バックアップを取得・転送します。移行先固有の設定を再適用します。データベースをリストアすると `settings` テーブルに移行元のパスが復元され、設定ファイルの復元によってリハーサル時の接続先や信頼設定が上書きされる可能性があるためです。
4. ポーラーキャッシュを再構築し、ストレージ検証を実行し、ファイル一覧を確認した上で、これらのチェックがすべて成功した後にのみ移行先でのデータ収集を開始します。

リハーサルの所要時間を計測し、検証とロールバックのための十分な予備時間を確保してください。切り替えが完了するか、
制御されたロールバックによって移行元が再び収集担当として再選定されるまで、移行元の停止状態を維持してください。

## 検証の手順

1. インストーラー画面へリダイレクトされることなく Web インターフェースが表示されること。リダイレクトされる場合は、コードとスキーマの不一致、DB 接続不良、リストアの不備を調査します。
2. 検証用デバイスが新しい収集試行に応答すること。リストアされた "up" ステータス単体は停止前の古い情報である可能性があります。
3. 初回収集サイクル完了後、RRD ファイルの最終更新時刻が更新されること。画面上のグラフではなく、ディスク上の実ファイルを確認してください。
4. 直近1時間を指定して描画したグラフに、途切れのない実線が表示されること。

ステップ3が失敗した場合は、パス、アクセス権、ストレージ事前チェック、キューの深さ、および RRDtool のエラーを確認してください。
ステップ4が失敗した場合は、保持されている測定値、グラフ定義、選択した時間範囲、および Web アカウントの読み取り権限を確認してください。
単一のファイルが正常に動作したからといって、すべてのデバイス、データ入力方式、リモートコレクターが正常であるとは限りません。

## よくある落とし穴

**両方のシステムを同一の RRD ディレクトリツリーに対して同時に稼働させないこと。** 2つのポーラーが同一のファイル群に書き込みを行うと、
更新データの拒否とグラフの歯抜けが発生し、データが統合されることはありません。

**新しいデータベースに対して古い RRD ディレクトリツリーを復元しないこと。** ファイルが過去に遡って自動補完されることはありません。
データ収集は現在時刻から再開され、両者の間の空白期間は恒久的なデータ欠落となります。

**バックアップにはデバイスの認証情報が平文で含まれています。** ハードウェアの移行は、それらの認証情報がネットワーク上を移動し、
2台のマシンに同時に存在することを意味します。バックアップへのアクセスを制限し、転送経路を暗号化してください。受け入れ確認が完了し、
保持ポリシーによって旧マシンの廃棄が許可されるまで、保護されたロールバック用コピーを維持してください。切り替え作業中に削除してはなりません。

**プラグインのテーブルはデータベース内に存在しますが、プラグインコード自体は含まれません。** 適合するプラグインコードと依存関係を
揃えずにデータベースのみをリストアすると、プラグイン画面のエラー、フックの破損、スケジュールジョブの停止を招く恐れがあります。
必要な各プラグインを個別に確認してください。

**既存の proxy ストレージ構成は本移行手順の適用対象外です。** proxy デプロイはサポートされていません。実際の RRD ファイルを特定して

維持し、新しいシステムでの収集、グラフ描画、リモート連携、プラグインの検証が完全にパスするまで、整合性のあるバックアップを保持してください。

サブシステムが正常に動作している証明にはなりません。
