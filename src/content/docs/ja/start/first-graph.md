ここでのグラフは、生データをそのまま描画したものではありません。データの「要約」を描画したものであり、どの要約を見ているのかを正しく把握することが重要です。

## 表示されているものの実態

すべてのグラフはラウンドロビンアーカイブから描画されます。このアーカイブは、直近のサンプルを高解像度で保持し、古いサンプルをより粗いバケットへと統合して保持します。表示範囲を1年間に広げた場合、5分ごとのすべてのサンプルを見ているわけではありません。統合関数によって選ばれた、バケットごとに1つの値を見ていることになります。

その関数は通常、平均値（average）です。最大値や最小値である場合もあります。これは本ページで解説する他の何よりも重要です。

通常のオンデマンドグラフ要求では、Kadupulはグラフ設定からRRDtoolコマンドを組み立て、ディスク上のファイルに対して実行します。そのコマンドには3種類の行が含まれており、それぞれの役割を把握しておくと理解が深まります。

| 部分 | 役割 |
|---|---|
| 定義項目 | ファイル名、内部のデータソース、および統合関数を指定します |
| 描画項目 | 1つのデータ系列を、折れ線、塗りつぶしエリア、または積み上げの帯に変換します |
| 凡例項目 | 表示中の時間枠全体にわたって計算された1つの数値を表示します |

全体の構造は [グラフの描画方法](/ja/concepts/how-graphs-are-drawn/) で解説されています。今日すぐにすべてを把握する必要はありません。グラフの定義と要求された時間範囲によって画像が決まるということだけを理解してください。なお、キャッシュやリアルタイムグラフの経路では挙動が異なる場合があります。

## 直近の4時間から始める

まずは短い直近の時間枠から確認してください。選択されるアーカイブは保持期間、ステップ、グラフの解像度に依存するため、4時間表示であっても生データや非統合データであることが保証されるわけではありません。最も細かいアーカイブであっても時間正規化された値が含まれます。値を比較する前に、グラフのデバッグコマンドや `rrdtool info` を使って、要求された関数と利用可能なアーカイブステップを確認してください。

作成したばかりのグラフには正常でありながら利用者を不安にさせる2つの特徴があります。

**現在時刻より手前で線が途切れることがある。** 現在進行中のバケットが未完了である可能性があります。収集のタイミング、バッファリング、正規化処理によっても、表示される終端が遅れることがあります。一定の遅延を健全性の証拠と見なすのではなく、更新タイムスタンプが進んでいるかを確認してください。

**最初の区間が空白になっていることがある。** 1時間前に作成されたデータソースには1時間分のデータしかなく、残りの11か月分は存在しません。アーカイブは作成時に全領域が割り当てられるため、空白部分は将来使われるのを待っている実際のストレージ領域です。

## 範囲を広げてピークの変化を観察する

表示範囲を1週間に広げてみてください。グラフがより粗い平均値を選択すると、ピークが小さくなることがあります。たとえば、使用率が5分間だけ100%になり、残りの55分間がゼロだった場合、1時間の平均値は約8.3%になります。平常時はアイドル状態の1時間の中に4分間のバーストが発生した場合、平均値は約6.7%になります。短いピークは、元のサンプリングインターバルの内部ですでに平滑化されている可能性があります。

統合処理は詳細を切り捨てます。高解像度の履歴が保持期間切れとなった場合、拡大表示し直しても平均値アーカイブからそれを復元することはできません。

これが3大ミスの中で最初の、そして最も議論の種になりやすい誤読です。

**平均値をピークと見誤る。** 帯域の飽和に関心がある場合は、平均値ではなく最大値に基づいて構築されたグラフを確認してください。ただし、これはアーカイブに最大値が保持されている場合にのみ機能します。粗い平均値しか残っていない場合、元のピークを再構成することはできません。MAXアーカイブが保持するのは時間正規化された入力ポイントの最大値であり、ポーリングの合間に生じた未観測の瞬間最大値ではありません。

ここで知っておくべき目立たないフォールバック動作があります。グラフ項目が最大値を要求しているにもかかわらずファイル内に最大値が存在しない場合、Kadupulの選択ヘルパーは利用可能な最初の関数にフォールバックするか、利用可能な関数が判定できない場合は AVERAGE にフォールバックすることがあります。画像自体は問題なく表示されますが、答えようとしている問いがすり替わっています。

**ギャップをゼロと見誤る。** グラフ上のギャップ（空白）は、描画された値が未知（unknown）であることを示します。原因としては、更新の欠落、明示的な未知の入力、拒否された値、グラフ計算式などが挙げられます。デバイスがダウンしていることだけを一意に示すわけではありません。

ハートビート（heartbeat）は更新間に許容される最大時間であり、ステップに追加される猶予時間ではありません。たとえば、ステップが300秒でハートビートが600秒の場合、更新間に許容されるのは最大600秒であり、900秒ではありません。アーカイブの未知データしきい値も目に見えるギャップに影響します。[RRDtool’s data-source definitions](https://oss.oetiker.ch/rrdtool/doc/rrdcreate.en.html) および [時間とインターバル](/ja/concepts/time-and-intervals/) を参照してください。

積み上げグラフには特に注意が必要です。テンプレートによっては、グラフ計算式の中で未知の値をゼロに置き換えるものがあります。そうしたグラフでは、障害発生時とアイドル状態が仕様上まったく同じに見えてしまいます。サービスが停止したと判断する前に、積み上げられていない個別のビューを確認してください。

**縦軸のスケールが異なる2つのグラフを比較する。** 2つのグラフを並べると、それぞれが自身のデータに合わせてスケールを調整します。小さな山と大きな山が視覚的にまったく同じに見えることがあります。結論を出す前に必ず軸の目盛りを確認してください。

軸を見る際には、その基数も確認してください。グラフの数値は1000単位（10進法）または1024単位（2進法）でラベル付けされることがあります。保存されている数値自体は同一であり、ラベルの表記だけが変わります。その差は接頭辞によって異なり、1乗の段階で1024と1000の差は2.4%となり、接頭辞が大きくなるにつれて広がります。また、ビットとバイトの違い、グラフ計算式、統合方式も確認してください。パーセンテージの差だけでは根本的な原因を特定できません。

## 凡例の読み方

凡例には、グラフの線の形状以上に重要な数値が示されています。「Current（現在値）」は通常、選択された系列の LAST 縮約値であり、グラフを閲覧した瞬間に測定された値であるとは限りません。平均値と最大値は現在表示している時間枠全体で計算されるため、すべての期間を通じた値ではなく、表示をズームすると変化します。

標準で提供される凡例項目は、最小値、最大値、平均値、そして「Current」と表示される最新値（LAST）です。これらについて、多くの人が見落としがちな2つの点があります。

**凡例の数値は、保存された値ではなく描画された値の縮約である。** 平均値で読み取られた系列に対して表示される最大値は、選択された解像度における導出平均値群の中の最大値です。これまでに記録された過去最大の生サンプル値ではありません。混雑した回線では、これら2つは大きく異なる数値になり、それぞれが異なる問いに対する正当な回答です。

**凡例がどの系列を使用しているかを確認する。** 単純な GPRINT エントリは直前の描画項目の系列を継承することがあります。一方、専用の最小値、最大値、平均値、最新値の項目には個別の処理が適用されます。そのため、グラフテンプレート内の項目の並び順を変更すると、凡例そのものを編集していなくても凡例の報告内容が変わってしまうことがあります。無関係なテンプレート編集後に数値が変わった場合は、まず項目の順序を確認してください。

## グラフの表示がおかしいとき

収集経路を次の順序で確認してください。複数の段階で障害が発生している可能性があります。

1. デバイスは今まさに正常に応答しているか？
2. ポーラーは実行されており、収集インターバル内に完了しているか？
3. RRDファイルに直近の更新時刻が記録されているか？
4. グラフは想定通りのデータソースを読み取っているか？

具体的な手順：

**ステップ 1。** デバイスを追加したときと同じ `snmpget` コマンドを、割り当てられたコレクターから実行します。失敗した場合は、グラフを評価する前にその収集障害を解決してください。

**ステップ 2。** 実行終了時のサマリー出力を探します。見当たらない場合は、スケジューリング、設定されたログの出力先、およびポーラーの早期終了エラーを確認してください。インターバルより長くかかる実行は更新を遅延させます。結果として生じる更新間隔とハートビートを比較してください。

**ステップ 3。** RRDtoolに直接問い合わせます。

```bash
rrdtool last /path/to/rra/the_file.rrd
rrdtool info /path/to/rra/the_file.rrd
```

`last` は、未知の値を含む更新を含め、最後の更新タイムスタンプを報告します。バッファリングされた書き込みによって遅延することがあります。デバイスガイドで説明したように、`lastupdate` と `fetch` を使用して値を検査してください。`info` はステップ、ハートビート、データソースタイプ、およびどのアーカイブが存在するかを教えてくれます。ファイルに最大値のアーカイブが存在しない場合、上記のピークに関する疑問はそれで解決します。

**ステップ 4。** グラフのデバッグモードを有効にし、グラフが生成するコマンドを確認します。コマンドには、ファイル名、その内部のデータソース、およびそれぞれの統合関数が明記されています。テンプレートの再適用やインターフェースの再インデックスを行った後には、グラフが想定とは異なるデータソースを指してしまうケースがよくあります。

## 主な症状と一般的な原因

| 表示される状態 | 一般的な原因 |
|---|---|
| ゼロの平坦な直線 | 実際の測定値がゼロであるか、計算式で未知の値をゼロに置換している可能性があります |
| 線が途切れ、その後再開する | 未知の値によって描画系列が中断されました。収集状況とグラフ計算式を確認してください |
| 全体を通して細かなギャップがある | ポーラーの終了が遅れているか、ハートビートがステップに近すぎる値に設定されています |
| 4時間表示ではピークが見えるが、1週間表示では消えている | データ損失や収集障害と決めつける前に、アーカイブ解像度と統合方式を確認してください |
| 凡例の最大値が描画されたピークより低い | 凡例が想定と異なる系列を縮約しています |
| グラフ全体が空白でエラーも出ない | 背後にデータソースが紐づいていないか、まだ何もデータが収集されていません |
| 値が一桁以上ずれている | データソースタイプの誤り、または32ビットカウンターの周回が原因です |
| 同じ回線の2つのグラフがわずかに食い違う | 軸の基数が異なるか、統合方式が異なっています |

[欠損データのトラブルシューティング](/ja/guides/troubleshoot-missing-data/) では、この診断手順をより深く掘り下げて解説しています。グラフの正確性が確認できた後は、[グラフの外観の調整](/ja/guides/tune-graph-appearance/) を参照して見た目をカスタマイズできます。

これでチュートリアルは完了です。動作する環境が整い、応答するデバイスがあり、正しく解釈できるグラフが手に入りました。ここから先は、[操作ガイド](/ja/guides/monitor-a-switch/) で個別の作業手順を確認し、[概念](/ja/concepts/architecture/) でシステム全体の仕組みを理解していってください。
