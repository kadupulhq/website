:::caution[사용 전 검증 필요]
소스 코드는 공개되어 있지만, 공식적으로 지원되는 Kadupul 릴리스나 마이그레이션 경로는
아직 없습니다. 본 운영 환경에 적용하기 전에 백업이 준비된 격리 환경에서 이 절차를
테스트하십시오. [프로젝트 상태](/ko/project/status/)를 참조하십시오.
:::

실제 물리적인 파일 손상은 매우 드뭅니다. 손상된 것으로 보고되는 파일의 대부분은 물리적으로 정상이며,
데이터베이스와의 불일치, 폴러의 쓰기 권한 부족, 또는 파일 자체와 무관한 이유로 데이터 수신이
중단된 경우입니다. 조치를 취하기 전에 어떤 상황에 해당하는지 정확히 파악하십시오.
한 상황에 맞는 복구 작업이 다른 상황을 악화시킬 수 있기 때문입니다.

:::danger[원본 파일을 반드시 보존하십시오]
**이 페이지의 복구 절차를 시작하기 전에 반드시 파일을 백업 복사하십시오.** 별도의 후보 파일로 복원하고
운영 파일과 교체하기 전에 철저히 검사하십시오. 아카이브를 축소하거나 삭제하면 보존된 기록 데이터가
영구적으로 손실됩니다. 최댓값 변경은 향후 입력 유효성 검사에만 영향을 미치며,
과거에 저장된 샘플을 소급하여 삭제하지 않습니다. RRD 파일에는 자동 실행 취소 기능이 없습니다.
:::

## 1. 장애 유형 식별

| 확인되는 현상 | 일반적인 원인 | 이동 |
|---|---|---|
| 그래프가 정상 렌더링되지 않고 오류가 표시됨 | 파일 누락, 읽기 불가, 또는 디렉터리 쓰기 권한 없음 | 2단계 |
| 오류는 없지만 그래프가 빈 상태로 표시됨 | 선택한 범위 내에 유효한 값이 없거나 그래프 정의 문제 | [누락된 데이터 문제 해결](/ko/guides/troubleshoot-missing-data/) |
| 그래프가 특정 시점에 멈추고 다시 갱신되지 않음 | 폴러 중단, 권한 문제, 또는 하트비트 만료 | 3단계 |
| 데이터는 존재하지만 구성 변경 없이 그래프 형태가 급변함 | 파일과 데이터베이스 간의 설정 불일치 | 4단계 |
| 저장된 값이 모두 알 수 없음(unknown)으로 표시됨 | 데이터 수집, 타이밍, 임계값 제한 또는 데이터 소스 구성 확인 필요 | [누락된 데이터 문제 해결](/ko/guides/troubleshoot-missing-data/) |
| `rrdtool`이 파일 읽기를 거부함 | 경로 누락, 접근 실패, 호환되지 않는 포맷 또는 파일 손상 | 2단계 및 3단계 후 5단계 |

Kadupul은 첫 번째 경우를 깨진 이미지 대신 판독 가능한 메시지로 변환하여,
쓰기 권한이 없는 디렉터리와 쓰기 권한이 없는 파일을 명확히 구분하고, 파일이 없을 경우 폴러가 아직
실행되지 않았을 가능성을 안내합니다. 이 메시지는 단서일 뿐 확정 진단이 아닙니다.
파일 삭제, 경로 변경, 또는 불완전한 복원 작업으로 인해서도 파일이 누락될 수 있습니다.

## 2. 파일 점검

데이터 소스 전용 페이지에서 세션 단위로 활성화할 수 있는 두 가지 뷰를 제공합니다.
디버그 뷰는 Kadupul이 오늘 이 데이터 소스를 위해 실행할 `rrdtool create` 명령어를 출력합니다.
여기서 핵심이 되는 것은 정보 뷰입니다. `rrdtool info`로 실제 파일을 읽고, 데이터베이스에서
데이터 소스 정의를 읽어와 그 차이점을 출력합니다. 재구축 없이 해결할 수 있는 불일치가 있는 경우,
명령을 즉시 실행하는 대신 관리자가 직접 검토하고 실행할 수 있도록 `rrdtool tune` 또는
`rrdtool resize` 명령어를 텍스트로 보여줍니다.

셸 환경에서도 동일한 첫 단계를 수행합니다.

```bash
rrdtool info /path/to/rra/42/1337.rrd
```

헤더는 스텝 주기, 마지막 갱신 시각, 데이터 소스 이름과 타입,
하트비트, 최솟값 및 최댓값, 각 아카이브의 통합 함수, 행 수,
해상도를 제공합니다. 이 명령어가 실패하면 오류 내용을 보존하고 파일 손상으로 결론짓기 전에
경로, 권한 및 RRDtool 호환성을 확인하십시오. `info` 명령어가 성공했다고 해서
데이터가 완전한 것은 아니며, 메타데이터가 읽힌 것일 뿐입니다. `fetch` 출력과 덤프 테스트를 수행하여 기록 데이터를 확인하십시오.

## 3. 기계적 및 시스템 원인 먼저 확인

| 점검 항목 | 복구 전에 먼저 확인해야 하는 이유 |
|---|---|
| 파일 소유권 및 권한 | 유지보수 중 root 권한으로 생성된 파일은 그 시점부터 폴러가 쓸 수 없게 됩니다 |
| 디렉터리 소유권 및 권한 | 폴러는 쓰기 권한이 없는 디렉터리에 대체 파일을 생성할 수 없습니다 |
| 디스크 여유 공간 및 inode | 파일시스템이 가득 차면 파일 손상과 동일하게 쓰기가 중간에 잘립니다 |
| 제2의 쓰기 프로세스 존재 여부 | 동시 쓰기나 순서가 뒤바뀐 갱신은 유지보수 스냅샷을 손상시킵니다. 로그를 확인하십시오 |

RRD 파일을 소유하고 업데이트하는 서비스 계정으로 유지보수를 실행하고, 파일 모드,
소유자, 그룹을 유지하십시오. 원격 수집기, 예약된 크론 작업, 수동 유지보수를 포함한 모든 쓰기 프로세스를
중지한 후 파일을 복사하거나 교체하십시오. 대기 중인 쓰기 큐 플러시는 데이터 생성자가 완전히 멈춘 후에만
수행하십시오. 단순한 셸 명령어는 Kadupul의 스토리지 락을 획득하지 않습니다.
[스토리지 요구사항](/ko/reference/requirements/) 및 [백업 및 복원](/ko/guides/back-up-and-restore/)의 정지 절차를 참조하십시오.

## 4. 검사기가 이미 발견한 내용 확인

Kadupul은 활성화된 디바이스에서 그래프에 연결된 데이터 소스를 주기적으로 점검하고
발견된 문제를 기록할 수 있습니다(디스크의 모든 파일을 전수 조사하는 것은 아닙니다). 이 기능은
기본적으로 비활성화되어 있습니다. 활성화 위치: Configuration -> Settings -> Data.

| 설정 항목 | 기본값 | 효과 |
|---|---|---|
| Enable RRDfile Check | off | 이 설정이 켜지기 전까지는 아무것도 검사하지 않습니다 |
| Check Frequency | 4 hours | 1 hour, 24 hours 또는 각 boost 주기 종료 후 실행 선택 가능 |
| Number of RRDfile Check Processes | 1 process | 파일 목록을 여러 병렬 워커 프로세스로 분할 처리 |
| RRDChecker Timeout | 1 hour | 실행 시간이 이 한도를 초과하면 강제 종료됩니다 |

점검 결과는 디바이스, 데이터 소스, 내부 데이터 소스 ID, 메시지, 날짜가 포함된
목록으로 누적됩니다. 경과 시간별 필터링과 텍스트 검색이 가능하며,
문제를 해결한 후 목록을 삭제할 수 있습니다.

검사기가 기록할 수 있는 메시지와 각각의 의미는 다음과 같습니다.

| 메시지 | 의미 |
|---|---|
| RRDfile does not exist | 파일이 생성된 적이 없거나, 이동/삭제되었거나, 구성된 경로가 변경되었습니다 |
| RRDfile is not writable | 폴러 실행 계정에 파일 쓰기 권한이 없습니다 |
| RRDfile modify time older than hour | 최소 1시간 이상 파일에 새로운 데이터가 기록되지 않았습니다 |
| Last update value in RRDfile is older than 1 hour | 파일 내부의 최종 갱신 타임스탬프가 오래되었습니다. 파일 수정 시각보다 확실한 증거입니다 |
| The RRDfile step does not match the Data Source Profile step | 프로필의 수집 주기와 다른 스텝으로 파일이 생성되었습니다 |
| There are more, or less, Data Sources in the database than in the RRDfile | 파일 생성 이후 템플릿의 필드가 추가되거나 삭제되었습니다 |
| The Data Source '...' exists in RRDfile, but not in database | 파일 관점에서 데이터베이스에 없는 필드를 명시합니다 |
| Data Source name '...' exists in the Database, but not in RRDfile | 폴러가 쓰려고 시도하지만 파일 내에 자리가 없는 필드를 명시합니다 |
| The RRDfile Minimal Heart... is lower than polling interval | 하트비트가 폴링 주기 이하로 설정되었습니다. 지연된 샘플이 알 수 없음으로 처리될 수 있습니다 |
| The RRDfile minimal heartbeat... should be 'N' and is currently 'M' | 파일의 하트비트가 프로필보다 낮습니다. 더 큰 값에 대해서는 경고하지 않습니다 |
| Stale values for last 24 hours, or last hour | 해당 시간 윈도우 동안 읽어온 모든 샘플 값이 알 수 없음(unknown)이었습니다 |
| More than 50% (n/m) values are NaN in last 24 hours, or last hour | 부분적인 데이터 수집 실패가 발생했습니다 |
| No data returned, maybe corrupted Data Source | 파일에 대한 fetch 실행 결과 아무런 데이터도 반환되지 않았습니다 |

이 점검은 실행 중에 데이터베이스에 기록된 스텝과 하트비트를 프로필과 일치하도록 자동으로 보정하여
프로필과 데이터 소스 정의 간의 드리프트를 해결하지만, 물리 파일 자체는 수정하지 않습니다.
파일과 데이터베이스 간의 필드 개수 불일치는 자동 복구되지 않고 보고만 되는데,
어느 쪽이 올바른 설정인지 자동으로 판단할 수 없기 때문입니다.

## 5. 덤프, 편집, 복원

RRDtool은 읽기 가능한 파일을 XML로 직렬화하고 이를 바탕으로 후보 파일을 재구축할 수 있습니다.
이는 알려진 구조적 불일치를 해결하는 데 유용하지만, 유실된 샘플을 복원할 수는 없으며
손상된 파일이 반드시 파싱된다는 보장도 없습니다. Kadupul 역시 구조적 변경 시 dump/restore 도구를 사용합니다.
로컬 복원 헬퍼는 임시 형제 파일을 생성하고 성공 시 대상 경로에 덮어쓰기 방식으로 이름을 변경하지만,
이것이 백업을 대체하지는 않습니다.

쓰기 프로세스를 중지한 상태에서 RRD 소유자 계정으로 다음 명령을 실행하십시오. 예제 경로를
실제 데이터 소스 경로로 변경하십시오. 후보 파일이 동일한 파일시스템에 위치하도록
개인 작업 디렉터리를 원본 파일과 동일한 디렉터리에 생성합니다.

```bash
set -eu
umask 077
rrd=/path/to/rra/42/1337.rrd
work=$(mktemp -d "$(dirname "$rrd")/rrd-recovery.XXXXXX")
cp -p "$rrd" "$work/original.rrd"
rrdtool dump "$work/original.rrd" > "$work/recovery.xml"
# Edit recovery.xml only when the required correction is understood.
rrdtool restore "$work/recovery.xml" "$work/candidate.rrd"
rrdtool info "$work/candidate.rrd"
rrdtool fetch "$work/candidate.rrd" AVERAGE --start end-1h --end now
```

정상적으로 보존된 데이터가 존재하는 fetch 시간 범위와 통합 함수를 선택하십시오
(마지막 1시간은 예시일 뿐입니다). 원본과 후보 파일의 데이터 소스 이름,
스텝, 아카이브, 최종 갱신 타임스탬프, 샘플 값을 면밀히 비교하십시오. 내용을 수정하지 않은 dump/restore
작업이라도 바이너리 레이아웃이 달라질 수 있으므로, 동일한 파일 해시를 요구하기보다는 실제 데이터 값을 비교하십시오.

원본 복사본은 반드시 보존하십시오. 철저한 검증을 마친 후에만, 쓰기 프로세스가 멈춘 상태에서
후보 파일에 필요한 권한 모드, 소유자, 그룹을 복원하고 운영 경로로 이름을 변경하십시오.
데이터 수집을 재개하기 전에 폴러 계정이 파일을 정상적으로 읽고 쓸 수 있는지 확인하십시오. 이 예제는
읽을 수는 있지만 잘못된 후보 파일이 실수로 적용되는 것을 방지하기 위해 배포 직전에 의도적으로 멈춥니다.

XML 파일과 후보 파일은 추가적인 디스크 공간을 필요로 합니다. 실패한 덤프는 불완전한
XML 파일을 남길 수 있으며, 이러한 파일을 복원해서는 안 됩니다. 접근 권한, 여유 공간, 오류 메시지를 확인하십시오.
이러한 점검 후에도 원본 파일이 덤프되지 않는다면 검증된 백업에서 복원하십시오. RRDtool의
[`restore -f`](https://oss.oetiker.ch/rrdtool/doc/rrdrestore.en.html) 옵션은 대상을 덮어쓰도록
허용하지만, 본 단계별 예제는 안전을 위해 의도적으로 새로운 대상을 사용합니다.

## 6. 보존되는 데이터와 영구 손실되는 데이터

| 손상 유형 | 기록 데이터 복구 가능 여부 |
|---|---|
| 파일 쓰기 불가(파일 자체는 온전함) | 저장된 기록은 유지됩니다. 권한을 고친다고 해서 누락된 과거 업데이트가 채워지지는 않습니다 |
| 하트비트, 최솟값, 최댓값 설정 오류 | 복구 가능. `rrdtool tune`은 저장된 데이터를 건드리지 않고 헤더만 변경합니다 |
| 스텝 불일치 | 검증된 명시적 변환 필요. 데이터베이스 프로필 변경만으로는 파일이 변환되지 않습니다 |
| 파일 내 데이터 소스 필드 누락 | 기존 필드는 기록을 유지합니다. 새 필드는 빈 상태로 시작합니다 |
| 아카이브 삭제 또는 미생성 | 불가능. 저장된 적이 없는 해상도 데이터는 재구성할 수 없습니다 |
| resize 작업으로 아카이브 행 수 축소 | 불가능. 버려진 행은 명령어가 실행되는 즉시 영구적으로 사라집니다 |
| 파일이 잘려 덤프 실패 | 불가능. 백업에서 복원해야 합니다 |
| 헤더는 정상이지만 파일 끝부분이 잘림 | 헤더가 읽힌다고 해서 덤프가 완전하다고 가정하지 마십시오. 덤프 실패 시 백업을 사용하십시오 |

폴러 주기를 변경하거나 데이터 소스를 다른 보존 프로필로 이동하더라도
기존 파일의 구조가 자동으로 재편성되지는 않습니다. RRDtool은 스텝 변경을 포함한 구조적
[`tune` 작업](https://oss.oetiker.ch/rrdtool/doc/rrdtune.en.html)을 제공하지만,
데이터 손실 없는 주기 변경을 맹신하지 말고 설치된 버전과 아카이브 구조에 맞는 변환 동작을 검증하십시오.
[데이터 소스 및 아카이브](/ko/concepts/data-sources-and-rras/)와
[데이터 보존 관리](/ko/guides/manage-data-retention/)를 참조하십시오. `tune`으로 최댓값을 올리는 것은
안전하지만, 최댓값을 낮추면 새로운 상한선 위의 향후 값들이 모두 알 수 없음으로 기록됩니다.

## 7. 유지 가능한 데이터를 보존하면서 재구축

Kadupul은 이전의 읽기 가능한 파일에서 새 파일로 데이터를 채워 넣을 수 있는 splice 유틸리티를 제공합니다.
이 결과물을 최종본이 아닌 검토 후보로 다루십시오. 공백을 메우고 정상적인 0 값을 대체할 수 있으므로,
측정된 원래 기록의 완전 무결한 복사본이 아닙니다. 메인 데이터 수집기의 애플리케이션 루트에서
신뢰할 수 있는 쓰기 가능 디렉터리의 격리된 복사본을 사용하여 실행하십시오.

5단계의 개인 `$work` 디렉터리 내에 원하는 구조로 `new.rrd`를 생성한 후,
병합을 미리 확인하십시오.

```bash
php cli/splice_rrd.php --oldrrd="$work/original.rrd" \
                       --newrrd="$work/new.rrd" \
                       --finrrd="$work/merged.rrd" --dryrun
```

두 입력 파일이 모두 이미 존재해야 하며 유틸리티의 쓰기 권한 검사를 통과해야 합니다.
새 파일이 기본 골격 구조를 제공합니다. `--finrrd`를 지정하지 않으면 출력 파일은 새 파일 경로에
`.new`가 추가된 형태가 됩니다. 이전 후보 파일을 덮어쓰지 않도록 명시적인 새 출력 경로를 사용하십시오.
`--dryrun`은 임시 XML과 SQLite 스토리지(지원 시)를 사용하여 파싱 및 병합을 수행하지만, 최종 RRD 복원은
건너뜁니다. 이것이 최종 복원의 성공을 보장하지는 않습니다. 독립적인 후보 파일을 생성하려면 `--dryrun`을 제거하십시오.
미리보기 중에는 `--owner`를 지정하지 말고 필요한 서비스 계정으로 실행하십시오. 설치 전에 출력 파일의 실제 소유권을 확인하십시오.

:::caution[splice는 0 값을 공백 데이터로 취급합니다]
병합 프로세스는 새 파일을 탐색하면서 알 수 없는 값 **또는 0**이 들어 있는 모든 슬롯에 대해
이전 파일에서 가장 가까운 일치 값을 찾아 그 값으로 덮어씁니다. 따라서 새 파일에 있던 실제 정상 0 값이
이전 데이터로 대체됩니다. 오랫동안 정상적으로 0 값을 유지하는 메트릭(유휴 포트, 비어 있는 큐,
정지 상태의 카운터 등)의 경우 실제 환경에 적용하기 전에 결과를 철저히 점검하십시오. 이전 파일의 알 수 없는 값 역시
앞선 값으로 메워지므로, 병합된 결과물이 누락된 데이터 구간에 허위 연속성을 만들어낼 수 있습니다.
:::

접합 작업이 끝나면 데이터 소스가 요구하는 경로에 파일을 배치하고, 폴러에게 필요한
소유권을 설정한 뒤 그래프가 정상적으로 그려지는지 확인하십시오.

## 8. 공백 채우기와 신중한 고려

| 유틸리티 | 기록하는 내용 |
|---|---|
| `cli/batchgapfix.php` | 마지막으로 알려진 정상 값이나 평균값을 사용하여 여러 장비에 걸쳐 지정 날짜 범위의 공백을 병렬로 채움 |
| `cli/float_rrdfiles.php` | 동일한 dump 및 restore 경로를 통해 선택된 그래프의 특정 범위를 유동적으로 조정함 |

두 도구 모두 허위 측정값을 생성합니다. 해당 타임스탬프에는 실제로 아무런 데이터도 수집되지 않았으며,
처리 후에는 파일 내에서 인위적으로 채워 넣은 값과 실제 측정값을 구분할 수 없게 됩니다. 유지보수를 위해 폴러를
중지했거나 마이그레이션 작업 구간 등 해당 공백이 실제 장애가 아님을 확신할 수 있는 경우에만 사용하십시오.
용량 산정이나 비용 청구의 근거가 되는 메트릭에는 절대로 사용해서는 안 됩니다. 동일한 주의사항이
[스파이크 제거](/ko/guides/remove-spikes-from-data/)에도 적용됩니다.

## 9. 단일 데이터 소스 자동 디버깅

비정상적으로 동작하는 단일 데이터 소스에 대해 Kadupul은 향후 몇 번의 폴링 주기 동안 디버그 검사를
실행하고 판정 결과를 보고할 수 있습니다. 파일 존재 여부, 파일 및 디렉터리 쓰기 가능 여부,
파일 소유 계정과 폴러 실행 계정의 일치 여부, 데이터 소스 활성화 여부, 데이터 소스 정의와 파일 구조의 일치 여부,
폴링 후 최종 갱신 시각의 진행 여부, 값의 유효성을 점검합니다.
자동 복구 동작은 매우 제한적입니다. 비교를 통해 생성된 `rrdtool tune` 권장 명령어만 실행하며,
목록이 비어 있거나 파일이 쓰기 불가인 경우 작업을 거부하고 이유를 로그에 남깁니다.
파일을 재생성하거나 데이터 소스를 추가하거나 아카이브를 변경하지는 않습니다.

## 10. 삭제 시 수반되는 별도의 위험

Kadupul은 데이터 소스가 더 이상 존재하지 않는 고아 아카이브 파일을 추적하고
삭제할 수 있는 옵션을 제공합니다. 또한 데이터 소스가 삭제될 때 자동으로 연동 조치하도록 설정할 수도 있으며,
완전 삭제와 아카이브 디렉터리로 이동이라는 두 가지 방식이 있습니다.

:::danger[삭제 작업은 되돌릴 수 없습니다]
완전 삭제 방식은 디스크에서 파일을 영구히 제거합니다. 휴지통 기능이 없으며 데이터는
데이터베이스에 저장되어 있지 않습니다. 목록의 모든 파일이 실제로 불필요한 고아 파일인지 완벽히 확신할 수 없다면,
지정한 디렉터리로 파일을 옮겨두는 이동 방식을 선택하고 나중에 수동으로 정리하십시오.
:::

실제로는 사용 중이지만 고아 파일처럼 보이는 경우가 있습니다. 데이터 소스가 새 경로로 이동되었거나,
복원 작업이 일부만 완료되었거나, 디바이스가 새 ID로 재생성된 경우 아무런 설정도 가리키지 않는 파일이 남게 됩니다.
파일을 삭제하기 전에 관리자 자신의 시스템 변경 기록과 대조하십시오.

## 장애 모드

| 증상 | 원인 |
|---|---|
| 복구 작업이 성공했으나 그래프가 여전히 비어 있음 | 접근 권한, 선택한 시간 범위, 데이터 수집 상태 및 그래프 정의를 점검하십시오 |
| `rrdtool dump` 실행 시 파일 오류가 발생함 | 파일 손상으로 결론짓기 전에 경로, 권한, 스토리지 상태 및 파일 포맷을 확인하십시오 |
| Tune을 적용했으나 아무것도 바뀌지 않음 | 헤더 변경은 과거의 알 수 없는 샘플을 소급해서 채워주지 않습니다. 파일과 DB 정의를 다시 확인하십시오 |
| 주기 변경 후 그래프 전역에 미세한 공백 줄무늬가 발생함 | 파일 내부에 이전 스텝과 하트비트 설정이 그대로 남아 있습니다 |
| 접합된 파일에서 새 파일이 0으로 읽었던 부분에 과거 데이터가 들어감 | 정상적인 동작입니다. splice는 알 수 없는 값뿐만 아니라 0 값도 채워 넣습니다 |
| 검사기 경고 목록이 계속 증가하고 줄어들지 않음 | 발견된 결과는 수동으로 정리하기 전까지 유지됩니다. 원인을 고쳐도 자동으로 삭제되지 않습니다 |

아카이브 디렉터리와 데이터베이스를 단일 일정에 따라 반드시 함께 백업하고
복원 훈련을 정기적으로 수행하십시오. 재해 복구는 백업이 캡처된 시점에 보존하고 있던 데이터로
엄격히 제한됩니다. [백업 및 복원](/ko/guides/back-up-and-restore/)을 참조하십시오.
