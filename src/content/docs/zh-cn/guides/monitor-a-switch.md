交换机是数据查询的经典用例。您无法预先知道存在多少个端口，端口数量可能会变化，且每个端口都需要自己的数据源。有关数据查询的工作原理，请参阅[模板](/zh-cn/concepts/templates/)；本页重点介绍正确配置。

## 开始之前

确保设备能够从分配的收集器做出响应，最好以轮询器用户身份进行测试。使用您配置的只读凭据。数值 OID 可避免对本地安装的 MIB 名称产生依赖。

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.31.1.1.1.1
```

使用 SNMP v2c 或 v3。64 位接口计数器属于 SMIv2 对象，无法通过 v1 进行查询。v1 设备仅会提供 32 位计数器，别无其他。

## 选择设备模板

设备模板决定了添加设备时提供哪些数据查询和图表模板。Kadupul 继承了 Cacti 附带的模板集，其中包括通用 SNMP 设备模板以及一系列特定供应商的模板。

无论您如何选择，端口发现都来自同一数据源：在 `resource/snmp_queries/interface.xml` 中定义的接口数据查询。如果没有适合您硬件的模板，请选择通用模板并为其关联接口查询。

## 运行数据查询

查询通过遍历 `ifIndex` 查找端口，并读取 `ifNumber` 以获知预期的端口总数。随后它会收集每个端口的一组字段。

| 字段 | OID | 用途 |
|---|---|---|
| `ifIndex` | `.1.3.6.1.2.1.2.2.1.1` | 在 SNMP 表中的位置 |
| `ifName` | `.1.3.6.1.2.1.31.1.1.1.1` | 简短端口名称，如 `Gi1/0/3` |
| `ifDescr` | `.1.3.6.1.2.1.2.2.1.2` | 详细描述 |
| `ifAlias` | `.1.3.6.1.2.1.31.1.1.1.18` | 您配置的接口描述 |
| `ifHwAddr` | `.1.3.6.1.2.1.2.2.1.6` | 端口 MAC 地址 |
| `ifSpeed` | `.1.3.6.1.2.1.2.2.1.5` | 速率（比特/秒），32 位 |
| `ifHighSpeed` | `.1.3.6.1.2.1.31.1.1.1.15` | 速率（兆比特/秒） |
| `ifOperStatus` | `.1.3.6.1.2.1.2.2.1.8` | Up 或 Down |
| `ifInOctets` / `ifOutOctets` | `.1.3.6.1.2.1.2.2.1.10` / `.16` | 32 位字节计数器 |
| `ifHCInOctets` / `ifHCOutOctets` | `.1.3.6.1.2.1.31.1.1.1.6` / `.10` | 64 位字节计数器 |

在设备上运行一次查询。它将返回已发现端口的表格。在创建图表之前，请仔细核阅该表，因为它是后续每个决策的基础。

## 选择 64 位计数器

接口查询提供了多个流量图表模板。主要包括：

| 图表模板 | 读取内容 |
|---|---|
| In/Out Bits | `ifInOctets`, `ifOutOctets` |
| In/Out Bits (64-bit) | `ifHCInOctets`, `ifHCOutOctets` |
| In/Out Bits (64-bit, 95th) | 同上，带有 95 百分位线 |
| In/Out Bits (64-bit, BW) | 同上，相对于接口速率 |
| Status (Up/Down) | `ifOperStatus` |
| In/Out (Errors/Discards) | `ifInErrors`, `ifInDiscards`, `ifOutDiscards`, `ifOutErrors` |

除非有充分的反对理由，否则请务必使用 64 位模板。32 位八位字节计数器的上限为 4294967295。千兆端口在满载情况下约 34 秒就会将其填满。在 300 秒步长下，轮询器无法区分一次溢出与七次溢出，且 `COUNTER` 仅能纠正两个采样之间的一次溢出。图表看起来不会有明显的损坏痕迹；它只会持续显示偏低的数值。

在创建数百个图表之前，请确认计数器确实在填充数据。

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.31.1.1.1.6
```

空遍历或失败遍历需要调查：检查报告的错误、访问视图以及代理支持情况。

## 检查速率变更后存储的最大值

当数据源根据查询速率使用最大值时，创建过程会从缓存的发现数据中获取速率。优先选择 `ifHighSpeed`，缺失时使用 `ifSpeed`，两者均为零时采用配置的默认值。

该数值会写入文件。以 100 Mbps 发现并随后协商至更高速率的端口可能会保留低于其实际流量的上限，而 RRDtool 会将超出该上限的速率记录为 unknown。使用 `rrdtool info` 对比缓存速率、数据源定义和实际文件。

## 索引决策

若出现疏忽，历史记录就会在此丢失。

每个数据源都存储关于其端口的两项内容：标识该端口的字段（索引类型）以及该字段的值。每次重新索引时，它通过询问哪个 SNMP 索引当前在该字段中具有该值来重新找到该端口。数据源跟踪的是值，而不是表中的位置。

因此核心问题在于哪个字段承载该值。

接口查询声明了偏好顺序：`ifName`，接着是 `ifDescr`，再者是 `ifHwAddr`，最后是 `ifIndex`。Kadupul 通常会在具备足够区分度且无重复值的候选字段中进行选择。

| 字段 | 耐受情况 | 失败场景 |
|---|---|---|
| `ifName` | 重启、板卡更换、重新编号 | 代理留空或在堆叠成员之间重复 |
| `ifDescr` | 在交换机硬件上通常稳定 | 在服务器上属于易变动的内核名称 |
| `ifHwAddr` | 重启 | 更换后的板卡拥有全新 MAC，这恰恰是您期望防范的场景 |
| `ifIndex` | 无法保障任何稳定性 | 更换板卡、重启或固件变更会导致表重新编号 |

如果查询回退到 `ifIndex`，请将其视为需要排查的异常，而非正常结果。否则，您的端口历史记录将绑定到一个交换机可随时自由重新分配的数字上。

## 重新索引方法

针对每个设备及每个数据查询进行设置。它决定了 Kadupul 何时重新读取索引字段。

| 方法 | 触发条件 | 资源开销 |
|---|---|---|
| None | 无；仅手动或脚本执行 | 无 |
| Uptime | 设备 SNMP 运行时间回退 | 每个周期一次对比 |
| Index Count | 发现的索引总数发生变化 | 每个周期一次计数 |
| Verify All | 缓存的身份验证检查失败 | 在轮询期间查询已知索引 |

Uptime 是默认设置，适用于大多数交换机，因为重启是导致索引重新编号的典型事件。Index Count 可以捕获无需重启即可添加或移除的板卡。Verify All 能够检测已知索引上变更的身份，但无法保证发现新端口。

要重新运行选定的设备和查询，请将两个 ID 替换为已安装的实际 ID。省略 `--qid` 将重新运行该设备的所有查询：

```bash
php cli/poller_reindex_hosts.php --id=42 --qid=16
```

`--id=all` 将执行范围扩展至所有已启用的设备。避免重叠的重新索引运行。`--force` 绕过进程注册并刷新标题缓存。

## 当端口消失时

不要假设端口缺失会自动停止采集。当身份未解析且没有源更改索引时，当前的重新索引代码可能会重置孤立标志并保留旧的轮询 OID。将存储的身份与新的发现缓存进行比对，并在确认匹配前禁用受影响的源。请参阅[数据查询与索引](/zh-cn/concepts/data-queries-and-indexes/)。

## 大型机箱

当端口数量激增时，每台设备的两项设置变得至关重要：检查每个 SNMP 请求配置的 OID 数量以及每台设备配置的线程数。批处理支持与有效并发性取决于收集器和代理；PHP `cmd.php` 和 Spine 提供的多线程行为并不相同。

一次仅更改一项设置，并密切观察轮询器周期耗时。

## 故障模式

| 症状 | 原因 |
|---|---|
| 创建了图表，但每个测量值均为 unknown | 未实现 64 位计数器，或设备使用 SNMP v1 |
| 计数器跳变至荒谬数值 | 32 位计数器在单个间隔内发生多次溢出 |
| 仅在高负载下出现数据断点 | RRD 最大值被锁定为陈旧的发现速率 |
| 维护后端口历史记录关联至错误端口 | 身份不稳定、映射陈旧或未解决的孤立项处理 |
| 轮询器记录关于无效 SNMP 索引的警告 | 数据源遗留且无索引；重新索引、删除或禁用 |
| 发现了端口，但未采集任何数据 | 带有空索引的数据源不会在轮询器缓存中创建条目 |
