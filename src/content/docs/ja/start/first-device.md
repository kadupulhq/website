まず1台のデバイスを追加して応答することを確認し、それから次へ進んでください。監視システムのトラブルの多くは、そもそも最初から応答していなかったデバイスに起因します。

失敗しても問題のないデバイスを選んでください。自分で所有し、自分で管理するネットワーク内にあり、SNMPがすでに有効になっているスイッチが適しています。誰かから監視を頼まれているようなデバイスから始めてはいけません。

## 始める前に

このSNMPの例では、デバイスが割り当てられたコレクターからの問い合わせに応答する必要があります。そのコレクター上で、できる限りポーラー実行ユーザーとして確認を行ってください。ノートPCからのリクエストはファイアウォールの経路が異なる場合があります。サンプルのアドレスとコミュニティ名を、デバイスに設定されている読み取り専用の認証情報に置き換えてください。ローカルのMIB名ファイルがインストールされていない場合でも、以下の数値OIDで動作します。

```bash
snmpget -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.1.1.0
```

これで説明文字列が返ってきたら、先へ進みます。タイムアウトした場合は、まずその問題を解決してください。Web管理画面でどれほど設定を調整しても、到達できないデバイスが応答することはありません。

次に、実際にグラフ化したいテーブルを確認します。デバイスが `sysDescr` に応答しても、インターフェーステーブルの照会を拒否することがあるためです。

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.2.2.1.2
```

2つ目のOIDは `ifDescr` 列です。公開されているインターフェースごとに1行ずつ返される必要があります。結果が空の場合は、SNMPビューの制限やサポートされていないテーブルである可能性があり、認証エラーの場合は認証情報やアクセス制御ポリシーに問題があります。デバイスやKadupulの設定を変更する前に、返されたエラーの内容を確認してください。

SNMPバージョンに関する2つの事実は後々の判断に影響するため、ここで確認しておきます。

| バージョン | 実際の運用における意味 |
|---|---|
| v1 | Counter64非対応。高速回線ではポーリング間隔の間に32ビットのオクテットカウンターが複数回周回することがあり、計算レートが曖昧になります |
| v2c | エージェントが公開している場合にCounter64をサポートします。コミュニティ名は平文で送信されます |
| v3 | `authPriv` による認証と暗号化をサポートします。v3を選択しただけでは両方が自動的に有効になるわけではありません |

対応している環境では `authPriv` を使用したv3を推奨します。あるいは、アクセス制限された管理ネットワークではv2cを使用してください。SNMPバージョンとともに、64ビットインターフェース用のグラフタイプを選択してください。デバイスがv1にしか対応していない場合は、このページ下部のトラブルシューティング表を参考に、ポーリング間隔とトラフィックレートを検討してください。[SNMP](/ja/reference/snmp/) に認証情報フィールドの詳しい説明があります。

## フォームを開く前に決める3つの項目

**認証情報。** 上記でテストしたものと同一のものを指定します。標準以外のポートを使用している場合はポート番号も含めます。

**可用性判定方法。** これはデータ収集が動作しているかとは独立して、Kadupulがデバイスの稼働（UP）を判定する方法です。用意されている選択肢は、なし（none）、ping、SNMP稼働時間、SNMP説明文、SNMP getNext、そしてpingとSNMP稼働時間の2種類の組み合わせ（両方を要求するものと、いずれか一方で可とするもの）です。

SNMPでポーリングするデバイスには、SNMPによる判定方法をお勧めします。実際に依存しているプロトコルそのものをテストできるからです。ICMP pingはRawソケットを必要とし、これにはWebユーザーやポーラーユーザーが通常持たない特権が求められます。そのため、シェルから `ping` に応答するデバイスであっても、画面上はダウンと判定されることがあります。開放が確認できているポートへのTCP pingであれば、この問題を回避できます。

**デバイステンプレート。** ハードウェアに合致するものを選択します。

## デバイスの追加

1. 従来の**デバイス**ページ（`host.php`）で、**追加**を選択します。Symfonyへの移行期間中も、デバイス作成とグラフ設定には引き続きこのページを使用します。説明、ホスト名またはIPアドレス、割り当てコレクター、SNMPバージョン、および認証情報を入力します。
2. 決定した可用性判定方法を設定します。
3. デバイステンプレートを選択します。
4. 保存し、デバイスが有効になっていることを確認したうえで、可用性/SNMPステータスパネルを確認します。データベースのレコードが保存されたこと自体は、データ収集の成功を意味するものではありません。

## デバイステンプレートが決定するもの

デバイステンプレートは、グラフテンプレートやデータクエリをデバイスに関連付けます。データクエリは、インターフェース一覧などデバイス上のテーブルをスキャンし、各行に対して1つのインデックスを生成します。テンプレートを適用すると、これらのインデックスを登録するためにデータクエリも実行されます。グラフの自動作成が無効になっている場合、この関連付けだけで勝手にグラフが作成されることはありません。グラフの自動作成が有効になっている場合は、テンプレートやクエリのフックが条件に一致するルールに従ってグラフを作成できます。重複して追加する前に既存のグラフを確認してください。

テンプレートを変更すると関連付けが変わり、それらのフックが再度実行されることがあります。既存のグラフやデータソースがリセットされるわけではありません。すでに履歴データが蓄積されているデバイスに適用する前に、選択したテンプレートと照会対象のインデックスを確認してください。

これらのインデックスがあるおかげで、OIDを手入力する代わりにリストからインターフェースを選択できます。[テンプレート](/ja/concepts/templates/) および [データクエリとインデックス](/ja/concepts/data-queries-and-indexes/) で両方の仕組みを詳しく解説しています。

## ステータスパネルの確認

SNMPの可用性判定方法を指定してデバイスを保存すると、Kadupulはセッションを開始して結果を報告します。これこそが最も重要な確認であり、多くの人が省略してしまうステップです。

| 表示内容 | 意味 |
|---|---|
| システムおよび稼働時間のクエリ成功 | パネルが基本的なSNMPメタデータを取得できています。ただし、インターフェースの収集成功を保証するものではありません |
| 場所または連絡先が空 | これらのオプションメタデータは未設定の場合があります。空であること自体は収集エラーではありません |
| SNMP未使用 | デバイスにコミュニティ名やユーザー名がないか、バージョンがなし（none）に設定されています |
| SNMPセッションエラー | セッション確立に失敗しました。表示されたエラー、認証情報、プロトコル、接続設定を確認してください |
| SNMPシステムエラー | `sysDescr` の読み取りに失敗しました。返されたエラー、エージェントビュー、認証情報、到達性を確認してください |
| SNMPホストエラー | 説明文も稼働時間も返されませんでした |
| 稼働時間が `U` と表示 | 稼働時間を読み取れませんでした。デバイスによっては最初からこの値を返さないものもあります |

可用性判定方法にpingが含まれている場合は、下に個別のping結果が表示されます。両方の結果を確認してください。一方が成功してもう一方が失敗することがあり、どちらが失敗したかによって調査すべき箇所がわかります。

システム説明が空だからといって、データ収集が失敗しているとは限りません。コード上は説明文が空で稼働時間だけが取得できるエージェントにも対応しています。無効化されたデバイスは可用性チェックをスキップし、SNMP以外の可用性判定方法ではこのSNMPパネル自体が表示されません。次に、実際のクエリとポーラーキャッシュを検証します。

## データソースとグラフの作成

自動ルールでグラフが作成されない新規デバイスの場合、次のステップはグラフとそのデータソースを作成することです。最初から空であると思い込まず、デバイスページの**データソース一覧**と**ポーラーキャッシュの表示**を確認してください。

デバイスページから、**このデバイスのグラフを作成**を選択します。スイッチの場合、これはインターフェースのデータクエリを実行し、対象としたいインターフェースを選んで、それらに適用するグラフタイプを選択することを意味します。48ポートすべてではなく、まずは2〜3個のインターフェースを選択してください。目的はデータ経路が正しく機能することを証明することであり、少数のデータの方が次のステップで格段に確認しやすくなります。

インデックス付きグラフは、データソースを選択したインターフェースに関連付け、ポーラーキャッシュのエントリを用意します。条件に合う既存のソースがあれば再利用される場合もあります。グラフ作成の応答画面が出たこと自体は、ポーリングの成功を証明するものではありません。キャッシュに想定通りのデバイス、インターフェースOID、RRDパスが含まれていることを確認してください。

## 収集の動作確認

スケジュールされた収集サイクルが実行されるのを待ち、タイムスタンプと値の両方を確認します。グラフが空の場合、起動直後の正規化、未知の値（unknown）、または収集失敗が考えられます。レートを算出するにはカウンターの読み取りが2回必要ですが、ポーラーが2回走ったからといって、必ずしも完全に有効なアーカイブバケットが完成するとは限りません。

次の3点をこの順序で確認してください。

**ポーラーが実行されたこと。** 設定されたログで、実行終了時のサマリー出力を探します。見当たらない場合は、スケジューリング、ログの出力先と権限、およびポーラーが完了前に異常終了していないかを確認してください。[ロギング](/ja/reference/logging/) を参照してください。

**ファイルが存在し、更新されていること。** ホスト名から当て推量するのではなく、データソースまたはポーラーキャッシュから実際のRRDパスをコピーしてください。パスやファイル名はカスタマイズされている場合があります。[ファイルレイアウト](/ja/reference/file-layout/) を参照してください。RRDtoolにファイルの最終書き込み時刻を問い合わせます。

```bash
rrdtool last /path/to/rra/the_actual_file.rrd
rrdtool lastupdate /path/to/rra/the_actual_file.rrd
rrdtool fetch /path/to/rra/the_actual_file.rrd AVERAGE --start end-30m --end now
```

書き込みが成功していれば、タイムスタンプが進みます。最新のタイムスタンプであっても値が未知である場合はあり、バッファリングされた書き込みによってディスク上のタイムスタンプ更新が遅れることもあります。`rrdcached` やBoostを使用している場合は、それらのフラッシュ状態も確認してください。

**値が未知（unknown）でないこと。** `lastupdate` は直近に提供された値を表示します。カウンターの場合、これらは計算されたトラフィックレートではなく累積カウント値です。有限のレート値が得られているかを調べるには、`fetch` から完了した行を確認してください。起動タイミング、ステップのアライメント、ハートビート、上限・下限値、およびアーカイブの未知データしきい値のすべてが、有効な行がいつ現れるかに影響します。最初の2行だけで不具合と即断しないでください。未知の値が続く場合は、収集された値、データソースタイプ、ハートビート、およびポーラーのエラーを確認してください。

## 最初につまずきやすい問題

| 現象 | 主な原因 |
|---|---|
| 保存は成功するが、システム説明の照会でエラーになる | 認証情報、エージェントビュー、コレクターからの到達性を確認してください。説明が空であることだけでは十分な判断材料になりません |
| KadupulからはSNMPセッションエラーになるが、ノートPCからの `snmpget` は成功する | ファイアウォールの経路が異なるか、エージェントが送信元IPアドレスでアクセスを制限しています |
| デバイスがダウン表示されるが、SNMPデータは届いている | 可用性判定がRawソケットを開けないICMP pingに設定されています |
| 説明は表示されるがデータが来ない | ポーラーがスケジュールされていないか、RRDディレクトリに書き込み権限のないユーザーで実行されています |
| データクエリがインターフェースを返さない | エージェントビューでインターフェーステーブルが除外されているか、デバイスの再インデックスが必要です |
| 最初の値が未知で、その後正常になる | カウンターでは正常な動作です。レートを計算するには2回の読み取りが必要です |
| 未知の値が継続する | 収集の失敗、無効な値、型や境界値の不一致、ハートビートまたはアーカイブ正規化の問題です |
| しばらくデータが取れた後に途切れる | ポーラーの実行時間がインターバルを超過しているか、デバイス側でSNMPをレート制限しています |
| カウンターの計算レートが異常に大きい | 32ビットカウンターの複数回周回、カウンターリセット、単位やデータソース設定を確認してください。高速回線では64ビットカウンターを使用してください |
| 再起動後にインターフェースグラフが別のポートを指す | インデックスがずれました。データクエリ側でインデックスの変化を検知できる再インデックス方式を設定する必要があります |

最後の項目は、何百台ものスイッチを管理する前に理解しておく価値があります。SNMPインターフェースのインデックスは、再起動やモジュールの抜き差しを経ても不変である保証はありません。データクエリの再インデックス方式こそが、グラフが同じ物理ポートを指し続けるように保つ仕組みです。[データクエリとインデックス](/ja/concepts/data-queries-and-indexes/) で選択肢について解説しています。

1台のデバイスで安定した収集ができるようになったら、1台ずつ手作業で繰り返すのではなく、まとめて一括追加してください。[デバイスの自動検出](/ja/guides/discover-devices-automatically/) や [コマンドラインツール](/ja/reference/command-line-tools/) に掲載されているツールを使えば、このページの手順を50回繰り返す手間を省くことができます。
