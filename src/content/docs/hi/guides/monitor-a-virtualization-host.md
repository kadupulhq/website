:::caution[उपयोग से पहले सत्यापित करें]
स्रोत उपलब्ध है, लेकिन कोई समर्थित Kadupul रिलीज़ या माइग्रेशन पथ नहीं है। इन प्रक्रियाओं पर निर्भर होने से पहले बैकअप के साथ एक अलग कॉपी पर इनका परीक्षण करें। [परियोजना की स्थिति](/hi/project/status/) देखें।
:::

शामिल किया गया ESXi पैकेज होस्ट माप और गेस्ट इन्वेंट्री गणना एकत्र करता है। यह प्रति-गेस्ट CPU, मेमोरी या विवाद माप प्रदान नहीं करता है। ग्राफ़ चुनने से पहले अपने हाइपरवाइज़र संस्करण द्वारा प्रदर्शित वस्तुओं को सत्यापित करें।

## क्या शामिल है

एक हाइपरवाइज़र डिवाइस टेम्पलेट प्रदान किया गया है: **ESXi Device**। यह एक डिवाइस पैकेज है, इसलिए `install/templates/ESXi_Device.xml.gz` में इसकी स्क्रिप्ट और डेटा-क्वेरी फ़ाइलें शामिल हैं। [टेम्पलेट्स आयात और निर्यात करें](/hi/guides/import-and-export-templates/) का पालन करें और फ़ाइल परिनियोजन सहित आयात पूर्ण होने की पुष्टि करें। डिवाइस टेम्पलेट का चयन करें, डिस्कवरी का निरीक्षण करें, और वांछित ग्राफ़ स्पष्ट रूप से बनाएं; केवल पैकेज आयात करना या डिवाइस टेम्पलेट जोड़ना उन्हें नहीं बनाता है।

| शामिल घटक | उद्देश्य |
|---|---|
| `resource/snmp_queries/esxi_cpu.xml` | प्रोसेसरों की खोज करता है और प्रति-प्रोसेसर लोड पढ़ता है |
| `resource/snmp_queries/esxi_hw.xml` | हार्डवेयर घटकों की खोज करता है और उनकी स्थिति पढ़ता है |
| `resource/snmp_queries/interface.xml` | मानक इंटरफ़ेस सांख्यिकी क्वेरी |
| `resource/script_server/host_disk.xml` | Host Resources स्टोरेज तालिका के माध्यम से माउंटेड विभाजन |
| `scripts/ss_esxi_vhosts.php` | `install/templates/ESXi_Device.xml.gz` के अंदर बंडल किया गया; गेस्ट की संख्या, चालू गेस्ट और गेस्ट टूल्स की स्थिति गिनता है |
| `scripts/ss_multicpu_avg.php` | प्रति-प्रोसेसर लोड का औसत एक संख्या में निकालता है |
| `scripts/ss_hstats.php` | डिवाइस के लिए Kadupul के पास पहले से मौजूद पोलिंग आँकड़े पढ़ता है |
| `scripts/ss_host_disk.php` | विभाजन क्वेरी का समर्थन करता है |

इस चेकआउट में Hyper-V, KVM/libvirt, Xen या Proxmox के लिए कोई समर्पित डिवाइस पैकेज शामिल नहीं है। सामान्य Linux/Windows टेम्पलेट उनके एजेंटों द्वारा समर्थित होस्ट मेट्रिक्स को कवर कर सकते हैं; हाइपरवाइज़र-विशिष्ट संग्रह के लिए उपयुक्त टेम्पलेट्स और संग्राहकों की आवश्यकता होती है। [डेटा संग्रह स्क्रिप्ट लिखें](/hi/guides/write-a-data-collection-script/) देखें।

## पहले एजेंट चालू करें

मौजूदा एजेंट कॉन्फ़िगरेशन की समीक्षा करें और अपने ESXi संस्करण के लिए निर्देशों का उपयोग करें। पैकेज नोट्स में फ़ैक्टरी रीसेट शामिल है; यह कोई नियमित पूर्वापेक्षा नहीं है और मौजूदा SNMP कॉन्फ़िगरेशन को मिटा देगा। कम्युनिटी-आधारित सेटअप के लिए, निम्नलिखित कमांड एजेंट मान सेट करते हैं; उदाहरणों को बदलें और कम्युनिटी सूची सेट करते समय किसी भी आवश्यक मौजूदा कम्युनिटी को सुरक्षित रखें।

```bash
esxcli system snmp get
esxcli system snmp set -c YOUR_STRING
esxcli system snmp set -p 161
esxcli system snmp set -L "City, State, Country"
esxcli system snmp set -C noc@example.com
esxcli system snmp set -e yes
```

पहला कमांड कॉन्फ़िगरेशन प्रदर्शित करता है; अंतिम कमांड एजेंट को सक्षम करता है। कम्युनिटी विकल्प इसकी कॉन्फ़िगर की गई सूची को प्रतिस्थापित करता है। पोलर से आवश्यक फ़ायरवॉल एक्सेस की जाँच करें और [ESXCLI SNMP कमांड संदर्भ](https://developer.broadcom.com/xapis/esxcli-command-reference/latest/namespace/esxcli_system.html) देखें। ये कमांड कम्युनिटी-आधारित पोलिंग कॉन्फ़िगर करते हैं; वे SNMPv3 कॉन्फ़िगर नहीं करते हैं। डिवाइस जोड़ने से पहले उस मशीन से सत्यापित करें जिस पर पोलर चलता है।

```bash
snmpget  -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.1.1.0
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.25.3.3.1.2
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.4.1.6876.2.1.1.6
```

यदि पहला काम करता है और तीसरा कुछ भी वापस नहीं करता है, तो SNMP त्रुटि, एक्सेस नीति और एजेंट समर्थन का निरीक्षण करें; केवल एक खाली वॉक कारण की पहचान नहीं करता है। बंडल की गई गेस्ट स्क्रिप्ट SNMPv1 का उपयोग करती है, इसलिए एक सफल v2c प्रोब इसके संग्रह पथ को मान्य नहीं करता है। खाली गेस्ट वॉक शून्य गणना उत्पन्न करते हैं, आवश्यक रूप से ग्राफ़ अंतराल नहीं; [खाली-परिणाम बग](https://github.com/kadupulhq/kadupul/issues/245) देखें।

## होस्ट क्या उजागर करता है

| क्षेत्र | सबट्री | आपको क्या प्रदान करता है |
|---|---|---|
| प्रोसेसर | `.1.3.6.1.2.1.25.3.3.1` | एजेंट द्वारा उजागर किए गए प्रत्येक प्रोसेसर के लिए लोड |
| हार्डवेयर घटक | `.1.3.6.1.2.1.25.3.2.1` | घटक सूचकांक, विवरण और स्थिति |
| भंडारण | `.1.3.6.1.2.1.25.2.3.1` | डेटास्टोर और स्थानीय फ़ाइल सिस्टम, जैसा कि एजेंट रिपोर्ट करना चुनता है |
| इंटरफेस | `.1.3.6.1.2.1.2` और `.1.3.6.1.2.1.31` | ट्रैफ़िक, त्रुटियाँ, स्थिति |
| गेस्ट इन्वेंट्री | `.1.3.6.1.4.1.6876` | प्रति-गेस्ट पावर स्थिति और गेस्ट टूल्स स्थिति |

पहले चार मानक Host Resources और इंटरफ़ेस तालिकाएँ हैं, वही जिनका उत्तर Linux होस्ट देता है। वे कैसे व्यवहार करते हैं और किस डिस्क तालिका को प्राथमिकता दी जाए, इसके लिए [Linux सर्वर की निगरानी करना](/hi/guides/monitor-a-linux-server/) देखें।

पांचवां विक्रेता सबट्री है जिसका उपयोग शामिल गेस्ट-काउंट स्क्रिप्ट द्वारा किया जाता है।

## ग्राफ़ टेम्पलेट्स

| ग्राफ़ | स्रोत | क्या पढ़ता है |
|---|---|---|
| ESXi - CPU | डेटा क्वेरी | एक खोजे गए प्रोसेसर के लिए लोड |
| ESXi - MultiCPU Average | स्क्रिप्ट | प्रत्येक प्रोसेसर के लोड का औसत |
| ESXi - Hardware | डेटा क्वेरी | एक खोजे गए घटक की स्थिति |
| ESXi - VHosts | स्क्रिप्ट | गेस्ट संख्या और गेस्ट टूल्स स्थिति |
| Host MIB - Processes | निश्चित OID | होस्ट पर प्रक्रियाओं की संख्या |
| Host MIB - Logged in Users | निश्चित OID | होस्ट पर सत्रों की संख्या |
| Device - Uptime | स्क्रिप्ट | Kadupul द्वारा अंतिम दर्ज किया गया अपटाइम |
| Device - Polling Time | स्क्रिप्ट | Kadupul को इस उपकरण को पोल करने में कितना समय लगा |
| इंटरफ़ेस ग्राफ़ | डेटा क्वेरी | प्रति इंटरफ़ेस ट्रैफ़िक, त्रुटियाँ, पैकेट, स्थिति |

प्रोसेसर क्वेरी प्रति खोजे गए आइटम पर लोड पढ़ती है। यह न मानें कि इसकी पंक्ति संख्या होस्ट के हार्डवेयर थ्रेड गणना से मेल खाती है: पैकेज्ड इंडेक्स पैटर्न केवल एक या दो अंकों के इंडेक्स स्वीकार करता है और 100 या उससे अधिक को अस्वीकार करता है, यहाँ तक कि कुछ CPU वाले होस्ट पर भी। खोज की तुलना रॉ वॉक से करें; [CPU-इंडेक्स बग](https://github.com/kadupulhq/kadupul/issues/246) देखें। औसत स्क्रिप्ट स्वतंत्र रूप से प्रोसेसर लोड को स्कैन करती है और लौटाई गई पंक्तियों का औसत निकालती है।

Device - Uptime और Device - Polling Time Kadupul के संग्रहीत डिवाइस रिकॉर्ड को पढ़ते हैं। अपटाइम हेल्पर बीते हुए समय का अनुमान लगाए बिना संग्रहीत SNMP अपटाइम लौटाता है; पोलिंग समय Kadupul के संग्रह कार्य का वर्णन करता है। एक पुराना संग्रहीत मान वर्तमान पहुँच क्षमता को साबित नहीं करता है। यदि संग्रह रुक जाता है, तो ये सहायक नए नमूने उत्पन्न नहीं करते हैं।

## गणना की समस्याएं

यह वह हिस्सा है जो वर्चुअलाइजेशन को भौतिक सर्वर से अलग बनाता है, और इनमें से कोई भी समस्या ग्राफ़ टेम्पलेट द्वारा हल नहीं होती है।

**गेस्ट स्थानांतरित होते हैं।** एक गेस्ट जो दूसरे होस्ट पर माइग्रेट करता है, वह पहले होस्ट की इन्वेंट्री से गायब हो जाता है और दूसरे होस्ट की इन्वेंट्री में दिखाई देता है। स्वतंत्र रूप से समयबद्ध नमूने अस्थायी रूप से उस गेस्ट की दोहरी गणना कर सकते हैं या छोड़ सकते हैं। केवल गणना परिवर्तन माइग्रेशन साबित नहीं करते हैं: उन्हें समझाने के लिए हाइपरवाइज़र इन्वेंट्री पहचान और घटनाओं का उपयोग करें।

**संसाधन साझा किए जाते हैं, इसलिए प्रति-गेस्ट एट्रिब्यूशन एक अनुमान है।** होस्ट भौतिक प्रोसेसर लोड की रिपोर्ट करता है। यह रिपोर्ट नहीं करता कि किस गेस्ट ने इसका कारण बना। होस्ट CPU को गेस्ट गणना से विभाजित करने पर एक ऐसी संख्या प्राप्त होती है जो अंकगणितीय रूप से सही होती है और किसी के द्वारा पूछे गए किसी भी प्रश्न का उत्तर नहीं देती है।

**ओवरकमिट आवंटन और उपयोग को अलग-अलग मात्राएँ बनाता है।** असाइन किए गए वर्चुअल CPU भौतिक कोर से अधिक हो सकते हैं, और असाइन की गई मेमोरी जानबूझकर भौतिक मेमोरी से अधिक हो सकती है। असाइन किए गए संसाधनों का ग्राफ़ मापी गई मांग के बजाय आवंटन का वर्णन करता है। इसकी तुलना भौतिक क्षमता, कॉन्फ़िगर की गई सीमाओं और वास्तविक उपयोग से करें।

**इन तालिकाओं में विवाद (Contention) दिखाई नहीं देता है।** वे माप जो आपको बताते हैं कि एक गेस्ट भूखा है, भौतिक प्रोसेसर की प्रतीक्षा में बिताया गया समय और होस्ट द्वारा उससे पुनः प्राप्त की गई मेमोरी, इस टेम्पलेट द्वारा एकत्र की गई चीज़ों में नहीं हैं। गंभीर रूप से विवादित गेस्ट वाला 60 प्रतिशत CPU वाला होस्ट यहाँ ठीक काम करने वाले गेस्ट वाले 60 प्रतिशत CPU वाले होस्ट के समान दिखता है।

**गेस्ट और होस्ट माप अलग-अलग सवालों के जवाब देते हैं।** केवल गेस्ट उपयोग होस्ट शेड्यूलिंग विलंब की व्याख्या नहीं कर सकता है। होस्ट लोड से एट्रिब्यूशन प्राप्त करने के बजाय हाइपरवाइज़र विवाद मेट्रिक्स के साथ गेस्ट/एप्लिकेशन मापों को सहसंबंधित करें।

### इसके बजाय क्या करें

| प्रश्न | उत्तर कहाँ है |
|---|---|
| क्या होस्ट संतृप्त है | होस्ट प्रोसेसर लोड, होस्ट से |
| क्या गेस्ट संतृप्त है | गेस्ट के अंदर, साथ ही हाइपरवाइज़र के पास मौजूद विवाद मीट्रिक |
| कितने गेस्ट चल रहे हैं | होस्ट गेस्ट इन्वेंट्री, एक संख्या के रूप में |
| क्या परिवेश क्षमता से अधिक है | इन ग्राफ़ों से नहीं। इसके लिए प्लेसमेंट डेटा की आवश्यकता है जिसे होस्ट उजागर नहीं करता |
| क्या कोई गेस्ट स्थानांतरित हुआ | हाइपरवाइज़र इन्वेंट्री पहचान और माइग्रेशन ईवेंट; केवल गिनती कदम अपर्याप्त हैं |

गेस्ट के बारे में किसी भी चीज़ के लिए गेस्ट को उनके अपने उपकरणों के रूप में मॉनिटर करें, और होस्ट के बारे में किसी भी चीज़ के लिए होस्ट को मॉनिटर करें। होस्ट-स्तरीय संख्याओं से प्रति-गेस्ट ग्राफ़ बनाने से बचें: वे व्युत्पन्न होते हैं, वे आधिकारिक दिखते हैं, और वे ऐसे तरीकों से गलत होते हैं जिन्हें बाद में कोई नहीं पहचान सकता।

## शामिल गेस्ट गणना में जाल (ट्रैप्स)

गेस्ट इन्वेंट्री स्क्रिप्ट के आउटपुट पर भरोसा करने से पहले उसे समझना उचित है।

**यह केवल SNMP संस्करण 1 और कम्युनिटी स्ट्रिंग के साथ चलता है।** संस्करण स्क्रिप्ट में तय है और डिवाइस पर v3 क्रेडेंशियल पास नहीं किए गए हैं। v3 के लिए कॉन्फ़िगर किया गया डिवाइस अन्य पथों के माध्यम से एकत्र हो सकता है जबकि गेस्ट संग्रह विफल हो जाता है। गेस्ट संग्रह अभी भी सफल हो सकता है यदि वह एजेंट स्वतंत्र रूप से v1 पर संग्रहीत कम्युनिटी को स्वीकार करता है; डिवाइस पर v3 का चयन करना अपने आप में परिणाम निर्धारित नहीं करता है। खाली गेस्ट वॉक शून्य के रूप में लौटाए जाते हैं। सहायक को समायोजित करने के लिए एजेंट की सुरक्षा नीति को डाउनग्रेड किए बिना इस प्रोटोकॉल बेमेल की जाँच करें।

**गणना पावर स्थिति तालिका से आती है।** गेस्ट कुल के रूप में रिपोर्ट की गई संख्या पावर स्टेट सबट्री के वॉक द्वारा लौटाई गई प्रविष्टियों की संख्या है, न कि किसी अलग इन्वेंट्री ऑब्जेक्ट की। एक गेस्ट जिसे होस्ट सूचीबद्ध करता है लेकिन जिसकी कोई पावर स्टेट प्रविष्टि नहीं है, उसकी गणना नहीं की जाती है।

**पावर्ड-ऑन का मिलान स्थिति पाठ पर किया जाता है।** ट्रिम करने और लोअरकेस करने के बाद, केवल `powered on` और `poweredon` ही चालू गणना को बढ़ाते हैं। अन्य प्रतिनिधित्व नहीं करते; शून्य की व्याख्या करने से पहले कच्चे एजेंट प्रतिक्रिया की तुलना करें।

**गेस्ट टूल्स वर्गीकरण में एक पुष्ट दोष है।** शाब्दिक `not installed` को चालू के रूप में गिना जाता है क्योंकि इसका मिलान ऑफ़सेट शून्य से शुरू होता है। अपरिचित पाठ भी चालू होने के रूप में माना जाता है। उस गणना को स्वस्थ टूल्स के प्रमाण के रूप में न लें; [टूल्स-स्थिति बग](https://github.com/kadupulhq/kadupul/issues/244) देखें।

**यह प्रति कॉल तीन बार चलता है।** यह पावर-स्टेट तालिका को दो बार पढ़ता है, फिर टूल्स तालिका को, इसलिए इसकी अपनी गणना भी एक परमाणु इन्वेंट्री स्नैपशॉट नहीं है। कई गेस्ट वाले होस्ट पर, उस संग्रह लागत को मापें। यदि पोलर तंग है, तो थ्रेड्स बढ़ाने से पहले यह एक लंबा अंतराल रखने का उम्मीदवार है। [पोलर को स्केल करें](/hi/guides/scale-the-poller/) देखें।

स्क्रिप्ट सामान्य रूप से सभी पाँच नामित मानों का उत्सर्जन करती है, जिसमें खाली वॉक के लिए शून्य भी शामिल हैं। इसलिए एक असफल वॉक वाक्यात्मक रूप से पूर्ण लेकिन भ्रामक नमूना दे सकता है। अपूर्ण आउटपुट के लिए, PHP आउटपुट प्रोसेसर संबंधित डेटा स्रोत द्वारा आवश्यक फ़ील्ड की जाँच करता है और अपूर्ण टाइमस्टैम्प समूहों को रोकता है; यह आवश्यक रूप से उन्हें तुरंत नहीं हटाता है। [पोलर कैश](/hi/concepts/the-poller-cache/) देखें।

## बाकी हिस्सों में जाल

**प्रोसेसर औसत असंतुलन को छुपाता है।** 1 अत्यधिक उपयोग वाले कोर और 63 निष्क्रिय कोर वाला होस्ट कम औसत दिखाता है। जहाँ यह मायने रखता है वहाँ मान्य प्रति-प्रोसेसर ग्राफ़ बनाए रखें। औसत सहायक खाली वॉक के लिए `load:0` भी लौटाता है, जो मापे गए निष्क्रिय CPU से अप्रभेद्य है; इसे संग्रह स्थिति और ज्ञात खाली-परिणाम बग के साथ सहसंबंधित करें।

**प्रोसेसर इंडेक्स स्थितीय होते हैं।** वे प्रोसेसर तालिका को स्कैन करके खोजे जाते हैं। यदि एजेंट इंडेक्स बदलते हैं, तो निरंतरता पर भरोसा करने से पहले पहचान मैपिंग सत्यापित करें। पैक किया गया एक-/दो-अंकीय प्रतिबंध एक अलग खोज दोष है।

**स्टोरेज प्रविष्टियाँ वही हैं जिन्हें एजेंट स्टोरेज कहता है।** उन आवंटन इकाइयों में अवांछित चीज़ों के साथ मिश्रित डेटास्टोर की अपेक्षा करें जिन्हें गुणा करने की आवश्यकता है। यह Host Resources का व्यवहार है, ESXi की कोई विचित्रता नहीं। बाइट्स की व्याख्या करने से पहले कैश्ड आवंटन इकाइयों को सत्यापित करें; अमान्य नकारात्मक नमूनों या अनुपलब्ध गुणकों के लिए साझा स्क्रिप्ट में एक [ज्ञात रूपांतरण दोष](https://github.com/kadupulhq/kadupul/issues/243) है।

**हाइपरवाइज़र पर इंटरफ़ेस के नाम तब तक स्थिर रहते हैं जब तक वे बदल नहीं जाते।** ड्राइवर अपडेट या पुनर्गठन उन्हें पुनः क्रमांकित कर सकता है। इंडेक्स कैसे चुना जाता है और यह क्यों मायने रखता है, इसके लिए [स्विच की निगरानी करना](/hi/guides/monitor-a-switch/) देखें।

**स्क्रिप्ट पोलर होस्ट पर चलती हैं।** वे कैश्ड कमांड द्वारा पारित डिवाइस ID का उपयोग करके स्वयं हाइपरवाइज़र तक पहुँचती हैं। गेस्ट और CPU-औसत सहायक प्रत्येक कॉल पर वर्तमान डिवाइस पंक्ति लाते हैं; कम्युनिटी परिवर्तन के लिए उन कमांड तर्कों के पुनर्निर्माण की आवश्यकता नहीं होती है। अन्य संग्राहक अपने कार्य मदों में क्रेडेंशियल एम्बेड कर सकते हैं। [पोलर कैश](/hi/concepts/the-poller-cache/) देखें।
