:::caution[使用前请先验证]
源代码已公开，但目前尚无受支持的 Kadupul 发行版或迁移路径。在依赖这些步骤
之前，请在带有备份的隔离副本上进行测试。参见[项目状态](/zh-cn/project/status/)。
:::

首先给出一个坦诚的忠告：请将系统部署在 VPN 之后。Kadupul 以明文形式存储了您所监控的每台设备
的 SNMP 凭据，并且在其正常运作过程中会在自身主机上执行系统命令。没有任何一种配置可以让它安全地
直接暴露在公共互联网上。

以下检查项有助于评估隔离的安装环境。它们并不代表受支持的或绝对安全的公网部署方案；在解读检查结果时，
请务必结合上文关于项目状态的限制说明。

## TLS

在 Web 服务器或其前端的反向代理上终结 TLS 连接。Kadupul 自身不会独立监听网络套接字。

随后开启将普通 HTTP 请求强制重定向至 HTTPS 的设置。该选项默认处于关闭状态（`off`）。
如果不开启，登录表单将通过明文 HTTP 提供服务，密码将在跨网络传输时完全暴露，使其他后续保护措施失去意义。

当 PHP 接收到非空且不为 `off` 的 `$_SERVER['HTTPS']` 变量时，应用程序会在会话 Cookie 上设置 Secure 标志。
在终结 TLS 的反向代理后方，请正确配置受信任的 Web 服务器或 FastCGI 层以如实传递 HTTPS 状态，并在浏览器中验证
最终生成的 `Set-Cookie` 响应头。

`$proxy_headers` 用于控制客户端真实 IP 地址的解析。它既不会设置 HTTPS 服务器变量，也不会自动启用 Secure Cookie。
务必仅信任由您的代理服务器写入的地址头，剥离客户端自行传入的伪造头部，并阻断对后端的直接网络访问。在公网反向代理
处即强制执行 HTTP 到 HTTPS 的重定向，确保在传输任何凭据前已建立加密连接。

应用程序为其会话 Cookie 设置了 HttpOnly 和 SameSite=Strict 属性。请在部署边界验证实际的 Cookie 和重定向表现；
这些标志的存在并不能保证所有其他 Cookie 也遵循相同的安全配置。参见
[PHP 会话配置手册](https://www.php.net/manual/en/session.configuration.php)。

## 默认凭据

系统内置的初始模式中包含一个名为 `admin` 的管理员账户，其初始密码哈希为字符串 `admin` 的 MD5 值。该账户被
标记为在首次登录时必须强制修改密码。请通过实际操作确认密码修改已生效，切勿仅凭假设。在 Web Basic 身份认证下，
该强制修改提示会被跳过，因为 Web 服务器在此之前已经确认了用户的身份。

接下来请检查那些非用户账户的凭据：

- 随附的配置模板中，数据库账户默认设置为 `cactiuser`，密码亦为 `cactiuser`。
- 自动化子系统附带了默认的 SNMP 选项，包含团体名 `public` 和 `private`，以及一组 SNMPv3 用户名和密码。
  这些属于自动扫描发现的默认值，并非您的实际设备配置，但却是网络发现模块首先尝试使用的凭据。

密码策略是可配置的。默认策略要求至少八个字符并混合大小写。密码过期机制和多次失败后的账户锁定功能均已提供，
但默认情况下两者都处于关闭状态。在面向互联网的环境中，必须启用账户锁定。

## 数据库权限

安装文档示例中使用了限定在数据库范围的权限以及对时区数据表的访问权限。请替换这些示例性的账户名和数据库名，
并针对实际的部署和维护操作逐一审计授权：

```sql
GRANT ALL ON kadupul.* TO 'someuser'@'localhost';
GRANT SELECT ON mysql.time_zone_name TO 'someuser'@'localhost';
```

第二项授权并非可选项。时区转换处理需要读取该表，安装程序会校验对该表的读取权限及其中已导入的时区数据。
在撤销权限前，请对照实际的系统维护和采集器要求核对各项补充授权；本示例并不意味着每个部署环境所需的权限都完全一致。

需要重点关注的作用域说明：

- 将数据库绑定到 localhost 或内网专用接口，绝不要绑定到 Web 服务器对外开放的地址。
- 为每个远程数据采集器分配独立的数据库账户。它们的凭据同时保存在中心数据库和各自的本地配置文件中；独立账户便于行为审计与定向权限撤销。不过，如果采集器被攻破且其账户拥有写入中心库的权限，仅靠独立账户本身并不能实现安全隔离。
- 数据库连接支持 TLS，可在配置文件中指定客户端密钥、证书和 CA 证书路径。只要数据库与应用程序不在同一主机上，就必须启用 TLS 连接。
- 确保配置文件对 Web 服务器运行账户可读，且在正常运行期间对 Web 用户和轮询器服务用户均不可写。应将其所有者设置为系统管理账户。远程轮询器的配置流程会特意检查自身能否修改该文件；切勿假设每台主服务器的安装都需要长期保留同样的临时写入权限。
- CSRF 防护密钥可以保存在文件中而非数据库中。如果使用该选项，该文件必须放置在 Web 根目录（document root）之外。这是一项硬性安全要求，而非建议。

## 将数据目录置于 Web 根目录之外

在以仓库根目录直接部署的架构中，私有数据和源码目录可能会暴露在 Web 服务根路径之下。若干子目录虽然包含
`.htaccess` 访问拒绝规则；但仍需实地核对检出环境和服务器配置，而不能假定所有路径都已被妥善保护。目前正在
推进的部分框架迁移也意味着，若在缺少遗留路由支持的情况下直接将整个站点切换至 `public/`，并不能构成一个完整的可用部署方案。

这些保护规则仅在 Apache 上有效，且必须在主配置明确允许该目录下使用覆盖（override）时才会生效。在 Nginx 上它们完全不起作用。
在配置不当的 Apache 上它们同样形同虚设。日志目录前端失效的访问阻断意味着任何人都能直接下载并阅读您的应用程序日志，
其中泄露了设备名称、用户账号、查询语句以及详细的错误信息。Apache 在其
[`.htaccess` 指南](https://httpd.apache.org/docs/2.4/howto/htaccess.html)中阐明了所需的覆盖行为规范。

必须同时落实以下两点：

**在迁移数据前核验存储路径。** 日志输出目标是可配置的，但 `include/global.php` 将 RRA 根基路径硬编码为安装环境下的 `rra` 目录；
系统 UI 中并没有通用的 RRA 目录配置项。单独挂载的存储结构虽然能够保留该预期路径，但仅凭文件系统层面的存放位置并不能阻止通过
公开目录或软链接发起的 HTTP 访问。请将现有数据源路径、服务权限、备份流程与 HTTP 访问封锁统筹考虑。切勿在没有核实消费端如何解析
文件的情况下擅自迁移缓存目录树。参见[迁移到新硬件](/zh-cn/guides/migrate-to-new-hardware/)与[安全升级](/zh-cn/guides/upgrade-safely/)。

**在 Web 服务器层拒绝访问私有路径。** 根据实际部署的 URL 前缀和服务器环境，改造源码中提供的
[仓库根目录 Nginx 示例配置](https://github.com/kadupulhq/kadupul/blob/661a57ff43ebf275e6b07211d4284dd727103959/tests/e2e/nginx.conf)；
拒绝规则必须优先于通用的 PHP 处理逻辑。下表仅用作排查盘点的参考，并非开箱即用的服务器配置：

| 目录路径 | 封锁原因 |
|---|---|
| `rra/` | 原始度量数据文件 |
| `log/` | 应用程序日志，包含查询细节与异常报错信息 |
| `cache/` | 审查预期的静态资源访问；严禁在缓存路径下执行任何 PHP 脚本 |
| `scripts/` | 数据采集代码绝不能通过 HTTP 直接对外提供或调用 |
| `cli/` | 仅限本地调用的命令行工具，不应暴露在 Web 端 |
| `mibs/`、`contrib/`、`docs/` | 内部资源与文档 |
| `src/`、`config/`、`templates/`、`var/`、`lib/`、`bin/`、`tests/`、`tools/` | 应用程序核心内部逻辑、状态数据及开发工具 |
| 点开头的隐藏文件、依赖清单、内部 include/bootstrap PHP 文件 | 代码仓库元数据与内部执行入口 |

保留必要的公开前端资源，例如 `include/js` 和 `include/themes`；对 include 目录一刀切的全面封锁将导致前端界面损毁。
使用安全的测试路径验证阻断效果，并确认 HTTP 响应中绝不泄露源代码或真实文件内容。切勿通过直接请求真实机密信息来测试终端或日志。

系统还提供了一个可选的安全响应头配置文件，用于静态资产。PHP 动态响应是在代码中自行注入安全头的；静态文件则不会携带这些头，
除非您启用了该配置文件，或在 Web 服务器主配置中显式写入了相同的指令。

内容安全策略（CSP）支持自定义配置。默认的脚本策略允许无 nonce 的内联 JavaScript 执行，因为现有插件高度依赖于此。设置中提供的
更严格的 nonce 模式目前仅工作在报告（report-only）模式下。尽管[设置页面的帮助信息已过时](https://github.com/kadupulhq/kadupul/issues/265)，
响应头实现逻辑其实也支持强制 `nonce` 执行。强制执行与纯报告模式完全不同；在切换模式之前，务必审查响应头并在所有业务页面及插件
上完成充分测试。已实现强制代码并不代表系统已具备完整的 nonce 兼容性。

## 轮询器具备命令执行能力

这是从根本上改变系统威胁模型的关键所在。

数据采集并不局限于 SNMP。数据输入方法（Data Input Method）可以定义任意命令行，并由轮询器负责调用执行。该命令行保存在轮询器
缓存中，并在每个采集周期由采集器以其所在操作系统的服务用户身份执行。PHP 脚本服务器输入则依托一个长期驻留的独立 PHP 进程。
外部命令与脚本服务器是完全不同的执行链路；切勿盲目假定所有脚本都会在该服务器内部安全运行，也不要认为本版本的 C 采集器已经过充分验证。

请将以下各项权限视为具有极高风险的代码执行配置入口。它们的具体破坏力取决于当前已开启的功能和输入校验控制：

| 权限名称 | 风险成因 |
|---|---|
| 数据输入方法 | 直接定义要执行的命令行指令 |
| 导入模板 | 导入的模板或数据包中可能潜藏恶意的数据输入方法 |
| 插件管理 | 插件代码直接在应用程序上下文中运行 |
| 设置 / 实用工具 | 控制系统调用各类二进制可执行程序的绝对路径 |

切勿将上述权限授予任何在轮询器主机上尚未拥有系统 Shell 访问权限的人员。仅具备图表查看权限的只读用户则完全处于不同的安全层级，
而这也正是绝大多数账号应当拥有的最小权限。

系统提供了两道防线，且都极具实用价值：

**元字符限制。** 数据输入命令字符串中的 Shell 元字符默认处于阻断状态。系统中虽然存在允许使用元字符的配置项（主要是为兼容早期
包含管道命令的旧配置），但请务必保持其关闭。如果您现有的定义必须依赖管道，请将整个管道封装进 scripts 目录下的独立脚本中，
然后直接调用该脚本。

**输入白名单。** 在主配置文件中指定一个白名单文件，其中按数据输入方法记录经过审批的命令字符串。配置该文件后，系统将禁止基于
未列入白名单的命令字符串创建新的图表和数据源。一旦已批准的命令被篡改，比对校验便会失败，直到管理员重新审核并更新白名单。
重新生成白名单必须在命令行中完成，而这正是其精髓所在：它必须拥有主机的 Shell 权限，无法仅通过浏览器管理员会话伪造。

当重建轮询器缓存时，白名单校验会再次运行。校验未通过的数据输入项将无法生成任何轮询任务，且其残留的数据行会在下一次提交重建/刷新时
被清理。这一机制把守着创建和缓存填充环节；但它并非针对正在运行任务的即时中断手段，也不能证明每个采集器在每次执行前都会重新加载
已更改的白名单。策略变更后，必须仔细核验已提交的缓存状态和采集器的实际行为。

```sh
php cli/input_whitelist.php --audit
# After reviewing this data input's command; 42 is an example data-input ID.
php cli/input_whitelist.php --update --id=42
```

未加范围限制的 `--update` 命令会无差别地将当前所有命令定义直接录入白名单；切勿用它替代人工审计。保护白名单文件及其父目录，
严禁服务运行用户对其拥有写权限。除非显式配置，否则该功能处于关闭状态。关于命令选取与输出格式的细节，参见
[编写数据采集脚本](/zh-cn/guides/write-a-data-collection-script/)。
这极大地抬高了攻击者通过浏览器端管理权限实施入侵的门槛，因为将恶意命令植入采集流程现在还需要攻破轮询器主机的文件系统写权限。
不过，它依然不能取代对上表所述高危权限的严格管控，因为攻击者如果能够利用已获批的命令字符串，就根本无需添加新的命令。

## 身份认证

系统提供了四种认证方式。具体可用性取决于环境中已安装的 PHP 扩展。

| 认证方式 | 用户凭据验证位置 | 说明事项 |
|---|---|---|
| 内置认证 | 本地数据库 | 密码存储、密码复杂度策略和失败锁定均在本地处理 |
| Web Basic 认证 | Web 服务器 | Kadupul 直接信任由 Web 服务器传递的用户身份信息 |
| LDAP | 单一目录服务 | 依赖 PHP LDAP 扩展 |
| 多 LDAP/AD 域 | 多个目录服务 | 依赖相同的 PHP LDAP 扩展 |

“设置”中的认证选择器仅展示这些经过认证的模式，不再提供废弃的“模式零”（无身份认证模式）。认证引导流程会尝试将旧版的无认证配置
迁移回本地认证模式，但底层授权逻辑中仍残留针对模式零的分支判断。请务必核实保存的认证方式、已配置的用户身份以及实际受保护的路由，
而不要将界面选项的缺失视为系统绝对安全的普遍证明。

需要逐一核实的关键点：

- **Web Basic 认证将身份校验完全委托给了外部。** 选中此模式时，Kadupul 会读取经 Web 服务器认证的身份变量，但仍会执行本系统的账户映射、启用状态及授权规则校验。未传递身份变量的请求绝不会自动获得管理员权限。请正确配置 Web 服务器以认证所有预期路由，严禁客户端自行伪造并提交受信任的身份变量；针对图片展示、数据导出路由以及明确允许的访客行为，必须单独进行安全验证。
- **“保持登录状态”功能默认处于开启状态。** 只有当用户在认证后主动勾选该选项时，系统才会生成持久化令牌，而不是为每个会话盲目创建。该令牌在连续 90 天未使用后会自动失效。在面向互联网的部署中，请谨慎权衡是否需要保留该特性。
- **将访客用户（guest user）设置为 nobody（空）**，除非您确实需要允许匿名查看监控图表。默认情况下系统未分配访客用户，这是最为稳妥的默认值；请核实该设置在部署过程中未被意外改动。
- **在整个系统前端部署多因素认证（MFA）。** 本应用程序内部未实现 MFA。请务必通过前置的身份感知代理（Identity-Aware Proxy）或 SSO 单点登录网关来提供 MFA 保护。

## 远程数据采集器接口

如果您部署了远程采集器，中心节点会暴露一个供它们调用的网络接口。该接口不依赖用户会话进行认证。它通过解析发起调用的客户端 IP，
并与已注册采集器的主机名列表进行匹配来进行授权，失败的调用会被记录在安全类别的日志中。

由此引出两点安全要求。首先，该接口绝不应该对公网开放；必须在 Web 服务器层设置白名单，仅允许合法的采集器 IP 访问。其次，系统校验
的客户端地址是由请求头推导而来的，因此前面提到的转发头部（forwarded-header）信任配置在此处同样适用。如果您盲目信任未受完全控制
的代理头部，攻击者便能够轻松伪造采集器的来源地址。

此外，当中心服务器与远程采集器通信时，默认允许使用自签名证书以及忽略主机名不匹配。请为您的所有采集器签发合法证书，并关闭该宽容选项。

## 最低安全清单

1. 必须终结 TLS，在登录页面加载前强制将 HTTP 重定向至 HTTPS，由受信任的服务器正确设置 PHP HTTPS 状态，并核验 Secure Cookie。客户端 IP 头部仅限代理明确添加和清洗后的字段。
2. 默认的 admin 密码必须修改并完成验证。开启账户锁定策略。
3. 针对安装、维护及采集器角色严格审计数据库授权；核实时区数据访问权限，并将数据库的网络访问限制在必要的客户端范围内。
4. 校验实际存储路径，在 Web 服务器层严密封锁私有目录与仓库元数据，同时确保合法的公开静态前端资源工作正常。
5. 配置文件在运行时必须保持只读。若启用了 CSRF 密钥文件，该文件必须位于 Web 根目录之外。
6. “数据输入方法”、“导入模板”和“插件管理”权限绝不授予未在轮询器主机上拥有 Shell 权限的任何人。开启元字符过滤。配置输入白名单。
