:::caution[使用前に検証してください]
ソースコードは公開されていますが、サポートされている Kadupul のリリースや移行パスはまだ存在しません。本運用で依存する前に、バックアップを備えた隔離された環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

アップグレードでは、異なるタイミングで、異なる可逆性を持つ3つの要素が変更されます。

| 変更対象 | 可逆性 | 方法 |
|---|---|---|
| コード、依存関係、および設定 | 保持されたコピーから復元可能 | 一致するリビジョンと設定を復元する |
| データベーススキーマとキュー内サンプル | 一致するバックアップから復元可能 | データベースを復元する（自動逆マイグレーションは存在しません） |
| RRD ファイル | 一致するバックアップから復元可能 | 保持された履歴を復元する（バックアップにないサンプルはロールバックで再生成できません） |

この手順は、これら3つの歩調を合わせるために存在します。

## 開始する前に

**完全なバックアップを取得する。** 3つの部分すべてを互いに整合した状態で取得します。[バックアップと復元](/ja/guides/back-up-and-restore/)に従ってください。最終キャプチャの前にすべてのライターを停止し、アップグレードの検収が完了するまで保護されたバックアップを保持します。

**現在のリビジョンとスキーマバージョンを記録する。** 依存関係、ローカルの変更、プラグイン、設定を含めます。複数のソースリビジョンが同じスキーマバージョンを報告することがあります。隔離された復元コピーに対してターゲットリビジョンのリハーサルを行ってください。

**すべてのプラグインを確認する。** 互換性宣言、コード、依存関係を検査し、必要な機能をターゲットリビジョンに対してテストします。最低バージョンの宣言だけでは互換性は保証されません。[プラグインの検証](/ja/guides/install-and-vet-plugins/)を参照してください。

**ランタイムを確認する。** PHP のバージョン、PHP 拡張モジュール、およびデータベースサーバーのバージョンを確認します。デプロイ前にターゲットの[システム要件](/ja/reference/requirements/)を確認してください。スキーマ CLI が Web インストーラーのすべてのチェックを実行すると想定しないでください。

**データベースアカウントがスキーマを変更できることを確認する。** 通常の稼働時、アカウントには自身のデータベース内での読み取りおよび書き込み権限が必要です。アップグレード時には、テーブルやインデックスの作成、変更、削除も行える必要があります。セットアップ後に権限を絞り込んだ環境では、この段階で問題が発覚します。

**すべてのプロデューサーを停止する。** スケジュールされた収集、リモートコレクター、Web トリガーによる収集、および手動メンテナンスを停止し、処理中の作業が完了するのを待ちます。プロデューサーが停止した後にのみ遅延書き込みをドレインし、未承認のキュー行を一致するバックアップとともに保護します。デプロイとスキーマ検証の間、プロデューサーを停止したままに保ちます。

## アプリケーションの置き換え

上書きコピーには特有の制限があります。

```bash
# Copies the contents of the new tree over the old one.
cp -a /path/to/new-release/. /path/to/kadupul/
```

末尾のドットがない場合、`cp -a /path/to/new-release /path/to/kadupul` は `kadupul/new-release/` を作成し、古いアプリケーションのすべてのファイルを元の場所にそのまま残してしまいます。アップグレードが成功したように見え、インターフェースは古いコードを実行し続け、最初のトラブルの兆候は、置き換えたはずのバージョンとの一致をスキーママイグレーションが拒否することになります。

上からの上書きコピーは、不要になったアプリケーションファイルを含め、新しいツリーに存在しないファイルをそのまま残します。また、一致するパスをすべて上書きする可能性があるため、設定やデータが除外されていると思い込まずに成果物を確認してください。一致する依存関係、設定、プラグインを備えたレビュー済みのステージングツリーを使用することをお勧めします。シンボリックリンク経由でリリースを切り替える場合は、切り替え前に有効な RRA パスとストレージアクセスを検証してください。現在のブートストラップはアプリケーションディレクトリに `/rra` を追加して導出します。シンボリックリンクの切り替えだけではデータベースのロールバックにはなりません。

**先へ進む前に、実際に実行されているものを確認してください。**

```bash
cat /path/to/kadupul/include/cacti_version
```

デプロイしたばかりのリリースが報告されない場合は、作業を中止してください。この時点以降のすべては、目的のコードがデプロイされていることを前提としています。また、ソースリビジョンや成果物のチェックサムをリリース記録と比較してください。バージョン文字列単体では不十分です。

## スキーママイグレーション

データベースは、コード内のバージョンとは別に独自のバージョンを保持しています。コードを置き換えても、それは変更されません。

コードとデータベースのバージョンが一致しない場合、従来の認証済みページはインストーラーにリダイレクトされます。これはすべてのエンドポイントや CLI に対する普遍的な保護ではなく、バージョン文字列の一致がすべてのマイグレーション完了を証明するわけでもありません。スキーマの状態を直接確認してください。

インストーラーと CLI は、順序付けられたマイグレーション手順を実行します。通常のスキーマアップグレードの前に、永続キューとサービスアカウントのストレージアクセスを確認してください。継承された `poller_output` キューが InnoDB でない場合は、ライターを停止しバックアップを保持した状態で、明示的に変換します。

```sh
php cli/upgrade_database.php --migrate-poller-queue
```

次に、実際のすべての Web アカウントおよびポーラーアカウントの下でこれを実行します。

```sh
php cli/upgrade_database.php --check-rrd-storage
```

この2つのフラグは別個の操作であり、組み合わせることはできません。キュー変換は保留中のサンプルを保持します。チェックを通過させるために行を切り捨てないでください。[ストレージ要件](/ja/reference/requirements/)を使用して、所有権と数値による信頼された UID/GID 設定を解決してください。オンラインのリモートコレクターは通常メインキューを選択します。意図的なローカルキューの確認または変換を行う場合にのみ `--local` を使用してください。これらのチェックに合格したら、アプリケーションルートからスキーマアップグレードを実行します。

```sh
php cli/upgrade_database.php
```

必要なファイルシステムアクセスとデータベース権限を持つ、設定されたサービスアカウントとして実行してください。root でのチェック成功は、サービスアカウントのアクセスを証明するものではありません。プレリリーステスト中にマイグレーションを再実行するために、開始バージョンを明示的に設定する `--forcever` オプションが存在します。これは通常のアップグレードの一部ではなく、失敗したステップをスキップするためにこれを使用すると、スキーマが中途半端に移行された状態になります。

終了ステータスと出力を記録し、データベースバージョンと必要なスキーマ変更を検証します。現在の CLI は、未知またはサポートされていないレガシーの開始バージョンを拒否しながらも終了コード 0 を返すことがあるため、シェルステータスの成功単体では不十分です。マイグレーションが途中で失敗した場合は、プロデューサーを停止したままにし、失敗したステップをスキップしようとするのではなく、一致するバックアップセットを復元してください。

## プラグインが機能しなくなる要因

Web インストーラーのプラグインチェックにより、互換性のないプラグインや欠落しているプラグインが無効化されることがあります。スキーマ CLI が同じプラグインライフサイクルチェックを実行すると想定しないでください。

**宣言された最低バージョンが新しいコアバージョンより高い場合。** 無効化されます。これは通常のケースであり、アップグレード前のチェックで検出されるべきものです。

**プラグインディレクトリ、そのセットアップファイル、または宣言ファイルが見つからない場合。** 無効化されます。データベース内で有効とマークされたままファイルが削除されたプラグインがこれに該当します。

**プラグインに宣言ファイルがまったくない場合。** インストーラーの互換性チェックに失敗する可能性があります。変更せずに再度有効化できると思い込まず、保守されている互換性のあるプラグインパッケージをテストしてください。

機能不全ではない第4のケースがあります。かつてプラグインであり、その後コアに統合された機能は、無効化されるのではなく完全に削除されます。フックと権限エントリが削除され、その行は削除されます。プラグインがグレー表示になるのではなく消えてしまった場合は、同等の機能が利用可能であると結論付ける前に、マイグレーションログと該当プラグインの扱いを確認してください。

プラグインの無効化はアンインストールとは異なります。プラグインのフックとマイグレーションは独自のテーブルと権限を変更する可能性があります。一致するプラグインコードとデータを保持し、特定のアップグレードパスを確認してください。無条件のデータ保持を保証しないでください。

## ロールバックの計画

どこまで進んだかによって判断が異なるため、開始する前にロールバック方針を決めておきます。

| 障害発生時点 | ロールバック方法 |
|---|---|
| コードが置き換えられたが、状態を変更する操作やライターは実行されていない | 状態が変更されていないことを確認後、以前のコード、依存関係、設定を復元する |
| キュー変換またはマイグレーションが開始された（部分的な失敗を含む） | ライターを停止し、一致するコード、設定、データベース、RRD バックアップを復元する |
| マイグレーションが完了したが、アプリケーションが不正な動作をする | ライターを停止し、一致するバックアップセットを復元する（バックアップ後に収集されたサンプルを考慮する） |
| プラグインのみが破損している | プラグインを無効にしたまま、受け入れ基準に照らして修復か連携ロールバックかを評価する |

表の下にある鉄則: コードとスキーマは一緒にロールバックするか、まったくロールバックしないかのどちらかです。新しいスキーマに対する古いコードの組み合わせは、サポートされている状態ではありません。互換性のないすべての操作を防ぐために Web のバージョンチェックだけに依存しないでください。

タイムボックス（制限時間）を設けてください。復元を行うまでに調査に費やす時間をあらかじめ決めておき、それを守ってください。システムが中途半端にアップグレードされた状態で稼働する時間が長くなるほど、バックアップの有用性は低下します。

## なぜ RRD ファイルを決して失ってはならないのか

デプロイ、メンテナンス、または収集の再開によって RRD が変更されないと思い込まないでください。状態変更をロールバックする際は、データベースと一緒にバックアップを取得し、一致するセットを復元してください。保持されたキュー内のサンプルは、それらのファイル内にまだ存在していない可能性があります。検証済みの RRD バックアップは取得された履歴を復元できますが、欠落したサンプルはスキーマやコードを復元するだけでは再構築できません。内部の解像度も再構築できない理由については、[データソースとラウンドロビンアーカイブ](/ja/concepts/data-sources-and-rras/)を参照してください。

アップグレード中にこれらを失ってしまう3つの典型的なパターン:

**インストールディレクトリを置き換えてデプロイする。** RRA ディレクトリはデフォルトでインストールのサブディレクトリになります。古いディレクトリを削除してその場所に新しいディレクトリを展開すると、保持されていた測定値が削除されてしまう可能性があります。アプリケーションを置き換える前に、テスト済みのストレージ構成によって RRA ツリーを保護してください。有効な `$config['rra_path']`、ネストされたパス、およびサービスアカウントの信頼チェックを検証してください。このリビジョンでは、任意のローカル RRA ルートに対する汎用的なデータベース設定は提供されていません。

**ツリー全体を所有するチェックアウトまたはパッケージからデプロイする。** 自動化されているだけで同じ失敗です。デプロイ方法が何を削除可能とみなしているか確認してください。

**所有権の再帰的変更でパーミッションを修正する。** データ自体には害はありませんが、ポーラーが書き込めない状態になる可能性があり、履歴グラフは完全に描画されるのに新しいデータが一切収集されないシステムとなって現れます。

## アップグレード後

1. アップグレードの出力、データベースバージョン、必要なスキーマ変更を検査し、インターフェースが読み込まれることを確認します。リダイレクトがないこと単体では不十分です。
2. リモートコレクターのプロデューサーを停止したまま、計画されていたリモートコレクターのコード/設定のアップグレードを完了し、データベースの接続先を検証します。
3. サービスアカウントのストレージチェックを再度行い、指定されたコレクターを再開し、代表的な RRD の最終更新日時と使用可能な保持値を確認します。
4. ログで実行統計の行を確認し、所要時間を以前のものと比較します。新しいリリースによって収集コストが変化することがあります。
5. 新しいコアとの互換性を宣言しているバージョンをインストールした後、無効化されていたプラグインを1つずつ再度有効化します。
6. 合意された検収期間にわたって、保持キューの深さ、リモート収集、およびプラグインジョブを確認します。これらのチェックに合格するまで、ロールバック用のバックアップを保持してください。
