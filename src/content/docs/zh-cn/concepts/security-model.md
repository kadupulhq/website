监控系统在安全防护上是出了名棘手的，其原因与代码质量无关，而在于其本质特征：

它保存着它所监控的所有资产的凭据。SNMP Community、v3 用户名与密码短语，以及设备所需的其他认证信息都被存储下来，以便轮询器能够在无人值守的情况下使用它们。不可能有运维人员每隔五分钟手动输入一次密码。

它按计划周期性执行外部命令。要采集 SNMP 没有暴露的指标，就必须运行脚本，而这些脚本的定义本身就是配置数据，存储在数据库中并可通过 Web 界面直接编辑。

它吸收由其监控的机器所产生的数据。网络接口描述、磁盘挂载点、传感器名称：所有这些都来自设备，最终全部写入数据库、显示在图表标题中，并作为参数传递给底层程序。一台被黑客攻破的交换机不仅是受害者，更是不可信数据的输入源。

以上任何一点都不是软件缺陷，而是监控工作本身的内在要求。以下详细说明每一个环节在系统架构中的落脚点。

## 不信任输入从何处进入

共有四个入口点，大致按照操作员对其控制力的高低排列。

| 入口点 | 来源 | 数据流向 |
|---|---|---|
| HTTP 参数 | 任何能访问 Web 服务器的人 | 数据库、页面 HTML 输出及 SQL 语句 |
| SNMP 指标值 | 被轮询的被控设备 | `host_snmp_cache`、图表标题、RRD 边界值、脚本参数 |
| 脚本执行输出 | 本地脚本或其通信的目标对端 | `poller_output`，进而写入 RRD 文件 |
| 上传的模板与数据包 | 任何持有导入权限范围的用户 | 模板记录行，对于数据包还会写入磁盘文件 |

### HTTP 参数

请求处理辅助函数位于 `lib/html_utility.php`。`get_filter_request_var()` 默认执行整数验证，但对空值、未定义值和正则表达式匹配也设有特殊处理分支。调用方仍然必须自行核验某个输入值是否为必须且符合业务预期。过滤并不等同于授权。

`set_request_var()` 会将值缓存在 `$_CACTI_REQUEST` 中并镜像同步到请求数组中。`get_nfilter_request_var()` 读取该缓存或原始请求，其自身不对值进行任何校验或写入。因此，后续的读取可能会获取到先前保存的值，读取顺序具有决定性意义。

在启用 `log_validation` 的情况下，`get_request_var()` 会记录某些未命中的请求读取。直接访问超全局变量和 `get_nfilter_request_var()` 并不完全受其覆盖。这属于诊断辅助功能，而非完备的验证审计或安全执行措施。

### SNMP 指标值

数据查询发现机制将选定的索引值保存到 `host_snmp_cache` 中；常规的 SNMP 轮询结果则走采集样本通道。`lib/data_query.php` 中的 `data_query_format_record()` 在持久化前会执行两项转换：根据查询定义执行可选的 `rewrite_value` 映射，以及对任何无法被 `mb_detect_encoding()` 识别编码的值调用 `bin2hex()`。后者仅仅是为了防止二进制字节串破坏存储，并不是为了防御恶意注入攻击。

此后，该数值开始在系统内传递。它通过 `substitute_snmp_query_data()` 命名图表；它可以设定 RRD 的上限（Max），因为数据模板可以将上限声明为 `|query_ifSpeed|`；它还会作为参数传递给脚本查询，在此过程中 `get_script_query_path()` 会首先将各个分段传入 `cacti_escapeshellarg()`。

转义机制以及在 [RRDtool 集成](/zh-cn/reference/rrdtool-integration/) 中描述的 RRDtool 验证器构成了这里的防御边界。来自设备的数据必须始终保持不受信任。验证和转义是具体调用点的属性；辅助函数的存在并不证明每个消费方都正确地使用了它们。必须同时检查命令行结构与实际代入的参数。

### 脚本执行输出

`exec_poll()` 中的 `popen()` 分支通过 `fgets(..., 8192)` 读取数据，最多返回 8,191 字节或直到第一个换行符。其备选的 `shell_exec()` 分支具有不同的输出行为，而脚本服务器（Script Server）采集则遵循另外的执行路径。

`prepare_validate_result()` 能够识别数值型和未知（Unknown）数值、十六进制形式以及某些多字段输出格式。它还可以剥离非数字文本以提取数值；但它绝非通用严格的标量过滤器。后续的解析逻辑和 RRDtool 验证同样至关重要。请参阅 [数据输入方法](/zh-cn/reference/data-input-methods/)。

输出检查无法为已经执行完毕的脚本提供沙箱隔离。在启用采集之前，必须先审查命令内容、输入白名单以及操作系统的执行特权。

### 模板与数据包

两种不同的机制共享同一个权限范围。

**模板导入**是未签名的纯 XML 文本。它会创建模板、数据查询和数据输入方法。数据输入方法本质上就是命令行，因此这是一条从上传文件直接通向轮询器执行命令的通道。`lib/import.php` 会对任何导入的 `input_string` 调用 `cacti_input_string_is_safe()`，并在其包含 Shell 元字符时拒绝该方法并输出日志：

```
ERROR: Refusing to import data input method '<hash>' - input_string contains shell metacharacters
```

**数据包导入**带有数字签名。`import_read_package_data()` 读取数据包内嵌的公钥，并将其与编译在 `lib/import.php` 中的三把公钥进行对比：两把 Cacti 密钥和一把 Kadupul 密钥。其他任何公钥都会验证失败。缺少 `<publickey>` 元素的数据包会被视为声明使用旧的 Cacti 密钥，且必须生成能被其验证的签名。`import_read_package_data()` 在尝试验证前会直接拒绝任何低于 2048 位的密钥，而 512 位的旧密钥无法通过这一门槛。数据包内包含的每个文件都带有独立签名并被单独校验。

通过验证的数据包随后可以写入特定文件。接受的文件路径必须以 `scripts/` 或 `resource/` 开头，或者可选地位于合法的 `plugins/<name>/` 前缀下。导入器会拒绝 NUL 字节、目录遍历和绝对路径，并严格检查其在安装根目录下的包含约束；仅包含某个目录名是不够的。目标目录的写权限同样决定写入是否成功。通过验证的数据包被设计为可将可执行的 PHP 写入安装目录树中。签名验证仅确立了受信任的签名身份和完整性，并不证明代码是无害的。权限范围授权、路径限制、目标文件、文件系统权限以及命令白名单策略同样至关重要。

这两种机制均受权限范围 17 的保护。预设的模板编辑员（Template Editor）角色同时持有权限范围 17 和权限范围 2（数据输入方法）。持有这些权限的账户可以定义采集命令，受制于验证规则与白名单机制。这就是该角色的设计初衷，在向用户授权前务必清楚这一点。有关经过验证的工作流程和已知局限性，请参阅 [导入与导出模板](/zh-cn/guides/import-and-export-templates/)。

## 哪些进程以何种特权运行

| 进程 | 启动方式 | 运行身份 | 职能 |
|---|---|---|---|
| Web 界面 | Web 服务器 | Web 服务器系统用户 | 读写数据库、通过 RRDtool 渲染图表、按需写入 RRD 文件、在导入期间写入数据包文件 |
| `poller.php` | 定时调度器或系统服务 | 调度器/服务账户 | 读取轮询器缓存、启动采集器、写入 RRD 文件 |
| `cmd.php` | 轮询器或实时采集通道 | 启动账户 | 执行 SNMP get 请求和外部采集命令 |
| `script_server.php` | 采集器 | 启动账户 | 包含 PHP 文件并在其自身进程中调用函数 |
| RRDtool | Web 进程或轮询器 | 启动它的对应进程用户 | 读写 `rra/` 目录下的文件 |

其中有两个组件尤其需要深入审视：

**脚本服务器并不是沙箱。** 它将目标脚本文件包含进一个长期驻留的 PHP 进程中，并在该进程内直接调用其函数。该函数共享整个进程、其内存空间以及其数据库连接。`script_server.php` 中的安全检查仅决定该调用是否被允许发生：被包含文件的 `realpath()` 必须解析在 `$config['base_path']` 或 `$config['scripts_path']` 之下、包含后目标函数必须存在、`ReflectionFunction::isInternal()` 必须为 false，且定义该函数的源文件也必须位于允许的根路径下。一旦这些检查通过，该代码将以轮询器的完全特权运行。脚本服务器方法是在 Kadupul *内部*执行 PHP 的一种途径，而不是在 Kadupul *旁边*运行隔离代码。

**Web 进程能够写入 RRD 文件。** 图表查看请求可能触发按需的 Boost 刷新和文件创建。将某一个目录创建操作委托给轮询器的警告并不意味着 Web 写入权限在全局范围内是可选的。存储预检与维护协调机制还会核查账户权限以及受信的数值型 UID/GID 配置。以 root 身份运行的创建尝试与存储属主匹配，但失败可能会被记录。请参阅 [安全升级](/zh-cn/guides/upgrade-safely/)。

Web 账户与计划轮询器账户可能不同。通过 Web 请求触发的实时采集可能会继承 Web 服务器账户，因此命令执行并不局限于计划轮询器的系统身份。继承的 Spine 集成需要针对实际二进制文件进行单独验证；本页面并不构成经过验证的构建指南。

## 数据库账户需要什么特权

使用相同数据库配置的进程通常共享其数据库账户。远程采集器可以拥有独立的本地和中央凭据；不同部署环境的配置可能有所差异。请仔细审查每个配置账户的实际权限授权。

| 权限要求 | 原因 |
|---|---|
| 对 Kadupul 架构的完全 DML 权限 | 日常监控业务运转 |
| 对 Kadupul 架构的 DDL 权限 | 软件升级，以及运行时的 Boost 表轮转、临时表操作和插件生命周期管理 |
| 对 `mysql.time_zone_name` 的 `SELECT` 权限 | 站点和数据采集器的时区列表直接查询该系统表 |

切勿因为假定只有升级过程才需要 DDL 权限而将其收回。应用程序并不会在全局范围内切换到单独的迁移身份；实现账户权限分离必须针对所有受影响的运行时执行路径进行环境特定的严格验证。

`include/config.php` 包含数据库凭据，远程采集器还可能持有中央 `$rdatabase_*` 凭据。文件系统权限、HTTP 访问规则、PHP 处理器配置以及备份保护都非常重要。PHP 通常会执行该文件而不是输出其源码，但这绝不能代替防止直接信息泄露的安全加固。请参阅
[保护面向互联网的安装](/zh-cn/guides/secure-an-internet-facing-install/)。

设备凭据以相同的方式存储。`host.snmp_community`、`host.snmp_password` 和 `host.snmp_priv_passphrase` 都是数据库普通列，由 `api_device_save()` 通过 `form_input_validate()` 写入，没有加密步骤，并直接复制到 `poller_item` 表行中供轮询器读取。对相关数据表的读取权限可能会泄露存储的设备凭据；但这并不意味着能直接访问所有外部凭据源。用户密码是一个例外：`compat_password_hash()` 使用 PHP 的 `password_hash()` 及 `PASSWORD_DEFAULT`，仍能通过验证的旧 MD5 哈希在用户下次登录时会被自动重新哈希升级。

## 代码强制执行与纯粹惯例约束

在评估代码变更时，这种界定最为重要。

### 代码强制机制及其作用范围

| 安全边界 | 防护机制 |
|---|---|
| 身份认证 | 通用界面页面使用 `include/auth.php`；专用端点有其自有的独立处理逻辑 |
| CSRF 防御 | 共享的 Web 引导程序配置令牌处理；格式错误的令牌数组会被拒绝。必须检查每个端点而非假定全局覆盖 |
| 仅限 CLI 的脚本 | 当 SAPI 不是 `cli` 时，`include/cli_check.php` 返回 `404` 并退出执行 |
| 数据查询 XML 位置 | `cacti_path_is_within()` 校验位于 `<base_path>/resource` 内，否则记录日志并拒绝 |
| 数据包真实性 | 针对内置公钥进行签名验证，至少 2048 位密钥，单文件独立签名 |
| 数据包文件放置 | 拒绝非法文件名；检查允许的 scripts/resource 前缀并确保严格限制在根目录内 |
| 脚本服务器调用目标 | `realpath()` 路径限制，加上上述函数内部校验 |
| Shell 命令参数 | 在适用的位置进行参数转义、结构化命令辅助处理和校验器；必须检查实际调用点 |
| RRDtool 参数 | `lib/functions.php` 中的控制字符及格式校验器 |
| SQL 注入防护 | 预编译辅助函数绑定参数值；动态 SQL、标识符拼接和未预编译调用仍需人工审查 |
| 远程代理调用方 | 源 IP 必须与 `poller` 表中启用的记录匹配（通过精确 IP 或前向反向解析双向确认） |

### 部署与调用点职责（纯惯例约束）

| 安全边界 | 为什么代码未强制执行 |
|---|---|
| 请求参数过滤 | 页面自行选择是否调用 `get_filter_request_var()`。`log_validation` 仅作报告，并不拦截阻断 |
| 输出内容转义 | `html_escape()` 与 `html_purify()` 依赖于各调用点显式调用 |
| 页面级授权控制 | 权限范围检查基于 `$user_auth_realm_filenames`（以文件名为键）。未映射的页面不会仅因该表获得正向授权。可能存在其他检查；插件页面必须自行注册并强制执行其访问策略 |
| 目录访问封禁 | `cli/`、`log/`、`rra/`、`scripts/`、`contrib/`、`mibs/` 和 `cache/*` 下的 `.htaccess` 是 Apache 指令。在 nginx 或禁用了 `AllowOverride` 的 Apache 下均完全失效 |
| 静态文件安全响应头 | `.htaccess.dist` 发布时未重命名。PHP 响应头发送取决于响应路径与设置；静态资源响应取决于实际的 Web 服务器/反向代理配置 |
| Web 与轮询器系统用户分离 | 这属于运维部署惯例，不是软件强制要求 |
| `include/config.php` 的文件权限 | 由安装程序或管理员在操作系统层设置 |

位于 `resource/` 及其子目录下的 `index.php` 重定向存根仅能阻止目录浏览列出文件。它们不是访问控制，也无法阻止对具体已知文件名的直接 HTTP 请求。

## 在认证前即响应的端点

这些属于专用入口点的典型示例，并非公开端点的完整详尽清单。缺少通用包含文件并不代表请求路径的其他位置不存在认证或授权。

| 文件 | 行为特征 |
|---|---|
| `auth_login.php`、`auth_changepassword.php` | 登录界面本身 |
| `csp_report.php` | 接收浏览器的 CSP 违规上报 |
| `service_check.php` | 对 `version` 表执行一次单查询后响应 `success` 或 `fail`。一个无认证的探活探针 |
| `link.php` | 加载外部链接记录，随后自行检查 `is_realm_allowed($page['id'] + 10000)` |
| `remote_agent.php` | 数据采集器的 RPC 接口，按来源 IP 地址进行授权 |

`remote_agent.php` 是最需要审慎对待的接口。它的授权依托于 `remote_client_authorized()`，该函数将 `get_client_addr()` 与 `poller` 表中的主机名和 IP 进行比对。它没有共享密钥。任何来源 IP 与启用的数据采集器记录相符的调用方均可调用该代理的操作：轮询数据、执行数据查询、Ping 设备、执行 SNMP get/walk、请求图表数据以及启动网络设备发现。这里有两层关键防护：第一，如果查询返回的启用采集器记录至多只有一条，该函数直接返回 false，从而在此场景下直接拒绝访问。第二，当通过主机名而非精确 IP 匹配时，在接受之前必须通过正向查询再次反向验证确认。

除非在 `include/config.php` 中配置了 `$proxy_headers`，否则 `get_client_addr()` 仅读取 `REMOTE_ADDR`。出厂默认值为 `null`。启用支持的代理标头会更改从中选择有效客户端地址的有序来源。请仅使用由受信入口代理所控制的标头，并防止客户端自行伪造或绕过这些值。这一行配置最根本地改变了系统中每一个基于 IP 地址的决策结果，包括远程代理授权和日志中记录的来源地址。

## 访客（Guest）访问

`guest_user` 配置项指定一个用户账户，其权限将直接用于未登录用户的图表浏览页面。默认没有配置任何用户，此时图表查看需要像系统其他部分一样进行登录认证。配置该项会将该账户所能看到的一切内容向任何能访问 Web 服务器的人公开发布。这正是该功能的设计意图。该账户仍然存在于用户记录中；访客设置只是让其适用的图表权限在没有常规登录的情况下生效。应当核查实际发起的请求与对象权限，而不仅仅是查看配置的账户名。

## 如何评估一项代码变更

请依次思考以下三个问题：

哪个进程将运行此代码，以哪个操作系统用户运行？对于数据输入方法，通常是启动采集器的操作系统账户；Web 触发的采集可能与定时采集的身份不同。

数据在流经系统的过程中会触碰什么？来自设备且仅最终写入 RRD 文件的数据只跨越了一道边界。同样的数据如果出现在图表标题中，就跨越了两道；如果作为脚本参数，则跨越了三道。

我所依赖的安全边界是由代码强制执行的，还是纯粹属于惯例约定？如果是惯例约定，那么您当前编写的代码就是唯一的强制执行者。
