[아키텍처](/ko/concepts/architecture/)에서는 폴러 캐시를 한 문장으로 소개합니다.
작업 목록은 미리 계산되어 있으며, 수집기는 매주기 설정을 분석하는 대신 해당 목록을
읽습니다. 이 페이지에서는 이 결정이 실제로 어떤 의미를 갖는지 다룹니다.

## 수집기가 그렇지 않을 경우 수행해야 하는 작업

단일 값에 대해 수집할 대상을 파악하려면 전체 종속성 체인을 확인해야 합니다.
데이터 소스는 장치와 데이터 템플릿을 가리킵니다. 템플릿은 데이터 입력을 가리킵니다.
데이터 입력에는 필드가 있으며, 일부는 장치별로 재정의되고 일부는 템플릿에서
상속됩니다. 데이터 소스가 데이터 쿼리에서 생성된 경우 쿼리 캐시를 통해 현재 인덱스를
확인해야 합니다. 그런 다음 특정 필드가 재정의하지 않는 한 장치에서 SNMP 자격 증명을
가져와야 합니다.

이는 단 하나의 값을 얻기 위해 여러 번의 조인(join)을 수행해야 함을 의미합니다.
규모가 크지 않은 설치 환경에서도 수만 개의 값을 보유하고 5분마다 한 번씩 주기를
실행합니다. 수집 시점에 이러한 확인 작업을 수행한다면 네트워크가 아닌 데이터베이스가
모니터링할 수 있는 장치 수를 결정하게 됩니다.

따라서 확인 작업은 무언가 변경되었을 때 한 번만 수행되며, 그 결과는 평면적인 형태로 기록됩니다.

## 캐시가 저장하는 항목

캐시는 수집 지침을 미리 계산합니다. 설정의 반복적인 확인을 줄여주지만 조인이나
실시간 장치 상태 조회를 완전히 제거하지는 않습니다.

| 행에 포함된 항목 | 존재하는 이유 |
|---|---|
| 소유한 수집기 | 각 수집기는 자신에게 속한 행만 선택합니다 |
| 작업 유형: SNMP, 스크립트 또는 스크립트 서버 | 실행할 코드 경로를 결정합니다 |
| 호스트 이름, SNMP 버전, 포트, 시간 초과, 커뮤니티 또는 자격 증명 | 캐시된 연결 필드이며, 실시간 호스트 상태도 함께 읽습니다 |
| OID 또는 전체 스크립트 명령줄 | 이미 치환되어 즉시 실행할 수 있습니다 |
| RRD 파일 경로 | 이미 확인되었습니다 |
| 해당 파일 내의 필드 이름 및 전체 읽기를 구성하는 필드 수 | 출력을 일치시키고 유효성을 검사할 수 있습니다 |
| 스텝(step) 및 이 항목의 다음 실행 시점까지의 카운트다운 | [시간과 간격](/ko/concepts/time-and-intervals/) 을 참조하십시오 |

`cmd.php`는 `poller_item`을 `host`에 조인하고 비활성화된 장치를 필터링하며
가용성 및 재인덱싱 확인을 위해 실시간 장치 필드를 사용합니다. 캐시된 OID, 명령 및
RRD 메타데이터는 여전히 의도한 데이터 소스와 일치해야 합니다.

캐시된 자격 증명은 스냅샷이지만 장치 API를 통해 변경된 자격 증명을 저장하면
일반적으로 영향을 받는 캐시가 새로 고쳐집니다. 데이터베이스를 직접 편집하면
해당 경로를 우회하므로 오래된 스냅샷이 남을 수 있습니다. 모든 자격 증명 변경 시
수동 재구축이 필요하다고 가정하기보다 실제 캐시를 확인하십시오.

RRD 경로 역시 스냅샷입니다. 파일을 이동하거나 파일 위치를 변경하면 캐시된 모든
행이 이전 위치를 계속 가리키게 됩니다.

## 캐시를 기록하는 작업

캐시는 무언가를 변경했음을 인지하는 작업들에 의해 증분 방식으로 유지 관리됩니다.

| 작업 | 다시 작성되는 행 |
|---|---|
| 장치 저장 | 연결 필드, 수집기 또는 비활성화 상태가 변경되면 푸시아웃이 트리거됩니다. 변경되지 않은 수집 필드는 빠른 저장 경로를 사용할 수 있습니다 |
| 데이터 소스 저장 | 해당 데이터 소스의 행 |
| 템플릿에서 그래프 및 데이터 소스 생성 | 새로 생성된 행 |
| 인덱스를 이동하거나 확인한 데이터 쿼리 실행 | 변경된 데이터 소스만 해당 |
| CLI 재구축 | 워커가 처리하는 활성화된 장치. 현재 `--host-id` 전달 결함으로 인해 장치 격리에 의존할 수 없습니다 |

다시 작성하는 것은 단순한 맹목적 삽입이 아닙니다. 재구축 중인 데이터 소스의 행은
먼저 부재 상태로 표시된 후 새 집합이 작성되며, 여전히 부재 상태로 표시된 항목은
삭제됩니다. 이것이 더 이상 존재하지 않는 필드의 행을 제거하는 방법입니다. 버퍼 정리는
수집기 및 데이터 소스 ID로 범위가 제한됩니다. 이는 일반적인 대상 경로에서 관련 없는
소스를 보호하지만 동시 재구축이나 데이터베이스 쓰기 실패에 대한 완전한 보장은 아닙니다.
재구축 후에는 범위를 조사할 때 영향을 받지 않는 인접 장치를 포함하여 생성된 행을 확인하십시오.

## 결코 기록되지 않는 행

일부 설정은 새 캐시 행을 생성하지 않습니다. 그래프뿐만 아니라 로그도 확인하십시오.

빌더는 비활성화된 장치를 건너뛰지만 일괄 **비활성화** 작업은 기존 캐시 행을 유지하고
수집 프로세스가 장치를 필터링하여 제외합니다. 비활성화된 상태에서 재구축하면 행이
제거될 수 있습니다. 일괄 **활성화** 작업은 채워진 캐시를 재사용하거나 비어 있을 때
초기화합니다. 일반적으로 추가적인 장치 저장은 필요하지 않습니다. 기존의 부분적이거나
오래된 캐시는 여전히 조사가 필요합니다.

장치에 유효한 SNMP 설정이 없는 SNMP 항목은 행을 생성하지 않습니다. 버전이 없거나
버전이 범위를 벗어나거나 버전 1 또는 2에서 커뮤니티가 비어 있으면 매주기 실패할
행을 작성하는 대신 해당 행을 건너뜁니다.

입력 화이트리스트가 구성된 경우 파일이 없거나 거부된 입력은 해당 입력에 대한
새 행 작성을 방지합니다. 커밋된 재구축은 여전히 오래된 행을 정리합니다.
`input_whitelist` 구성이 없으면 이 검사는 입력을 허용합니다. 이는 항상 활성화된
보호 조치가 아닙니다. 화이트리스트를 변경하기 전에 거부된 명령과 구성된 정책을
검토하십시오.

인터페이스에는 캐시가 비어 있는 데이터 소스가 여전히 표시될 수 있습니다. 해당
그래프는 이전 기록을 유지하거나 간격을 표시할 수 있습니다. 평평한 0 선은 신뢰할 수
있는 지표가 아닙니다. 누락된 자격 증명과 거부된 입력은 해결해야 할 구성 상태입니다.

## 변경 사항이 아무것도 하지 않는 것처럼 보이는 이유

세 가지 서로 다른 메커니즘이 동일한 증상을 유발합니다.

**행이 재구축되지 않았습니다.** 인터페이스에서 수집에 영향을 미치지 않는 것으로
간주하는 항목을 변경했거나 인터페이스 외부에서 변경했습니다. 캐시는 여전히 이전
답을 유지합니다. 의도한 구성을 확인한 후 재구축을 통해 캐시된 필드를 새로 고칠 수 있습니다.

**행이 생성된 적이 없습니다.** 위에서 설명했습니다. 재구축으로 이 문제도 해결되지만
근본적인 문제가 해결된 후에만 가능하며, 진단 정보는 그래프가 아닌 로그에 나타나는 경우가 많습니다.

**값이 수집된 후 삭제됩니다.** 다중 값 출력은 템플릿 필드 정의를 통해 매핑되며,
참조되지 않은 필드는 파싱 중에 건너뛸 수 있습니다. 예상되는 필드 이름, 매핑 및
그래프 연결을 확인하십시오. 이 규칙이 그래프 참조가 없는 모든 숫자 샘플을 일괄적으로
폐기하는 것은 아닙니다. 캐시 재구축으로 잘못된 출력 계약을 복구할 수는 없습니다.

## 일괄 재구축 도구

단일 장치의 경우 기존 장치 페이지에서 **폴러 캐시 다시 채우기**를 사용하십시오.
해당 작업은 장치 범위의 `push_out_host()` 경로를 호출합니다. 그 후 생성된 행과
진단 정보를 확인하십시오.

현재 상위 스크립트인 `rebuild_poller_cache.php`는 `--host-id`를 허용하지만 해당
필터를 워커 명령으로 전달하지 않습니다. 따라서 단일 장치에 대한 CLI 재구축이라도
다른 활성화된 장치를 함께 재구축할 수 있습니다. 이 응용 프로그램 결함이 수정될
때까지 격리를 위해 해당 옵션에 의존하지 마십시오.

폴러 사용자로 실행하는 광범위한 CLI 재구축은 애플리케이션 루트에서 사용할 수 있습니다.

```bash
php cli/rebuild_poller_cache.php
```

활성화된 장치를 처리하며, 호스트가 없거나 비활성화된 모든 소스에 대한 복구 작업은
아닙니다. 이 작업은 수집 테이블에 기록하므로 시간이 걸릴 수 있습니다. 겹치는 재구축을
피하고 프로세스를 중단하지 마십시오. CLI의 `--force` 옵션은 프로세스 중복 등록
방지 장치를 재정의하므로 일반적인 복구 옵션이 아닙니다.

재구축은 파생된 상태를 새로 고칩니다. 장치 접근성을 복구하거나 RRD 파일을 이동하거나
거부된 입력 명령을 수정하거나 손실된 기록을 복구하지는 않습니다. 복구가 완료되었다고
판단하기 전에 생성된 캐시, 로그 및 후속 수집 상태를 점검하십시오.

Kadupul은 캐시가 마지막으로 변경된 시간을 기록하므로 시스템의 다른 부분에서 캐시를
다시 읽어야 함을 감지할 수 있습니다.

## 다중 수집기

둘 이상의 수집기가 있는 경우 각 행은 정확히 그중 하나에만 속하며, 해당 수집기
자체의 데이터베이스와 중앙 데이터베이스 모두에 행이 푸시됩니다.

변경 사항을 저장할 때 원격 수집기에 연결할 수 없는 경우 변경 사항은 원격이 아닌
중앙에만 적용되며, Kadupul은 수집기가 복구된 후 전체 동기화를 요청합니다. 해당
동기화가 완료될 때까지 원격 수집기는 인터페이스에 표시되는 것보다 오래된 작업 목록을
실행합니다. 특정 수집기의 불일치는 복제 상태, 연결성 및 각 수집기의 로컬 캐시를
점검해야 하는 이유가 됩니다.

캐시를 읽는 위치와 재인덱싱 명령이 처리되는 시점을 포함하여 전체 주기 내의 실행 순서는
[폴러 수명 주기](/ko/reference/poller-lifecycle/)에 설명되어 있습니다. 수집기 확장에
대해서는 [폴러 확장](/ko/guides/scale-the-poller/)을 참조하십시오.
