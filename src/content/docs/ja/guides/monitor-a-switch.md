:::caution[使用前に検証してください]
ソースコードは利用可能ですが、サポートされている Kadupul のリリースや移行パスはありません。本番環境で信頼する前に、バックアップを備えた隔離されたコピーでこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

スイッチは、データクエリの典型的な使用例です。存在するポートの数は事前にわからず、数は変更される可能性があり、各ポートには独自のデータソースが必要です。データクエリがどのように機能するかについては[テンプレート](/ja/concepts/templates/)を参照してください。このページでは適切な設定について説明します。

## 開始する前に

できればポーラーユーザーとして、割り当てられたコレクターからデバイスが応答することを確認します。設定された読み取り専用の資格情報を使用してください。数値 OID を使用することで、ローカルにインストールされた MIB 名への依存を回避できます。

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.31.1.1.1.1
```

SNMP v2c または v3 を使用してください。64 ビットインターフェースカウンターは SMIv2 オブジェクトであり、v1 経由でクエリを実行することはできません。v1 デバイスは 32 ビットカウンターのみを提供し、他には何も提供しません。

## デバイステンプレートの選択

デバイステンプレートは、デバイスを追加するときに提供されるデータクエリとグラフテンプレートを決定します。Kadupul は、Cacti によって提供されるテンプレートセットを継承します。これには、一般的な SNMP デバイステンプレートとベンダー固有のテンプレートのセットが含まれます。

どちらを選択しても、ポートの検出は同じソースから行われます。`resource/snmp_queries/interface.xml` で定義されているインターフェースデータクエリです。ハードウェアに一致するテンプレートがない場合は、汎用テンプレートを選択し、それにインターフェースクエリを関連付けます。

## データクエリの実行

クエリは `ifIndex` をトラバースしてポートを見つけ、`ifNumber` を読み取って期待されるポート数を把握します。次に、ポートごとにフィールドのセットを収集します。

| フィールド | OID | 用途 |
|---|---|---|
| `ifIndex` | `.1.3.6.1.2.1.2.2.1.1` | SNMP テーブル内の位置 |
| `ifName` | `.1.3.6.1.2.1.31.1.1.1.1` | 短いポート名、`Gi1/0/3` |
| `ifDescr` | `.1.3.6.1.2.1.2.2.1.2` | より長い説明 |
| `ifAlias` | `.1.3.6.1.2.1.31.1.1.1.18` | 設定したインターフェースの説明 |
| `ifHwAddr` | `.1.3.6.1.2.1.2.2.1.6` | ポートの MAC アドレス |
| `ifSpeed` | `.1.3.6.1.2.1.2.2.1.5` | 速度（bps）、32 ビット |
| `ifHighSpeed` | `.1.3.6.1.2.1.31.1.1.1.15` | 速度（Mbps） |
| `ifOperStatus` | `.1.3.6.1.2.1.2.2.1.8` | Up または Down |
| `ifInOctets` / `ifOutOctets` | `.1.3.6.1.2.1.2.2.1.10` / `.16` | 32 ビットバイトカウンター |
| `ifHCInOctets` / `ifHCOutOctets` | `.1.3.6.1.2.1.31.1.1.1.6` / `.10` | 64 ビットバイトカウンター |

デバイスに対してクエリを 1 回実行します。検出されたポートのテーブルが返されます。このテーブルは後続のすべての決定の基礎となるため、グラフを作成する前に必ず確認してください。

## 64 ビットカウンターの選択

インターフェースクエリは、いくつかのトラフィックグラフテンプレートを提供します。主なものは次のとおりです。

| グラフテンプレート | 読み取り内容 |
|---|---|
| In/Out Bits | `ifInOctets`, `ifOutOctets` |
| In/Out Bits (64-bit) | `ifHCInOctets`, `ifHCOutOctets` |
| In/Out Bits (64-bit, 95th) | 同様、95 パーセンタイルライン付き |
| In/Out Bits (64-bit, BW) | 同様、インターフェース速度に対する相対値 |
| Status (Up/Down) | `ifOperStatus` |
| In/Out (Errors/Discards) | `ifInErrors`, `ifInDiscards`, `ifOutDiscards`, `ifOutErrors` |

特に理由がない限り、64 ビットテンプレートを使用してください。32 ビットのオクテットカウンターは 4294967295 で上限に達します。全負荷状態のギガビットポートは、約 34 秒でこれを満杯にします。300 秒のステップでは、ポーラーは 1 回のオーバーフローと 7 回のオーバーフローを区別できず、`COUNTER` は 2 つのサンプル間の単一のオーバーフローのみを修正します。グラフは明確に破損しているようには見えません。単に永続的に低すぎる値が表示されます。

何百ものグラフを作成する前に、カウンターに実際にデータが入力されていることを確認してください。

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.31.1.1.1.6
```

空または失敗した walk には調査が必要です。報告されたエラー、アクセスビュー、およびエージェントのサポートを確認してください。

## 速度変更後の保存された最大値の確認

データソースがクエリ速度に基づいた最大値を使用する場合、作成時にキャッシュされた検出データから速度が取得されます。`ifHighSpeed` が優先され、最初の項目がない場合は `ifSpeed` が使用され、両方がゼロの場合は設定されたデフォルトが適用されます。

その値はファイルに書き込まれます。100 Mbps で検出され、後にそれ以上にネゴシエートされたポートは、実際のトラフィックを下回る上限を保持する可能性があり、RRDtool はその上限を超えるレートを unknown として記録します。キャッシュされた速度、データソース定義、および実際のファイルを `rrdtool info` で比較してください。

## インデックスの決定

ここで誤りがあると履歴が失われます。

各データソースは、そのポートに関する 2 つの情報を保存します。どのフィールドがポートを識別するか（インデックスタイプ）と、そのフィールドの値です。再インデックスごとに、そのフィールドに現在その値を持っている SNMP インデックスを尋ねることによって、ポートを再検出します。データソースはテーブルの位置ではなく、値に従います。

したがって、問題はどのフィールドが値を保持しているかです。

インターフェースクエリは優先順位を宣言します。`ifName`、`ifDescr`、`ifHwAddr`、`ifIndex` の順です。Kadupul は通常、十分に明確な値を持ち、重複のない候補の中から選択します。

| フィールド | 耐久性 | 失敗する状況 |
|---|---|---|
| `ifName` | 再起動、カード交換、番号の再割り当て | エージェントが空のままにするか、スタックメンバー間で繰り返す |
| `ifDescr` | スイッチハードウェアでは通常安定 | サーバー上では変更されやすいカーネル名 |
| `ifHwAddr` | 再起動 | 交換されたカードには新しい MAC があり、まさに保護したかったケースである |
| `ifIndex` | 信頼性なし | カード交換、再起動、またはファームウェアの変更によってテーブルの番号が付け直される |

クエリが `ifIndex` にフォールバックする場合は、通常の結果ではなく問題として扱ってください。ポート履歴は、スイッチが自由に再割り当てできる番号に関連付けられます。

## 再インデックス方法

デバイスごと、データクエリごとに設定されます。Kadupul がインデックスフィールドをいつ再読み込みするかを決定します。

| 方法 | トリガー | コスト |
|---|---|---|
| None | なし。手動またはスクリプトのみ | なし |
| Uptime | デバイスの SNMP 稼働時間が後退する | 1 サイクルあたり 1 回の比較 |
| Index Count | 検出されたインデックスの数の変化 | 1 サイクルあたり 1 回のカウント |
| Verify All | キャッシュされた ID チェックの失敗 | ポーリング中に既知のインデックスをクエリ |

Uptime がデフォルトであり、再起動がインデックス番号の再割り当てを引き起こすイベントであるため、ほとんどのスイッチに適しています。Index Count は、再起動なしで追加または削除されたカードをキャプチャします。Verify All は、既知のインデックスで変更された ID を検出できますが、新しいポートの検出は保証されません。

選択したデバイスとクエリを再実行するには、両方の ID をインストールされている ID に置き換えます。そのデバイスのすべてのクエリを再実行するには、`--qid` を省略します。

```bash
php cli/poller_reindex_hosts.php --id=42 --qid=16
```

`--id=all` は実行をすべての有効なデバイスに拡張します。重複する再インデックス実行は避けてください。`--force` はプロセス登録をバイパスし、タイトルキャッシュを更新します。

## ポートが消失した場合

ポートがないからといって、収集が自動的に停止するとは見なさないでください。現在の再インデックスコードは、ID が未解決で、どのソースもインデックスを変更しない場合に、孤立フラグをリセットし、古いポーリング OID を保持する可能性があります。保存された ID を新しい検出キャッシュと比較し、一致が確認されるまで影響を受けるソースを無効にします。[データクエリとインデックス](/ja/concepts/data-queries-and-indexes/)を参照してください。

## 大型シャーシ

ポート数が多くなると、デバイスごとの 2 つの設定が重要になります。SNMP リクエストごとに設定された OID と、デバイスごとのスレッド数を確認します。バッチ処理のサポートと効果的な並列処理は、コレクターとエージェントに依存します。PHP `cmd.php` と Spine は同じスレッド動作を提供しません。

一度に 1 つの設定のみを変更し、ポーラーサイクルの継続時間を観察してください。

## 障害モード

| 症状 | 原因 |
|---|---|
| グラフが作成されるが、すべての測定値が unknown | 64 ビットカウンターが実装されていないか、デバイスが SNMP v1 を使用している |
| カウンターが不合理な値に急増する | 32 ビットカウンターが 1 インターバル内に複数回オーバーフローする |
| 高負荷時のみギャップが発生する | RRD の最大値が古い検出速度に固定されている |
| メンテナンス後にポート履歴が誤ったポートに割り当てられる | 不安定な ID、古いマッピング、または未解決の孤立処理 |
| ポーラーが無効な SNMP インデックスに関する警告をログに記録する | データソースがインデックスなしで残されている。再インデックス、削除、または無効化を行う |
| ポートは検出されたが、何も収集されない | インデックスが空のデータソースはポーラーキャッシュエントリを作成しない |
