:::caution[ব্যবহারের আগে যাচাই করুন]
সোর্স কোড উপলব্ধ, তবে কোনো সমর্থিত Kadupul রিলিজ বা মাইগ্রেশন পাথ নেই। এগুলোর ওপর নির্ভর করার আগে ব্যাকআপসহ একটি আলাদা অনুলিপিতে এই পদ্ধতিগুলো পরীক্ষা করুন। [প্রকল্পের অবস্থা](/bn/project/status/) দেখুন।
:::

এই ধাপগুলো ক্রমানুসারে একবার সম্পন্ন করুন। প্রতিটি ধাপ একটি পরীক্ষার মাধ্যমে শেষ হয়। পরবর্তী ধাপে যাওয়ার আগে পরীক্ষাটি সম্পন্ন করুন: এখানে তালিকাভুক্ত প্রতিটি ব্যর্থতা এখন শনাক্ত করা সহজ, কিন্তু পোলার এক সপ্তাহ চলার পর তা শনাক্ত করা অত্যন্ত কঠিন।

হোস্টভিত্তিক পূর্বশর্তের জন্য [Windows হোস্টে Linux](/bn/guides/install-on-windows/) এবং [FreeBSD](/bn/guides/install-on-freebsd/) দেখুন। এই পদ্ধতিগুলো পূর্ণাঙ্গ গ্রহণযোগ্যতা পরীক্ষার প্রমাণ নয়।

## প্রথমে আপনার যা প্রয়োজন

Kadupul হলো একটি PHP অ্যাপ্লিকেশন যা MySQL বা MariaDB-তে কনফিগারেশন সংরক্ষণ করে এবং ডিস্কের RRD ফাইলে পরিমাপসমূহ সংরক্ষণ করে। এই পৃষ্ঠাটি বর্তমান `main` সোর্স থেকে একটি নতুন মূল-সার্ভার ইনস্টলেশন বর্ণনা করে, কোনো আপগ্রেড বা সংরক্ষিত LTS শাখা নয়। এটি চলার আগে চারটি উপাদান বিদ্যমান থাকতে হবে।

| উপাদান | এটি কেন প্রয়োজন |
|---|---|
| নিরাপত্তা-সমর্থিত রিলিজে PHP 8.4 বা নতুন | ওয়েব ইন্টারফেস এবং পোলার চালায় |
| MySQL বা MariaDB | ডিভাইস, টেমপ্লেট, ব্যবহারকারী এবং পোলার ক্যাশ ধারণ করে |
| RRDtool | রাউন্ড-রবিন আর্কাইভ তৈরি ও আপডেট করে এবং গ্রাফ রেন্ডার করে |
| net-snmp | ডিভাইসে কোয়েরি করার জন্য ব্যবহৃত ক্লায়েন্ট সরঞ্জাম এবং লাইব্রেরি সরবরাহ করে |

PHP-এর [অ্যাপ্লিকেশন ম্যানিফেস্ট](https://github.com/kadupulhq/kadupul/blob/main/composer.json) দ্বারা প্রয়োজনীয় এক্সটেনশনগুলোরও প্রয়োজন, যার মধ্যে রয়েছে `pdo_mysql`, `gd`, `sockets`, `gmp`, `intl`, `ldap`, `mbstring`, `pcntl`, `posix` এবং `sqlite3`। কমান্ড-লাইন এবং ওয়েব রানটাইম উভয়ের জন্যই এগুলো ইনস্টল করুন। [প্রয়োজনীয়তা](/bn/reference/requirements/) ইনস্টলারের পৃথক পরীক্ষা থেকে Composer-এর প্রয়োজনীয়তাগুলোকে আলাদা করে দেখায়।

## ধাপ ১: রানটাইম ইনস্টল করুন

আপনার ডিস্ট্রিবিউশনের প্যাকেজগুলো থেকে এর এক্সটেনশনসহ PHP, আপনার ডেটাবেস সার্ভার, RRDtool এবং net-snmp ইনস্টল করুন।

**এটি পরীক্ষা করুন।**

```bash
php -v
php -m | sort
rrdtool --version
snmpget --version
```

`php -m`-এ অবশ্যই প্রয়োজনীয় এক্সটেনশনগুলোর তালিকা থাকতে হবে। net-snmp কমান্ড-লাইন সরঞ্জামগুলো উপলব্ধ থাকলে PHP `snmp` এক্সটেনশনটি ঐচ্ছিক। নির্ভরতা ইনস্টলেশনের সময় Composer তার নিজস্ব প্রয়োজনীয় এক্সটেনশনগুলো পরীক্ষা করে; ওয়েব ইনস্টলারের একটি পৃথক এক্সটেনশন পরীক্ষা রয়েছে। রানটাইম ফলব্যাক Composer-এর প্রয়োজনীয়তাকে দূর করে না।

কমান্ড-লাইন এবং ওয়েব-সার্ভার PHP কনফিগারেশন ভিন্ন হতে পারে। উভয়ই পরীক্ষা করুন। ইনস্টলার অন্তত 400M-এর `memory_limit` এবং অন্তত 60 সেকেন্ডের `max_execution_time` সুপারিশ করে; এটি সেগুলোর সীমাহীন মান (`-1` এবং `0`) গ্রহণ করে। এই সুপারিশগুলোর নিচের মান সতর্কবার্তা তৈরি করে, যেখানে অনুপস্থিত `date.timezone` একটি ত্রুটি। একটি স্পষ্ট সময় অঞ্চল সেট করুন, যেমন `UTC`, এবং কমান্ড-লাইন কনফিগারেশন শনাক্ত করতে `php --ini` ব্যবহার করুন।

## ধাপ ২: ডেটাবেস এবং এর ব্যবহারকারী তৈরি করুন

একটি খালি ডেটাবেস এবং সেই ডেটাবেসের অধিকারসহ একজন ব্যবহারকারী তৈরি করুন। স্থানীয় ডেটাবেসের জন্য, ডেটাবেস প্রশাসক হিসেবে এই SQL চালান, ব্যবহারের আগে উদাহরণের পাসওয়ার্ড পরিবর্তন করুন:

```sql
CREATE DATABASE kadupul CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kadupul'@'localhost' IDENTIFIED BY 'replace-with-a-unique-password';
GRANT ALL PRIVILEGES ON kadupul.* TO 'kadupul'@'localhost';
```

PHP অন্য মেশিন থেকে সংযুক্ত হলে সংশ্লিষ্ট ডেটাবেস অ্যাকাউন্ট হোস্ট ব্যবহার করুন।

ডেটাবেস সার্ভারে সময় অঞ্চল টেবিলগুলো পূরণ করাও প্রয়োজন, এবং Kadupul ব্যবহারকারীর `mysql` ডেটাবেসের সেই টেবিলগুলোতে পড়ার অনুমতি থাকা প্রয়োজন। এটি তার নিজস্ব স্কিমার বাইরে একমাত্র অনুমতি। কোনো পর্যবেক্ষণ ব্যবস্থা এটি নির্দেশ করে না, এবং এটি ঐচ্ছিক নয়; এটি ছাড়া নিচের পরীক্ষা ব্যর্থ হবে।

```bash
# Populate the tables, then grant the one extra read the installer needs.
mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root -p mysql
mysql -u root -p -e "GRANT SELECT ON mysql.time_zone_name TO 'kadupul'@'localhost';"
```

**এটি পরীক্ষা করুন।** Kadupul ডেটাবেস ব্যবহারকারী হিসেবে লগইন করুন এবং চালান:

```sql
SELECT COUNT(*) FROM mysql.time_zone_name;
```

অনুমতি ত্রুটি ছাড়া একটি অ-শূন্য সংখ্যা ফিরে আসা হলো কাঙ্ক্ষিত ফলাফল। শূন্যের অর্থ টেবিলগুলো কখনোই লোড করা হয়নি; ত্রুটির অর্থ ব্যবহারকারী সেগুলো পড়তে পারছে না। উভয়ই ইনস্টলার বন্ধ করে দেয়।

সার্ভারের নিজস্ব চারটি সেটিংস এখনই ঠিক করার মতো গুরুত্বপূর্ণ।

| সেটিং | কাঙ্ক্ষিত | কারণ |
|---|---|---|
| `max_allowed_packet` | 16M বা বেশি | মূল সার্ভার এবং দূরবর্তী সংগ্রাহকদের মধ্যে বড় সিঙ্ক |
| `character_set_server`, `collation_server` | `utf8mb4`, `utf8mb4_unicode_ci` | ডিভাইসের বিবরণে মাল্টি-বাইট অক্ষর থাকে |
| `innodb_file_per_table` | On | টেবিলস্পেস আলাদা এবং পরিচালনাযোগ্য রাখে |
| `innodb_buffer_pool_size` | সিস্টেম মেমরির প্রায় এক চতুর্থাংশ | মেমরিতে র্কিং সেট বজায় রাখে |

ইনস্টলার এগুলোর নিজস্ব পাঠ জানায় এবং যা কম পড়ে তা চিহ্নিত করে, তাই আপনাকে অন্ধভাবে টেবিলের ওপর নির্ভর করতে হবে না। কাজের চাপ বাড়লে [ডেটাবেস কর্মক্ষমতা টিউনিং](/bn/guides/tune-database-performance/) আরও বিস্তারিত আলোচনা করে।

## ধাপ ৩: এটি আনপ্যাক করুন, মালিকানা ঠিক করুন এবং পরিবেশন করুন

অ্যাপ্লিকেশনটি এমন কোথাও রাখুন যেখানে আপনার ওয়েব সার্ভার এটি পরিবেশন করতে পারে, তারপর সিদ্ধান্ত নিন কোন সিস্টেম ব্যবহারকারী এটির মালিক হবে। সেই সিদ্ধান্তটি অবস্থানের চেয়ে বেশি গুরুত্বপূর্ণ। দুটি প্রক্রিয়া এখানে লেখে: ওয়েব সার্ভার, এবং যা পোলার নির্ধারণ করে। উভয়কে একই ব্যবহারকারী হিসেবে চালান। পোলারটি বিশেষাধিকারহীন হিসেবে চালান এবং উভয় প্রক্রিয়াকে প্রয়োজনীয় অ্যাক্সেস দিন। ভুল মালিকানা বা অনুমতি মোড গ্রাফ রেন্ডার হলেও পরবর্তী আপডেটগুলোকে বাধা দিতে পারে।

### রিলিজ আনপ্যাক করার পরিবর্তে রিপোজিটরি ক্লোন করে থাকলে

একটি Git চেকআউটে PHP নির্ভরতা এবং প্রস্তুতকৃত ব্রাউজার সম্পদ উভয়ই প্রয়োজন। রিপোজিটরির `mise.toml` রানটাইম ইনস্টল করা অবস্থায়, রিপোজিটরির মূল ডিরেক্টরি থেকে চালান:

```bash
mise exec -- php "$(command -v composer)" install --no-dev --optimize-autoloader
mise exec -- npm ci --ignore-scripts
mise exec -- npm run build
mise exec -- php bin/console asset-map:compile
mise exec -- php bin/console about
```

Composer `include/vendor/` পূর্ণ করে এবং নির্দিষ্ট সামঞ্জস্যপূর্ণ ফাইলগুলো পুনরুদ্ধার করে। npm বিল্ড `include/js/`, `include/fa/` এবং `include/vendor/flag-icons/`-এর অধীনে সম্পদ তৈরি করে। সোর্স ইনস্টলেশনের জন্য শুধুমাত্র Composer যথেষ্ট নয়।

সম্পূর্ণ নির্ভরতাসহ একটি অফলাইন বান্ডেল হলো একটি পৃথক বিল্ড আর্টিফ্যাক্ট। একটি সাধারণ GitHub সোর্স আর্কাইভ সেই বান্ডেল নয়। লক্ষ্য হোস্টে ইন্টারনেট অ্যাক্সেস না থাকলে [অফলাইন বিল্ড এবং যাচাইকরণ পদ্ধতি](https://github.com/kadupulhq/kadupul/blob/main/docs/symfony-migration.md#offline-installation) অনুসরণ করুন।

নির্ভরতা ইনস্টল করার পর লেখার যোগ্য পথগুলো প্রস্তুত করুন:

| দল | ডিরেক্টরি | লেখার যোগ্য যখন |
|---|---|---|
| ইনস্টলেশনের সময় | `resource/snmp_queries`, `resource/script_server`, `resource/script_queries`, `scripts` | শুধুমাত্র ইনস্টল বা আপগ্রেড করার সময় |
| ইনস্টলেশনের সময় | `include/vendor/csrf/`, বা কনফিগার করা `path_csrf_secret` অবস্থান | ইনস্টলারকে ইনস্টলেশন-নির্দিষ্ট গোপন কোড তৈরি করতে হবে; পরে এটি সংরক্ষণ করুন |
| সর্বদা | `log`, `cache/boost`, `cache/mibcache`, `cache/purifier`, `cache/realtime`, `cache/spikekill`, সিস্টেমের অস্থায়ী ডিরেক্টরি | ইনস্টলেশনের সম্পূর্ণ জীবনকালের জন্য |
| Symfony রানটাইম | `var/cache`, এবং ফাইল লগিং কনফিগার করা থাকলে `var/log` | PHP রানটাইম এবং ক্যাশ-ওয়ার্মিং ব্যবহারকারীর জন্য |

RRD ডিরেক্টরিটি ইনস্টলেশনের সম্পূর্ণ জীবনকালের জন্যও লেখার যোগ্য হতে হবে। এটি আপনার ইতিহাস ধারণ করে, তাই একটি ডেটাবেস ডিরেক্টরিকে আপনি যেভাবে যত্ন করেন সেভাবে এটি যত্ন করুন।

বর্তমান মাইগ্রেশনে এখনও পুরোনো লগইন, ইনস্টলার এবং প্লাগইন রুটের প্রয়োজন। এই যৌথ ইনস্টলেশনের জন্য, ব্যক্তিগত ডিরেক্টরি, কনফিগারেশন, নির্ভরতা এবং রানটাইম অবস্থায় অ্যাক্সেস অস্বীকার করার স্পষ্ট নিয়মসহ রিপোজিটরির মূল ডিরেক্টরি পরিবেশন করুন। পুরো ইনস্টলেশনটি `public/`-এ পরিবর্তন করবেন না: এটি এখনও ব্যবহৃত পুরোনো রুটগুলোকে সরিয়ে দেবে। Symfony-এর পৃথক এন্ডপয়েন্টে ভিন্ন রাউটিং রয়েছে; [মাইগ্রেশন নির্দেশিকা](https://github.com/kadupulhq/kadupul/blob/main/docs/symfony-migration.md) দেখুন।

Nginx-এর জন্য, রুট এবং PHP-FPM আপস্ট্রিম সামঞ্জস্য করে রিপোজিটরির [Nginx অবস্থানের নিয়ম](https://github.com/kadupulhq/kadupul/blob/main/tests/e2e/nginx.conf) থেকে শুরু করুন। সাধারণ PHP পরিচালনার আগে অস্বীকৃতির নিয়মগুলো রাখুন এবং `/app.php/...`-এর জন্য PATH_INFO সংরক্ষণ করুন। Nginx `.htaccess` পড়ে না। HTTP-এর মাধ্যমে RRD ফাইল, লগ এবং গোপন কোডগুলো অগম্য রাখুন; ফাইলের অনুমতি পরিবেশন বাধা দেয় তা ধরে নেওয়ার পরিবর্তে প্রকৃত সার্ভার কনফিগারেশন যাচাই করুন।

**এটি পরীক্ষা করুন।** পোলার ব্যবহারকারী হন, প্রতিটি সর্বদা-দলের ডিরেক্টরিতে একটি ফাইল লিখুন, তারপর সেটি মুছে ফেলুন। `ls -l`-এ সঠিক মনে হওয়া অনুমতিও SELinux বা AppArmor দ্বারা অস্বীকৃত হতে পারে, এবং ফাইল লেখাই একমাত্র পরীক্ষা যা এটি যাচাই করে। তারপর HTTP-এর মাধ্যমে লগ ডিরেক্টরির অধীনে একটি ফাইলের অনুরোধ করুন। আপনি একটি অস্বীকৃতি চান।

## ধাপ ৪: কনফিগারেশন ফাইল লিখুন

একটি নতুন ইনস্টলেশনের জন্য, সরবরাহকৃত কনফিগারেশন ফাইলটি অনুলিপি করুন:

```bash
cp include/config.php.dist include/config.php
```

বিদ্যমান ইনস্টলেশনের কনফিগারেশন ওভাররাইট করবেন না। ধাপ ২ থেকে ডেটাবেস হোস্ট, নাম, ব্যবহারকারী এবং পাসওয়ার্ড সেট করুন। প্রথম ইনস্টলেশনে অন্য দুটি মান গুরুত্বপূর্ণ: `url_path`, যে পাথের অধীনে অ্যাপ্লিকেশনটি শুরু এবং শেষের স্ল্যাশসহ পরিবেশন করা হয়, এবং `poller_id`, যা মূল সার্ভারে `1` এবং শুধুমাত্র একটি দূরবর্তী সংগ্রাহকে অন্য মান।

দূরবর্তী সংগ্রাহক ব্লকটি মন্তব্য হিসেবে ছেড়ে দিন। আপনি এখনও এটি তৈরি করছেন না; প্রস্তুত হলে [দূরবর্তী ডেটা সংগ্রহ](/bn/concepts/remote-data-collection/) এটি আলোচনা করে। অন্যান্য প্রতিটি সেটিংয়ের একটি কার্যকরী ডিফল্ট রয়েছে, তাই সেগুলোর যেকোনো একটি পরিবর্তন করার আগে [কনফিগারেশন](/bn/reference/configuration/) পড়ুন।

যেসব Symfony বৈশিষ্ট্য এটি ব্যবহার করে সেগুলোর জন্য PHP प्रक्रिया পরিবেশে একটি ডিপ্লয়মেন্ট-নির্দিষ্ট `APP_SECRET` কনফিগার করুন। বুটস্ট্র্যাপ ডিফল্ট হিসেবে `APP_ENV=prod` এবং `APP_DEBUG=0` ব্যবহার করে এবং `.env` ফাইলগুলো লোড করে না। এটি পুরোনো ইনস্টলারের CSRF গোপন কোড থেকে আলাদা।

**এটি পরীক্ষা করুন।** ক্রেডেনশিয়াল না দেখিয়ে সিনট্যাক্স পরীক্ষা করুন:

```bash
php -l include/config.php
```

ব্রাউজারে ইনস্টলার খোলার আগে পরবর্তী ধাপে স্কিমা আমদানি করুন।

## ধাপ ৫: স্কিমা আমদানি করুন

ইনস্টলার টেবিলগুলো ইতিমধ্যে বিদ্যমান থাকার প্রত্যাশা করে। আপনার তৈরি করা ডেটাবেসে সরবরাহকৃত স্কিমা লোড করুন:

```bash
mysql -u kadupul -p kadupul < cacti.sql
```

একটি খালি ডেটাবেসে একবার এটি করুন। এটি কোনো আপগ্রেড স্ক্রিপ্ট নয়; তথ্যপূর্ণ ডেটাবেসে এটি আমদানি করলে তা ব্যর্থ হতে পারে বা বিরোধপূর্ণ ও অসম্পূর্ণ ডেটা রেখে যেতে পারে।

## ধাপ ৬: ইনস্টলার চালান

একটি ব্রাউজারে সাইটটি খুলুন এবং পর্যায়ক্রমে কাজ করুন। ইনস্টলার একটি নির্দিষ্ট ক্রম অনুসরণ করে, এবং প্রতিটি ধাপ পরবর্তী ধাপের প্রবেশদ্বার:

1. স্বাগতম এবং লাইসেন্স।
2. নির্ভরতা পরীক্ষা: PHP সংস্করণ এবং এক্সটেনশন, কমান্ড লাইন এবং ওয়েব সার্ভার উভয়ের জন্য ধাপ ১ থেকে PHP সেটিংস, সময় অঞ্চল টেবিল, এবং ধাপ ২ থেকে ডেটাবেস সেটিংস। ত্রুটি পরবর্তী বোতামকে অবরুদ্ধ করে। সতর্কবার্তা অবরুদ্ধ করে না, তবে সেগুলো পড়ুন।
3. ইনস্টলেশনের ধরন: একটি নতুন মূল সার্ভার, বা একটি দূরবর্তী সংগ্রাহক।
4. অনুমতি পরীক্ষা: ধাপ ৩-এর ডিরেক্টরিগুলো, সেগুলোতে লিখে পরীক্ষা করা হয়।
5. বাইনারি অবস্থান: PHP, RRDtool এবং net-snmp সরঞ্জামগুলোর পাথ।
6. ডেটা সোর্স প্রোফাইল এবং লঞ্চার ব্যবধান।
7. টেমপ্লেট নির্বাচন: কোন ডিভাইস টেমপ্লেট লোড করতে হবে।
8. টেবিল রূপান্তর, নিশ্চিতকরণ এবং ইনস্টলেশন স্বয়ংক্রিয়ভাবে সম্পন্ন হওয়া।

সেই তালিকার ৬ নম্বর আইটেমটি পূর্বাবস্থায় ফিরিয়ে আনা কঠিন। আপনার বেছে নেওয়া প্রোফাইলটি এর পরে তৈরি হওয়া প্রতিটি RRD ফাইলে লেখা স্টেপ এবং আর্কাইভ সেট নির্ধারণ করে, এবং প্রোফাইল সম্পাদনা করলে বিদ্যমান ফাইলগুলো স্থানান্তরিত হয় না। ধারণ ক্ষমতার পরিবর্তনের জন্য একটি পৃথক, পরীক্ষিত মাইগ্রেশন প্রয়োজন; সেগুলোতে সর্বদা ইতিহাস বর্জন করার প্রয়োজন হয় না। শীর্ষ মান গুরুত্বপূর্ণ হলে, প্রোফাইলটি শুধুমাত্র গড় নয় বরং সর্বোচ্চ মান সংরক্ষণ করে কিনা তা নিশ্চিত করুন: এটি অতিক্রম করার আগে [ডেটা সোর্স এবং রাউন্ড-রবিন আর্কাইভ](/bn/concepts/data-sources-and-rras/) পড়ুন। সেখানে প্রস্তাবিত লঞ্চার ব্যবধান হলো এক মিনিট বা পাঁচ মিনিট। ডেটা সোর্স প্রোফাইল সংগ্রহের ব্যবধান সেট করে; লঞ্চার এবং প্রোফাইল অবশ্যই ধারাবাহিকভাবে কনফিগার করতে হবে।

## ধাপ ৭: ডিফল্ট ক্রেডেনশিয়াল পরিবর্তন করুন

সরবরাহকৃত স্কিমা পাসওয়ার্ড `admin` সহ `admin` নামের একটি প্রশাসক অ্যাকাউন্ট যুক্ত করে, যা এমনভাবে চিহ্নিত করা যাতে প্রথম লগইনে পরিবর্তনের বাধ্যবাধকতা থাকে। এটি একটি নিষ্ক্রিয় গেস্ট অ্যাকাউন্টও যুক্ত করে। ইনস্ট্যান্সটি অন্য কারও কাছে পৌঁছানোর আগে পাসওয়ার্ড পরিবর্তন করুন, যার অর্থ অন্যরা রুট করতে পারে এমন একটি নেটওয়ার্কে এটি সংযুক্ত করার আগে।

## ধাপ ৮: পোলার নির্ধারণ করুন

পোলার বাইরে থেকে শুরু করতে হবে। এর সংগ্রহের ব্যবধান এবং লঞ্চার ব্যবধান ধারাবাহিকভাবে কনফিগার করুন; পোলার এক মিনিট বা পাঁচ মিনিটের লঞ্চার ব্যবধান সমর্থন করে এবং নির্ধারিত সময়ের খুব আগে সাধারণ রান পৌঁছানোর বিরুদ্ধে নিরাপত্তা রয়েছে। এক মিনিটের লঞ্চারের জন্য, `php` এবং অ্যাপ্লিকেশন পাথকে সেগুলোর পূর্ণ পাথ দিয়ে প্রতিস্থাপন করে বিশেষাধিকারহীন পোলার ব্যবহারকারীর crontab-এ এই এন্ট্রি ইনস্টল করুন:

```
* * * * * php -q /path/to/kadupul/poller.php > /dev/null 2>&1
```

অথবা আপনার ইনস্টলেশন পাথ এবং বিশেষাধিকারহীন ব্যবহারকারীর জন্য সামঞ্জস্য করে `service/cactid.service` ব্যবহার করে সরবরাহকৃত `cactid.php` ডেমন চালান। একটি মাত্র লঞ্চার ব্যবহার করুন: ডেমন ব্যবহার করার সময় cron জব বা টাইমার নিষ্ক্রিয় করুন।

প্রকৃত সময়সূচীকে কনফিগার করা লঞ্চার ব্যবধানের সঙ্গে মেলান। এক মিনিটের কম সংগ্রহের প্রোফাইলের জন্য, চালু করা পোলার সেই ব্যবধানের ভেতরে সংগ্রহের চক্র চালায়; এই cron এন্ট্রি দিয়ে এক মিনিটের কম ছন্দ প্রকাশ করার চেষ্টা করবেন না।

**এটি পরীক্ষা করুন।** পোলার ব্যবহারকারী হিসেবে নিজের হাতে একটি চক্র চালান:

```bash
php -q /path/to/kadupul/poller.php --force --debug
```

`--force` সময় নির্ধারণের প্রাথমিক নিরাপত্তা ব্যবস্থা এড়িয়ে যায়। নির্ধারিত রানের সঙ্গে যাতে ওভারল্যাপ না হয় সেজন্য সময়সূচী বন্ধ রেখে এই ম্যানুয়াল পরীক্ষা ব্যবহার করুন। এটি অন্যান্য রক্ষণাবেক্ষণ বা নিরাপত্তা পরীক্ষা এড়িয়ে যায় না। আপনি একটি সারাংশ লাইনসহ একটি পরিষ্কার সমাপ্তি চান। তারপর সময়সূচী সক্রিয় করুন এবং দুটি ব্যবধানের জন্য এটি ছেড়ে দিন; নিশ্চিত করুন যে আপনি ছাড়া অন্য একটি রান ঘটেছে।

## কোথায় সমস্যা হতে পারে

প্রথম ইনস্টলেশনে প্রকৃতপক্ষে যে ব্যর্থতাগুলোর সম্মুখীন হতে হয় তা নিচে দেওয়া হলো।

| লক্ষণ | কারণ | কোথায় দেখতে হবে |
|---|---|---|
| সঠিক মনে হওয়া PHP সেটিংসে ইনস্টলার আটকে যায় | ওয়েব সার্ভার এবং কমান্ড লাইন ভিন্ন `php.ini` ফাইল পড়ে | `php --ini`, এবং ওয়েব SAPI যে ফাইলটি জানায় |
| সময় অঞ্চলে ইনস্টলার আটকে যায় | সময় অঞ্চল টেবিল লোড করা নেই, বা Kadupul ব্যবহারকারী সেগুলো পড়তে পারে না | `SELECT COUNT(*) FROM mysql.time_zone_name` |
| লেখার যোগ্য মনে হওয়া ডিরেক্টরিতে অনুমতি ধাপ ব্যর্থ হয় | ভুল মালিক, বা SELinux এবং AppArmor | পোলার ব্যবহারকারী হিসেবে একটি ফাইল লিখুন |
| ইনস্টলেশন সম্পূর্ণ, কোনো ডেটা কখনোই আসে না | পোলার কখনোই নির্ধারিত হয়নি | হাত দিয়ে `poller.php --force --debug` চালান |
| কয়েক চক্রের জন্য ডেটা, তারপর কিছু নেই | ভুল ব্যবহারকারী হিসেবে পোলার চলছে, যার ফলে এমন ফাইল থেকে যাচ্ছে যা ওয়েব ব্যবহারকারী আপডেট করতে পারে না | RRD ডিরেক্টরির ফাইলগুলোর মালিক |
| গ্রাফ ছোট ফাঁকে পূর্ণ | নির্ধারিত ব্যবধান এবং কনফিগার করা ব্যবধান অমিল | crontab, কনফিগার করা ব্যবধানের বিপরীতে |
| Composer ইনস্টলেশন প্রত্যাখ্যান করে | PHP 8.4-এর নিচে বা ম্যানিফেস্ট-প্রয়োজনীয় এক্সটেনশন অনুপস্থিত | `php -v`, `php -m`, এবং Composer-এর ত্রুটি আউটপুট |
| পোলার একাধিক প্রক্রিয়া চালাতে পারে না | `pcntl` বা `posix` অনুপস্থিত | `php -m` |

[লগিং](/bn/reference/logging/) আলোচনা করে কোথায় প্রতিটি রেকর্ড সংরক্ষিত হয়। [অনুপস্থিত ডেটার সমস্যা সমাধান](/bn/guides/troubleshoot-missing-data/) আলোচনা করে যখন ইনস্টলেশন ঠিক থাকে এবং একটি ডিভাইস ঠিক থাকে না।

## উন্মুক্ত করার আগে

পোলার একটি সিস্টেম ব্যবহারকারী হিসেবে চলে এবং RRDtool ও আপনার সংগ্রহ স্ক্রিপ্টগুলো সম্পাদন করে। ইনস্টলেশনটিকে এমন কিছু হিসেবে বিবেচনা করুন যা কমান্ড চালায়, কারণ এটি প্রকৃতপক্ষে তা-ই করে।

- TLS-এর মাধ্যমে এটি পরিবেশন করুন।
- ডিফল্ট প্রশাসক পাসওয়ার্ডটি সামান্য সময়ের জন্যও বহাল রাখবেন না।
- ডেটাবেস ব্যবহারকারীকে তার নিজস্ব ডেটাবেসেই সীমাবদ্ধ রাখুন।
- RRD এবং লগ ডিরেক্টরিগুলোকে ডকুমেন্ট রুটের বাইরে রাখুন।
- অন্য কোনো সিদ্ধান্ত না নেওয়া পর্যন্ত গেস্ট অ্যাকাউন্টটি নিষ্ক্রিয় রাখুন।
