源代码已公开，但目前尚无受支持的 Kadupul 发行版或迁移路径。在依赖这些步骤之前，请在带有备份的隔离副本上进行测试。参见[项目状态](/zh-cn/project/status/)。

一套完整的 Kadupul 恢复集包含三个部分。部分备份可以恢复配置或度量数据，但无法还原整个安装环境。

| 组成部分 | 包含内容 | 存放位置 |
|---|---|---|
| 数据库 | 设备、模板、用户、权限、轮询器缓存以及每个 RRD 文件的路径 | MySQL 或 MariaDB |
| RRD 文件 | 保留的度量数据和合并归档 | RRA 目录，默认位于安装目录下的 `rra/` |
| 配置 | 数据库凭据、路径、采集器配置、插件及脚本代码 | `include/config.php`、spine 配置文件、`plugins/`、`scripts/`、`resource/` |

## 仅备份数据库可以恢复什么

数据库保存图表定义和监控配置，而 RRD 文件保存历史图表归档。在启用 Boost 的情况下，最近的读数也可以暂存在数据库队列中，直到刷新写入文件。请务必将这些队列作为数据库备份的一部分予以保留。参见[架构](/zh-cn/concepts/architecture/)。

如果仅恢复数据库，你将得到一个能够识别四百台设备、已定义好每个图表、但绘制出的每个图表均为空白的数据系统。从你启动轮询器的那一刻起，它会重新开始采集数据，但历史数据已彻底丢失。

## 仅备份 RRD 会缺失什么

RRD 文件包含具名数据源、归档定义和具体数值，但缺少将这些数值重新关联至应用程序所需的完整 Kadupul 设备、查询、图表和权限元数据。

从“交换机 12 的端口 3 上的入站字节数”到磁盘路径的映射关系保存在数据库中，位于数据源的某一列中。如果仅恢复文件树，你将面对数千个填满数字的文件，除了手动进行逆向工程外，根本无法分辨哪个文件对应哪项指标。

这两部分合起来才算是一套完整的备份。请务必统一对待。

## 两者之间的一致性

这正是大多数备份流程悄无声息出错的地方。

轮询器会持续向 RRD 文件写入数据。在更新正在进行时复制的文件，可能会截取到写入一半的瞬态内容。数据库也在同一时刻被写入。如果你在 02:00 转储数据库并在 02:20 开始复制文件，这两部分描述的将是不同的时间点，在此期间创建或删除的每个数据源都会产生不匹配。

延迟 RRD 写入使得问题更加棘手，也更为复杂。在该模式下，轮询器并不会在每次轮询时都写入 RRD 文件。结果先累积在一个持久化数据库表中，稍后批量刷新。因此，数据库在逻辑上完全可能领先 RRD 文件多达一个刷新周期，其中包含磁盘上其他任何位置都不存在的真实度量数据。

请在以下方案中选择其一，按优先级降序排列：

**协调快照。** 使用数据库引擎支持的备份或静默（quiescing）流程，并将其与所有 RRD 存储及应用程序配置的快照进行协调。仅靠文件系统快照无法在独立存储卷、远程采集器、待处理队列或活跃数据库之间建立一致性。

**静默逻辑备份。** 禁用计划启动器和其他生产者，等待已经运行的采集器执行完毕，然后刷新延迟写入并等待刷新工作进程处理完成。在整个捕获过程中保持配置变更、维护任务和其他 RRD 写入进程处于停止状态。采集暂停可能会导致采样缺失；缺失的呈现方式取决于心跳周期和数据整合。

在运行示例之前，请先完成这些静默步骤并确认队列/工作进程状态。仅仅 `poller_boost.php --force` 返回 0 并不足以证明刷新已完整结束：一个已注册的 Boost 进程可能导致其直接退出而未真正执行工作。请单独协调所有 rrdcached 服务或远程存储。

此 Bash 示例假定使用本地存储、在私有客户端选项文件中配置了数据库账户，并且 RRA 目录包含所有受管理的 RRD 文件。请替换所有路径。清点自定义绝对 RRD 路径、符号链接目标、外部配置和远程采集器，并同样单独进行捕获。

```bash
set -euo pipefail
umask 077

APP=/path/to/kadupul
RRA=/path/to/kadupul/rra             # use the actual configured storage path
DEST=/var/backups/kadupul            # outside the served tree
MYSQL_CNF=/secure/path/backup-client.cnf
DB=$(php -r 'require $argv[1]; echo $database_default;' "$APP/include/config.php")
STAMP=$(date -u +%Y%m%dT%H%M%SZ)

install -d -m 0700 "$DEST"
STAGE=$(mktemp -d "$DEST/.partial-XXXXXXXX")
FINAL="$DEST/backup-$STAMP-${STAGE##*partial-}"

# All writers must already be stopped and deferred queues handled.
mysqldump --defaults-extra-file="$MYSQL_CNF" \
  --single-transaction --routines --events --triggers "$DB" > "$STAGE/db.sql"
tar -C "$RRA" -cf "$STAGE/rrd.tar" .
tar --exclude='./rra' --exclude='./log' --exclude='./cache' --exclude='./.git' \
  -C "$APP" -cf "$STAGE/application.tar" .

( cd "$STAGE"
  sha256sum db.sql rrd.tar application.tar > SHA256SUMS
  sha256sum --check SHA256SUMS )
test ! -e "$FINAL"
mv "$STAGE" "$FINAL"
```

应用程序归档包中包含配置与相匹配的代码。请在备份集合中同步记录源代码版本、数据库和 RRDtool 版本、实际存储路径以及写入停止/刷新状态。该示例排除了常规日志、缓存和 Git 元数据；请根据实际安装环境审查这些排除项。

只有成功捕获并通过校验和验证的备份集才会获得最终的目录名称。失败的命令仍可能在 `.partial-*` 中留下截断的文件；`set -e` 会中止后续命令，但不会删除已生成的输出。切勿将该目录提升为已完成的备份。校验和只能检测后续变动，不能保证逻辑完整性；恢复测试依然必不可少。

`--single-transaction` 仅涵盖事务表，无法为非事务性插件表或并发架构更改提供一致性快照。请确保写入进程和架构变更均处于停止状态，或者使用适合该引擎的备份方法。只有在确认捕获已完成且存储可用后，方可恢复数据采集。关于事务与权限要求，请参阅 [mysqldump 文档](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)。早期方案中遗漏的问题在 [website #12](https://github.com/kadupulhq/website/issues/12) 中有追踪记录。

**接受时间偏差并予以记录。** 无论你先捕获哪一部分，先捕获的部分总是较旧的，而两种捕获顺序都无法单独使活跃的数据对达到一致。记录下时间窗口；这正是确保结果可恢复的关键。

如果先转储数据库再复制文件，文件中的数据将更新。在窗口期内被删除的数据源仍存在于转储中，但其文件已不存在，留下的引用会导致轮询器重新创建该文件。在窗口期内创建的数据源会以数据库无法识别的文件形式到达，处于闲置状态。

如果先复制文件再转储数据库，数据库中的数据将更新。在窗口期内创建的数据源存在于转储中，但缺少底层文件，轮询器会将其重新创建为空文件。

两种顺序都可能由于所需文件在复制前被删除而丢失窗口期前的历史记录。它们还可能捕获到部分写入的文件或不一致的排队样本。记录时间偏差只是如实记录了一项限制；它并不能消除数据对的不一致性，也无法保证完全可恢复。

## 备份中存在哪些你未曾想到的内容

设备凭据以明文形式存储在数据库中。轮询器缓存将 SNMP 共同体名称以及 SNMPv3 用户名、密码和密码短语作为普通数据列保存，因为采集器在每次运行时都需要使用它们。配置文件中则包含数据库密码。

因此，Kadupul 备份实质上是你所监控的所有设备的凭据库。请对其进行静态加密，严格限制读取权限，切勿将其推送到通用文件共享中。

## 恢复顺序

顺序至关重要，因为每个步骤都依赖于前一步骤。

1. **首先恢复配置。** 如果没有数据库凭据和 RRA 路径，其他任何内容都无法进行校验。如果要恢复到不同的硬件上，请在此时修正路径，而不是留到之后。

2. **恢复 RRD 目录树。** 将其放置在配置所指定的位置。检查所有权和权限模式：轮询器以轮询器用户身份写入这些文件，而 Web 界面以 Web 服务器用户身份读取它们。如果恢复时保留了内容却未保留所有权，系统将能够正常绘制图形，却无法采集任何新数据。

3. **恢复数据库。** 转储中的版本表必须与恢复目标环境中的代码版本相匹配。在恢复的各组件经过统一验证之前，请保持所有启动器和写入进程处于禁用状态。将较旧版本的转储恢复到较新的代码上会使 Web 界面跳转至安装向导，这是正常行为，但在故障恢复过程中并不是你想要的结果。请先恢复相匹配的代码。

4. **重建轮询器缓存。** 该缓存是衍生数据，而恢复正是其极可能过期的典型场景。重建只需运行一次，却能消除整整一类令人困惑的异常现象。

5. **启动轮询器，然后检查单个文件。** 确认 RRD 文件的最后更新时间在首次运行后有所推进。如果图表数据填充到恢复点之后便呈现一条平直线，请检查采集结果、队列、时间戳、路径以及权限。单纯一条平直的图表线并不能直接说明故障原因。

## 常见陷阱

**RRD 文件会拒绝过去时间的更新。** RRD 文件不会接受早于或等于其已有时间戳的采样数据。将较旧的文件集恢复到较新的数据库中，本身并不能补录丢失的样本。保留的延迟队列或其他来源可能包含可恢复的读数，但重新回放需要单独的验证并按时间戳排序。若没有这些读数，采集恢复后将存在数据断层。这也是为什么不能通过在两个备份之间相互复制文件来进行合并。

**在重写任何内容之前，先检查存储的路径是否使用了占位符。** 生成的数据源将路径存储为 `<path_rra>/name.rrd`，该占位符在读取时会根据 RRD 路径设置进行展开。对于这些数据源，迁移安装位置意味着修改该设置并重建轮询器缓存，而不是去修改数据行。手动输入的路径是以字面量形式存储的，确实需要重写。在对整张表执行更新之前请务必确认，因为将带有占位符的路径重写为绝对路径，正是导致下一次迁移更加艰难的操作。

**远程采集器拥有独立的配置文件。** 每个远程采集器都保存着各自的数据库凭据和采集器 ID。它们并不包含在中心数据库备份中。请按主机单独捕获。

**插件数据保存在同一个数据库中。** 插件在安装时会创建自己的数据表，因此完整的数据库转储会涵盖这些数据。但插件代码并不保存在数据库中。如果你在恢复数据库时没有附带相匹配的 `plugins/` 目录，安装环境将禁用它找不到的插件。

**未经恢复验证的备份只是一种假设。** 请定期恢复到临时测试实例中。此做法最常捕获到的故障模式不是数据损坏，而是一个从来都只捕获了三部分中某一部分的无效备份。
