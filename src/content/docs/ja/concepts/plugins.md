プラグインとは、アプリケーションが自身のプロセス内にインクルードし、名前付きのポイントで呼び出すコードのことです。
プラグインモデルの他のすべての特性は、この1つの文から導かれます。

他者のプラグインをインストールする前に確認すべき点については、
[プラグインのインストールと精査](/ja/guides/install-and-vet-plugins/) を参照してください。

## なぜプロセス内で実行されるのか

プラグインの用途を確認してください。アプリケーションが描画しているリストに列を追加する、グラフが描画される前にそのオプションを変更する、削除されようとしているデバイスに対して処理を行う、タブを添付するなどです。これらのいずれも、アプリケーションがその瞬間にメモリ内に保持している対象に対する編集作業です。

隔離されたワーカープロセスを使用する場合は、明示的なインターフェースと処理結果の検証が必要になります。これは権限の分離を維持できますが、ここで採用されている仕組みではありません。プラグインファイルがインクルードされ、その関数がアプリケーションプロセス内で直接呼び出されます。

## プラグインが継承するもの

プラグインコードは呼び出し元のオペレーティングシステムアカウントとして実行され、プロセスのデータベース接続およびファイルシステム権限へのアクセス権を持ちます。Web呼び出し元はセッションを持つ場合もありますが、CLI呼び出し元は必ずしもセッションを持ちません。プラグイン機構は個別のID、サンドボックス、または署名検証を提供しません。

ユーザーおよびグループの権限はアプリケーションへのアクセスを制御しますが、プラグイン内の任意のPHPコードを封じ込めるものではありません。データベース権限、ファイルシステム権限、およびプロセスの制限が、そのプロセスが実行できる操作を引き続き制限します。インストール前にプラグインを精査し、アプリケーションアカウントの権限を最小限に留めてください。

## 2つの呼び出しスタイル

| スタイル | アプリケーションの動作 | 何も返さないプラグイン |
|---|---|---|
| 通知 | 引数を渡し、結果を無視する | 戻り値は使用されません。副作用と例外は依然として重要です |
| 変換 | 値を渡し、返ってきた結果を使用する | 値を null に置き換えて後続の呼び出し元を破壊する可能性があります |

変換スタイルは、プラグインがボタンを追加したり、アクションリストを拡張したり、グラフを変更したりできるようにするものです。ここはプラグインが相互に絡み合う場所でもあります。同じポイントにある2つのプラグインは、設定されたプラグイン順序に従って前のプラグインの出力をそれぞれ受け取ります。

ディスパッチャーは、配列が非配列になった場合や、以前は空でなかった値が null のようになった場合に警告を発しますが、これは一致するフック行が複数存在する場合に限られます。このチェックはフック規約の完全な検証ではありません。単一のプラグインがこの警告なしに値を破損させる可能性があります。

## 登録は状態であり検出ではない

フックはテーブル内に保持されます。どのプラグインか、どのフック名か、どのファイルか、どの関数か、有効化されているかどうかが記録されます。インストール、アップグレード、およびセットアップのルーチンがフックを登録できます。登録は初回インストールに限定されません。

代替案としてはリクエスト時の動的検出が考えられますが、これはプラグインディレクトリを走査し、各プラグインのコードをインクルードして何を望んでいるかを問い合わせることを意味します。単一のページが多くのフックポイントに到達します。何も接続されていないことを確認するためだけにすべてをインクルードするのは非常に高コストであるため、アプリケーションはテーブルを照会し、リクエストの間その結果をキャッシュし、一致する行が指定するファイルのみをインクルードします。

この選択には把握しておくべき代償が伴います。テーブルとファイルシステムの内容が一致しなくなる可能性があります。手動で削除されたプラグインディレクトリは、その行をテーブル内に残します。存在しない通知コールバックはデバウンスされた警告を発することがあります。変換ディスパッチャーには存在しないコールバックに対する同等の警告機構がありません。静かなログは、登録が健全であることを証明するものではありません。

実行順序はプラグインの登録順序に由来し、調整可能です。したがって、変換チェーンは管理者が制御する設定によって順序付けられます。

## プラグインがアクセスできる範囲

| 機能 | 備考 |
|---|---|
| 独自のテーブルを作成する | アンインストール時に削除できるよう記録されます |
| コアを含む既存テーブルに列を追加する | アンインストール時に削除できるよう記録されます |
| 権限レルムを登録する | アクセス制御されたインターフェースの新しいセクション |
| 他のプラグインへの依存関係を宣言する | インストール前にバージョンを確認 |
| リモートコレクター上で実行する | ディスパッチはフック、呼び出しスタイル、機能、および接続状態に依存 |

記録されたスキーマ変更が、アンインストールが破壊的である理由です。アプリケーションは、データを含めて追跡対象のテーブルと列を削除できます。また、クリーンアップの前にプラグインのアンインストールコールバックを呼び出します。そのコールバックは他の変更を行うことができます。追跡されていない変更は自動的にはロールバックされず、プラグインのソースディレクトリは残ります。

プラグインによって登録されたレルムは、コアレルムと同じ方法でユーザーおよびグループによって保持されます。登録時に要求された場合、新しいレルムはプライマリ管理者および現在のセッションユーザーにもアクセス権を付与できます。インストールおよびアップグレード後に結果として生じる権限付与を確認してください。既存のポリシーが新しい領域を自動的にカバーしていると想定しないでください。
[権限とアクセス](/ja/concepts/permissions-and-access/) を参照してください。

## ガードが実際に保護するもの

ガードは存在し、それらを確認することで脅威モデルが明らかになります。

フックが指定するファイルは、そのプラグイン自身のディレクトリ内で解決されます。外部にエスケープするパスは拒否され、セキュリティイベントとしてログに記録されます。プラグインのディレクトリ名は英数字、アンダースコア、ハイフンに制限されています。フックおよびレルムの登録は、インストール、アップグレード、またはセットアップルーチンのような名前を持つ関数からのみ受け入れられます。他の場所からの呼び出しは拒否され、ログに記録されます。

パスガードは、フック行がインクルードできるファイルを制限します。登録チェックは呼び出し元関数名に install、upgrade、または setup が含まれているかを調べるだけであり、ライフサイクル操作を認証するものではありません。プラグインコードは通常のページロード時にこのような名前を使用できるため、この慣例はセキュリティ境界ではありません。

プラグイン自身のコードが実行された後に何を行うかについては何も関与しません。これらは封じ込め境界ではなく、そのように構築されたものでもありません。

## 無効化は停止ではない

一部のフック種別はインストール時に有効な状態で登録されます。設定ページ、設定配列、およびフォーム定義を提供するものです。プラグインはオンにする前に設定可能である必要があるため、これらはいずれの場合も実行されます。

したがって、無効化されたプラグインであっても、一部のページロード時にコードがインクルードされて実行されます。無効化は機能スイッチであり、直接のプラグインURLも検証が必要です。悪意のあるコードが疑われる場合は、アンインストールを呼び出す前にインストール環境を隔離し、削除手順を確認してください。アンインストール自体もプラグインコードを実行するためです。ソースファイルのみを削除しても、登録情報はクリーンアップされず、データベースの変更もロールバックされません。

## リモートコレクターの接続面はより狭い

プラグインは情報ファイル内でその機能を宣言します。コレクターがメインインストール環境にアクセスできる場合に動作するか、アクセスできない場合に動作するか、およびデータ収集に参加するかどうかを指定します。

コレクター上では、一覧表示されたフックが機能要件に対してチェックされます。一覧にない変換フックは引き続きディスパッチされます。一覧にない通知フックは、オンライン時またはプラグインがオフラインでの管理/表示サポートを宣言している場合にディスパッチされます。スキップされた処理は必ずしもログに記録されるわけではありません。これはルーティングロジックであり、包括的な許可リストや隔離境界ではありません。使用するフックについて、正確なディスパッチャーと接続状態を調査してください。

その理由は、コレクターが異なる環境であるためです。その設定は数時間前のものである可能性のあるレプリカであり、中央データベースへのリンクがまったく存在しない場合もあります。中央データベースへの問い合わせが1回のクエリですぐに可能であるという前提で書かれたフックはそこでは誤りとなるため、モデルはプラグインに対して前提を推測させるのではなく明示的に宣言することを要求します。
[リモートデータ収集](/ja/concepts/remote-data-collection/) を参照してください。

## ポラーはフックを配置する最も高コストな場所

ポーリングパス上のフックは、その呼び出しポイントに到達したときに実行されます。その頻度はイベント、プロセス、およびコレクターのルーティングに依存します。すべてのプロセスですべてのサイクルで実行されるわけではありません。頻繁に通過するパス上の遅いコードはポーリング間隔を消費し、グラフの欠損につながる可能性があります。

ページ上のフックは、すでに待機している1人のユーザーに対して1回描画されます。両者は登録テーブル内では同じように見えますが、コストの規模は桁違いに異なります。

## なぜ接続面が不均一に見えるのか

フックAPIは、異なる目的と引数構造を持つ呼び出しポイントを公開しています。

そのため、リストは広範で不規則であり、一部のポイントは変更するための値を渡し、他のポイントは単にイベントが発生したことを通知するだけであり、引数の構造がフックごとに異なります。宣言されたコアの最小バージョンは、すべてのフックとの互換性を証明するものではありません。各呼び出しポイントの引数と戻り値の期待値を調査し、対象バージョンでプラグインを実際に実行してください。
[プラグインのインストールと精査](/ja/guides/install-and-vet-plugins/) に記載されているCLI互換性およびレルム付与の制限事項も適用されます。インストールが成功したことだけでは互換性の証明にはなりません。

実践的な結論として、プラグインはそれが書かれたコアバージョンに対して、宣言された最小バージョンが示唆するよりもはるかに強固に結合しています。コアのアップグレード後ではなく、アップグレード前にプラグインを再確認してください。
