플러그인은 애플리케이션이 자체 프로세스에 포함하고 명명된 지점에서 호출하는 코드입니다.
플러그인 모델의 다른 모든 속성은 이 한 문장에서 비롯됩니다.

타사의 플러그인을 설치하기 전에 확인해야 할 사항은
[플러그인 설치 및 검증](/ko/guides/install-and-vet-plugins/)을 참조하십시오.

## 프로세스 내부에서 실행되는 이유

플러그인의 용도를 살펴보십시오: 애플리케이션이 렌더링 중인 목록에 열을 추가하거나, 그래프가 그려지기 전에 옵션을 수정하거나, 삭제 중인 디바이스에 대응하거나, 탭을 첨부하는 것입니다. 이 모든 작업은 애플리케이션이 그 순간 메모리에 보관하고 있는 대상을 편집하는 작업입니다.

격리된 작업자 프로세스는 명시적인 인터페이스와 결과에 대한 유효성 검사가 필요합니다. 이는 권한 격리를 유지할 수 있지만, 여기서 사용되는 메커니즘은 아닙니다: 플러그인 파일이 포함되고 해당 함수가 애플리케이션 프로세스 내에서 직접 호출됩니다.

## 플러그인이 상속하는 것

플러그인 코드는 프로세스의 데이터베이스 연결 및 파일 시스템 권한에 대한 액세스 권한을 가진 채 호출 운영체제 계정으로 실행됩니다. 웹 호출자는 세션을 가질 수도 있지만, CLI 호출자는 반드시 세션을 갖는 것은 아닙니다. 플러그인 메커니즘은 별도의 ID, 샌드박스 또는 서명 확인을 제공하지 않습니다.

사용자 및 그룹 권한은 애플리케이션 접근을 제어하며, 임의의 플러그인 PHP 코드를 격리하지 않습니다. 데이터베이스 권한, 파일 시스템 권한 및 프로세스 제한은 여전히 해당 프로세스가 수행할 수 있는 작업을 제한합니다. 설치 전에 플러그인을 검토하고 애플리케이션 계정의 권한을 최소한으로 유지하십시오.

## 두 가지 호출 방식

| 스타일 | 애플리케이션 | 아무것도 반환하지 않는 플러그인 |
|---|---|---|
| 알림 | 인수를 전달하고 결과를 무시함 | 반환 값은 사용되지 않으며 부작용 및 예외는 여전히 중요함 |
| 변환 | 값을 전달하고 반환된 결과를 사용함 | 값을 null로 대체하여 다운스트림 호출자를 손상시킬 수 있음 |

변환 스타일은 플러그인이 버튼을 추가하거나 작업 목록을 확장하거나 그래프를 변경할 수 있도록 하는 메커니즘입니다. 또한 플러그인이 서로 얽히는 지점이기도 합니다: 동일한 지점에 있는 두 개의 플러그인은 구성된 플러그인 순서에 따라 이전 플러그인의 출력을 각각 확인합니다.

디스패처는 일치하는 훅 행이 여러 개 존재하는 경우에만 배열이 비배열로 바뀌거나 이전에 비어 있지 않던 값이 null과 유사하게 변경될 때 경고를 발생시킵니다. 이 검사는 훅 계약에 대한 완전한 유효성 검사가 아니므로 단일 플러그인이 이러한 경고 없이 값을 손상시킬 수 있습니다.

## 등록은 검색이 아닌 상태임

훅은 테이블에 유지됩니다: 어떤 플러그인인지, 훅 이름, 대상 파일, 대상 함수, 활성화 여부 등이 저장됩니다. 설치, 업그레이드 및 설정 루틴이 훅을 등록할 수 있으며 등록이 최초 설치로 제한되지 않습니다.

대안은 요청 시 동적으로 검색하는 것인데, 이는 플러그인 디렉터리를 스캔하고 각 플러그인의 코드를 포함하여 원하는 것을 질의하는 것을 의미합니다. 단일 페이지가 많은 훅 지점에 도달합니다. 연결된 것이 없음을 확인하기 위해 모든 항목을 포함하는 것은 비용이 많이 드는 방식이므로, 애플리케이션은 테이블에 질의하고 요청에 대해 결과를 캐시하며 일치하는 행이 지정하는 파일만 포함합니다.

이러한 선택에는 알아둘 가치가 있는 대가가 따릅니다. 테이블이 파일 시스템과 일치하지 않을 수 있습니다. 수동으로 삭제된 플러그인 디렉터리는 테이블에 해당 행을 남깁니다. 누락된 알림 콜백은 디바운스된 경고를 생성할 수 있지만, 변환 디스패처에는 누락된 콜백에 대한 동등한 경고가 없습니다. 조용한 로그가 등록의 무결성을 입증하지는 않습니다.

실행 순서는 플러그인의 등록 순서에서 비롯되며 조정 가능합니다. 따라서 변환 체인은 관리자가 제어하는 항목에 의해 정렬됩니다.

## 플러그인이 접근할 수 있는 범위

| 기능 | 참고 |
|---|---|
| 자체 테이블 생성 | 설치 제거 시 삭제할 수 있도록 기록됨 |
| 코어를 포함한 기존 테이블에 열 추가 | 설치 제거 시 제거할 수 있도록 기록됨 |
| 권한 렐름 등록 | 접근 제어되는 인터페이스의 새로운 섹션 |
| 다른 플러그인에 대한 종속성 선언 | 설치 전 버전 확인 |
| 원격 수집기에서 실행 | 디스패치는 훅, 호출 스타일, 기능 및 연결 상태에 따라 달라짐 |

기록된 스키마 변경 사항은 설치 제거가 파괴적인 이유입니다. 애플리케이션은 데이터를 포함하여 추적된 테이블과 열을 삭제할 수 있습니다. 또한 정리 전에 플러그인 설치 제거 콜백을 호출합니다. 해당 콜백은 다른 변경을 수행할 수 있으며 추적되지 않은 변경 사항은 자동으로 롤백되지 않고 플러그인 소스 디렉터리가 유지됩니다.

플러그인이 등록한 렐름은 코어 렐름과 동일한 방식으로 사용자 및 그룹에 의해 유지됩니다. 새로운 렐름은 등록 시 요청하는 경우 기본 관리자 및 현재 세션 사용자에게도 접근 권한을 부여할 수 있습니다. 설치 및 업그레이드 후 결과 권한 부여를 검토하십시오. 기존 정책이 새로운 공격 표면을 포함한다고 가정하지 마십시오.
[권한과 접근 제어](/ko/concepts/permissions-and-access/)를 참조하십시오.

## 가드가 실제로 보호하는 것

가드가 존재하며, 이를 살펴보면 위협 모델이 무엇인지 파악할 수 있습니다.

훅이 지정하는 파일은 해당 플러그인의 자체 디렉터리 내에서 확인됩니다. 외부로 벗어나는 경로는 거부되고 보안 이벤트로 기록됩니다. 플러그인의 디렉터리 이름은 영문자, 숫자, 밑줄 및 하이픈으로 제한됩니다. 훅 및 렐름 등록은 설치, 업그레이드 또는 설정 루틴처럼 보이는 함수에서만 허용되며 다른 위치에서의 호출은 거부되고 기록됩니다.

경로 가드는 훅 행이 포함할 수 있는 파일을 제한합니다. 등록 검사는 호출자 함수 이름에 install, upgrade 또는 setup이 포함되어 있는지만 검사할 뿐 수명 주기 작업을 인증하지 않습니다. 플러그인 코드는 일반 페이지 로드 시 이러한 이름을 사용할 수 있으므로 이 규칙은 보안 경계가 아닙니다.

이러한 가드는 플러그인 자체 코드가 실행된 후 수행하는 작업에 대해서는 아무런 조치를 취하지 않습니다. 이들은 격리 경계가 아니며 그렇게 구축되지도 않았습니다.

## 비활성화가 완전히 꺼진 것은 아님

설정 페이지, 구성 배열 및 양식 정의를 제공하는 일부 훅 유형은 설치 시 활성화된 상태로 등록됩니다. 플러그인을 켜기 전에 구성할 수 있어야 하므로 이러한 훅은 어느 쪽이든 실행됩니다.

따라서 비활성화된 플러그인이라도 일부 페이지 로드 시 코드가 포함되어 실행될 수 있습니다. 비활성화는 기능 스위치일 뿐이며 직접적인 플러그인 URL도 검토가 필요합니다. 악성 코드가 의심되는 경우 설치 환경을 격리하고 설치 제거를 호출하기 전에 제거 절차를 검토하십시오. 설치 제거 자체도 플러그인 코드를 실행하기 때문입니다. 소스 파일만 삭제한다고 해서 등록이 정리되거나 데이터베이스 변경 사항이 취소되지는 않습니다.

## 원격 수집기는 더 좁은 표면을 가짐

플러그인은 정보 파일에서 자체 기능을 선언합니다: 수집기가 메인 설치에 연결될 때 작동하는지, 연결되지 않을 때 작동하는지, 데이터 수집에 참여하는지 여부를 지정합니다.

수집기에서는 나열된 훅이 기능 요구 사항에 대해 확인됩니다. 나열되지 않은 변환 훅은 여전히 디스패치되며 나열되지 않은 알림 훅은 온라인 상태이거나 플러그인이 오프라인 관리/보기 지원을 선언할 때 디스패치될 수 있습니다. 건너뛴 항목이 항상 로그에 기록되는 것은 아닙니다. 이것은 라우팅 로직이며 전면적인 허용 목록이나 격리 경계가 아닙니다. 사용하는 훅에 대해 정확한 디스패처 및 연결 상태를 점검하십시오.

그 이유는 수집기가 다른 환경이기 때문입니다. 해당 구성은 몇 시간 전의 복제본일 수 있으며 중앙 데이터베이스에 대한 링크가 전혀 없을 수도 있습니다. 중앙 데이터베이스가 단 한 번의 쿼리로 접근 가능하다는 가정하에 작성된 훅은 그곳에서 오류를 일으키므로, 모델은 플러그인이 가정을 추론하게 두지 않고 명시적으로 선언하도록 요구합니다.
[원격 데이터 수집](/ko/concepts/remote-data-collection/)을 참조하십시오.

## 폴러는 훅을 배치하기에 가장 비싼 위치임

폴링 경로의 훅은 해당 호출 지점에 도달할 때 실행됩니다. 실행 빈도는 이벤트, 프로세스 및 수집기 라우팅에 따라 달라지며, 모든 주기의 모든 프로세스에서 모든 훅이 실행되는 것은 아닙니다. 자주 실행되는 경로의 느린 코드는 폴링 간격을 소모하고 그래프 데이터 누락을 유발할 수 있습니다.

페이지의 훅은 이미 대기 중인 한 명의 사용자를 위해 한 번 렌더링됩니다. 둘은 등록 테이블에서 동일하게 보이지만 비용 측면에서는 수치적으로 큰 차이가 납니다.

## 표면이 불규칙해 보이는 이유

훅 API는 서로 다른 목적과 인수 형태를 가진 호출 지점을 노출합니다.

이 때문에 목록이 방대하고 불규칙하며, 어떤 지점은 변경할 값을 넘겨주고 다른 지점은 이벤트 발생만 알리며, 인수 형태가 훅마다 다릅니다. 선언된 최소 코어 버전이 모든 훅과의 호환성을 보장하지는 않습니다: 각 호출 지점의 인수와 반환 기대치를 점검하고 대상 버전에서 플러그인을 직접 실행해 보십시오.
[플러그인 설치 및 검증](/ko/guides/install-and-vet-plugins/)에 문서화된 CLI 호환성 및 렐름 부여 제한 사항도 적용되며, 성공적인 설치만으로는 호환성의 증거가 되지 않습니다.

실질적인 결론은 플러그인이 작성된 코어 버전에 선언된 최소 요구 사항이 시사하는 것보다 훨씬 더 긴밀하게 결합되어 있다는 점입니다. 코어 업그레이드 후가 아니라 업그레이드 전에 플러그인을 다시 확인하십시오.
