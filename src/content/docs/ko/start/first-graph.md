이곳의 그래프는 원시 데이터를 그대로 보여주는 그림이 아닙니다. 데이터 요약본을 시각화한 것이며, 어떤 요약이 적용되었는지를 아는 것이 매우 중요합니다.

## 보고 있는 내용의 실체

모든 그래프는 라운드 로빈 아카이브(round-robin archive)를 기반으로 그려집니다. 아카이브는 최근 샘플을 전체 해상도로 보관하고, 오래된 샘플은 더 큰 단위의 버킷으로 통합하여 저장합니다. 표시 기간을 1년으로 축소하면 5분 단위의 모든 샘플이 보이는 것이 아닙니다. 통합 함수에 의해 선택된 버킷당 하나의 값을 보게 됩니다.

그 함수는 보통 평균(average)입니다. 최대값(maximum)이나 최소값(minimum)일 수도 있습니다. 이는 이 페이지의 그 어떤 내용보다 중요합니다.

일반적인 온디맨드 그래프 요청 시, Kadupul은 그래프 설정에 따라 RRDtool 명령을 조합하여 디스크의 파일을 대상으로 실행합니다. 이 명령에는 세 가지 종류의 라인이 포함되며 각 라인의 역할을 알아두면 도움이 됩니다.

| 구성 항목 | 역할 |
|---|---|
| 정의 항목 | 파일 이름, 파일 내부의 데이터 소스, 그리고 통합 함수를 지정합니다 |
| 그리기 항목 | 단일 시계열 데이터를 선, 면 또는 스택의 띠 형태로 변환합니다 |
| 범례 항목 | 현재 보고 있는 시간 창 전체에 걸쳐 계산된 단일 숫자를 출력합니다 |

전체 구성 방식은 [그래프 생성 방식](/ko/concepts/how-graphs-are-drawn/) 문서에 설명되어 있습니다. 오늘 당장 이를 모두 파악할 필요는 없습니다. 그래프 정의와 요청된 시간 범위가 최종 이미지를 결정한다는 점만 이해하면 됩니다. 캐싱 및 실시간 그래프 경로는 동작이 다를 수 있습니다.

## 최근 4시간부터 시작하기

짧은 최근 시간 창부터 확인하세요. 선택되는 아카이브는 보존 기간, 단계 크기 및 그래프 해상도에 따라 달라지므로, 4시간 창이라고 해서 원시 데이터나 통합되지 않은 데이터가 보장되는 것은 아닙니다. 가장 정밀한 아카이브라도 시간 정규화된 값을 포함합니다. 값을 비교하기 전에 그래프의 디버그 명령과 `rrdtool info` 를 사용하여 요청된 함수와 사용 가능한 아카이브 단계를 확인하세요.

새로 만든 그래프에서 정상적이지만 사용자를 불안하게 만드는 두 가지 특징이 있습니다.

**선이 현재 시점 이전에 끝날 수 있습니다.** 현재 버킷의 데이터가 아직 완료되지 않았을 수 있습니다. 수집 타이밍, 버퍼링 및 정규화로 인해 표시되는 끝점이 지연될 수도 있습니다. 고정된 시차가 정상 작동의 증거라고 단정하지 말고 업데이트 타임스탬프가 계속 진행되고 있는지 확인하세요.

**초기 구간이 비어 있을 수 있습니다.** 1시간 전에 생성된 데이터 소스에는 1시간 분량의 데이터만 있고 11개월 동안의 데이터는 없습니다. 아카이브는 생성 시 전체 용량이 미리 할당되므로 빈 부분은 향후 사용되기를 기다리는 실제 저장 공간입니다.

## 범위를 넓히고 피크 변화 관찰하기

조회 범위를 1주일로 넓혀보세요. 그래프가 더 큰 단위의 평균을 선택하면 피크(최고치)가 줄어들 수 있습니다. 예를 들어 5분 동안 사용률이 100%이고 나머지 55분 동안 0%였다면 시간당 평균은 약 8.3%가 됩니다. 유휴 상태였던 1시간 중 4분 동안 버스트 트래픽이 발생한 경우 평균은 약 6.7%에 불과합니다. 짧은 피크는 원래의 샘플링 간격 내부에서 이미 평활화(smooth)되었을 수 있습니다.

통합 과정은 세부 정보를 버립니다. 고해상도 기록의 보존 기한이 만료되면 아무리 확대하더라도 평균 아카이브로부터 원본 세부 데이터를 재구성할 수 없습니다.

이것이 세 가지 흔한 실수 중 첫 번째이며 가장 많은 논쟁을 불러일으키는 원인입니다.

**평균값을 피크로 오인하는 것.** 포화 상태에 관심이 있다면 평균이 아닌 최대값을 기반으로 구성된 그래프를 확인하세요. 이는 아카이브가 최대값을 저장하고 있을 때만 유효합니다. 거친 단위의 평균만 남아 있다면 원래의 피크는 재구성할 수 없습니다. MAX 아카이브는 시간 정규화된 입력 포인트의 최대값을 보존하는 것이지, 폴링 사이에 발생한 관측되지 않은 순간 피크를 보존하는 것이 아닙니다.

여기서 알아두어야 할 조용한 오류가 있습니다. 그래프 항목이 최대값을 요구하는데 파일에 해당 데이터가 없는 경우, Kadupul의 선택 도우미는 사용 가능한 첫 번째 함수로 대체하거나 사용 가능한 함수를 확인할 수 없을 때 AVERAGE 로 되돌아갈 수 있습니다. 그래프 자체는 정상적으로 보이지만 실제로는 전혀 다른 질문에 답하고 있는 것입니다.

**공백을 0으로 오인하는 것.** 공백은 플롯된 값이 알 수 없음(unknown)임을 나타냅니다. 원인으로는 업데이트 누락, 명시적인 알 수 없는 입력, 거부된 값 및 그래프 계산식이 포함됩니다. 공백이 장치 다운만을 유일하게 나타내는 것은 아닙니다.

하트비트(heartbeat)는 업데이트 사이에 허용되는 최대 시간이며 단계에 추가되는 추가 시간이 아닙니다. 예를 들어 600초 하트비트를 가진 300초 단계는 업데이트 사이에 최대 600초를 허용하는 것이지 900초를 허용하는 것이 아닙니다. 아카이브의 알 수 없는 데이터 임계값도 눈에 보이는 공백에 영향을 줍니다. [RRDtool’s data-source definitions](https://oss.oetiker.ch/rrdtool/doc/rrdcreate.en.html) 및 [시간 및 간격](/ko/concepts/time-and-intervals/) 문서를 참조하세요.

스택(누적) 그래프에서는 특히 주의하세요. 일부 템플릿은 그래프 식에서 알 수 없는 값을 0으로 대체합니다. 이러한 그래프에서는 장애 발생과 유휴 상태가 의도치 않게 동일하게 보입니다. 서비스가 완전히 중단되었다고 결론을 내리기 전에 스택되지 않은 단일 보기를 확인하세요.

**수직 눈금이 서로 다른 두 그래프 비교하기.** 나란히 배치된 두 그래프는 각자의 데이터에 맞춰 축을 조정합니다. 작은 변동과 큰 변동이 겉보기에 똑같아 보일 수 있습니다. 결론을 내리기 전에 축의 눈금을 반드시 확인하세요.

축을 확인할 때 기준 단위도 함께 살펴보세요. 그래프는 1000 단위(10진) 또는 1024 단위(2진)로 라벨을 표시할 수 있습니다. 저장된 데이터 숫자는 동일하며 라벨 표기만 달라집니다. 그 차이는 접두사에 따라 달라집니다. 1승에서 1024와 1000의 차이는 2.4%이며 더 큰 접두사에서는 차이가 더욱 벌어집니다. 비트와 바이트, 그래프 식 및 통합 방식도 함께 확인하세요. 백분율 차이만으로는 근본적인 원인을 규명할 수 없습니다.

## 범례 읽기

범례에는 그래프의 곡선 모양보다 더 중요한 수치가 표시됩니다. “Current(현재값)”는 일반적으로 선택된 시리즈의 LAST 축약값이며 그래프를 보고 있는 바로 그 순간에 측정된 값일 필요는 없습니다. 평균과 최대값은 전체 기간이 아니라 현재 보고 있는 창에 걸쳐 계산되므로 확대하거나 축소할 때마다 값이 변경됩니다.

기본 제공되는 범례 항목은 최소값, 최대값, 평균, 그리고 현재값으로 표시되는 최근값입니다. 이에 대해 사용자들이 놀라는 두 가지 사실이 있습니다.

**범례의 숫자는 저장된 데이터가 아니라 그려진 데이터의 축약값입니다.** 평균으로 읽어들인 시리즈 위에 인쇄된 최대값은 선택된 해상도에서 파생된 평균값들 중의 최대값입니다. 지금까지 측정된 역사상 가장 큰 원본 샘플이 아닙니다. 트래픽이 많은 링크에서는 이 두 수치가 크게 달라질 수 있으며 둘 다 서로 다른 질문에 대한 타당한 답입니다.

**범례가 어떤 시리즈를 사용하는지 확인하세요.** 일반 GPRINT 항목은 바로 앞에 그려진 항목의 시리즈를 상속할 수 있습니다. 반면 전용 최소값, 최대값, 평균 및 최근값 항목은 별도로 처리됩니다. 따라서 그래프 템플릿에서 항목 순서를 변경하면 범례 설정을 직접 편집하지 않았더라도 범례가 보고하는 내용이 달라질 수 있습니다. 무관한 템플릿 수정 후 숫자가 변경되었다면 항목 순서부터 먼저 확인하세요.

## 그래프가 비정상적으로 보일 때

수집 경로를 다음 순서대로 확인하세요. 둘 이상의 단계에서 오류가 발생했을 수 있습니다.

1. 장치가 지금 정상적으로 응답하고 있습니까?
2. 폴러가 실행 중이며 주기 간격 내에 작업을 완료합니까?
3. RRD 파일에 최근 업데이트 시간이 기록되어 있습니까?
4. 그래프가 예상한 데이터 소스를 정확히 읽고 있습니까?

구체적인 점검 절차:

**1단계.** 장치를 추가할 때 실행했던 동일한 `snmpget` 명령을 할당된 수집기에서 실행하세요. 실패할 경우 그래프를 평가하기 전에 해당 수집 오류부터 해결하세요.

**2단계.** 실행 완료 요약 출력을 찾으세요. 요약이 없다면 일정 예약, 구성된 로그 대상 및 폴러의 조기 중단 오류를 확인하세요. 주기 간격보다 오래 걸리는 실행은 업데이트를 지연시킬 수 있으므로, 결과적으로 발생하는 업데이트 공백을 하트비트와 비교하세요.

**3단계.** RRDtool에 직접 조회하세요.

```bash
rrdtool last /path/to/rra/the_file.rrd
rrdtool info /path/to/rra/the_file.rrd
```

`last` 는 알 수 없는 값을 포함한 마지막 업데이트 타임스탬프를 보고하며, 버퍼링된 쓰기로 인해 이 시간이 지연될 수 있습니다. 장치 가이드에 설명된 대로 `lastupdate` 와 `fetch` 를 사용하여 값을 검사하세요. `info` 는 단계 크기, 하트비트, 데이터 소스 유형 및 존재하는 아카이브 목록을 알려줍니다. 파일에 최대값 아카이브가 없다면 위에서 언급한 피크 관련 의문이 해결됩니다.

**4단계.** 그래프 디버그 모드를 켜고 그래프가 생성하는 명령을 읽으세요. 해당 명령에는 파일 이름, 파일 내부의 데이터 소스 및 각각의 통합 함수가 명시되어 있습니다. 템플릿을 다시 적용하거나 인터페이스를 다시 인덱싱한 후에는 그래프가 의도치 않은 다른 데이터 소스를 가리키는 경우가 흔히 발생합니다.

## 주요 증상과 일반적인 원인

| 관찰된 현상 | 일반적인 원인 |
|---|---|
| 0에 머무는 평평한 직선 | 실제 0이거나 알 수 없는 값을 0으로 대체하는 계산식 때문일 수 있습니다 |
| 선이 멈췄다가 다시 시작됨 | 알 수 없는 값이 그려지던 시리즈를 중단시켰습니다. 수집 상태와 그래프 계산식을 확인하세요 |
| 전반적으로 미세한 공백 존재 | 폴러가 늦게 완료되거나 하트비트가 단계 크기에 너무 가깝게 설정되어 있습니다 |
| 4시간에서는 피크가 보이지만 1주일에서는 사라짐 | 데이터 유실이나 수집 오류로 단정하기 전에 아카이브 해상도와 통합을 먼저 확인하세요 |
| 범례 최대값이 그려진 피크보다 낮음 | 범례가 예상과 다른 시리즈를 축약하고 있습니다 |
| 전체 그래프가 비어 있고 오류 없음 | 연결된 데이터 소스가 없거나 아직 수집된 데이터가 없습니다 |
| 값이 자릿수 단위로 크게 벗어남 | 데이터 소스 유형이 잘못되었거나 32비트 카운터가 래핑되었습니다 |
| 동일 링크의 두 그래프가 약간 불일치함 | 축 기준 단위가 다르거나 서로 다른 통합 방식이 적용되었습니다 |

[누락된 데이터 문제 해결](/ko/guides/troubleshoot-missing-data/) 문서에서 이 점검 경로를 더 심도 있게 다룹니다. 그래프가 신뢰할 만한 정보를 전달한다는 확신이 든 후에는 [그래프 모양 조정](/ko/guides/tune-graph-appearance/) 을 참조하여 시각적 디자인을 변경할 수 있습니다.

이것으로 시작 튜토리얼을 마칩니다. 이제 정상적인 설치 환경, 응답하는 장치, 판독 가능한 그래프를 갖추었습니다. 앞으로는 [사용 안내](/ko/guides/monitor-a-switch/) 에서 특정 작업 수행 방법을 확인하고, [개념](/ko/concepts/architecture/) 에서 시스템이 이렇게 동작하는 이유를 살펴보세요.
