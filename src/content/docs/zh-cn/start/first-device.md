先添加单台设备，确认它正常响应，然后再继续后续操作。监控系统遇到的大多数问题，根源往往在于某台设备从一开始就从未真正响应过。

请选择一台允许试错的设备：你自己拥有的交换机，位于你所控制的网络中，且已预先启用了 SNMP。不要从别人催促你监控的那台设备开始。

## 开始之前

在本 SNMP 示例中，设备必须能够响应来自其指定采集器的查询。请在该采集器上执行检查，最好以轮询器用户的身份运行；从你的笔记本电脑发出的请求可能会走不同的防火墙路径。请将示例中的地址和共同体字符串替换为你在设备上配置的只读凭据。即使本地未安装 MIB 名称文件，下方的数值 OID 也可以正常工作。

```bash
snmpget -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.1.1.0
```

如果该命令返回了系统描述字符串，即可继续。如果发生超时，请先解决此问题。如果设备网络不可达，在 Web 界面中做再多的配置也无法让它响应。

接下来检查你实际想要绘制图表的表，因为设备即使响应了 `sysDescr`，仍有可能拒绝接口表的查询请求。

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.2.2.1.2
```

第二个 OID 是 `ifDescr` 列。理想情况下每个公开的接口会返回一行数据。如果返回空结果，可能意味着 SNMP 视图受限或该表不受支持；若返回授权错误，则通常是凭据或访问策略问题。在修改设备或 Kadupul 配置之前，请仔细检查返回的具体错误。

有关 SNMP 版本的两个事实会影响后续决策，因此现在就明确它们。

| 版本 | 对你的意义 |
|---|---|
| v1 | 不支持 Counter64。高速链路在两次轮询之间可能会导致 32 位八位字节计数器多次回绕，从而使速率计算产生歧义 |
| v2c | 当代理公开时支持 Counter64；共同体字符串以明文方式传输 |
| v3 | 通过 `authPriv` 支持身份验证与加密；仅选择 v3 本身并不会自动启用这两项功能 |

在支持的情况下优先选用带有 `authPriv` 的 v3，或者在受限的管理网络中使用 v2c。请同时选择 64 位接口图表类型和相应的 SNMP 版本。如果设备仅支持 v1，请参考本页底部的故障排查表来评估轮询间隔和流量速率。[SNMP](/zh-cn/reference/snmp/) 详细介绍了所有凭据字段。

## 打开表单前需要确定的三件事

**凭据。** 严格使用你在上一步中测试通过的凭据，如果端口不是默认端口，也需包含端口号。

**可用性检测方法。** 这是 Kadupul 判断设备是否在线的方式，它与数据采集是否正常运行相互独立。自带的选项包括：无（none）、ping、SNMP 运行时间（SNMP uptime）、SNMP 描述（SNMP description）、SNMP getNext，以及 ping 与 SNMP 运行时间的两组组合（一组要求两者均满足，另一组只需满足其一即可）。

对于通过 SNMP 轮询的设备，优先选用 SNMP 检测方法。它直接测试了你所依赖的服务。ICMP ping 需要原始套接字（raw socket），这需要 Web 用户和轮询器用户通常不具备的高权限；因此在你的 Shell 中能够响应 `ping` 的设备，在系统界面中仍可能被报告为宕机。针对已知开放端口发起 TCP ping 可以避免该问题。

**设备模板。** 选择与硬件类型匹配的模板。

## 添加设备

1. 在旧版**设备**页面（`host.php`）中选择**添加**。在 Symfony 迁移期间，设备创建和图表设置仍使用此页面。输入描述、主机名或 IP 地址、指定采集器、SNMP 版本及凭据。
2. 设置你所选择的可用性检测方法。
3. 选择设备模板。
4. 保存配置，确认设备已处于启用状态，并查看其可用性/SNMP 面板。数据库记录保存成功并不代表数据采集已经成功。

## 设备模板决定的内容

设备模板将图表模板和数据查询与设备关联起来。数据查询会遍历设备上的表（例如其接口列表），并为每一行生成一个索引。应用模板还会运行其数据查询以填充这些索引。在禁用图表自动创建时，这些关联本身不会直接生成图表。启用图表自动创建后，模板与查询的挂钩可以根据匹配规则自动生成图表；在添加重复副本之前，请先检查现有图表。

更改模板可能会改变原有关联并重新触发这些挂钩。这并不是对现有图表或数据源的重置。在对已有历史数据的设备应用新模板之前，请仔细核对所选模板和已查询的索引。

正是由于这些索引的存在，你才能够从列表中直接挑选接口，而无需手动输入 OID。[模板](/zh-cn/concepts/templates/)与[数据查询与索引](/zh-cn/concepts/data-queries-and-indexes/)对此均有详细阐述。

## 查看状态面板

当使用 SNMP 可用性检测方法保存设备后，Kadupul 会建立会话并报告状态反馈。这是至关重要的检查步骤，也是人们最容易跳过的一步。

| 显示内容 | 实际含义 |
|---|---|
| 系统和运行时间查询成功 | 面板可以读取基本的 SNMP 元数据。但这尚未证明接口数据采集正常 |
| 位置或联系人为空 | 这些可选元数据字段可能未在设备上配置；字段为空本身并非采集故障 |
| SNMP 未使用 | 设备上未配置共同体或用户名，或者版本被设置为无（none） |
| SNMP 会话错误 | 会话建立失败；请检查显示的错误信息、凭据、协议和连接设置 |
| SNMP 系统错误 | 读取 `sysDescr` 失败；请检查返回的错误、代理视图、凭据和网络可达性 |
| SNMP 主机错误 | 描述和运行时间均未返回 |
| 运行时间显示为 `U` | 运行时间不可读。某些设备确实根本不报告此项 |

如果可用性方法中包含 ping，下方会显示单独的 ping 结果。两项结果都要查看。设备可能通过其中一项而另一项失败，失败的具体项目会指明问题的排查方向。

系统描述为空并不代表采集失败。代码能够兼容描述为空但运行时间可用的代理设备。已禁用的设备会绕过可用性检查，而非 SNMP 可用性方法则不会显示该 SNMP 面板。接下来请验证实际查询和轮询器缓存。

## 创建数据源与图表

对于没有通过自动化规则创建图表的新设备，下一步是手动创建图表及其数据源。请在设备页面上查看**数据源列表**和**查看轮询器缓存**，而不是假定它们为空。

在设备页面上，选择**为此设备创建图表**。对于交换机而言，这意味着运行接口数据查询，勾选你关注的接口，并为它们选择图表类型。建议挑选两到三个接口，而不要全选四十八个。你目前的目标是验证整个链路是否通畅，在下一步中较小的第一批数据会更容易阅读和核对。

索引图表会将数据源与所选接口关联起来，并准备好它们的轮询器缓存条目；兼容的现有数据源可以被复用。图表创建成功的提示并不等于轮询已经成功。请检查缓存中是否包含预期的设备、接口 OID 和 RRD 路径。

## 确认数据采集正常

等待计划的采集周期执行完毕，然后检查时间戳和数据值。图表为空可能意味着启动初期的归一化、未知值（unknown）或采集失败。计算速率需要两次计数器读数，但两次轮询运行并不保证一定能生成完整有效的归档数据桶。

请按以下顺序检查三件事。

**轮询器已运行。** 在配置的日志中查找运行结束摘要。如果缺失，请检查计划任务调度、日志目标位置与权限，以及轮询器是否在完成前异常退出。请参阅[日志记录](/zh-cn/reference/logging/)。

**文件存在且已更新。** 从数据源或轮询器缓存中复制实际的 RRD 路径；不要根据主机名凭空猜测。路径和文件名都可以自定义。请参阅[文件布局](/zh-cn/reference/file-layout/)。通过 RRDtool 查询文件最后写入的时间：

```bash
rrdtool last /path/to/rra/the_actual_file.rrd
rrdtool lastupdate /path/to/rra/the_actual_file.rrd
rrdtool fetch /path/to/rra/the_actual_file.rrd AVERAGE --start end-30m --end now
```

成功写入时时间戳应当向前推进。较新的时间戳仍然可能伴随未知值，缓冲写入也可能推迟磁盘时间戳的更新。对于使用了 `rrdcached` 或 Boost 的环境，也需同时检查相应组件的刷盘（flush）状态。

**数据值不是未知值。** `lastupdate` 显示最新提供的原始值；对于计数器而言，这些是累计计数值，而不是计算后的流量速率。请检查 `fetch` 返回的已完成数据行，看是否存在有限的数值速率。启动时机、步长对齐、心跳（heartbeat）、上下限边界以及归档的未知数据阈值都会影响可用数据行何时出现。切勿仅凭前两行就断定存在故障。如果未知值持续存在，请检查采集到的原始数值、数据源类型、心跳配置和轮询器错误日志。

## 常见初次故障

| 现象 | 常见原因 |
|---|---|
| 保存成功，但系统描述查询报告错误 | 检查凭据、代理视图和采集器的网络可达性；仅描述为空不能作为充分依据 |
| Kadupul 报告 SNMP 会话错误，但笔记本电脑上运行 `snmpget` 正常 | 防火墙路径不一致，或者代理根据源 IP 地址限制了访问 |
| 设备显示为宕机，但 SNMP 数据仍能到达 | 可用性方法设置为 ICMP ping，而该环境无法打开原始套接字 |
| 描述正常显示，但没有数据 | 轮询器未设置计划任务，或以无权写入 RRD 目录的用户身份运行 |
| 数据查询未返回任何接口 | 代理视图排除了接口表，或者设备需要重新建立索引 |
| 第一个值为未知值，随后恢复正常 | 计数器的正常现象。它需要两次读数才能计算出速率 |
| 未知值持续存在 | 采集失败、无效数值、类型/上下限不匹配、心跳或归档归一化问题 |
| 数据记录一段时间后出现间断 | 轮询耗时超过了轮询间隔，或者设备对 SNMP 进行了限速 |
| 计数器速率不合常理 | 发生多次 32 位回绕、计数器重置、单位或数据源设置有误；在高速链路上请使用支持的 64 位计数器 |
| 重启后接口图表对应到了错误的端口 | 索引发生偏移。数据查询需要配置能够察觉此变化的重新索引方法 |

最后一点在管理数百台交换机之前非常有必要理解：SNMP 接口索引在设备重启或更换板卡后并不保证保持不变。数据查询中的重新索引方法正是为了确保图表始终指向同一物理端口。[数据查询与索引](/zh-cn/concepts/data-queries-and-indexes/)解释了各项选项。

当单台设备能够干净稳定地采集数据后，建议批量添加其余设备，而不是逐台重复操作。[自动发现设备](/zh-cn/guides/discover-devices-automatically/)以及[命令行工具](/zh-cn/reference/command-line-tools/)中介绍的工具，都远比把本页步骤重复五十次高效得多。
