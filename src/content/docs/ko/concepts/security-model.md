모니터링 시스템은 코드 품질과 관련 없는 세 가지 이유로 방어하기가 까다로운 대상입니다.

감시하는 모든 대상에 대한 자격 증명을 보유합니다. SNMP 커뮤니티, v3 사용자 이름 및 암호 문구를 비롯하여 디바이스에 필요한 모든 항목이 저장되어 폴러가 무인으로 사용할 수 있도록 합니다. 5분마다 이를 수동으로 입력할 인간은 없습니다.

예정에 따라 명령을 실행합니다. SNMP가 노출하지 않는 값을 수집하려면 스크립트를 실행해야 하며, 해당 스크립트의 정의는 데이터베이스에 저장되고 인터페이스를 통해 편집 가능한 구성입니다.

모니터링하는 머신이 생성하는 데이터를 수집합니다. 인터페이스 설명, 디스크 마운트 지점, 센서 이름 등 모든 것이 디바이스에서 수신되며 모든 것이 데이터베이스, 그래프 제목 및 다른 프로그램에 전달되는 인수로 귀결됩니다. 침해된 스위치는 피해자일 뿐만 아니라 입력 소스이기도 합니다.

이 중 어느 것도 결함이 아닙니다. 작업이 요구하는 본질적인 특성입니다. 다음은 각각이 아키텍처의 어디에 배치되는지 설명합니다.

## 신뢰할 수 없는 입력이 유입되는 위치

운영자가 통제할 수 있는 대략적인 수준에 따른 4가지 진입 지점입니다.

| 진입 지점 | 소스 | 도달 위치 |
|---|---|---|
| HTTP 매개변수 | 웹 서버에 도달할 수 있는 모든 사용자 | 데이터베이스, 페이지 출력 및 SQL |
| SNMP 값 | 폴링 대상 디바이스 | `host_snmp_cache`, 그래프 제목, RRD 경계, 스크립트 인수 |
| 스크립트 출력 | 로컬 스크립트 또는 통신한 대상 | `poller_output`, 이후 RRD 파일 |
| 업로드된 템플릿 및 패키지 | 가져오기 렐름을 보유한 사용자 | 템플릿 행, 패키지의 경우 디스크 파일 |

### HTTP 매개변수

요청 헬퍼는 `lib/html_utility.php`에 있습니다. `get_filter_request_var()`는 기본적으로 정수 유효성 검사를 수행하지만 비어 있거나 정의되지 않았거나 정규식 값에 대한 특수 사례도 포함합니다. 호출자는 여전히 작업에 특정 값이 필요하고 적절한지 확인해야 합니다. 필터링이 권한 부여를 확립하지는 않습니다.

`set_request_var()`는 `$_CACTI_REQUEST`에 값을 캐시하고 이를 요청 배열에 미러링합니다. `get_nfilter_request_var()`는 해당 캐시 또는 원시 요청을 읽으며 값 자체를 검증하거나 쓰지 않습니다. 따라서 후속 읽기에서 이전에 저장된 값을 관찰할 수 있으므로 읽기 순서가 중요합니다.

`log_validation`이 활성화되면 `get_request_var()`는 특정 캐시되지 않은 요청 읽기를 기록합니다. 직접적인 수퍼글로벌 읽기 및 `get_nfilter_request_var()`가 모두 포함되는 것은 아닙니다. 이는 진단 보조 수단이며 완전한 유효성 검사 감사 또는 시행이 아닙니다.

### SNMP 값

데이터 쿼리 검색은 선택된 인덱스 값을 `host_snmp_cache`에 저장합니다. 일반적인 SNMP 폴링 결과는 샘플 경로를 따릅니다. `lib/data_query.php`의 `data_query_format_record()`는 저장 전에 두 가지 변환을 적용합니다: 쿼리 정의의 선택적 `rewrite_value` 맵과 `mb_detect_encoding()`이 인코딩을 식별할 수 없는 모든 값에 대한 `bin2hex()`입니다. 두 번째는 바이너리 옥텟 문자열에 대한 보호이며 적대적인 콘텐츠에 대한 방어가 아닙니다.

거기서부터 값이 이동합니다. `substitute_snmp_query_data()`를 통해 그래프의 이름을 지정합니다. 데이터 템플릿이 최대값을 `|query_ifSpeed|`로 선언할 수 있으므로 RRD 최대값을 설정할 수 있습니다. 스크립트 쿼리의 인수가 되며, 여기서 `get_script_query_path()`는 먼저 각 부분을 `cacti_escapeshellarg()`에 전달합니다.

이스케이프 처리 및 [RRDtool 통합](/ko/reference/rrdtool-integration/)에 설명된 RRDtool 검증기가 여기서의 경계가 됩니다. 디바이스 데이터는 신뢰할 수 없는 상태로 유지되어야 합니다. 유효성 검사 및 이스케이프는 각 호출 지점의 속성이며 헬퍼의 존재가 모든 소비자가 이를 올바르게 사용함을 증명하지는 않습니다. 명령 구조와 대체된 인수를 모두 점검하십시오.

### 스크립트 출력

`exec_poll()`의 `popen()` 분기는 `fgets(..., 8192)`로 읽어 최대 8,191바이트 또는 첫 번째 줄바꿈까지 반환합니다. 대체 `shell_exec()` 분기는 서로 다른 출력 동작을 보이며 스크립트 서버 수집은 또 다른 경로를 따릅니다.

`prepare_validate_result()`는 숫자 및 알 수 없는 값, 16진수 형태 및 일부 다중 필드 출력 구조를 인식합니다. 또한 숫자 값을 얻기 위해 텍스트를 제거할 수도 있습니다; 범용적인 엄격한 스칼라 필터는 아닙니다. 후속 구문 분석 및 RRDtool 검증도 중요합니다. [데이터 입력 방법](/ko/reference/data-input-methods/)을 참조하십시오.

출력 검사는 이미 실행된 스크립트를 샌드박스화하지 않습니다. 수집을 활성화하기 전에 명령, 입력 허용 목록 및 운영체제 권한을 검토하십시오.

### 템플릿 및 패키지

두 가지 서로 다른 메커니즘이 하나의 렐름을 공유합니다.

**템플릿 가져오기**는 서명이 없는 일반 XML입니다. 템플릿, 데이터 쿼리 및 데이터 입력 방법을 만듭니다. 데이터 입력 방법은 명령줄이므로 업로드된 파일에서 폴러가 실행할 항목으로 이어지는 경로입니다. `lib/import.php`는 가져온 모든 `input_string`에 대해 `cacti_input_string_is_safe()`를 실행하고 쉘 메타 문자가 포함된 경우 메서드를 거부하고 다음을 기록합니다:

```
ERROR: Refusing to import data input method '<hash>' - input_string contains shell metacharacters
```

**패키지 가져오기**는 서명되어 있습니다. `import_read_package_data()`는 패키지의 내장 공개 키를 읽고 이를 `lib/import.php`에 컴파일된 3개의 키(두 개의 Cacti 키와 Kadupul 키)와 비교합니다. 다른 모든 키는 실패합니다. `<publickey>` 요소가 없는 패키지는 이전 Cacti 키를 요구하는 것으로 해석되며 이에 대해 확인되는 서명을 생성해야 합니다. `import_read_package_data()`는 검증을 시도하기 전에 2048비트 미만의 키를 거부하며, 512비트의 이전 키는 이 조건을 통과하지 못합니다. 포함된 각 파일은 별도로 확인되는 자체 서명을 전달합니다.

그런 다음 패키지는 선택한 파일을 쓸 수 있습니다. 허용되는 이름은 `scripts/` 또는 `resource/`로 시작하며 선택적으로 유효한 `plugins/<name>/` 접두사 아래에 배치됩니다. 가져오기 도구는 NUL 바이트, 디렉터리 순회 및 절대 경로를 거부하고 설치 루트 아래의 포함을 확인합니다; 단순히 디렉터리 이름을 포함하는 것만으로는 부족합니다. 대상의 쓰기 가능 여부도 쓰기 성공 여부를 제어합니다. 확인을 통과한 패키지는 설계상 실행 가능한 PHP를 설치 트리에 씁니다. 서명 확인은 허용된 서명 ID와 무결성을 보장하지만 코드가 무해함을 입증하지는 않습니다. 렐름 권한 부여, 경로 격리, 선택된 파일, 파일 시스템 권한 및 명령 허용 목록 정책도 중요합니다.

두 메커니즘 모두 렐름 17 뒤에 있습니다. 표준 템플릿 편집자 역할은 렐름 17과 렐름 2(데이터 입력 방법)를 보유합니다. 해당 권한을 가진 계정은 검증 및 허용 목록 처리에 따라 수집 명령을 정의할 수 있습니다. 그것이 역할의 목적이며 권한을 부여하기 전에 알아둘 가치가 있습니다. 검증된 워크플로 및 알려진 제한 사항은 [템플릿 가져오기 및 내보내기](/ko/guides/import-and-export-templates/)를 참조하십시오.

## 어떤 권한으로 무엇이 실행되는가

| 프로세스 | 시작 주체 | 실행 사용자 | 역할 |
|---|---|---|---|
| 웹 인터페이스 | 웹 서버 | 웹 서버 사용자 | 데이터베이스 읽기 및 쓰기, RRDtool을 통한 그래프 렌더링, 필요 시 RRD 파일 쓰기, 가져오기 시 패키지 파일 쓰기 |
| `poller.php` | 구성된 스케줄러 또는 서비스 | 스케줄러/서비스 계정 | 폴러 캐시 읽기, 수집기 시작, RRD 파일 쓰기 |
| `cmd.php` | 폴러 또는 실시간 수집 경로 | 실행 계정 | SNMP get 및 수집 명령 수행 |
| `script_server.php` | 수집기 | 실행 계정 | PHP 파일을 포함하고 자체 프로세스에서 함수 호출 |
| RRDtool | 웹 프로세스 또는 폴러 | 호출한 측의 프로세스 | `rra/` 아래의 파일 읽기 및 쓰기 |

그 중 두 가지는 더 자세히 살펴볼 가치가 있습니다:

**스크립트 서버는 샌드박스가 아닙니다.** 대상 파일을 장기 실행 PHP 프로세스에 포함하고 그 안에서 함수를 호출합니다. 해당 함수는 프로세스, 메모리 및 데이터베이스 연결을 공유합니다. `script_server.php`의 검사는 호출 발생 여부를 결정합니다: 포함할 파일의 `realpath()`가 `$config['base_path']` 또는 `$config['scripts_path']` 아래에서 확인되어야 하고, 포함 후 함수가 존재해야 하며, `ReflectionFunction::isInternal()`이 false여야 하고, 함수를 정의하는 파일도 허용된 루트 아래에 있어야 합니다. 이를 통과하면 코드는 폴러의 전체 권한으로 실행됩니다. 스크립트 서버 방식은 Kadupul 내부에서 PHP를 실행하는 방법이지 격리하여 실행하는 방법이 아닙니다.

**웹 프로세스는 RRD 파일을 쓸 수 있습니다.** 그래프 요청은 온디맨드 Boost 업데이트 및 파일 생성을 트리거할 수 있습니다. 디렉터리 생성 경로 하나를 폴러에 위임한다는 경고가 웹 쓰기 권한이 전면적으로 선택 사항임을 의미하지는 않습니다. 스토리지 사전 검사 및 유지 관리 조정에서도 계정 액세스 및 신뢰할 수 있는 숫자 UID/GID 구성을 확인합니다. 루트 권한으로 실행되는 생성은 스토리지 소유권을 일치시키려고 시도하지만 실패가 기록될 수 있습니다. [안전하게 업그레이드](/ko/guides/upgrade-safely/)를 참조하십시오.

웹 계정과 예약된 폴러 계정은 다를 수 있습니다. 웹 요청에서 시작된 실시간 수집은 웹 계정을 상속할 수 있으므로 명령 실행이 예약된 폴러의 신원으로 제한되지 않습니다. 상속된 Spine 통합은 실제 바이너리에 대한 별도의 검증이 필요합니다; 이 페이지는 지원되는 빌드를 규정하지 않습니다.

## 데이터베이스 계정에 필요한 것

동일한 데이터베이스 구성을 사용하는 프로세스는 일반적으로 계정을 공유합니다. 원격 수집기는 별도의 로컬 및 중앙 자격 증명을 가질 수 있습니다; 배포별 구성이 다를 수 있습니다. 구성된 모든 계정에 대해 실제 권한 부여를 검토하십시오.

| 요구 사항 | 이유 |
|---|---|
| Kadupul 스키마에 대한 전체 DML | 일반적인 운영 |
| Kadupul 스키마에 대한 DDL | 업그레이드 및 Boost 테이블 순환, 임시 테이블, 플러그인 수명 주기 변경과 같은 런타임 작업 |
| `mysql.time_zone_name`에 대한 `SELECT` | 사이트 및 데이터 수집기 시간대 목록이 해당 테이블을 직접 읽음 |

업그레이드에만 필요하다는 가정하에 DDL 권한을 제거하지 마십시오. 애플리케이션이 별도의 마이그레이션 ID로 일괄 전환되지는 않습니다; 계정 분리에는 영향을 받는 모든 런타임 경로에 대한 배포별 검증이 필요합니다.

`include/config.php`에는 데이터베이스 자격 증명이 포함되어 있으며 원격 수집기는 중앙 `$rdatabase_*` 자격 증명도 보유할 수 있습니다. 파일 시스템 권한, HTTP 액세스 규칙, PHP 핸들러 구성 및 백업 보호가 모두 중요합니다. PHP는 일반적으로 소스 코드를 제공하는 대신 파일을 실행하지만 직접적인 유출로부터 보호하는 것을 대신할 수는 없습니다.
[인터넷 연결 설치 보안](/ko/guides/secure-an-internet-facing-install/)을 참조하십시오.

디바이스 자격 증명도 같은 방식으로 저장됩니다. `host.snmp_community`, `host.snmp_password` 및 `host.snmp_priv_passphrase`는 일반 열로 암호화 단계 없이 `form_input_validate()`를 통해 `api_device_save()`에 의해 기록되며 폴러가 읽을 수 있도록 `poller_item` 행에 복사됩니다. 관련 테이블에 대한 읽기 액세스는 저장된 자격 증명을 노출할 수 있습니다; 이것이 모든 외부 자격 증명 소스에 대한 액세스를 의미하지는 않습니다. 사용자 암호는 예외입니다: `compat_password_hash()`는 `PASSWORD_DEFAULT`와 함께 PHP의 `password_hash()`를 사용하며 여전히 검증되는 레거시 MD5 해시는 다음 로그인 시 다시 해시됩니다.

## 강제됨, 그리고 단순한 관례

이는 코드 변경을 고려할 때 가장 중요한 구분입니다.

### 코드 메커니즘 및 범위

| 경계 | 메커니즘 |
|---|---|
| 인증 | 공통 인터페이스 페이지는 `include/auth.php`를 사용; 특수 엔드포인트는 자체 처리 |
| CSRF | 공유 웹 부트스트랩이 토큰 처리를 구성; 잘못된 형식의 토큰 배열 거부. 전면적인 적용을 가정하지 말고 각 엔드포인트 검토 |
| CLI 전용 스크립트 | SAPI가 `cli`가 아닌 경우 `include/cli_check.php`가 `404`로 응답하고 종료 |
| 데이터 쿼리 XML 위치 | `<base_path>/resource`에 대한 `cacti_path_is_within()` 검사, 실패 시 기록 및 거부 |
| 패키지 신뢰성 | 컴파일된 키에 대한 서명 확인, 최소 2048비트, 파일별 개별 서명 |
| 패키지 파일 배치 | 잘못된 이름 거부; 허용된 scripts/resource 접두사 및 확인된 루트 포함 확인 |
| 스크립트 서버 대상 | `realpath()` 포함 제한 및 위의 함수 검사 |
| 쉘 인수 | 적용되는 곳에서의 이스케이프, 구조화된 명령 헬퍼 및 유효성 검사기; 실제 호출 지점 점검 |
| RRDtool 인수 | `lib/functions.php`의 제어 문자 및 형식 유효성 검사기 |
| SQL | 준비된 헬퍼가 값을 바인딩; 동적 SQL, 식별자 및 비준비 호출은 여전히 검토 필요 |
| 원격 에이전트 호출자 | 소스 주소가 정확한 IP 또는 확인된 역방향 조회를 통해 `poller`의 활성화된 행과 일치해야 함 |

### 배포 및 호출 지점의 책임

| 경계 | 강제되지 않는 이유 |
|---|---|
| 요청 필터링 | 페이지가 `get_filter_request_var()`를 선택하는지 여부에 따름. `log_validation`은 보고할 뿐 차단하지 않음 |
| 출력 이스케이프 | `html_escape()` 및 `html_purify()`가 호출 지점별로 적용됨 |
| 페이지별 권한 부여 | 렐름 검사는 파일 이름으로 색인화된 `$user_auth_realm_filenames`를 사용. 매핑되지 않은 페이지는 해당 맵만으로 권한을 얻지 못함. 추가 검사가 적용될 수 있음; 플러그인 페이지는 자체 정책을 등록하고 시행해야 함 |
| 디렉터리 거부 | `cli/`, `log/`, `rra/`, `scripts/`, `contrib/`, `mibs/`, `cache/*` 아래의 `.htaccess`는 Apache 지시문임. nginx 또는 `AllowOverride`가 비활성화된 Apache에서는 적용되지 않음 |
| 정적 파일 보안 헤더 | `.htaccess.dist`는 이름이 변경되지 않은 상태로 제공됨. PHP 헤더 전송은 응답 경로 및 설정에 따라 달라짐; 정적 응답은 서버/프록시 구성에 따름 |
| 웹 및 폴러 사용자 분리 | 관례일 뿐 엄격한 요구 사항은 아님 |
| `include/config.php` 권한 | 설치한 사람에 의해 설정됨 |

`resource/` 및 해당 하위 디렉터리의 `index.php` 리디렉션 스텁은 디렉터리 목록 표시를 중지합니다. 이는 접근 제어가 아니며 명명된 파일에 대한 직접적인 요청을 차단하지 않습니다.

## 인증 전에 응답하는 엔드포인트

이것은 특수 진입 지점의 예시이며 공개 엔드포인트의 전체 목록이 아닙니다. 공통 포함 파일의 부재가 요청 경로의 다른 곳에서 인증이나 권한 부여가 없음을 증명하지는 않습니다.

| 파일 | 동작 |
|---|---|
| `auth_login.php`, `auth_changepassword.php` | 로그인 표면 자체 |
| `csp_report.php` | 브라우저 CSP 위반 보고서 수신 |
| `service_check.php` | `version`에 대한 1회 쿼리 후 `success` 또는 `fail` 응답. 인증 없는 활성 상태 프로브 |
| `link.php` | 외부 링크 행을 로드한 후 자체적으로 `is_realm_allowed($page['id'] + 10000)` 확인 |
| `remote_agent.php` | 소스 주소로 승인된 데이터 수집기 RPC |

`remote_agent.php`는 신중하게 고려해야 할 대상입니다. 권한 부여는 `remote_client_authorized()`에 의존하며, 이는 `get_client_addr()`를 `poller` 테이블의 호스트 이름 및 주소와 비교합니다. 공유 암호는 없습니다. 주소가 활성화된 데이터 수집기 행과 일치하는 호출자는 에이전트의 작업을 호출할 수 있습니다: 데이터 폴링, 데이터 쿼리 실행, 디바이스 핑, SNMP get 및 walk 수행, 그래프 데이터 요청, 네트워크 검색 실행 등입니다. 두 가지 보호 장치가 이를 규정합니다: 첫째, 활성화된 수집기 행이 최대 1개 반환되는 경우 함수는 즉시 false를 반환하므로 해당 사례는 거부됩니다. 둘째, 정확한 IP가 아닌 호스트 이름으로 일치하는 경우 역방향 조회가 수락되기 전에 정방향 조회로 확인되어야 합니다.

`get_client_addr()`는 `include/config.php`에 `$proxy_headers`가 설정되어 있지 않는 한 `REMOTE_ADDR`만 읽습니다. 기본값은 `null`입니다. 지원되는 프록시 헤더를 활성화하면 유효한 클라이언트 주소가 선택되는 순서가 지정된 소스가 변경됩니다. 신뢰할 수 있는 수신 프록시가 제어하는 헤더만 사용하고 클라이언트가 해당 값을 우회하거나 직접 제공하지 못하도록 방지하십시오. 이는 원격 에이전트 권한 부여 및 로그에 기록된 주소를 포함하여 시스템의 모든 주소 기반 결정의 의미를 가장 크게 바꾸는 단일 구성 행입니다.

## 게스트 액세스

`guest_user` 설정은 로그인 없이 그래프 페이지에 사용되는 권한을 가진 계정을 지정합니다. 기본적으로 사용자가 없으며 그래프를 보려면 다른 모든 것과 마찬가지로 인증이 필요합니다. 이를 설정하면 해당 계정이 볼 수 있는 내용이 웹 서버에 연결할 수 있는 모든 사람에게 공개됩니다. 그것이 이 기능의 목적입니다. 계정은 여전히 사용자 레코드에 존재합니다; 게스트 설정은 일반 로그인 없이 적용 가능한 그래프 권한을 사용할 수 있도록 하는 것입니다. 구성된 계정 이름뿐만 아니라 실제 요청 및 객체 권한을 확인하십시오.

## 변경 사항을 검토하는 방법

다음 세 가지 질문을 순서대로 던져보십시오:

어떤 프로세스가 어떤 사용자로 이를 실행하는가? 데이터 입력 방법의 답은 일반적으로 시작하는 수집기의 OS 계정입니다; 웹 트리거 수집은 예약된 수집과 다를 수 있습니다.

데이터가 전달되는 과정에서 무엇을 건드리는가? RRD 파일에만 도달하는 디바이스의 값은 하나의 경계를 넘었습니다. 그래프 제목의 동일한 값은 두 개의 경계를 넘었고 스크립트 인수에서는 세 개의 경계를 넘었습니다.

내가 의존하는 경계가 강제되는 것인가 아니면 단순한 관례인가? 관례라면 여러분이 작성하는 코드가 바로 그 시행 주체입니다.

관련 문서: 권한 부여 모델 자체에 대해서는 [권한과 접근 제어](/ko/concepts/permissions-and-access/), 실행 계약 및 입력 허용 목록에 대해서는 [데이터 입력 방법](/ko/reference/data-input-methods/), 데이터 수집기가 부여된 신뢰를 어떻게 다루는지에 대해서는 [원격 데이터 수집](/ko/concepts/remote-data-collection/)을 참조하십시오.
