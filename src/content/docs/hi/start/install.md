:::caution[उपयोग से पहले सत्यापित करें]
स्रोत उपलब्ध है, लेकिन अभी कोई समर्थित Kadupul रिलीज़ या माइग्रेशन पथ नहीं है। इन प्रक्रियाओं पर निर्भर होने से पहले बैकअप के साथ एक अलग प्रति पर इनका परीक्षण करें। [परियोजना की स्थिति](/hi/project/status/) देखें।
:::

इसे क्रम से एक बार पूरा करें। प्रत्येक चरण एक जाँच के साथ समाप्त होता है। आगे बढ़ने से पहले जाँच करें: यहाँ सूचीबद्ध हर विफलता का पता लगाना अभी आसान है और पोलर के एक सप्ताह तक चलने के बाद बहुत कठिन।

होस्ट-विशिष्ट पूर्वापेक्षाओं के लिए [Windows होस्ट पर Linux](/hi/guides/install-on-windows/) और [FreeBSD](/hi/guides/install-on-freebsd/) देखें। ये प्रक्रियाएँ शुरू से अंत तक स्वीकृति परीक्षण का प्रमाण नहीं हैं।

## पहले आपको क्या चाहिए

Kadupul एक PHP एप्लिकेशन है जो कॉन्फ़िगरेशन को MySQL या MariaDB में और मापों को डिस्क पर RRD फ़ाइलों में संग्रहीत करता है। यह पृष्ठ वर्तमान `main` स्रोत से एक नए मुख्य-सर्वर इंस्टॉलेशन का वर्णन करता है, न कि अपग्रेड या संग्रहीत LTS शाखा का। इसके चलने से पहले चार चीज़ें मौजूद होनी चाहिए।

| घटक | इसकी आवश्यकता क्यों है |
|---|---|
| सुरक्षा-समर्थित रिलीज़ पर PHP 8.4 या नया | वेब इंटरफ़ेस और पोलर चलाता है |
| MySQL या MariaDB | डिवाइस, टेम्पलेट, उपयोगकर्ता और पोलर कैश रखता है |
| RRDtool | राउंड-रॉबिन संग्रह बनाता और अपडेट करता है, और ग्राफ़ रेंडर करता है |
| net-snmp | डिवाइस से डेटा पूछने के लिए उपयोग किए जाने वाले क्लाइंट टूल और लाइब्रेरी प्रदान करता है |

PHP को [एप्लिकेशन मैनिफ़ेस्ट](https://github.com/kadupulhq/kadupul/blob/main/composer.json) द्वारा आवश्यक एक्सटेंशन की भी आवश्यकता होती है, जिसमें `pdo_mysql`, `gd`, `sockets`, `gmp`, `intl`, `ldap`, `mbstring`, `pcntl`, `posix` और `sqlite3` शामिल हैं। उन्हें कमांड-लाइन और वेब रनटाइम दोनों के लिए इंस्टॉल करें। [आवश्यकताएँ](/hi/reference/requirements/) Composer की आवश्यकताओं को इंस्टॉलर की अलग जाँचों से अलग करती है।

## चरण 1: रनटाइम इंस्टॉल करें

अपने वितरण के पैकेजों से इसके एक्सटेंशन के साथ PHP, अपना डेटाबेस सर्वर, RRDtool और net-snmp इंस्टॉल करें।

**इसकी जाँच करें।**

```bash
php -v
php -m | sort
rrdtool --version
snmpget --version
```

`php -m` को आवश्यक एक्सटेंशन सूचीबद्ध करने चाहिए। जब net-snmp कमांड-लाइन टूल उपलब्ध हों, तो PHP `snmp` एक्सटेंशन वैकल्पिक होता है। Composer निर्भरता स्थापना के दौरान अपने स्वयं के आवश्यक एक्सटेंशन की जाँच करता है; वेब इंस्टॉलर की एक अलग एक्सटेंशन जाँच होती है। एक रनटाइम फ़ॉलबैक Composer की आवश्यकता को नहीं हटाता है।

कमांड-लाइन और वेब-सर्वर PHP कॉन्फ़िगरेशन भिन्न हो सकते हैं। दोनों की जाँच करें। इंस्टॉलर कम से कम 400M के `memory_limit` और कम से कम 60 सेकंड के `max_execution_time` की अनुशंसा करता है; यह उनके असीमित मानों (`-1` और `0`) को भी स्वीकार करता है। उन अनुशंसाओं से नीचे के मान चेतावनियाँ उत्पन्न करते हैं, जबकि एक अनुपलब्ध `date.timezone` एक त्रुटि है। एक स्पष्ट समय क्षेत्र सेट करें, जैसे `UTC`, और कमांड-लाइन कॉन्फ़िगरेशन की पहचान करने के लिए `php --ini` का उपयोग करें।

## चरण 2: डेटाबेस और उसका उपयोगकर्ता बनाएँ

एक खाली डेटाबेस और उस डेटाबेस के अधिकारों वाला एक उपयोगकर्ता बनाएँ। स्थानीय डेटाबेस के लिए, इस SQL को डेटाबेस व्यवस्थापक के रूप में चलाएँ, उपयोग करने से पहले उदाहरण पासवर्ड को बदलें:

```sql
CREATE DATABASE kadupul CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kadupul'@'localhost' IDENTIFIED BY 'replace-with-a-unique-password';
GRANT ALL PRIVILEGES ON kadupul.* TO 'kadupul'@'localhost';
```

यदि PHP किसी अन्य मशीन से जुड़ता है, तो मिलान वाले डेटाबेस खाता होस्ट का उपयोग करें।

डेटाबेस सर्वर को अपनी समय क्षेत्र तालिकाओं को भरने की भी आवश्यकता होती है, और Kadupul उपयोगकर्ता को `mysql` डेटाबेस में उन तक पढ़ने की पहुँच की आवश्यकता होती है। यह अपने स्वयं के स्कीमा के बाहर एकमात्र विशेषाधिकार है। एक निगरानी प्रणाली के बारे में कुछ भी यह सुझाव नहीं देता है, और यह वैकल्पिक नहीं है; नीचे दी गई जाँच इसके बिना विफल हो जाती है।

```bash
# Populate the tables, then grant the one extra read the installer needs.
mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root -p mysql
mysql -u root -p -e "GRANT SELECT ON mysql.time_zone_name TO 'kadupul'@'localhost';"
```

**इसकी जाँच करें।** Kadupul डेटाबेस उपयोगकर्ता के रूप में लॉग इन करें और चलाएँ:

```sql
SELECT COUNT(*) FROM mysql.time_zone_name;
```

अनुमति त्रुटि के बिना लौटाया गया एक गैर-शून्य मान वही है जो आप चाहते हैं। शून्य का अर्थ है कि तालिकाएँ कभी लोड नहीं की गईं; एक त्रुटि का अर्थ है कि उपयोगकर्ता उन्हें नहीं पढ़ सकता है। दोनों इंस्टॉलर को रोक देते हैं।

सर्वर की अपनी चार सेटिंग्स इतनी महत्वपूर्ण हैं कि उन्हें अभी ठीक किया जाना चाहिए।

| सेटिंग | वांछित | क्यों |
|---|---|---|
| `max_allowed_packet` | 16M या अधिक | मुख्य सर्वर और रिमोट कलेक्टरों के बीच बड़ा सिंक |
| `character_set_server`, `collation_server` | `utf8mb4`, `utf8mb4_unicode_ci` | डिवाइस विवरण में मल्टी-बाइट वर्ण होते हैं |
| `innodb_file_per_table` | On | टेबलस्पेस को अलग और प्रबंधनीय रखता है |
| `innodb_buffer_pool_size` | सिस्टम मेमोरी का लगभग एक चौथाई | वर्किंग सेट को मेमोरी में रखता है |

इंस्टॉलर इनमें से अपनी रीडिंग की रिपोर्ट करता है और जो कम पड़ता है उसे फ़्लैग करता है, इसलिए आपको तालिका पर भरोसा करने की आवश्यकता नहीं है। एक बार लोड होने पर [डेटाबेस प्रदर्शन ट्यून करें](/hi/guides/tune-database-performance/) आगे की जानकारी देता है।

## चरण 3: इसे अनपैक करें, स्वामित्व ठीक करें और इसे सर्व करें

एप्लिकेशन को ऐसी जगह रखें जहाँ आपका वेब सर्वर इसे सर्व कर सके, फिर तय करें कि किस सिस्टम उपयोगकर्ता का इस पर स्वामित्व है। वह निर्णय स्थान से अधिक मायने रखता है। दो प्रक्रियाएँ यहाँ लिखती हैं: वेब सर्वर, और जो कुछ भी पोलर को शेड्यूल करता है। दोनों को एक ही उपयोगकर्ता के रूप में चलाएँ। पोलर को विशेषाधिकार-रहित चलाएँ और दोनों प्रक्रियाओं को वह पहुँच दें जिसकी उन्हें आवश्यकता है। गलत स्वामित्व या मोड बाद के अपडेट को रोक सकते हैं, भले ही ग्राफ़ रेंडर हो रहे हों।

### यदि आपने रिलीज़ अनपैक करने के बजाय रिपॉजिटरी क्लोन की है

एक Git चेकआउट को PHP निर्भरताओं और उत्पन्न ब्राउज़र संपत्तियों दोनों की आवश्यकता होती है। रिपॉजिटरी के `mise.toml` रनटाइम स्थापित होने के साथ, रिपॉजिटरी रूट से चलाएँ:

```bash
mise exec -- php "$(command -v composer)" install --no-dev --optimize-autoloader
mise exec -- npm ci --ignore-scripts
mise exec -- npm run build
mise exec -- php bin/console asset-map:compile
mise exec -- php bin/console about
```

Composer `include/vendor/` को भरता है और पिन की गई संगतता फ़ाइलों को पुनर्स्थापित करता है। npm बिल्ड `include/js/`, `include/fa/` और `include/vendor/flag-icons/` के तहत संपत्तियाँ बनाता है। स्रोत इंस्टॉलेशन के लिए केवल Composer पर्याप्त नहीं है।

एक निर्भरता-पूर्ण ऑफ़लाइन बंडल एक अलग बिल्ड आर्टिफ़ैक्ट है। एक सामान्य GitHub स्रोत संग्रह वह बंडल नहीं है। जब लक्ष्य होस्ट के पास इंटरनेट की पहुँच न हो, तो [ऑफ़लाइन बिल्ड और सत्यापन प्रक्रिया](https://github.com/kadupulhq/kadupul/blob/main/docs/symfony-migration.md#offline-installation) का पालन करें।

निर्भरताएँ स्थापित करने के बाद लिखने योग्य पथ तैयार करें:

| समूह | डायरेक्टरी | लिखने योग्य जब |
|---|---|---|
| स्थापना के दौरान | `resource/snmp_queries`, `resource/script_server`, `resource/script_queries`, `scripts` | केवल इंस्टॉल या अपग्रेड करते समय |
| स्थापना के दौरान | `include/vendor/csrf/`, या कॉन्फ़िगर किया गया `path_csrf_secret` स्थान | इंस्टॉलर को इंस्टॉलेशन-विशिष्ट सीक्रेट बनाना होगा; बाद में इसे सुरक्षित रखें |
| हमेशा | `log`, `cache/boost`, `cache/mibcache`, `cache/realtime`, `cache/spikekill`, सिस्टम अस्थायी डायरेक्टरी | इंस्टॉलेशन के पूरे जीवनकाल के लिए |
| Symfony रनटाइम | `var/cache`, और `var/log` यदि फ़ाइल लॉगिंग कॉन्फ़िगर की गई है | PHP रनटाइम और कैश-वार्मिंग उपयोगकर्ता के लिए |

RRD डायरेक्टरी को इंस्टॉलेशन के पूरे जीवनकाल के लिए लिखने योग्य होना चाहिए। यह आपके इतिहास को रखती है, इसलिए इसे उतनी ही सावधानी से रखें जितनी आप डेटाबेस डायरेक्टरी को देंगे।

वर्तमान माइग्रेशन को अभी भी लेगेसी लॉगिन, इंस्टॉलर और प्लगइन रूट की आवश्यकता है। इस संयुक्त इंस्टॉलेशन के लिए, निजी डायरेक्टरी, कॉन्फ़िगरेशन, निर्भरताओं और रनटाइम स्थिति तक पहुँच को अस्वीकार करने वाले स्पष्ट नियमों के साथ रिपॉजिटरी रूट को सर्व करें। पूरे इंस्टॉलेशन को `public/` पर स्विच न करें: यह अभी भी उपयोग में आने वाले लेगेसी रूट को हटा देगा। Symfony के अलग समापन बिंदु में अलग रूटिंग है; [माइग्रेशन निर्देश](https://github.com/kadupulhq/kadupul/blob/main/docs/symfony-migration.md) देखें।

Nginx के लिए, रिपॉजिटरी के [Nginx स्थान नियम](https://github.com/kadupulhq/kadupul/blob/main/tests/e2e/nginx.conf) से शुरू करें, रूट और PHP-FPM अपस्ट्रीम को अनुकूलित करें। जेनेरिक PHP हैंडलिंग से पहले अस्वीकार नियमों को रखें और `/app.php/...` के लिए PATH_INFO सुरक्षित रखें। Nginx `.htaccess` को नहीं पढ़ता है। HTTP पर RRD फ़ाइलों, लॉग और गोपनीय जानकारी को दुर्गम रखें; यह मानने के बजाय कि फ़ाइल अनुमतियाँ सर्व करने से रोकती हैं, वास्तविक सर्वर कॉन्फ़िगरेशन सत्यापित करें।

**इसकी जाँच करें।** पोलर उपयोगकर्ता बनें, प्रत्येक हमेशा-समूह डायरेक्टरी में एक फ़ाइल लिखें, फिर उसे हटा दें। एक अनुमति जो `ls -l` में सही दिखती है, उसे अभी भी SELinux या AppArmor द्वारा अस्वीकार किया जा सकता है, और फ़ाइल लिखना ही एकमात्र जाँच है जो इसे कवर करती है। फिर HTTP पर लॉग डायरेक्टरी के तहत एक फ़ाइल का अनुरोध करें। आप एक अस्वीकृति चाहते हैं।

## चरण 4: कॉन्फ़िगरेशन फ़ाइल लिखें

नए इंस्टॉलेशन के लिए, वितरित कॉन्फ़िगरेशन फ़ाइल को कॉपी करें:

```bash
cp include/config.php.dist include/config.php
```

किसी मौजूदा इंस्टॉलेशन के कॉन्फ़िगरेशन को ओवरराइट न करें। चरण 2 से डेटाबेस होस्ट, नाम, उपयोगकर्ता और पासवर्ड सेट करें। पहले इंस्टॉलेशन पर दो अन्य मान मायने रखते हैं: `url_path`, वह पथ जिसके तहत एप्लिकेशन को आगे और पीछे के स्लैश के साथ सर्व किया जाता है, और `poller_id`, जो मुख्य सर्वर पर `1` है और केवल रिमोट कलेक्टर पर कुछ और।

रिमोट कलेक्टर ब्लॉक को टिप्पणी के रूप में छोड़ दें। आप अभी इसे नहीं बना रहे हैं; जब आप तैयार होंगे तब [रिमोट डेटा संग्रह](/hi/concepts/remote-data-collection/) इसे कवर करता है। हर दूसरी सेटिंग में एक काम करने वाला डिफ़ॉल्ट मान होता है, इसलिए उनमें से किसी को भी बदलने से पहले [कॉन्फ़िगरेशन](/hi/reference/configuration/) पढ़ें।

Symfony की उन सुविधाओं के लिए जो इसका उपयोग करती हैं, PHP प्रक्रिया परिवेश में एक परिनियोजन-विशिष्ट `APP_SECRET` कॉन्फ़िगर करें। बूटस्ट्रैप डिफ़ॉल्ट रूप से `APP_ENV=prod` और `APP_DEBUG=0` पर रहता है और `.env` फ़ाइलें लोड नहीं करता है। यह लेगेसी इंस्टॉलर के CSRF सीक्रेट से अलग है।

**इसकी जाँच करें।** क्रेडेंशियल प्रदर्शित किए बिना सिंटैक्स की जाँच करें:

```bash
php -l include/config.php
```

ब्राउज़र में इंस्टॉलर खोलने से पहले अगले चरण में स्कीमा आयात करें।

## चरण 5: स्कीमा आयात करें

इंस्टॉलर को उम्मीद है कि तालिकाएँ पहले से मौजूद होंगी। आपके द्वारा बनाए गए डेटाबेस में शामिल स्कीमा लोड करें:

```bash
mysql -u kadupul -p kadupul < cacti.sql
```

इसे खाली डेटाबेस पर एक बार करें। यह कोई अपग्रेड स्क्रिप्ट नहीं है; इसे भरे हुए डेटाबेस में आयात करने से विफलता हो सकती है या परस्पर विरोधी और अधूरा डेटा छूट सकता है।

## चरण 6: इंस्टॉलर चलाएँ

ब्राउज़र में साइट खोलें और इसके माध्यम से आगे बढ़ें। इंस्टॉलर एक निश्चित क्रम में चलता है, और प्रत्येक चरण अगले चरण को नियंत्रित करता है:

1. स्वागत और लाइसेंस।
2. निर्भरता जाँच: PHP संस्करण और एक्सटेंशन, कमांड लाइन और वेब सर्वर दोनों के लिए चरण 1 से PHP सेटिंग्स, समय क्षेत्र तालिकाएँ, और चरण 2 से डेटाबेस सेटिंग्स। त्रुटियाँ अगले बटन को ब्लॉक करती हैं। चेतावनियाँ ब्लॉक नहीं करतीं, लेकिन उन्हें पढ़ें।
3. स्थापना का प्रकार: एक नया मुख्य सर्वर, या एक रिमोट कलेक्टर।
4. अनुमति जाँच: चरण 3 की डायरेक्टरी, उनमें लिखकर परीक्षण किया गया।
5. बाइनरी स्थान: PHP, RRDtool और net-snmp टूल के पथ।
6. डेटा स्रोत प्रोफ़ाइल और लॉन्चर अंतराल।
7. टेम्पलेट चयन: कौन से डिवाइस टेम्पलेट लोड करने हैं।
8. तालिका रूपांतरण, पुष्टि और स्वयं स्थापना।

उस सूची में आइटम 6 वह है जिसे पूर्ववत करना कठिन है। आपके द्वारा चुनी गई प्रोफ़ाइल बाद में बनाई गई प्रत्येक RRD फ़ाइल में लिखे गए स्टेप और संग्रह सेट को तय करती है, और प्रोफ़ाइल को संपादित करने से मौजूदा फ़ाइलें माइग्रेट नहीं होती हैं। अवधारण परिवर्तनों के लिए एक अलग, परीक्षण किए गए माइग्रेशन की आवश्यकता होती है; उन्हें हमेशा इतिहास को त्यागने की आवश्यकता नहीं होती है। यदि पीक मायने रखते हैं, तो सुनिश्चित करें कि प्रोफ़ाइल केवल औसत ही नहीं बल्कि अधिकतम मान भी रखती है: इस पर क्लिक करने से पहले [डेटा स्रोत और राउंड-रॉबिन संग्रह](/hi/concepts/data-sources-and-rras/) पढ़ें। वहाँ पेश किया जाने वाला लॉन्चर अंतराल एक मिनट या पाँच मिनट है। डेटा स्रोत प्रोफ़ाइल संग्रह अंतराल सेट करती है; लॉन्चर और प्रोफ़ाइल को लगातार कॉन्फ़िगर किया जाना चाहिए।

## चरण 7: डिफ़ॉल्ट क्रेडेंशियल बदलें

शामिल किया गया स्कीमा पासवर्ड `admin` के साथ `admin` नाम का एक व्यवस्थापक खाता तैयार करता है, जिसे इस तरह चिह्नित किया जाता है कि पहला लॉगिन बदलाव के लिए बाध्य करता है। यह एक अक्षम अतिथि खाते को भी तैयार करता है। इससे पहले कि इंस्टेंस किसी अन्य द्वारा पहुँचा जा सके पासवर्ड बदलें, जिसका अर्थ है कि इसे ऐसे नेटवर्क से जोड़ने से पहले जिसे अन्य लोग रूट कर सकते हैं।

## चरण 8: पोलर को शेड्यूल करें

पोलर को बाहर से शुरू किया जाना है। इसके संग्रह अंतराल और लॉन्चर अंतराल को सुसंगत रूप से कॉन्फ़िगर करें; पोलर एक मिनट या पाँच मिनट के लॉन्चर अंतराल का समर्थन करता है और इसके पास बहुत जल्दी आने वाले सामान्य रन के विरुद्ध सुरक्षा होती है। एक मिनट के लॉन्चर के लिए, विशेषाधिकार-रहित पोलर उपयोगकर्ता के crontab में यह प्रविष्टि स्थापित करें, `php` और एप्लिकेशन पथ को उनके पूर्ण पथों से बदलें:

```
* * * * * php -q /path/to/kadupul/poller.php > /dev/null 2>&1
```

या अपनी स्थापना पथ और विशेषाधिकार-रहित उपयोगकर्ता के लिए समायोजित `service/cactid.service` का उपयोग करके शामिल `cactid.php` डेमन चलाएँ। केवल एक लॉन्चर का उपयोग करें: डेमन का उपयोग करते समय cron कार्य या टाइमर अक्षम करें।

वास्तविक शेड्यूल को कॉन्फ़िगर किए गए लॉन्चर अंतराल से मिलाएँ। उप-मिनट संग्रह प्रोफ़ाइल के लिए, लॉन्च किया गया पोलर उस अंतराल के भीतर संग्रह चक्र चलाता है; इस cron प्रविष्टि के साथ उप-मिनट की गति को व्यक्त करने का प्रयास न करें।

**इसकी जाँच करें।** पोलर उपयोगकर्ता के रूप में हाथ से एक चक्र चलाएँ:

```bash
php -q /path/to/kadupul/poller.php --force --debug
```

`--force` प्रारंभिक-रन समय सुरक्षा को छोड़ देता है। शेड्यूलर को रोककर इस मैन्युअल जाँच का उपयोग करें ताकि यह किसी निर्धारित रन के साथ ओवरलैप न हो। यह अन्य रखरखाव या सुरक्षा जाँचों को बायपास नहीं करता है। आप सारांश पंक्ति के साथ एक स्पष्ट समाप्ति चाहते हैं। फिर शेड्यूलर को सक्षम करें और इसे दो अंतरालों के लिए अकेला छोड़ दें; पुष्टि करें कि आपके बिना एक और रन हुआ।

## क्या गलत हो सकता है

ये वे विफलताएँ हैं जो पहले इंस्टॉलेशन में वास्तव में सामने आती हैं।

| लक्षण | कारण | कहाँ देखना है |
|---|---|---|
| इंस्टॉलर सही दिखने वाली PHP सेटिंग्स पर रुकता है | वेब सर्वर और कमांड लाइन अलग-अलग `php.ini` फ़ाइलें पढ़ते हैं | `php --ini`, और वह फ़ाइल जिसकी वेब SAPI रिपोर्ट करता है |
| इंस्टॉलर समय क्षेत्र पर रुकता है | समय क्षेत्र तालिकाएँ लोड नहीं हैं, या Kadupul उपयोगकर्ता उन्हें नहीं पढ़ सकता है | `SELECT COUNT(*) FROM mysql.time_zone_name` |
| लिखने योग्य दिखने वाली डायरेक्टरी पर अनुमति चरण विफल होता है | गलत स्वामी, या SELinux और AppArmor | पोलर उपयोगकर्ता के रूप में एक फ़ाइल लिखें |
| स्थापना पूरी हो गई, कोई डेटा कभी नहीं आता | पोलर कभी शेड्यूल नहीं किया गया | हाथ से `poller.php --force --debug` चलाएँ |
| कुछ चक्रों के लिए डेटा, फिर कुछ नहीं | पोलर गलत उपयोगकर्ता के रूप में चल रहा है, जिससे ऐसी फ़ाइलें छूट जाती हैं जिन्हें वेब उपयोगकर्ता अपडेट नहीं कर सकता | RRD डायरेक्टरी में फ़ाइलों का स्वामी |
| ग्राफ़ छोटे अंतरालों से भरे हैं | निर्धारित अंतराल और कॉन्फ़िगर किया गया अंतराल असहमत हैं | crontab, कॉन्फ़िगर किए गए अंतराल के विरुद्ध |
| Composer स्थापना से इनकार करता है | PHP 8.4 से नीचे है या मैनिफ़ेस्ट-आवश्यक एक्सटेंशन गायब है | `php -v`, `php -m`, और Composer का त्रुटि आउटपुट |
| पोलर एक से अधिक प्रक्रिया नहीं चला सकता | `pcntl` या `posix` गायब है | `php -m` |

[लॉगिंग](/hi/reference/logging/) कवर करता है कि प्रत्येक कहाँ रिकॉर्ड करता है। [गुम डेटा का निवारण करें](/hi/guides/troubleshoot-missing-data/) उस मामले को कवर करता है जहाँ इंस्टॉलेशन ठीक है और एक डिवाइस नहीं है।

## इसे सार्वजनिक करने से पहले

पोलर एक सिस्टम उपयोगकर्ता के रूप में चलता है और RRDtool और आपकी संग्रह स्क्रिप्ट निष्पादित करता है। इंस्टॉलेशन को ऐसी चीज़ के रूप में मानें जो कमांड चलाती है, क्योंकि यह वास्तव में ऐसा करती है।

- इसे TLS पर सर्व करें।
- डिफ़ॉल्ट व्यवस्थापक पासवर्ड को थोड़ी देर के लिए भी न छोड़ें।
- डेटाबेस उपयोगकर्ता को उसके अपने डेटाबेस तक सीमित करें।
- RRD और लॉग डायरेक्टरी को डॉक्यूमेंट रूट से बाहर रखें।
- जब तक आप अन्यथा निर्णय न लें, अतिथि खाते को अक्षम छोड़ दें।

[इंटरनेट से जुड़े इंस्टॉलेशन को सुरक्षित करें](/hi/guides/secure-an-internet-facing-install/) में बाकी बातें हैं। अगला: [अपना पहला उपकरण जोड़ें](/hi/start/first-device/).
