:::caution[使用前に検証してください]
ソースコードは公開されていますが、正式にサポートされた Kadupul のリリースや移行パスは
まだ存在しません。本番環境で運用する前に、バックアップを備えた隔離環境で手順を
検証してください。[プロジェクトステータス](/ja/project/status/)を参照してください。
:::

物理的なファイル破損は極めて稀です。破損と報告されるファイルのほとんどは物理的には健全であり、
データベースとの定義不一致、ポーラーの書き込み権限不足、あるいはファイル自体とは無関係な理由による
データ受信停止が原因です。一方の修復手順が他方の状態を悪化させる恐れがあるため、作業前に
状況を正確に特定してください。

:::danger[必ず元ファイルを保護してください]
**本ページの手順を実行する前に、必ずファイルの複製を取得してください。** 独立した候補ファイルに
リストアし、本番ファイルを置き換える前に十分に検証してください。アーカイブの縮小や削除を行うと、
蓄積された履歴データが失われます。最大値の変更は以後の入力検証に影響を与えるのみであり、
過去の保存値を遡って修正することはありません。RRD ファイルに自動取り消し機能はありません。
:::

## 1. 障害の特定

| 画面上の状態 | 一般的な原因 | 参照先 |
|---|---|---|
| グラフが描画されずエラーメッセージが表示される | ファイルが存在しない、読み取り不能、またはディレクトリが書き込み不可 | ステップ 2 |
| エラーは出ないがグラフが空白のまま | 選択範囲内に有効なデータが存在しない、またはグラフ定義の問題 | [欠損データのトラブルシューティング](/ja/guides/troubleshoot-missing-data/) |
| ある特定の日時でグラフが止まり更新されない | ポーラーの停止、パーミッションの不備、またはハートビート切れ | ステップ 3 |
| 設定を変更していないのにグラフの形状が急変した | 実ファイルとデータベースの設定内容に不一致が生じている | ステップ 4 |
| 保持されているデータがすべて不明値 (unknown) | データ収集、タイムスタンプ、閾値、またはデータソース設定の確認が必要 | [欠損データのトラブルシューティング](/ja/guides/troubleshoot-missing-data/) |
| `rrdtool` がファイルの読み取りを拒否する | パス指定誤り、アクセス権限不足、非互換フォーマット、またはファイル破損 | ステップ 2 と 3、次に 5 |

Kadupul は最初のケースにおいて壊れた画像の代わりに判読可能なテキストを表示し、
ディレクトリの書き込み不可とファイルの書き込み不可を明確に区別し、ファイル不在の場合はポーラーが
まだ実行されていない可能性として通知します。この表示は手がかりに過ぎず確定診断ではありません。
削除、パスの変更、またはリストアの中断によってもファイル不在となります。

## 2. ファイルの検査

データソースの専用ページでは2種類の画面がセッション単位で利用可能です。
デバッグビューには、Kadupul が現在そのデータソースに対して実行するであろう `rrdtool create` コマンドが表示されます。
ここで重要なのは情報ビューです。実ファイルを `rrdtool info` で読み込み、
データベース上のデータソース定義と比較して差異を出力します。再構築を行わずに解決できる差異がある場合は、
自動実行するのではなく、管理者が手動で実行すべき `rrdtool tune` や `rrdtool resize` コマンドを
テキスト形式で提示します。

シェルから実行する場合も同様に以下から始めます。

```bash
rrdtool info /path/to/rra/42/1337.rrd
```

ヘッダーからステップ、最終更新時刻、各データソース名と型、
ハートビート、最小値・最大値、および各アーカイブの統合関数、行数、
解像度を確認できます。このコマンドが失敗した場合はエラー内容を保存し、破損と判断する前に
パス、パーミッション、RRDtool の互換性を確認してください。`info` コマンドの成功はメタデータが
読めたことを示すのみです。履歴データを検証するには `fetch` の出力やテストダンプも確認してください。

## 3. 最初にシステム・機械的要因を確認する

| 確認項目 | 修復作業の前に確認すべき理由 |
|---|---|
| ファイルの所有者とパーミッション | メンテナンス中に root で作成されたファイルは、以後ポーラーから一切書き込めなくなります |
| ディレクトリの所有者とパーミッション | ポーラーは書き込み権限のないディレクトリに置換ファイルを生成できません |
| ディスクの空き容量と inode | ファイルシステムが満杯になると書き込みが途中で途切れ、破損と同様の症状になります |
| 他の書き込みプロセスの有無 | 並行または不規則な書き込みが発生するとスナップショットが無効化されます。ログを点検してください |

メンテナンス作業は必ず RRD ファイルを所有・更新するアカウントで実行し、パーミッション、
所有者、グループを正しく維持してください。リモートコレクター、定期ジョブ、手動スクリプトを含む
すべての書き込みプロセスを停止した上でファイルのコピーや置換を行ってください。保留中の書き込みキューのフラッシュは、
データ生成元を停止させた後にのみ実施してください。通常のシェルコマンドは Kadupul のストレージロックを獲得しません。
[ストレージ要件](/ja/reference/requirements/)および[バックアップと復元](/ja/guides/back-up-and-restore/)の休止手順を参照してください。

## 4. チェッカーが検出した内容を確認する

Kadupul は有効なデバイス上のグラフ関連データソースを定期的に巡回し、
検出結果を記録する機能を備えています（ディスク上の全ファイルを網羅するものではありません）。この機能は
デフォルトで無効になっています。有効化の場所：Configuration -> Settings -> Data。

| 設定項目 | デフォルト | 効果 |
|---|---|---|
| Enable RRDfile Check | off | 有効化するまでチェックは一切行われません |
| Check Frequency | 4 hours | 1 hour、24 hours、または各 boost サイクル終了後の実行も選択可能 |
| Number of RRDfile Check Processes | 1 process | ファイル一覧を複数の並列ワーカーに分散して処理 |
| RRDChecker Timeout | 1 hour | この時間を超過した処理は強制終了されます |

検出結果は、対象デバイス、データソース、内部データソース ID、メッセージ、
日時を含む一覧として記録されます。経過時間での絞り込みやテキスト検索が可能で、
対処完了後はリストをクリアできます。

記録されるメッセージとその意味は以下の通りです。

| メッセージ | 意味 |
|---|---|
| RRDfile does not exist | ファイルが作成されていない、移動もしくは削除された、または設定パスが変更された |
| RRDfile is not writable | ポーラーの実行ユーザーにファイルの書き込み権限がありません |
| RRDfile modify time older than hour | 少なくとも1時間以上ファイルへの書き込みが行われていません |
| Last update value in RRDfile is older than 1 hour | ファイル内部の最終更新タイムスタンプが古縮しています。更新日時より強力な証拠です |
| The RRDfile step does not match the Data Source Profile step | プロファイルの設定と異なるステップ間隔で作成されています |
| There are more, or less, Data Sources in the database than in the RRDfile | ファイル作成後にテンプレート側のフィールドが増減しています |
| The Data Source '...' exists in RRDfile, but not in database | ファイル側にのみ存在するフィールド名を特定します |
| Data Source name '...' exists in the Database, but not in RRDfile | ポーラーが書き込もうとしているがファイル内に格納先がないフィールド名を特定します |
| The RRDfile Minimal Heart... is lower than polling interval | ハートビートがポーリング間隔以下に設定されています。到着の遅れたサンプルが不明値になります |
| The RRDfile minimal heartbeat... should be 'N' and is currently 'M' | ファイルのハートビートがプロファイルより低くなっています。大きな値は検知されません |
| Stale values for last 24 hours, or last hour | 対象期間内に読み戻されたすべてのサンプルが不明値 (unknown) でした |
| More than 50% (n/m) values are NaN in last 24 hours, or last hour | 収集データの一部に欠損が発生しています |
| No data returned, maybe corrupted Data Source | ファイルに対して fetch を実行しても何もデータが返されませんでした |

この検査処理は、データベースに記録されたステップとハートビートをプロファイルに合わせて自動修正し、
プロファイルとデータソース定義間のズレを解消しますが、物理ファイル自体には
手を加えません。ファイルとデータベース間のフィールド数の不一致は自動修復されず通知のみ行われます。
どちら側が正しい定義であるか自動では判断できないためです。

## 5. ダンプ、編集、リストア

RRDtool は正常なファイルを XML にシリアライズし、そこから候補ファイルを再構築できます。
これは既知の構造的差異の修正には有効ですが、消失したサンプルを復元することはできず、
破損したファイルが必ず解析できるとも限りません。Kadupul も構造変更時に dump/restore ヘルパーを利用します。
ローカルのリストア処理は一時的な別名ファイルを生成し、成功時に目的のファイルへ上書きリネームしますが、
これはバックアップの代わりにはなりません。

書き込みプロセスを停止した状態で、RRD の所有者ユーザーとして実行してください。サンプルのパスを
実際のデータソースパスに置き換えてください。候補ファイルが同一ファイルシステム上に配置されるよう、
作業ディレクトリは元ファイルと同じ階層に作成します。

```bash
set -eu
umask 077
rrd=/path/to/rra/42/1337.rrd
work=$(mktemp -d "$(dirname "$rrd")/rrd-recovery.XXXXXX")
cp -p "$rrd" "$work/original.rrd"
rrdtool dump "$work/original.rrd" > "$work/recovery.xml"
# Edit recovery.xml only when the required correction is understood.
rrdtool restore "$work/recovery.xml" "$work/candidate.rrd"
rrdtool info "$work/candidate.rrd"
rrdtool fetch "$work/candidate.rrd" AVERAGE --start end-1h --end now
```

過去の正常なデータが含まれている時間範囲と統合関数を指定して fetch を実行してください
（最後の1時間はあくまで例です）。元ファイルと候補ファイルのデータソース名、
ステップ、アーカイブ構成、最終更新時刻、サンプル値を綿密に比較してください。内容を変更しない dump/restore でも
バイナリ配置が変わることがあるため、ファイルハッシュの一致を求めるのではなくデータ値を比較してください。

元ファイルのバックアップは必ず保持してください。検証完了後、すべての書き込みを停止したまま、
候補ファイルのパーミッション、所有者、グループを正しく整えてから本番パスへリネームします。
データ収集を再開する前に、ポーラーアカウントがファイルを読み書きできることを確認してください。この例では
不完全な候補ファイルが配備されるのを防ぐため、最終配置の手前で意図的に停止しています。

XML および候補ファイルの生成には追加のディスク容量が必要です。失敗したダンプによって中途半端な
XML が残ることがありますが、それをリストアしてはいけません。アクセス権、空き容量、エラー内容を確認してください。
これらの確認を経てもダンプができない場合は、正常なバックアップから復元してください。RRDtool の
[`restore -f`](https://oss.oetiker.ch/rrdtool/doc/rrdrestore.en.html) は出力先の上書きを
許可しますが、本手順では安全のため意図的に新しい出力先を指定しています。

## 6. 残るデータと失われるデータ

| 障害・損傷の種類 | 履歴データの復旧可否 |
|---|---|
| ファイル書き込み不可（ファイル自体は正常） | 蓄積された履歴は保持されます。アクセス権を修正しても欠落した更新分は戻りません |
| ハートビート、最小値、最大値の設定ミス | 復旧可能。`rrdtool tune` は保存データを損なうことなくヘッダーのみを変更します |
| ステップの不一致 | 明示的な検証済み変換が必要。データベースの変更だけではファイルは変換されません |
| ファイル内にデータソースが不足 | 既存フィールドのデータは残ります。新規フィールドは空の状態で始まります |
| アーカイブの削除・未作成 | 不可能。一度も保存されなかった解像度のデータを後から再構築することはできません |
| resize によるアーカイブ行数の削減 | 不可能。削除された行はコマンドが実行された瞬間に完全に消失します |
| ファイルの末尾欠損・ダンプ失敗 | 不可能。バックアップからリストアしてください |
| ヘッダーは正常だが末尾が破損 | ヘッダーが読めるからといってダンプが完全であると過信せず、ダンプ不能時はバックアップを使用してください |

ポーラーの間隔変更やデータソースの別プロファイルへの移動を行っても、
既存ファイルが自動的に再構成されることはありません。RRDtool にはステップ変更を含む構造的な
[`tune` 操作](https://oss.oetiker.ch/rrdtool/doc/rrdtune.en.html) が用意されていますが、
データ欠落のない間隔変更を過信せず、環境とアーカイブ構成に応じた変換動作を必ず検証してください。
[データソースとアーカイブ](/ja/concepts/data-sources-and-rras/)および
[データ保持期間の管理](/ja/guides/manage-data-retention/)を参照してください。`tune` で最大値を
引き上げるのは安全ですが、引き下げると新上限を超える以後の値がすべて不明値として記録されます。

## 7. 保持可能な履歴を残して再構築する

Kadupul には古い読み取り可能ファイルから新しいファイルへデータを移植する splice ユーティリティが付属しています。
この処理結果はあくまで候補として扱ってください。欠損の穴埋めや正当なゼロ値の書き換えを行う可能性があるため、
測定履歴の完全な無損失コピーとはなりません。メインデータコレクター上のアプリケーションルートから、
書き込み可能な信頼できるディレクトリ内の隔離コピーを使用して実行してください。

ステップ5の非公開作業ディレクトリ `$work` 内に目的の構造を持つ `new.rrd` を作成し、
結合処理をプレビューします。

```bash
php cli/splice_rrd.php --oldrrd="$work/original.rrd" \
                       --newrrd="$work/new.rrd" \
                       --finrrd="$work/merged.rrd" --dryrun
```

両方の入力ファイルが既に存在し、ツールの書き込み権限チェックを通過する必要があります。
新ファイル側が骨格構造を提供します。`--finrrd` を指定しない場合、新ファイル名に `.new` が
付与されたファイルが出力されます。以前の候補ファイルを誤って上書きしないよう、明示的な出力パスを指定してください。
`--dryrun` は一時的な XML と SQLite（利用可能な場合）を用いて解析・結合を行いますが、最後の RRD リストアは
スキップします。これは最終リストアの成功を保証するものではありません。独立した候補を生成するには `--dryrun` を外してください。
プレビュー時に `--owner` を指定せず、必要なサービスアカウントで実行し、配置前に出力ファイルの実際の所有者を確認してください。

:::caution[splice はゼロ値を欠落（穴）として扱います]
結合処理は新ファイルを走査し、値が不明値**またはゼロ**のスロットごとに
旧ファイルから最も近い一致値を探してその値で上書きします。そのため、新ファイル側の正当なゼロ値は
古いデータによって上書きされます。長期間正常にゼロを示すメトリクス（非稼働ポート、空のキュー、
停止中のカウンタなど）では、本番配置前に結果を綿密に確認してください。また、旧ファイル側の不明値も
前後の値で補完されるため、結合出力が欠落部分に架空の連続性を作り出す可能性があります。
:::

結合処理の完了後、データソースが想定しているパスにファイルを配置し、ポーラーに必要な
所有権を設定して、グラフが正しく描画されることを確認してください。

## 8. ギャップの穴埋めとその慎重な検討

| ツール | 書き込む内容 |
|---|---|
| `cli/batchgapfix.php` | 多数のデバイスにわたり、直前の正常値または平均値を用いて日付範囲の欠損を並列補完する |
| `cli/float_rrdfiles.php` | 同様の dump/restore 経路を通じて、特定グラフのデータ範囲をオフセット調整する |

これらはいずれも架空の測定値を生成します。そのタイムスタンプにおいてデータ収集は実際には行われておらず、
処理後はファイル内で架空の数値と実測値を区別する手段が失われます。メンテナンスによるポーラー停止や
移行作業など、欠落がシステム障害によるものではないと確信できる場合にのみ使用してください。
キャパシティ計画や課金計算に用いるメトリクスには絶対に使用してはいけません。同様の注意が
[スパイクの除去](/ja/guides/remove-spikes-from-data/)にも当てはまります。

## 9. 単一データソースの自動デバッグ

挙動が疑わしい単一のデータソースに対して、Kadupul はその後の数回のポーリング周期にわたり
デバッグ検査を実行し、判定結果を出力できます。ファイル存在の有無、ファイルとディレクトリの
書き込み権限、所有者とポーラー実行アカウントの整合性、データソースのアクティブ状態、
定義と実ファイルの整合性、ポーリング後のタイムスタンプ更新、値の有効性を確認します。
自動修復機能は極めて限定的です。比較によって算出された `rrdtool tune` の推奨コマンドのみを実行し、
リストが空の場合やファイルが書き込み不可の場合は理由をログに記録して処理を中断します。
ファイルの再作成、データソースの追加、アーカイブの改変などは一切行いません。

## 10. ファイル削除に伴う個別の危険性

Kadupul はデータソースが存在しなくなった孤立アーカイブファイルを追跡し、
削除の選択肢を提示します。また、データソース削除時に連動して自動処理するよう設定することも可能です。
方式は完全削除、または退避ディレクトリへの移動の2通りです。

:::danger[削除は取り消せません]
削除方式を選択するとファイルはディスクから物理的に消去されます。ゴミ箱はなく、
データはデータベースにも残りません。対象の全ファイルが完全に不要な孤立ファイルであると確信できない場合は、
移動方式を選択して指定ディレクトリに退避させ、後から手動で整理してください。
:::

ファイルは実際には孤立していないのに孤立しているように見えることがあります。データソースのパス変更、
不完全なリストア、新しい ID で再登録されたデバイスなどは、参照先を失ったファイルを残します。
削除を実行する前に、自身の変更履歴記録と照合してください。

## 障害モード

| 兆候 | 原因 |
|---|---|
| 修復が成功したのにグラフが空白のまま | アクセス権、選択中の時間範囲、データ収集状態、グラフ定義を確認してください |
| `rrdtool dump` がエラーを出力する | 破損と断定する前に、パス、パーミッション、ストレージ状態、形式を確認してください |
| Tune を適用したが何も変化しない | ヘッダーの変更は過去の不明値を遡って補完しません。ファイルと DB の定義を再確認してください |
| 収集間隔を変更した後に全域で細かなギャップが発生する | ファイル内部に古いステップとハートビートがそのまま残っています |
| 結合後ファイルで、新ファイル側でゼロだった箇所に古いデータが入る | 仕様通りの動作です。splice は不明値だけでなくゼロ値も補完対象とします |
| チェッカーの警告リストが増え続け減少しない | 検出結果はクリア操作を行うまで保持されます。原因を解消しても自動消去はされません |

アーカイブディレクトリとデータベースは同一スケジュールで必ずペアでバックアップし、
リストア手順を定期的に検証してください。復元可能な範囲は、バックアップ取得時点で保持されていたデータに
厳密に制限されます。[バックアップと復元](/ja/guides/back-up-and-restore/)を参照してください。
