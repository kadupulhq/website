:::caution[继承的 RRDtool 代理行为]
Kadupul 不支持 RRDtool 代理部署。请使用本地 RRDtool 存储
(`storage_location = 0`)。本页中的代理设置、协议说明及工作流程仅记录了继承而来的行为，并非受支持的部署或迁移路径。参见 [RRDtool proxy](/zh-cn/reference/rrdproxy/)。
:::

Kadupul 的 Web 应用程序、数据库、计划采集和 RRD 存储各司其职，但它们的执行路径存在重叠。明确哪个操作发生故障有助于缩小排查范围；界面工作正常并不能证明采集工作正常。

**Web 界面**是一个 PHP 应用程序。它负责管理配置，并渲染或提供缓存的图表。某些 Web 操作也会触发采集，例如实时图表请求，而普通图表请求也可以触发挂起的 RRD 更新。

**数据库**保存配置、权限、运行状态、poller 缓存和测量队列。采集到的数值在等待 RRD 写入或重试期间可以暂存在数据库中；它不仅仅是一个配置存储库。

**poller** 协调计划工作和采集子进程。采集结果在标准写入器或延迟写入器更新 RRD 文件之前，会先经过数据库队列。

**RRD 文件**保存有界的时间序列历史数据。一个数据源通常对应一个包含其字段的 RRD 文件；创建图表可以重用现有数据源，创建元数据并不保证对应文件已经存在。

## 边界划分

| 边界 | 跨越内容 | 承载方式 |
|---|---|---|
| 界面到数据库 | 配置、会话、授权、缓存的任务及运行数据 | SQL；数据库可以是远程主机 |
| 界面到文件 | 图表读取、缓存图像以及符合条件的按需 RRD 更新或创建 | 文件系统和 RRDtool |
| Poller 到数据库 | 工作清单、采集到的数值、保留的队列、状态及倒计时 | SQL |
| 采集到设备 | SNMP、采集脚本和连通性检查 | 网络或本地命令；也支持 Web 触发的采集 |
| 写入器到文件 | 分组样本，每次更新可能包含多个时间戳 | RRDtool 命令及确认管道 |
| 数据库服务器到 RRD 文件 | 在常规应用路径中无直接 RRD 更新 | 应用程序写入器代码协调这两个存储 |

数据库行将数据源与设备及其配置的文件路径关联起来。RRDtool 文件描述序列和归档；它们不能替代应用程序的映射关系。网络流量不仅限于设备轮询：数据库连接、远程采集器和其他已配置的集成也可能跨主机通信。

应以一致的方式备份数据库状态、挂起样本和 RRD 文件。仅恢复数据库无法恢复历史 RRD 内容，而仅恢复文件会遗漏配置和未刷盘的样本。在未校对路径的情况下移动文件可能导致文件丢失错误或写入滞留；这并不必然表现为无声的采集失败。参见[备份与恢复](/zh-cn/guides/back-up-and-restore/)和[迁移到新硬件](/zh-cn/guides/migrate-to-new-hardware/)。

## 为什么长期历史数据使用 RRD 文件

长期图表历史存储在 RRD 中，但测量队列保留在数据库中。在此版本中，常规在途队列使用 InnoDB，延迟写入则将样本保留在 Boost 表中。写入失败或远程传输延迟可能会使这些队列膨胀。参见[大容量写入](/zh-cn/concepts/high-volume-writes/)。

RRD 在选定的分辨率下分配固定数量的行。常规更新会重用该空间，而不是无限追加历史记录。在结构未变的情况下，文件大小是有界的；但添加数据源、更改结构、保留恢复副本或堆积队列仍会增加总存储需求。

这里的权衡是预先确定的保留策略。一旦细粒度的历史数据到期或被合并，后续的结构更改将无法重建已丢弃的细节。参见[数据源与轮转归档](/zh-cn/concepts/data-sources-and-rras/)。

配置和运行状态使用数据库，是因为应用程序需要共享更新和关系查询。这并不意味着每项关系都必须由数据库外键强制约束，也不意味着行存储一定会无休止膨胀；这描述的是该应用程序的职责划分。

## 两条路径，共享两个部件

常规页面或图表请求通常遵循以下路径：

1. 浏览器发送请求；PHP 加载配置并连接到数据库。
2. 请求应用身份验证以及相关的领域/对象授权。
3. 控制台操作读取或更新配置，并可能触发额外任务。
4. 图表请求可以检查挂起的 Boost 样本和图像缓存，或者组装 RRDtool 命令并读取配置文件。参见[图表如何绘制](/zh-cn/concepts/how-graphs-are-drawn/)。
5. 实时图表请求可以启动实时采集器并使用独立的临时数据。图表变平本身既不能证明文件为空，也不能证明采集和渲染成功。

计划轮询通常遵循以下路径：

1. 调度程序启动 poller，检查启用状态、计时和存储。
2. 它从 poller 缓存中选择到期的工作并启动采集子进程。
3. 子进程查询设备或运行采集脚本，并将结果暂存到数据库中。
4. 相应的写入器处理分组样本，在配置了延迟队列时使用延迟队列，并保留可重试的失败项。
5. 在数据库中更新运行状态和调度状态。

有关顺序和故障处理，请参见 [Poller 生命周期](/zh-cn/reference/poller-lifecycle/)。这些路径共享数据库和存储资源，并可能产生竞争。重启 Web 服务器无法修复独立调度的 poller，但 Web 请求可以参与采集和写入；请排查实际发生故障的进程。

## 什么进程以什么用户运行

| 进程 | 运行身份 | 启动者 |
|---|---|---|
| PHP Web 应用程序 | Web 服务器或 PHP-FPM 池账户 | Web 服务器 |
| 计划 poller | 调度程序配置的账户 | cron、任务计划程序或配置的服务 |
| RRDtool | 通常继承启动进程的账户 | Web、poller 或维护路径 |
| 采集脚本 | 通常继承其采集器的账户 | 计划采集或 Web 触发的采集 |

所有参与的写入器账户都需要对配置的存储拥有适当的访问权限。常规的数据源创建会写入元数据；RRD 可以在写入器需要时稍后创建。文件缺失可能表明采集尚未执行到这一步，也可能是路径、信任、权限或创建失败所致。

某些以 root 身份运行的创建路径会尝试应用 RRA 目录的所有者和组。这些尝试可能会失败并记录错误；它们不能替代正确配置服务账户。非 root 权限遵循操作系统规则，包括目录组继承和 ACL。请在每个 Web 和 poller 写入器账户下验证存储权限以及受信任的数字 UID/GID 设置。参见[安全升级](/zh-cn/guides/upgrade-safely/)。

经过审查的 PHP ICMP 实现会调用操作系统的 ping 工具。其发送探测的能力取决于该工具和操作系统策略；存在旧版有效 UID 辅助程序并不意味着每次 ICMP 探测都会将 PHP 提权为 root。不要仅仅为了启用 ping 而以 root 身份运行应用程序。请检查实际命令、账户及错误输出；TCP 或 UDP 检查具有不同的连通性语义。

## 工作清单是预先计算好的

poller 缓存存储了已解析的采集工作，因此每次运行无需从模板关系中重新推导每个命令。配置操作可以重新构建受影响的条目；需要时也可以使用显式重建工具。

缓存字段中表示的变更需要先同步到这些条目，然后采集才能使用它们。其他设置是单独读取的，因此并非每次配置更改都需要手动重建缓存。应检查缓存内容、采集错误和远程复制状态，而不是假设只有单一原因。参见 [Poller 缓存](/zh-cn/concepts/the-poller-cache/)和[远程数据采集](/zh-cn/concepts/remote-data-collection/)。

## 常见故障点

| 症状 | 有效检查项 |
|---|---|
| 界面正常，图表变平 | 调度程序运行情况、采集错误、队列、样本新鲜度及图表时间窗口 |
| Poller 运行，文件未更新 | 写入器确认/错误、存储信任与权限、延迟积压 |
| 单个数据源变平 | 设备响应、缓存行、文件映射、未知样本及绘图表达式 |
| 配置更改似乎无效 | 保存结果、模板覆盖、受影响的缓存条目及复制状态 |
| 规律性间隙 | 计时、heartbeat、超时、设备可用性及写入失败 |
| 预期之外的图表形状 | 生成的命令、CDEF/CF 选择、实际文件数据、图像缓存及映射 |
| 端口历史似乎挂载到另一个接口 | 查询标识、重新编号及重新索引结果 |
| 账户可查看控制台但看不到图表 | 图表页面领域、对象授权及请求的图表标识 |
| 采集器之间数据不一致 | 分配关系、复制的配置、本地覆盖及连接状态 |
| 整体运行缓慢 | 数据库等待、写入器/存储竞争、采集器运行时长及 Web 负载 |
| 数据源元数据存在但文件不存在 | 首次采集/写入、配置路径、信任及创建错误 |

这些是排查的切入点，而非最终诊断。请顺着相关边界追踪证据，并在更改后验证结果。参见[排查数据缺失问题](/zh-cn/guides/troubleshoot-missing-data/)。
