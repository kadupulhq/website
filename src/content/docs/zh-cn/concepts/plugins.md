插件是应用程序包含到自身进程中并在具名调用点执行的代码。
插件模型的所有其他特性，均源自这同一句话。

有关在安装第三方插件之前应阅读的内容，请参阅
[安装与审查插件](/zh-cn/guides/install-and-vet-plugins/)。

## 为什么在进程内运行

审视一下插件的实际用途：为应用程序正在渲染的列表中添加一列、在图表绘制之前修改其选项、对正在删除的设备作出响应，或是附加一个选项卡。每一个操作都是在修改应用程序在该瞬间保存在内存中的数据。

一个隔离的工作进程将需要明确的接口以及对其返回结果的验证。这虽然可以维持特权隔离，但并不是此处采用的机制：插件文件被直接包含，其函数直接在应用程序进程内被调用。

## 插件继承了什么

插件代码以调用方操作系统的账户身份运行，具有访问该进程的数据库连接和文件系统权限的能力。Web 调用方可能还拥有会话；CLI 调用方则不一定拥有。插件机制不提供单独的身份标识、沙箱或签名验证。

用户和组权限负责控制对应用程序的访问；它们无法约束插件内任意的 PHP 代码。数据库授权、文件系统权限和进程限制仍然制约着该进程能执行的操作。在安装之前必须审查插件，并始终限制应用程序账户的系统特权。

## 两种调用风格

| 风格 | 应用程序 | 不返回任何内容的插件 |
|---|---|---|
| 通知 | 传递参数，忽略结果 | 返回值不被使用；副作用和异常仍然具有实质影响 |
| 转换 | 传递一个值，使用返回的内容 | 可能会将该值替换为 null 并破坏下游调用方 |

转换风格使得插件能够添加按钮、扩展操作列表或更改图表。这也是插件容易产生耦合的地方：位于同一个 Hook 上的两个插件，各自会按照配置的插件顺序看到前一个插件的处理输出。

分发器仅在存在多行匹配的 Hook 记录时，才会对数组变成非数组、或先前非空的值变成类似 null 的情况发出警告。该检查并不是对 Hook 约定的全面验证；单个插件可以在不触发此警告的情况下损坏数据值。

## 注册是状态而非动态发现

Hook 存储在数据库表中：对应哪个插件、Hook 名称、哪个文件、哪个函数、是否启用。安装、升级和设置程序均可注册 Hook；注册并不局限于首次安装。

替代方案是在请求发生时进行动态发现，这意味着需要扫描插件目录并包含每个插件的代码以询问其需求。单个页面会触及许多 Hook 点。全部包含仅为了发现没有任何挂载是一项极其昂贵的开销，因此应用程序查询数据表，针对当前请求缓存结果，并且仅包含匹配行所指定的文件。

这种设计权衡带来了一个必须知晓的代价：数据表可能与文件系统不一致。手动删除插件目录会在表中残留孤立记录。丢失的通知回调可能会产生防抖警告；而转换分发器对于丢失的回调则没有对应的警告机制。安静的日志并不能证明注册状态是健全的。

执行顺序源自插件的注册顺序，并且是可以调整的。因此，转换链是由管理员控制的配置所排序的。

## 插件可以触及的范围

| 能力 | 说明 |
|---|---|
| 创建自有数据表 | 会被记录，以便卸载程序将其删除 |
| 向现有表中添加列，包括核心表 | 会被记录，以便卸载程序将其移除 |
| 注册权限范围（Realm） | 界面中新增的受访问控制保护的区域 |
| 声明对其他插件的依赖 | 安装前进行版本校验 |
| 在远程采集器上运行 | 分发取决于 Hook、调用风格、功能声明和连接状态 |

记录数据库架构变更正是卸载具有破坏性的原因。应用程序可以删除被跟踪的表和列（包括其中的数据）。在清理之前，它还会调用插件的卸载回调。该回调可以执行其他更改；未被跟踪的更改不会自动回滚，并且插件的源文件目录仍会保留。

插件注册的权限范围由用户和组持有，其方式与核心权限范围完全相同。当注册显式请求时，新权限范围还可以向主管理员和当前会话用户授予访问权限。在安装和升级后务必审查生成的授权；切勿假定现有安全策略会自动覆盖新增的攻击面。
请参阅 [权限与访问控制](/zh-cn/concepts/permissions-and-access/)。

## 防护措施实际保护了什么

系统中存在防护措施，理解它们有助于明确系统的威胁模型。

Hook 指定的文件仅在其自身插件的目录内解析。跳出该目录的路径会被拒绝，并作为安全事件记录在日志中。插件的目录名仅限于字母、数字、下划线和连字符。Hook 和权限范围的注册仅接受来自名称形似安装、升级或设置程序的函数调用；来自其他位置的调用将被拒绝并记录。

路径防护限制了 Hook 记录能够包含的文件范围。注册检查仅检查调用方函数名是否包含 install、upgrade 或 setup；它并不对生命周期操作进行真正的身份验证。插件代码在常规页面加载中也可以使用此类函数名，因此该约定并不是安全边界。

这些防护措施对于插件自身代码运行后的行为没有任何约束作用。它们不是隔离沙箱，也不是为此而构建的。

## 禁用并不等于关闭

有几种类型的 Hook 在安装时默认以启用状态注册：即提供设置页面、配置数组和表单定义的那部分。插件在开启之前必须是可配置的，因此无论插件是否启用，这些 Hook 都会运行。

因此，被禁用的插件在某些页面加载时仍会有代码被包含并执行。禁用仅仅是一项功能开关，直接访问插件的 URL 同样需要仔细审查。如果您怀疑存在恶意代码，请隔离整个安装实例并在调用卸载程序前审查移除流程，因为卸载操作本身也会执行插件代码。仅删除源代码文件既不能清理注册表项，也不能回滚数据库变更。

## 远程采集器拥有更收敛的接口面

插件在其信息文件中声明其能力：在采集器能连接到主安装实例时是否工作、在断网时是否工作，以及是否参与数据采集。

在采集器上，列出的 Hook 会根据能力要求进行校验。未列出的转换 Hook 仍会分发；未列出的通知 Hook 在在线状态下或插件声明支持离线管理/视图时可以分发。被跳过的调用并不会全部记录在日志中。这属于路由逻辑，而非绝对的白名单或隔离边界；请仔细检查您所使用的 Hook 的具体分发器与连接状态。

其原因在于采集器属于不同的运行环境。它的配置是可能存在数小时延迟的副本，并且它可能完全没有与中央数据库的直接连接。如果编写的 Hook 假定中央数据库随时只需一次查询即可访问，在采集器上就会出错，因此该模型要求插件显式声明其所作的假定，而不是由系统推断。
请参阅 [远程数据采集](/zh-cn/concepts/remote-data-collection/)。

## 轮询器是挂载 Hook 最昂贵的环节

轮询执行路径上的 Hook 会在其调用点被触发时运行。其执行频率取决于事件类型、进程以及采集器路由；并不是每个 Hook 都会在每个周期的每个进程中运行。在频繁路径上运行缓慢的代码会耗尽轮询时间间隔，并可能导致图表数据断点。

页面上的 Hook 仅为当前正在等待响应的一位用户渲染一次。两者在注册表中看起来完全一样，但在系统开销上存在数个数量级的差异。

## 为什么接口表面看起来不规整

Hook API 暴露出的调用点具有各不相同的业务目标和参数结构。

这就是为什么 Hook 列表庞大且不规整、为什么有些点传递一个值供您修改而另一些点仅通知事件发生、以及为什么各个 Hook 的参数结构大相径庭的原因。声明的核心最低版本并不意味着能与每个 Hook 兼容：必须审查每个调用点的参数与返回值预期，并在目标版本上实际测试插件。
在 [安装与审查插件](/zh-cn/guides/install-and-vet-plugins/) 中说明的 CLI 兼容性与权限范围授予限制同样适用；仅凭安装成功并不能作为兼容性的证明。

实际结论是：插件与编写它时所依据的核心版本紧密绑定，其耦合程度远超所声明的最低版本暗示的范围。核心升级之前应当重新验证插件，而不是留在升级之后。
