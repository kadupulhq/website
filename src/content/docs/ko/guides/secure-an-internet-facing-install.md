:::caution[사용 전 검증]
소스를 사용할 수 있지만 지원되는 Kadupul 릴리스 또는 마이그레이션 경로는 아직
없습니다. 시스템에 의존하기 전에 백업이 포함된 격리된 사본에서 이 절차를
테스트하세요. [프로젝트 상태](/ko/project/status/)를 참조하세요.
:::

솔직한 답변부터 시작하자면, 시스템을 VPN 뒤에 배치하세요. Kadupul은 모니터링하는 모든 장치의 SNMP 자격 증명을
일반 텍스트로 보관하며, 정상 작동의 일환으로 자체 호스트에서 명령을 실행합니다. 공용 인터넷에 직접 노출하는 것을
안전하게 만들어 주는 설정은 존재하지 않습니다.

아래의 점검 사항들은 격리된 설치 환경을 평가하는 데 도움을 줍니다. 이것이 지원되거나 안전한 공개 배포 환경을
보장하지는 않으므로, 결과를 해석할 때 위의 프로젝트 상태 제한 사항을 염두에 두세요.

## TLS

Web 서버 또는 그 전단의 프록시에서 TLS를 종료하세요. Kadupul은 자체 네트워크 소켓을 직접 수신 대기하지 않습니다.

그런 다음 일반 HTTP 요청을 HTTPS로 리디렉션하는 설정을 활성화하세요. 이 설정은 기본적으로 비활성화(`off`)되어
있습니다. 이 설정이 없으면 로그인 폼이 HTTP로 제공되어 다른 보안 조치가 작동하기도 전에 비밀번호가 네트워크를 통해
평문으로 전송됩니다.

PHP가 `off`가 아닌 비어 있지 않은 `$_SERVER['HTTPS']` 값을 수신하면 애플리케이션은 세션 쿠키의 Secure 플래그를 설정합니다.
TLS를 종료하는 프록시 뒤에서는 신뢰할 수 있는 Web 서버 또는 FastCGI 계층이 HTTPS 상태를 정확히 반영하도록 구성하고,
브라우저에서 최종 `Set-Cookie` 헤더를 확인하세요.

`$proxy_headers`는 클라이언트 IP 주소 확인을 제어합니다. 이 설정은 HTTPS 서버 변수를 설정하거나 Secure 쿠키를 활성화하지
않습니다. 프록시가 설정한 주소 헤더만 신뢰하고, 클라이언트가 직접 제공한 헤더 사본은 제거하며, 백엔드에 대한 직접 접근을 차단하세요.
자격 증명이 전송되기 전에 공용 프록시에서 HTTP-to-HTTPS 리디렉션을 강제 적용하세요.

애플리케이션은 세션 쿠키에 HttpOnly 및 SameSite=Strict를 설정합니다. 배포 경계에서 실제 쿠키와 리디렉션 동작을 확인하세요.
이러한 플래그가 존재한다고 해서 다른 모든 쿠키가 동일한 구성을 공유한다는 보장은 없습니다.
[PHP 세션 구성 참조 문서](https://www.php.net/manual/en/session.configuration.php)를 확인하세요.

## 기본 자격 증명

기본 제공되는 스키마에는 비밀번호 해시가 문자열 `admin`의 MD5 값인 `admin`이라는 이름의 관리자 계정이 하나 포함되어 있습니다.
이 계정은 최초 로그인 시 비밀번호 변경을 요구하도록 플래그가 설정되어 있습니다. 변경이 실제로 이루어졌는지 직접 확인하세요.
Web 서버가 사용자의 신원을 이미 확인한 Web Basic 인증 환경에서는 이 변경 요구 화면이 건너뛰어집니다.

그 다음으로 사용자 계정이 아닌 자격 증명을 점검하세요.

- 제공된 구성 템플릿에서 데이터베이스 계정은 기본적으로 `cactiuser`, 비밀번호는 `cactiuser`로 설정되어 있습니다.
- 자동화 하위 시스템은 커뮤니티 문자열 `public` 및 `private`과 SNMPv3 사용자 이름/비밀번호 쌍이 포함된 기본 SNMP 옵션을 제공합니다. 이는 스캔 기본값일 뿐 실제 장치 구성은 아니지만, 자동 검색 시 가장 먼저 시도되는 문자열입니다.

비밀번호 정책은 구성 가능합니다. 기본값은 8자 이상 및 대소문자 혼합을 요구합니다. 비밀번호 만료 및 반복 실패 후 계정 잠금 기능이
모두 제공되며, 기본적으로 둘 다 비활성화되어 있습니다. 인터넷에 연결된 설치 환경에서는 계정 잠금을 활성화하세요.

## 데이터베이스 권한

설치 예시에서는 데이터베이스 범위의 권한과 표준 시간대 테이블 접근 권한을 사용합니다. 아래의 예시 계정/데이터베이스 이름을
실제 환경에 맞게 변경하고, 실제 배포 및 유지 관리 작업에 필요한 권한을 검토하세요.

```sql
GRANT ALL ON kadupul.* TO 'someuser'@'localhost';
GRANT SELECT ON mysql.time_zone_name TO 'someuser'@'localhost';
```

두 번째 권한 부여는 선택 사항이 아닙니다. 표준 시간대 처리 로직이 해당 테이블을 읽으며, 설치 프로그램은 접근 권한과 입력된
표준 시간대 데이터의 유무를 검사합니다. 임의로 권한을 제거하기 전에 실제 유지 관리 및 수집기 요구 사항과 비교하여 추가 권한을
검토하세요. 이 예시가 모든 배포 환경에 정확히 동일한 권한이 필요하다는 것을 의미하지는 않습니다.

주의해야 할 범위 관련 사항:

- 데이터베이스를 localhost 또는 비공개 인터페이스에 바인딩하고, Web 서버가 응답하는 공용 주소에는 바인딩하지 마세요.
- 각 원격 데이터 수집기에 별도의 데이터베이스 계정을 부여하세요. 수집기의 자격 증명은 중앙 데이터베이스와 자체 구성 파일에 저장되므로, 계정을 분리하면 감사 및 권한 취소 관리가 수월해집니다. 다만 수집기 권한이 여전히 중앙 쓰기를 허용한다면 계정 분리만으로 손상된 수집기를 완벽히 격리할 수는 없습니다.
- 연결은 TLS를 지원하며, 구성 파일에 지정된 키, 인증서 및 CA 경로를 통해 구성됩니다. 데이터베이스가 동일한 호스트에 있지 않은 경우에는 항상 TLS를 사용하세요.
- 정상 작동 중에 구성 파일이 Web 서버 사용자에게는 읽기 가능하고, Web 및 폴러 서비스 사용자에게는 쓰기 권한이 없도록 설정하세요. 소유권은 관리자 계정으로 유지하세요. 원격 폴러 설정 과정에서는 구성 파일을 업데이트할 수 있는지 구체적으로 확인합니다. 주 서버 설치 환경 전체에 동일한 임시 쓰기 권한이 필요하다고 단정하지 마세요.
- CSRF 시크릿은 데이터베이스 대신 파일에 저장할 수 있습니다. 이 옵션을 사용하는 경우 해당 파일은 반드시 문서 루트(document root) 외부에 있어야 합니다. 이는 권장 사항이 아니라 필수 조건입니다.

## 데이터 디렉터리를 문서 루트 외부에 유지

저장소 루트 배포 구조에서는 비공개 데이터 및 소스 디렉터리가 서비스되는 루트 아래에 위치할 수 있습니다. 여러 디렉터리에
`.htaccess` 거부 규칙이 포함되어 있지만, 모든 경로가 보호된다고 가정하지 말고 실제 체크아웃 및 서버 구성을 전수 조사하세요.
현재 진행 중인 부분적인 프레임워크 마이그레이션 상황을 감안할 때, 레거시 라우트를 고려하지 않고 사이트 전체를 `public/`으로만
전환하는 것은 온전한 배포 절차가 아닙니다.

이러한 설정 파일은 Apache에서만 작동하며, 해당 디렉터리에서 오버라이드가 허용된 구성일 때만 유효합니다. Nginx에서는 아무런
영향을 미치지 못합니다. 잘못 구성된 Apache에서도 작동하지 않습니다. 로그 디렉터리 전단의 거부 규칙이 무력화되면 장치 이름,
사용자 이름, 쿼리 내용, 오류 세부 정보가 포함된 애플리케이션 로그를 누구나 열람할 수 있게 됩니다. Apache는 필요한 오버라이드
동작을 [`.htaccess` 가이드](https://httpd.apache.org/docs/2.4/howto/htaccess.html)에 설명하고 있습니다.

다음 두 조치를 모두 수행하세요.

**데이터를 이동하기 전에 스토리지 경로를 검증하세요.** 로그 저장 위치는 변경 가능하지만, `include/global.php`는 RRA 기준 경로를
설치 환경의 `rra` 디렉터리로 고정합니다. UI에는 RRA 디렉터리를 위한 범용 설정 항목이 없습니다. 별도로 마운트된 스토리지 구성을 통해
해당 경로를 유지할 수는 있지만, 파일시스템 배치만으로는 서비스 중인 디렉터리나 심볼릭 링크를 통한 HTTP 접근을 차단할 수 없습니다.
기존 데이터 소스 경로, 서비스 권한, 백업 및 HTTP 거부 규칙을 종합적으로 점검하세요. 클라이언트가 파일을 확인하는 방식을 검증하지 않고
캐시 트리를 이동하지 마세요. [새 하드웨어로 마이그레이션](/ko/guides/migrate-to-new-hardware/) 및
[안전한 업그레이드](/ko/guides/upgrade-safely/)를 참조하세요.

**Web 서버에서 비공개 경로에 대한 접근을 거부하세요.** 소스에 포함된
[저장소 루트 Nginx 예제](https://github.com/kadupulhq/kadupul/blob/661a57ff43ebf275e6b07211d4284dd727103959/tests/e2e/nginx.conf)를
실제 URL 접두사 및 서버 환경에 맞게 조정하세요. 접근 거부 규칙은 일반적인 PHP 처리보다 우선 적용되어야 합니다. 아래 목록은 점검을
위한 참고 자료일 뿐, 그대로 복사해 사용하는 서버 구성이 아닙니다.

| 디렉터리 | 차단 이유 |
|---|---|
| `rra/` | 측정 데이터 파일 |
| `log/` | 쿼리 및 오류 세부 정보를 포함한 애플리케이션 로그 |
| `cache/` | 의도된 에셋 접근을 점검하고 캐시 경로 내에서의 PHP 실행을 원천 차단 |
| `scripts/` | 수집 코드는 HTTP를 통해 직접 제공되거나 호출되어서는 안 됨 |
| `cli/` | HTTP를 통해 접근되도록 설계되지 않은 명령줄 도구들 |
| `mibs/`, `contrib/`, `docs/` | 내부 리소스 및 문서 |
| `src/`, `config/`, `templates/`, `var/`, `lib/`, `bin/`, `tests/`, `tools/` | 애플리케이션 내부 구조, 상태 데이터 및 개발 도구 |
| 숨김 파일(dotfile), 종속성 매니페스트, 내부 include/bootstrap PHP | 저장소 메타데이터 및 내부 실행 진입점 |

`include/js` 및 `include/themes`와 같은 필수 공개 에셋은 유지하세요. include 디렉터리 전체를 무차별 차단하면 UI가 손상될 수 있습니다.
무해한 테스트 경로를 사용하여 거부 동작을 검증하고, 응답에 소스 코드나 파일 내용이 노출되지 않는지 확인하세요. 실제 비밀 정보를 터미널이나
로그로 가져오는 방식으로 테스트하지 마세요.

정적 에셋을 위한 보안 응답 헤더 옵션 파일도 제공됩니다. PHP 응답은 코드 내에서 자체 헤더를 설정하지만, 정적 파일은 해당 파일을 활성화하거나
서버 구성에 동일한 지시문을 넣지 않는 한 헤더를 추가하지 않습니다.

콘텐츠 보안 정책(CSP)은 구성 가능합니다. 플러그인이 인라인 코드에 의존하므로 기본 스크립트 정책은 nonce 없는 인라인 JavaScript를 허용합니다.
설정에서 제공되는 더 엄격한 nonce 모드는 보고 전용(report-only)으로 작동합니다.
[오래된 설정 도움말](https://github.com/kadupulhq/kadupul/issues/265)의 설명과 달리 헤더 구현은 `nonce` 강제 적용도 수용합니다.
강제 적용과 보고 전용 모드는 완전히 다릅니다. 모드를 전환하기 전에 헤더를 점검하고 필요한 모든 페이지와 플러그인을 테스트하세요.
강제 적용 코드가 구현되어 있다고 해서 완전한 nonce 호환성을 보장하는 것은 아닙니다.

## 폴러의 시스템 명령어 실행

이 부분은 시스템의 위협 모델을 근본적으로 변화시키는 요소입니다.

데이터 수집은 SNMP에만 국한되지 않습니다. 데이터 입력 방법(Data Input Method)은 명령줄을 정의할 수 있으며, 폴러는 이를 실행합니다.
명령줄은 폴러 캐시에 저장되고 수집기에 의해 매 주기마다 수집기의 OS 사용자 권한으로 실행됩니다. PHP 스크립트 서버 입력은 별도의 오래 지속되는
PHP 프로세스를 사용합니다. 외부 명령과 스크립트 서버 입력은 서로 다른 경로입니다. 모든 스크립트가 해당 서버 내에서 실행된다거나 C 수집기가
이 릴리스에서 검증되었다고 단정하지 마세요.

다음 권한들을 코드 실행을 가능하게 하는 고위험 권한 구성 영역으로 취급하세요. 구체적인 영향은 활성화된 기능과 검증 제어에 따라 달라집니다.

| 권한 항목 | 위험 사유 |
|---|---|
| 데이터 입력 방법 | 실행할 명령줄을 직접 정의함 |
| 템플릿 가져오기 | 가져온 템플릿이나 패키지에 데이터 입력 방법이 포함될 수 있음 |
| 플러그인 관리 | 플러그인 코드가 애플리케이션 내에서 직접 실행됨 |
| 설정 / 유틸리티 | 실행되는 바이너리의 절대 경로를 제어함 |

해당 호스트에 이미 쉘 권한을 가지고 있지 않은 사람에게는 이 권한들을 절대로 부여하지 마세요. 그래프를 볼 수 있는 읽기 전용 사용자는
완전히 다른 권한이며, 거의 모든 계정이 가져야 할 역할은 바로 이것입니다.

두 가지 방어 제어가 존재하며 둘 다 적용할 가치가 있습니다.

**메타문자 제한.** 데이터 입력 명령 문자열의 쉘 메타문자는 기본적으로 차단됩니다. 쉘 파이프라인을 사용하던 이전 정의를 위해 이를
허용하는 설정이 존재하지만, 비활성화 상태를 유지하세요. 파이프라인이 필요한 정의가 있다면 파이프라인을 scripts 디렉터리 아래의 스크립트로
옮긴 후 해당 스크립트를 호출하세요.

**입력 화이트리스트.** 구성 파일에 지정된 파일로, 데이터 입력 방법별로 승인된 명령 문자열을 보관합니다. 이 파일이 설정되면 명령 문자열이
목록에 없는 데이터 입력 방법으로부터는 그래프와 데이터 소스를 생성할 수 없습니다. 승인된 명령을 변경하면 검토된 화이트리스트가 업데이트될 때까지
비교 검증이 실패합니다. 화이트리스트 재생성은 명령줄에서 수행하도록 설계되어 있으며, 이것이 핵심입니다. 즉, 브라우저 관리자 세션이 아니라
호스트에 대한 쉘 접근 권한이 요구됩니다.

이 검사는 폴러 캐시가 재구축될 때 다시 실행됩니다. 검사에 실패한 데이터 입력은 폴러 항목을 생성하지 않으며, 남겨진 행들은 다음 커밋된
재구축/플러시 시 삭제됩니다. 이는 생성 및 캐시 채우기를 통제하는 메커니즘이며, 이미 실행 중인 작업을 즉시 취소하는 기능이나 각 수집기가
매 실행 전 변경된 화이트리스트를 다시 로드함을 보장하는 것은 아닙니다. 정책 변경 후 커밋된 캐시 상태와 수집기의 동작을 검증하세요.

```sh
php cli/input_whitelist.php --audit
# After reviewing this data input's command; 42 is an example data-input ID.
php cli/input_whitelist.php --update --id=42
```

범위를 지정하지 않은 `--update`는 현재의 명령 정의를 무비판적으로 화이트리스트에 승인 처리하므로, 이를 정밀 검토의 대체 수단으로
사용하지 마세요. 서비스 사용자가 화이트리스트 파일과 상위 디렉터리에 쓸 수 없도록 보호하세요. 이 기능은 명시적으로 구성하지 않는 한 꺼져 있습니다.
항목 선택 및 출력 세부 정보는 [데이터 수집 스크립트 작성](/ko/guides/write-a-data-collection-script/)을 참조하세요.
이를 통해 브라우저를 통한 관리자 권한 탈취 공격의 비용을 크게 높일 수 있습니다. 수집 흐름에 새 명령을 추가하려면 이제 폴러 호스트의
파일시스템 쓰기 권한까지 필요하기 때문입니다. 다만 이미 승인된 명령 문자열을 악용할 수 있는 공격자는 새 명령을 추가할 필요가 없으므로,
위 표의 권한을 제한하는 조치를 완전히 대체할 수는 없습니다.

## 인증

네 가지 인증 방법이 제공됩니다. 어떤 방법을 사용할 수 있는지는 설치된 PHP 확장에 따라 다릅니다.

| 인증 방식 | 사용자 신원 확인 위치 | 참고 사항 |
|---|---|---|
| 내장(Built-in) | 로컬 데이터베이스 | 비밀번호, 정책, 계정 잠금이 모두 로컬에서 처리됨 |
| Web Basic | Web 서버 | 서버가 전달하는 사용자 신원을 전적으로 신뢰함 |
| LDAP | 단일 디렉터리 | PHP LDAP 확장이 필수 |
| 다중 LDAP/AD 도메인 | 여러 디렉터리 | 동일한 확장 필요 |

설정 화면의 선택기에는 레거시 무인증 모드(모드 0)를 제외한 이 인증 방법들이 표시됩니다. 인증 부트스트랩은 오래된 무인증 구성을
로컬 인증으로 마이그레이션하려고 시도하지만, 하위 수준 권한 부여 헬퍼에는 여전히 모드 0 분기 코드가 남아 있습니다. UI에 선택지가
없다는 것만을 근거로 삼지 말고, 저장된 방식, 구성된 신원 정보 및 실제로 보호되는 라우트를 확인하세요.

확인해야 할 핵심 사항:

- **Web Basic 인증은 신원 검증을 외부에 위임합니다.** 이 모드가 선택되면 Kadupul은 서버에서 인증된 신원 변수를 읽어오지만, 계정 매핑, 활성화 상태 및 권한 부여 규칙은 여전히 적용합니다. 신원 정보가 누락되었다고 해서 자동으로 관리자가 되지는 않습니다. 의도된 모든 라우트를 인증하도록 서버를 구성하고 클라이언트가 임의의 신원 변수를 주입하지 못하도록 차단하세요. 이미지/내보내기 라우트 및 의도된 게스트 동작은 개별적으로 검증하세요.
- **"로그인 상태 유지" 지원**은 기본적으로 활성화되어 있습니다. 사용자가 인증 후 해당 옵션을 선택할 때 영구 토큰이 생성되며, 모든 세션에 무조건 생성되는 것은 아닙니다. 90일 동안 사용하지 않으면 만료됩니다. 인터넷에 공개된 환경에서는 이 기능의 유지 여부를 신중히 결정하세요.
- **게스트 사용자를 nobody(미지정)로 설정하세요.** 익명 그래프 조회를 명시적으로 허용하려는 경우가 아니라면 사용자를 지정하지 않는 것이 올바른 기본값입니다. 설정 과정에서 변경되지 않았는지 확인하세요.
- **시스템 전단에 다중 요소 인증(MFA)을 배치하세요.** 애플리케이션 자체에는 MFA가 구현되어 있지 않습니다. 신원 인식 프록시나 SSO 게이트웨이를 앞단에 두어 적용해야 합니다.

## 원격 데이터 수집기 엔드포인트

원격 수집기를 실행하는 경우 중앙 설치 환경은 이들이 통신할 수 있는 엔드포인트를 노출합니다. 이 엔드포인트는 사용자 세션을 통해
인증하지 않습니다. 호출한 클라이언트 주소를 확인하여 등록된 수집기의 호스트 이름과 대조함으로써 인가를 수행하며, 실패 내역은
보안 카테고리 로그에 기록됩니다.

두 가지 주의 사항이 뒤따릅니다. 첫째, 해당 엔드포인트는 공용 인터넷에서 접근할 수 없어야 합니다. Web 서버에서 수집기 주소로만
접근을 제한하세요. 둘째, 검사하는 클라이언트 주소는 요청에서 파생된 것이므로 앞서 구성한 전달 헤더(forwarded-header) 신뢰 규칙이
여기에도 동일하게 적용됩니다. 통제하지 않는 헤더를 신뢰하면 공격자가 수집기 주소를 사칭할 수 있습니다.

이와 별도로 중앙 서버가 수집기와 통신할 때 자체 서명된 인증서와 호스트 이름 불일치를 허용하는 설정이 기본적으로 켜져 있습니다.
수집기에 유효한 실제 인증서를 발급하고 이 허용 설정을 끄세요.

## 최소 점검 목록

1. TLS 종료, 로그인 전 HTTP 리디렉션, 신뢰할 수 있는 서버를 통한 PHP HTTPS 상태 구성 및 Secure 쿠키 확인. 클라이언트 주소 헤더는 프록시가 설정하고 정리하는 헤더로만 제한.
2. 기본 admin 비밀번호 변경 및 확인. 계정 잠금 정책 활성화.
3. 설치, 유지 관리 및 수집기 역할을 고려한 데이터베이스 권한 검토. 표준 시간대 접근 권한 확인 및 데이터베이스 네트워크 접근을 필요한 클라이언트로 제한.
4. 스토리지 경로 검증, Web 서버에서 비공개 디렉터리 및 메타데이터 차단, 필수 정적 에셋의 정상 작동 확인.
5. 런타임에 구성 파일 쓰기 금지. CSRF 시크릿 파일 사용 시 문서 루트 외부에 배치.
6. 폴러 호스트의 쉘 권한이 없는 사용자에게 데이터 입력 방법, 템플릿 가져오기, 플러그인 관리 권한을 부여하지 않음. 메타문자 제한 활성화. 입력 화이트리스트 구성.
7. 원격 수집기 엔드포인트를 IP 주소로 제한. 엄격한 인증서 검증 활성화.
8. 전체 시스템 앞단의 프록시에 MFA 적용.
