:::caution[使用前に検証してください]
ソースは利用可能ですが、サポートされている Kadupul のリリースや移行パスはありません。これらに依存する前に、バックアップを用意した隔離環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

同梱されている ESXi パッケージは、ホストの測定値とゲストのインベントリカウントを収集します。ゲストごとの CPU、メモリ、または競合の測定値は提供されません。グラフを選択する前に、ハイパーバイザーのバージョンによって公開されているオブジェクトを確認してください。

## 同梱されているもの

1つのハイパーバイザーデバイステンプレートが提供されています：**ESXi Device**。これはデバイスパッケージであるため、`install/templates/ESXi_Device.xml.gz` にはそのスクリプトとデータクエリファイルが含まれています。[テンプレートのインポートとエクスポート](/ja/guides/import-and-export-templates/)に従い、ファイルのデプロイを含めてインポートが完了したことを確認してください。デバイステンプレートを選択し、検出結果を確認して、目的のグラフを明示的に作成します。パッケージのインポートやデバイステンプレートの関連付けだけではグラフは作成されません。

| 同梱物 | 目的 |
|---|---|
| `resource/snmp_queries/esxi_cpu.xml` | プロセッサを検出し、プロセッサごとの負荷を読み取ります |
| `resource/snmp_queries/esxi_hw.xml` | ハードウェアコンポーネントを検出し、その状態を読み取ります |
| `resource/snmp_queries/interface.xml` | 標準のインターフェース統計クエリ |
| `resource/script_server/host_disk.xml` | Host Resources ストレージテーブルを介したマウントされたパーティション |
| `scripts/ss_esxi_vhosts.php` | `install/templates/ESXi_Device.xml.gz` 内に同梱。ゲスト数、電源オンのゲスト数、ゲストツールの状態をカウントします |
| `scripts/ss_multicpu_avg.php` | プロセッサごとの負荷を1つの数値に平均化します |
| `scripts/ss_hstats.php` | Kadupul がそのデバイスについてすでに保持しているポーリング統計を読み取ります |
| `scripts/ss_host_disk.php` | パーティションクエリをサポートします |

このリポジトリのチェックアウトには、Hyper-V、KVM/libvirt、Xen、または Proxmox 用の専用デバイスパッケージは含まれていません。汎用の Linux/Windows テンプレートは、それらのエージェントがサポートするホストメトリクスをカバーできる場合があります。ハイパーバイザー固有の収集には、適切なテンプレートとコレクターが必要です。[データ収集スクリプトの作成](/ja/guides/write-a-data-collection-script/)を参照してください。

## 最初にエージェントを有効にする

お使いの ESXi バージョンの既存のエージェント設定と使用手順を確認してください。パッケージの注意事項には工場出荷時設定へのリセットが含まれていますが、これは日常的な前提条件ではなく、既存の SNMP 設定を消去してしまいます。コミュニティベースのセットアップの場合、次のコマンドでエージェントの値を設定します。例を置き換え、コミュニティリストを設定する際は必要な既存のコミュニティを保持してください。

```bash
esxcli system snmp get
esxcli system snmp set -c YOUR_STRING
esxcli system snmp set -p 161
esxcli system snmp set -L "City, State, Country"
esxcli system snmp set -C noc@example.com
esxcli system snmp set -e yes
```

最初のコマンドは設定を表示し、最後のコマンドはエージェントを有効にします。コミュニティオプションは設定されたリストを置き換えます。ポーラーからの必要なファイアウォールアクセスを確認し、[ESXCLI SNMP コマンドリファレンス](https://developer.broadcom.com/xapis/esxcli-command-reference/latest/namespace/esxcli_system.html)を参照してください。これらのコマンドはコミュニティベースのポーリングを設定するものであり、SNMPv3 を設定するものではありません。デバイスを追加する前に、ポーラーが実行されているマシンから確認してください。

```bash
snmpget  -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.1.1.0
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.25.3.3.1.2
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.4.1.6876.2.1.1.6
```

最初のコマンドが機能し、3番目のコマンドが何も返さない場合は、SNMP エラー、アクセスポリシー、およびエージェントのサポート状況を確認してください。空の walk だけでは原因を特定できません。同梱のゲストスクリプトは SNMPv1 を使用するため、v2c プローブが成功してもその収集パスが検証されたことにはなりません。空のゲスト walk はゼロカウントを生成しますが、必ずしもグラフの欠落になるとは限りません。[空結果の不具合](https://github.com/kadupulhq/kadupul/issues/245)を参照してください。

## ホストが公開するもの

| 領域 | サブツリー | 取得できる情報 |
|---|---|---|
| プロセッサ | `.1.3.6.1.2.1.25.3.3.1` | エージェントによって公開される各プロセッサの負荷 |
| ハードウェアコンポーネント | `.1.3.6.1.2.1.25.3.2.1` | コンポーネントのインデックス、説明、および状態 |
| ストレージ | `.1.3.6.1.2.1.25.2.3.1` | エージェントが報告することを選択したデータストアおよびローカルファイルシステム |
| インターフェース | `.1.3.6.1.2.1.2` および `.1.3.6.1.2.1.31` | トラフィック、エラー、ステータス |
| ゲストインベントリ | `.1.3.6.1.4.1.6876` | ゲストごとの電源状態とゲストツールのステータス |

最初の4つは、Linux ホストが応答するものと同じ標準の Host Resources テーブルおよびインターフェーステーブルです。それらがどのように動作し、どのディスクテーブルを優先すべきかについては、[Linux サーバーの監視](/ja/guides/monitor-a-linux-server/)を参照してください。

5番目は、同梱のゲストカウントスクリプトが使用するベンダーサブツリーです。

## グラフテンプレート

| グラフ | ソース | 読み取り対象 |
|---|---|---|
| ESXi - CPU | データクエリ | 検出された1つのプロセッサの負荷 |
| ESXi - MultiCPU Average | スクリプト | すべてのプロセッサの負荷の平均値 |
| ESXi - Hardware | データ查询 | 検出された1つのコンポーネントの状態 |
| ESXi - VHosts | スクリプト | ゲスト数とゲストツールのステータス |
| Host MIB - Processes | 固定 OID | ホスト上のプロセス数 |
| Host MIB - Logged in Users | 固定 OID | ホスト上のセッション数 |
| Device - Uptime | スクリプト | Kadupul が最後に記録した稼働時間 |
| Device - Polling Time | スクリプト | Kadupul がこのデバイスのポーリングに要した時間 |
| インターフェースグラフ | データクエリ | インターフェースごとのトラフィック、エラー、パケット、ステータス |

プロセッサクエリは、検出されたエントリごとの負荷を読み取ります。その行数がホストのハードウェアスレッド数と一致すると想定しないでください。パッケージ化されたインデックスパターンは1桁または2桁のインデックスのみを受け入れ、CPU が少ないホスト上であっても 100 以上を拒否します。検出結果を生の walk と比較してください。[CPU インデックスの不具合](https://github.com/kadupulhq/kadupul/issues/246)を参照してください。平均化スクリプトは、プロセッサの負荷を個別に走査し、返された行を平均化します。

Device - Uptime および Device - Polling Time は、Kadupul が保存したデバイスレコードを読み取ります。稼働時間ヘルパーは、経過時間を外挿することなく、保存された SNMP 稼働時間を返します。ポーリング時間は Kadupul の収集作業を表します。古い保存値は現在の到達可能性を証明するものではありません。収集が停止した場合、これらのヘルパーは新しいサンプルを生成しません。

## カウントにおける課題

これこそが仮想化を物理サーバーと異ならせている部分であり、そのいずれもグラフテンプレートによって解決されるものではありません。

**ゲストは移動します。** 別のホストに移行したゲストは、最初のホストのインベントリから消え、2番目のホストのインベントリに現れます。独立してタイミングをとったサンプリングでは、そのゲストが一時的に二重カウントされたり除外されたりする可能性があります。カウントの変化だけでは移行を証明できません。ハイパーバイザーのインベントリ ID とイベントを使用して説明してください。

**リソースは共有されるため、ゲストごとの帰属は推定値となります。** ホストは物理プロセッサの負荷を報告します。どのゲストがそれを引き起こしたかは報告しません。ホストの CPU をゲスト数で割ると、算術的には正しくても誰も尋ねていない質問に対する答えが得られるだけです。

**オーバーコミットにより、割り当て量と使用量は異なる値になります。** 割り当てられた仮想 CPU は意図的に物理コア数を超えることができ、割り当てられたメモリも意図的に物理メモリを超えることができます。割り当てられたリソースのグラフは、測定された需要ではなく割り当てを表します。物理容量、設定された制限、および実際の使用状況と比較してください。

**競合はこれらのテーブルには現れません。** ゲストが飢餓状態にあることを示す測定値、物理プロセッサを待機した時間、およびホストがそこから再利用したメモリは、このテンプレートが収集するものには含まれていません。CPU 使用率が 60% でゲストが激しく競合しているホストは、CPU 使用率が 60% でゲストが快適に動作しているホストとここではまったく同じに見えます。

**ゲストとホストの測定値は異なる質問に答えます。** ゲストの使用率だけでは、ホストのスケジューリング遅延を説明できない場合があります。ホストの負荷から帰属を導出するのではなく、ゲスト/アプリケーションの測定値をハイパーバイザーの競合メトリクスと関連付けてください。

### 代わりに行うべきこと

| 質問 | 答えがある場所 |
|---|---|
| ホストが飽和しているか | ホストからの物理プロセッサ負荷 |
| ゲストが飽和しているか | ゲスト内部、およびハイパーバイザーが保持する競合メトリクス |
| 実行中のゲスト数 | ホストのゲストインベントリカウント |
| 環境が容量超過になっているか | これらのグラフからはわからない。ホストが公開していない配置データが必要 |
| ゲストが移動したか | ハイパーバイザーのインベントリ ID と移行イベント。カウントの段階的変化だけでは不十分 |

ゲストに関するあらゆる事項についてはゲストを独自のデバイスとして監視し、ホストに関するあらゆる事項についてはホストを監視します。ホストレベルの数値からゲストごとのグラフを構築することは避けてください。それらは派生したものであり、信頼できるように見えますが、後から誰も気づけないような方法で誤っています。

## 同梱されたゲストカウントにおける落とし穴

ゲストインベントリスクリプトの出力に依存する前に、その内容を理解しておく価値があります。

**SNMP バージョン 1 とコミュニティ文字列のみで walk を実行します。** バージョンはスクリプトで固定されており、デバイス上の v3 認証情報は渡されません。v3 用に設定されたデバイスは他のパスを通じて収集できますが、ゲストの収集は失敗します。エージェントが v1 経由で保存されたコミュニティを独自に受け入れる場合、ゲストの収集は依然として成功する可能性があります。デバイス上で v3 を選択すること自体が結果を決定するわけではありません。空のゲスト walk はゼロとして返されます。ヘルパーに対応するためにエージェントのセキュリティポリシーをダウングレードすることなく、このプロトコルの不一致を確認してください。

**カウントは電源状態テーブルから取得されます。** ゲストの合計として報告される数値は、個別のインベントリオブジェクトではなく、電源状態サブツリーの walk によって返されたエントリの数です。ホストがリストアップしていても電源状態エントリがないゲストはカウントされません。

**電源オンは状態テキストで照合されます。** トリムして小文字に変換した後、`powered on` と `poweredon` のみが実行中カウントを増加させます。その他の表記は増加させません。ゼロを解釈する前に、エージェントの生の応答を比較してください。

**ゲストツールの分類には確認済みの不具合があります。** リテラルの `not installed` は、その一致がオフセットゼロから始まるため、実行中としてカウントされます。認識されないテキストも実行中に分類されます。そのカウントをツールが正常であることの証拠として扱わないでください。[ツールステータスの不具合](https://github.com/kadupulhq/kadupul/issues/244)を参照してください。

**呼び出しごとに3回 walk を実行します。** 電源状態テーブルを2回読み取り、次にツールテーブルを読み取るため、それ自身のカウントであってもアトミックなインベントリスナップショットではありません。多数のゲストを持つホストでは、その収集コストを測定してください。ポーラーの負荷が高い場合、これはスレッドを増やす候補になる前に、間隔を長くする候補となります。[ポーラーのスケール](/ja/guides/scale-the-poller/)を参照してください。

スクリプトは通常、空の walk に対するゼロを含め、5つの名前付き値をすべて出力します。したがって、失敗した walk は構文的には完全であっても誤解を招くサンプルを生成する可能性があります。不完全な出力に対して、PHP 出力プロセッサは関連付けられたデータソースに必要なフィールドを確認し、不完全なタイムスタンプグループを保留します。必ずしもそれらを即座に破棄するわけではありません。[ポーラーキャッシュ](/ja/concepts/the-poller-cache/)を参照してください。

## その他の落とし穴

**プロセッサの平均値は不均衡を隠します。** 1つのコアが高負荷で他の 63 個がアイドル状態のホストでは、平均値は低くなります。それが重要となる環境では、検証済みのプロセッサごとのグラフを維持してください。平均化ヘルパーは、空の walk に対して `load:0` も返します。これは測定されたアイドル CPU と区別できません。収集ステータスおよび既知の空結果の不具合と関連付けてください。

**プロセッサインデックスは位置に基づいています。** それらはプロセッサテーブルを walk することによって検出されます。エージェントのインデックスが変更された場合は、連続性を信頼する前に ID マッピングを確認してください。パッケージ化された1桁または2桁の制限は、別の検出の不具合です。

**ストレージエントリは、エージェントがストレージと呼ぶあらゆるものです。** 乗算が必要な割り当て単位で、不要なものと混ざったデータストアを想定してください。これは Host Resources の動作であり、ESXi の特異な動作ではありません。バイト数を解釈する前に、キャッシュされた割り当て単位を確認してください。共有スクリプトには、無効な負のサンプルまたは欠落した乗数に関する[既知の変換の不具合](https://github.com/kadupulhq/kadupul/issues/243)があります。

**ハイパーバイザー上のインターフェース名は、変更されるまでは安定しています。** ドライバーの更新や再構成によって番号が付け直されることがあります。インデックスがどのように選択され、なぜそれが重要なのかについては、[スイッチの監視](/ja/guides/monitor-a-switch/)を参照してください。

**スクリプトはポーラーホスト上で実行されます。** スクリプトは、キャッシュされたコマンドによって渡されたデバイス ID を使用して、ハイパーバイザー自体に到達します。ゲストおよび CPU 平均ヘルパーは、呼び出しごとに現在のデバイス行を取得します。コミュニティの変更によってそれらのコマンド引数を再構築する必要はありません。他のコレクターは、作業項目内に認証情報を埋め込む場合があります。[ポーラーキャッシュ](/ja/concepts/the-poller-cache/)を参照してください。

## 障害モード

| 現象 | 一般的な原因 |
|---|---|
| ゲスト数以外のすべてが収集される | デバイスが SNMP v3 用に設定されており、ゲストスクリプトが v1 を使用している |
| ゲスト数は正しいが、電源オンの数がゼロ | 正確な電源状態テキストを確認し、2回目の walk が成功したかどうかを確認する |
| ゲスト数がゼロに落ちてから回復する | 失敗した walk または空の walk を確認する。ヘルパーはすべてゼロの行を出力することがある |
| ハードウェア変更後にプロセッサグラフが表示され、その後停止する | 変更されたインデックスと、パッケージ化された1桁または2桁への制限を確認する |
| ゲストの動作が遅いのにホストの CPU が低く平坦 | 競合だけでなく収集の失敗も確認する。空の平均 walk はゼロとして報告される |
| データストアグラフに要求していないパーティションが含まれる | エージェントがそれらをストレージとして報告している |
| ポーラー停止後に稼働時間グラフが異常に見える | ライブでの読み取りではなく、Kadupul が最後に記録した値を報告している |
| メンテナンス中にホスト間の総ゲスト数が跳ね上がる | 移行中のゲストが一時的に2回カウントされるか、まったくカウントされない |
