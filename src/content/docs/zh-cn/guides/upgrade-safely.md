:::caution[使用前请先验证]
源代码已公开，但目前尚无受支持的 Kadupul 发行版或迁移路径。在依赖这些步骤之前，请在带有备份的隔离副本上进行测试。参见[项目状态](/zh-cn/project/status/)。
:::

升级会在不同的时间点更改三个组件，且它们的可逆性各有不同。

| 变更项 | 是否可逆 | 如何逆转 |
|---|---|---|
| 代码、依赖项与配置 | 可从保留的副本恢复 | 恢复匹配的版本和配置设置 |
| 数据库架构与排队样本 | 可从匹配的备份恢复 | 恢复数据库；不存在自动反向迁移机制 |
| RRD 文件 | 可从匹配的备份恢复 | 恢复保留的历史记录；备份中缺失的样本无法通过回滚重新生成 |

本流程的目的就是确保这三者保持同步。

## 开始之前

**执行完整备份。** 备份全部三个部分，并确保彼此一致。请遵循[备份与恢复](/zh-cn/guides/back-up-and-restore/)。在最终捕获前停止所有写入进程，并妥善保留受保护的备份，直至升级验收完成。

**记录当前代码版本与架构版本。** 包括依赖项、本地修改、插件和配置。多个源代码版本可能对应相同的架构版本。请在隔离的恢复副本上对目标版本进行演练。

**检查每个插件。** 检查其兼容性声明、代码和依赖项，然后在目标版本上测试你所需的功能。单纯满足最低版本声明并不能确立兼容性。参见[插件验证](/zh-cn/guides/install-and-vet-plugins/)。

**检查运行时环境。** 包括 PHP 版本、PHP 扩展以及数据库服务器版本。在部署之前，请核对目标版本的[运行环境要求](/zh-cn/reference/requirements/)。切勿假定架构 CLI 工具会执行 Web 安装向导的每一项检查。

**确认数据库账户具备更改架构的权限。** 在正常运行时，该账户只需在其专属数据库内进行读写。而在升级时，它还需要具备创建、修改和删除数据表及索引的权限。在完成初始配置后收紧权限的安装环境，通常会在该步骤遇到问题。

**停止所有生产者。** 停止计划采集、远程采集器、Web 触发的采集以及手动维护任务；等待正在进行的任务执行完毕。仅在生产者停止后排空延迟写入队列，并将任何未确认的队列数据行与相匹配的备份一并保存。在部署和架构验证期间，保持生产者处于停止状态。

## 替换应用程序

覆盖复制有其特定的限制：

```bash
# Copies the contents of the new tree over the old one.
cp -a /path/to/new-release/. /path/to/kadupul/
```

如果不带末尾的点，`cp -a /path/to/new-release /path/to/kadupul` 会创建 `kadupul/new-release/`，并将旧应用程序的每个文件原封不动地留在原处。升级看似成功，界面仍在运行旧代码，而故障的第一个征兆通常是架构迁移拒绝匹配一个你以为已经替换掉的版本。

直接覆盖复制会保留新目录树中不存在的文件，包括废弃的应用程序文件。它可能会覆盖任何匹配的路径，因此请仔细检查打包产物，而不要默认配置或数据已被排除在外。更推荐使用经过审查、带有匹配依赖项、配置和插件的暂存目录树。如果通过符号链接切换版本，请在切换前验证有效的 RRA 路径和存储访问权限；当前的引导逻辑是从应用程序目录加上 `/rra` 来派生路径的。仅切换符号链接绝不等于完成了数据库回滚。

**在继续操作之前，检查当前实际运行的版本。**

```bash
cat /path/to/kadupul/include/cacti_version
```

如果未输出你刚刚部署的发行版本，请立即停止。此后的所有步骤都假定目标代码已部署到位。同时，请将源代码版本或产物校验和与版本记录进行比对；单凭版本字符串本身并不充分。

## 架构迁移

数据库有其自身的版本号，与代码中的版本是分开的。仅替换代码并不会改变数据库版本。

当代码版本与数据库版本不一致时，传统的已认证页面会重定向至安装程序。这并不是针对每个端点或 CLI 的通用防护措施，且匹配的版本字符串也不能证明每项迁移均已完成。请直接检查架构状态。

安装程序和 CLI 工具会按顺序执行迁移步骤。在常规架构升级之前，请检查持久队列和专用服务账户的存储访问权限。如果继承的 `poller_output` 队列不是 InnoDB 格式，请在停止写入进程并保留备份的前提下，对其进行显式转换：

```sh
php cli/upgrade_database.php --migrate-poller-queue
```

然后在每个实际运行的 Web 账户和轮询器账户下执行以下命令：

```sh
php cli/upgrade_database.php --check-rrd-storage
```

这两个选项属于独立操作，不能合并执行。队列转换会保留挂起的样本；切勿为了通过检查而清空数据行。请依据[存储要求](/zh-cn/reference/requirements/)来解决所有权归属以及数值型可信 UID/GID 配置。在线远程采集器通常会选择主队列；仅在需要对本地队列进行明确的检查或转换时，才使用 `--local`。一旦这些检查通过，即可从应用程序根目录执行架构升级：

```sh
php cli/upgrade_database.php
```

请以配置的服务账户身份运行该命令，并确保具备所需的文件系统访问权限和数据库特权。以 root 身份成功通过检查并不能证明服务账户也拥有相应访问权限。该工具提供了一个 `--forcever` 选项来显式指定起始版本，该选项仅用于预发布测试期间重新运行迁移。它不属于常规升级流程的一部分，使用它来跳过失败的步骤会导致架构处于半迁移状态。

捕获命令退出状态及输出内容，然后验证数据库版本和所需的架构变更。当前的 CLI 可能会拒绝未知或不受支持的旧起始版本，却依然退出码为 0；单纯的 shell 成功状态并不足以证明迁移成功。如果迁移中途失败，请保持生产者处于停止状态，并恢复匹配的备份集，切勿尝试跳过失败的步骤。

## 是什么导致插件损坏

Web 安装程序的插件检查可能会禁用不兼容或缺失的插件。切勿假定架构 CLI 工具会执行相同的插件生命周期检查。

**声明的最低版本高于新的核心版本。** 插件将被禁用。这是最常见的情况，也是升级前检查理应排查出的问题。

**插件目录、其 setup 文件或其声明文件丢失。** 插件将被禁用。在数据库中仍标记为启用状态但文件已被删除的插件就属于此类。

**插件完全没有声明文件。** 它可能无法通过安装程序的兼容性检查。请测试经过维护且兼容的插件包，而不是假定无需改动即可重新启用它。

还有第四种情况，它并不属于故障损坏。曾经作为插件存在但后来已合并到核心系统中的功能会被直接彻底移除，而不是被禁用：其钩子（hooks）和权限条目会被剥离，对应的数据行会被删除。如果你发现某个插件直接消失而不是变成灰色不可用状态，在判定已有对等功能可用之前，请先查阅迁移日志和该特定插件的处理说明。

禁用插件与卸载插件不同。插件钩子和迁移操作可能会更改其自身的数据表与权限；请保留相匹配的插件代码和数据，并核对具体的升级路径。切勿盲目承诺所有数据都能完好无损地保留。

## 回滚计划

在开始前就确定好回滚方案，因为根据升级进展所处的阶段不同，应对决策也有所不同。

| 故障节点 | 回滚方式 |
|---|---|
| 代码已替换，尚未运行任何改变状态的操作或写入进程 | 在确认状态未发生变化后，恢复先前的代码、依赖项与配置 |
| 队列转换或迁移已启动，包括部分失败的情况 | 停止写入进程，恢复匹配的代码、配置、数据库及 RRD 备份 |
| 迁移已完成，但应用程序运行异常 | 停止写入进程，恢复匹配的备份集；妥善处理备份后新采集的样本 |
| 仅有插件出现异常 | 保持该插件处于禁用状态，同时依据验收标准评估就地修复与协调回滚的利弊 |

表格背后的基本准则：代码与架构必须同步回滚，否则就不要回滚。在新架构上运行旧代码是不受支持的状态。切勿依赖 Web 版本检查来阻止所有不兼容操作。

给自己设定一个时间限制。提前决定在执行恢复之前最多花费多少时间排查问题，并严格遵守。系统处于半升级状态运行的时间越长，备份的实用价值就越低。

## 为什么 RRD 文件是绝不能丢失的部分

不要以为部署、维护或恢复采集不会改变 RRD 文件。在回滚状态变更时，请将它们与数据库一并备份并恢复相匹配的备份集。排队中保留的样本可能尚未写入这些文件。经验证的 RRD 备份可以找回其捕获的历史记录；而仅靠恢复架构或代码，根本无法重建缺失的样本。关于为什么内部的分辨率也无法重建，请参阅[数据源与轮转归档（RRA）](/zh-cn/concepts/data-sources-and-rras/)。

在升级过程中导致数据丢失的三种典型方式：

**通过直接替换安装目录进行部署。** RRA 目录默认是安装目录下的一个子目录。删除旧目录并在原位置解压新目录可能会彻底删除保留的度量数据。在替换应用程序之前，请通过经过测试的存储规划来保护 RRA 目录树。验证有效的 `$config['rra_path']`、嵌套路径和服务账户信任检查；本版本不提供用于任意本地 RRA 根目录的通用数据库设置。

**从接管整个目录树的代码检出或软件包进行部署。** 同样的错误，只是以自动化方式发生。请核对你的部署方法将哪些内容视为可删除对象。

**通过递归更改所有权来修复权限。** 对数据本身虽无损害，但可能会导致轮询器无法写入，其表现为系统能够完美绘制历史图表，却无法采集任何新数据。

## 升级之后

1. 检查升级输出、数据库版本和所需的架构变更，然后确认界面能够正常加载。单纯没有发生重定向并不足以证明成功。
2. 在远程采集器的生产者保持停止的状态下，完成计划中的远程采集器代码/配置升级，并验证其数据库目标。
3. 重复执行服务账户存储检查，恢复指定的采集器运行，并验证代表性 RRD 文件的最后更新时间及可用保留数值。
4. 检查日志中的运行统计行，将耗费时间与升级前进行对比。新版本可能会改变数据采集的性能开销。
5. 在安装了声明与新核心兼容的版本之后，逐个重新启用被禁用的插件。
6. 在约定的验收时间窗口内，检查保留队列深度、远程采集以及插件作业。在这些检查通过之前，请妥善保留用于回滚的备份。
