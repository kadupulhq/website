[アーキテクチャ](/ja/concepts/architecture/)ではポーラーキャッシュを次の一文で紹介しています。
作業リストは事前に計算されており、コレクターは各サイクルで設定を評価するのではなく、
そのリストを読み取ります。このページでは、その決定が実際に何を意味するのかを解説します。

## コレクターが本来行う必要のある処理

単一の値に対して何を収集すべきかを判断するには、一連の依存関係チェーンを解決する必要があります。
データソースはデバイスとデータテンプレートを指します。テンプレートはデータ入力を指します。
データ入力には複数のフィールドがあり、一部はデバイスごとに上書きされ、一部はテンプレートから継承されます。
データソースがデータクエリからのものである場合、現在のインデックスをクエリキャッシュ経由で解決する必要があります。
次に、フィールドが上書きしていない限り、デバイスから SNMP 認証情報を取得する必要があります。

これは単一の値に対して複数の結合（join）を行うことを意味します。控えめな構成のインストールでも
数万個の値を持ち、5分ごとに1サイクルを実行します。収集時にこの解決を実行すると、
ネットワークではなくデータベースが監視可能なデバイス数を決定することになります。

そのため、解決は何かが変更されたときに一度だけ行われ、その結果がフラットな形で書き込まれます。

## キャッシュが保存するもの

キャッシュは収集指示を事前に計算します。設定の繰り返し評価を削減しますが、
結合や稼働中のデバイス状態の読み取りを完全になくすわけではありません。

| 行に保持される内容 | 保持される理由 |
|---|---|
| どのコレクターが所有しているか | 各コレクターは自身に割り当てられた行のみを選択します |
| アクション：SNMP、スクリプト、またはスクリプトサーバー | どのコードパスを実行するかを決定します |
| ホスト名、SNMP バージョン、ポート、タイムアウト、コミュニティ名、または認証情報 | キャッシュされた接続フィールド。稼働中のホスト状態も読み取られます |
| OID、または完全なスクリプトコマンドライン | すでに置換済みで、即座に実行可能な状態です |
| RRD ファイルへのパス | すでに解決済みです |
| そのファイル内のフィールド名、および完全な読み取りに含まれるフィールド数 | 出力の照合と検証を可能にします |
| ステップ（step）、およびこの項目が次回実行されるまでのカウントダウン | [時間とインターバル](/ja/concepts/time-and-intervals/) を参照してください |

`cmd.php` は `poller_item` と `host` を結合し、無効化されたデバイスを除外し、
稼働中のデバイスフィールドを使用して可用性および再インデックスのチェックを行います。
キャッシュされた OID、コマンド、および RRD メタデータは、意図したデータソースと
引き続き一致している必要があります。

キャッシュされた認証情報はスナップショットですが、デバイス API 経由で変更された
認証情報を保存すると、通常は影響を受けるキャッシュが更新されます。
データベースを直接編集するとそのパスがバイパスされ、古いスナップショットが
残る可能性があります。すべての認証情報変更に手動の再構築が必要であると決めつけず、
実際のキャッシュを確認してください。

RRD パスも同様にスナップショットです。ファイルを移動したり、ファイルの保存場所を
変更したりすると、キャッシュされたすべての行が古い場所を指したままになります。

## キャッシュを書き込む処理

キャッシュは、変更を認識している各操作によって段階的に保守されます。

| 操作 | 書き換えられる行 |
|---|---|
| デバイスの保存 | 接続フィールド、コレクター、または無効化状態の変更によりプッシュアウトがトリガーされます。未変更の収集フィールドはクイック保存パスを使用できます |
| データソースの保存 | そのデータソースの行 |
| テンプレートからのグラフおよびデータソースの作成 | 新規に作成された行 |
| インデックスを移動または解決したデータクエリの実行 | 変更されたデータソースのみ |
| CLI による再構築 | ワーカーによって処理される有効化されたデバイス。現在の `--host-id` 転送の不具合により、デバイスの完全な隔離に依存することはできません |

書き換えは単なる機械的な挿入ではありません。再構築対象のデータソースの行は
まず存在しないものとしてマークされ、次に新しいセットが書き込まれ、
依然として存在しないとマークされている行が削除されます。これにより、
存在しなくなったフィールドの行が削除されます。バッファのクリーンアップは、
コレクターおよびデータソース ID によってスコープが制限されます。これにより、
通常のターゲットパスにおいて無関係なソースが保護されます。ただし、
同時並行の再構築や失敗したデータベース書き込みに対する完全な保証ではありません。
再構築後は、影響範囲を調査する際に近くの無関係なデバイスも含め、
生成された行を確認してください。

## 決して書き込まれない行

一部の設定では新しいキャッシュ行が生成されません。グラフだけでなくログも確認してください。

ビルダーは無効化されたデバイスをスキップしますが、一括**無効化**操作は既存のキャッシュ行を
保持し、収集プロセスがデバイスをフィルタリングして除外します。無効化された状態での再構築は
行を削除する可能性があります。一括**有効化**操作は設定済みのキャッシュを再利用するか、
空の場合は初期化します。通常、追加のデバイス保存は不要です。既存の部分的または古いキャッシュは、
依然として調査が必要です。

デバイスに使用可能な SNMP 設定がない SNMP 項目は、行を生成しません。バージョンがない、
バージョンが範囲外、またはバージョン 1 もしくは 2 でコミュニティ名が空の場合、
各サイクルで確実に失敗する行を書き込むのではなく、その行はスキップされます。

入力ホワイトリストが設定されている場合、ファイルの欠落や拒否された入力により、
その入力に対する新しい行の生成が阻止されます。確定された再構築は、
依然として古い行をクリーンアップします。`input_whitelist` の設定がない場合、
このチェックは入力を許可します。これは常に有効な保護機能ではありません。
ホワイトリストを変更する前に、拒否されたコマンドと設定されたポリシーを確認してください。

インターフェース上には、キャッシュが空であるデータソースが依然として表示されることがあります。
そのグラフは古い履歴を保持しているか、ギャップを表示している可能性があります。
平坦なゼロの線は信頼できる指標ではありません。欠落した認証情報や拒否された入力は、
解決すべき設定上の問題です。

## 変更が何も反映されないように見える理由

3つの異なるメカニズムが同じ症状を引き起こします。

**行が再構築されなかった。** インターフェースが収集に影響しないと判断する項目を変更したか、
インターフェースの外部で変更を行った場合です。キャッシュは依然として古い結果を保持しています。
意図した設定を確認した上で、再構築によりキャッシュされたフィールドを更新できます。

**行が一度も構築されなかった。** 上述のとおりです。再構築によってこれも解決されますが、
それは根本的な問題が修正された後であり、診断情報はグラフではなくログに現れることがよくあります。

**値は収集された後に破棄された。** 複数値の出力はテンプレートフィールド定義を介して
マッピングされ、参照されていないフィールドは解析中にスキップされることがあります。
期待されるフィールド名、マッピング、およびグラフの関連付けを確認してください。
このルールは、グラフ参照のないすべての数値サンプルを一律に破棄するものではありません。
キャッシュの再構築では、誤った出力契約を修正することはできません。

## 包括的な再構築ツール

単一のデバイスについては、従来のデバイスページで**ポーラーキャッシュを再作成**を使用します。
そのアクションは、デバイススコープの `push_out_host()` パスを呼び出します。
その後、生成された行と診断情報を確認してください。

現在の親スクリプト `rebuild_poller_cache.php` は `--host-id` を受け入れますが、
そのフィルターをワーカーコマンドに転送しません。そのため、単一デバイスに対する
CLI 再構築であっても、他の有効なデバイスが再構築される可能性があります。
このアプリケーションの欠陥が修正されるまでは、隔離のためにそのオプションに依存しないでください。

ポーラーユーザーとして実行する包括的な CLI 再構築がアプリケーションのルートから利用可能です。

```bash
php cli/rebuild_poller_cache.php
```

これは有効化されたデバイスを処理します。ホストのないソースやすべての無効化された
ソースに対する修復ではありません。この処理は収集テーブルに書き込みを行うため、
時間がかかる場合があります。重複する再構築を避け、処理を中断しないでください。
CLI の `--force` オプションはプロセス重複登録ガードをオーバーライドするため、
日常的な修復オプションではありません。

再構築は派生状態を更新します。デバイスの到達性を修復したり、RRD ファイルを移動したり、
拒否された入力コマンドを修正したり、失われた履歴を復元したりすることはありません。
修復が完了したと判断する前に、生成されたキャッシュ、ログ、およびその後の収集を確認してください。

Kadupul はキャッシュが最後に変更された日時を記録しており、これによりシステムの他の部分が
キャッシュを再読み込みする必要があることを認識できます。

## 複数のコレクター

複数のコレクターが存在する場合、各行は厳密にいずれか1つのコレクターに属し、
行はそのコレクター自身のデータベースと中央データベースの両方にプッシュされます。

変更を保存したときにリモートコレクターに到達できない場合、変更はリモートではなく
中央にのみ反映され、Kadupul はその旨を通知します。コレクターが復帰した際に
完全な同期を要求します。その同期が行われるまで、リモートコレクターはインターフェースに
表示されているものよりも古い作業リストを実行しています。コレクター固有の不一致は、
レプリケーションステータス、接続性、および各コレクターのローカルキャッシュを
調査する理由となります。

キャッシュが読み取られる場所や再インデックスコマンドが処理されるタイミングを含む、
完全な実行サイクル内の順序は、[ポーラーのライフサイクル](/ja/reference/poller-lifecycle/)
に記載されています。コレクターのスケーリングについては、
[ポーラーのスケーリング](/ja/guides/scale-the-poller/) を参照してください。
