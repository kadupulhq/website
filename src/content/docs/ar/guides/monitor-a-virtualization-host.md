:::caution[تحقق قبل الاستخدام]
التعليمات البرمجية المصدرية متاحة، ولكن لا يوجد إصدار مدعوم من Kadupul أو مسار ترقية مضمون. اختبر هذه الإجراءات على نسخة معزولة مع وجود نسخ احتياطية قبل الاعتماد عليها. راجع [حالة المشروع](/ar/project/status/).
:::

تجمع حزمة ESXi المرفقة قياسات المضيف وتعداد أصول الضيوف. وهي لا توفر قياسات المعالج أو الذاكرة أو التنافس لكل ضيف على حدة. تحقق من الكائنات التي يكشفها إصدار برنامج مراقبة الأجهزة الافتراضية لديك قبل تحديد الرسوم البيانية.

## ما يتم توفيره

يتم شحن قالب جهاز واحد لبرنامج مراقبة الأجهزة الافتراضية: **ESXi Device**. إنه حزمة جهاز، لذا يحتوي `install/templates/ESXi_Device.xml.gz` على البرامج النصية وملفات استعلام البيانات الخاصة به. اتبع [استيراد وتصدير القوالب](/ar/guides/import-and-export-templates/) وتحقق من اكتمال الاستيراد، بما في ذلك نشر الملفات. حدد قالب الجهاز، وافحص الاكتشاف، وأنشئ الرسوم البيانية المطلوبة صراحةً؛ استيراد الحزمة أو ربط قالب الجهاز وحده لا ينشئهما.

| ما يتم توفيره | الغرض |
|---|---|
| `resource/snmp_queries/esxi_cpu.xml` | يكتشف المعالجات ويقرأ الحمل لكل معالج |
| `resource/snmp_queries/esxi_hw.xml` | يكتشف مكونات العتاد ويقرأ حالتها |
| `resource/snmp_queries/interface.xml` | استعلام إحصائيات الواجهة القياسي |
| `resource/script_server/host_disk.xml` | الأقسام المثبتة، من خلال جدول تخزين Host Resources |
| `scripts/ss_esxi_vhosts.php` | مجمّع داخل `install/templates/ESXi_Device.xml.gz`؛ يعد الضيوف، والضيوف قيد التشغيل، وحالة أدوات الضيف |
| `scripts/ss_multicpu_avg.php` | يحسب متوسط حمل المعالجات في رقم واحد |
| `scripts/ss_hstats.php` | يقرأ إحصائيات الاستقصاء التي يحتفظ بها Kadupul بالفعل للجهاز |
| `scripts/ss_host_disk.php` | يدعم استعلام الأقسام |

لا يتم شحن أي حزمة أجهزة مخصصة لـ Hyper-V أو KVM/libvirt أو Xen أو Proxmox في هذا الإصدار. قد تغطي قوالب Linux/Windows العامة مقاييس المضيف التي يدعمها عملاؤها؛ يتطلب التجميع الخاص ببرنامج مراقبة الأجهزة الافتراضية قوالب ومجمعات مناسبة. راجع [كتابة برنامج نصي لجمع البيانات](/ar/guides/write-a-data-collection-script/).

## تشغيل العميل أولاً

راجع تكوين العميل الحالي واستخدم الإرشادات الخاصة بإصدار ESXi لديك. تتضمن ملاحظات الحزمة إعادة ضبط المصنع؛ وهي ليست متطلباً روتينياً مسبقاً وستؤدي إلى محو تكوين SNMP الحالي. بالنسبة للإعداد المستند إلى المجتمع (community)، تقوم الأوامر التالية بتعيين قيم العميل؛ استبدل الأمثلة واحتفظ بأي مجتمعات موجودة مطلوبة عند تعيين قائمة المجتمعات.

```bash
esxcli system snmp get
esxcli system snmp set -c YOUR_STRING
esxcli system snmp set -p 161
esxcli system snmp set -L "City, State, Country"
esxcli system snmp set -C noc@example.com
esxcli system snmp set -e yes
```

يعرض الأمر الأول التكوين؛ والأمر الأخير يمكّن العميل. يستبدل خيار المجتمع قائمته المكونة. تحقق من وصول جدار الحماية المطلوب من المجمّع واستشر [مرجع أوامر ESXCLI SNMP](https://developer.broadcom.com/xapis/esxcli-command-reference/latest/namespace/esxcli_system.html). تقوم هذه الأوامر بتكوين الاستقصاء المستند إلى المجتمع؛ ولا تقوم بتكوين SNMPv3. تحقق من الجهاز الذي يعمل عليه المجمّع قبل إضافة الجهاز.

```bash
snmpget  -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.1.1.0
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.2.1.25.3.3.1.2
snmpwalk -v2c -c YOUR_STRING esxi.example.net .1.3.6.1.4.1.6876.2.1.1.6
```

إذا نجح الأول ولم يُعد الثالث شيئاً، فافحص خطأ SNMP وسياسة الوصول ودعم العميل؛ فالمسح (walk) الفارغ وحده لا يحدد السبب. يستخدم البرنامج النصي للضيوف المرفق SNMPv1، وبالتالي فإن فحص v2c الناجح لا يثبت صحة مسار التجميع الخاص به. تنتج عمليات فحص الضيوف الفارغة تعدادات صفرية، وليس بالضرورة فجوات في الرسم البياني؛ راجع [خلل النتيجة الفارغة](https://github.com/kadupulhq/kadupul/issues/245).

## ما يكشفه المضيف

| المنطقة | الشجرة الفرعية | ما يوفره لك |
|---|---|---|
| المعالجات | `.1.3.6.1.2.1.25.3.3.1` | الحمل لكل معالج يكشفه العميل |
| مكونات العتاد | `.1.3.6.1.2.1.25.3.2.1` | فهرس المكون ووصفه وحالته |
| التخزين | `.1.3.6.1.2.1.25.2.3.1` | مخازن البيانات وأنظمة الملفات المحلية، كما يختار العميل الإبلاغ عنها |
| الواجهات | `.1.3.6.1.2.1.2` و `.1.3.6.1.2.1.31` | حركة المرور، الأخطاء، الحالة |
| جرد الضيوف | `.1.3.6.1.4.1.6876` | حالة الطاقة لكل ضيف وحالة أدوات الضيف |

الأربعة الأولى هي جداول Host Resources والواجهات القياسية، وهي نفس الجداول التي يستجيب بها مضيف Linux. راجع [مراقبة خادم Linux](/ar/guides/monitor-a-linux-server/) لمعرفة كيفية تصرف تلك الجداول وجدول الأقراص الذي يجب تفضيله.

والخامس هو الشجرة الفرعية للمورّد التي يستخدمها البرنامج النصي لتعداد الضيوف المرفق.

## قوالب الرسوم البيانية

| الرسم البياني | المصدر | ما يقرأه |
|---|---|---|
| ESXi - CPU | استعلام البيانات | الحمل لمعالج واحد مكتشف |
| ESXi - MultiCPU Average | برنامج نصي | متوسط حمل جميع المعالجات |
| ESXi - Hardware | استعلام البيانات | حالة مكون واحد مكتشف |
| ESXi - VHosts | برنامج نصي | أعداد الضيوف وحالة أدوات الضيف |
| Host MIB - Processes | OID ثابت | عدد العمليات على المضيف |
| Host MIB - Logged in Users | OID ثابت | عدد الجلسات على المضيف |
| Device - Uptime | برنامج نصي | وقت التشغيل كما سجله Kadupul آخر مرة |
| Device - Polling Time | برنامج نصي | كم من الوقت استغرقه Kadupul لاستقصاء هذا الجهاز |
| رسوم بيانية للواجهة | استعلام البيانات | حركة المرور والأخطاء والحزم والحالة لكل واجهة |

يقرأ استعلام المعالج الحمل لكل إدخال مكتشف. لا تفترض أن عدد صفوفه يطابق عدد خيوط عتاد المضيف: يقبل نمط الفهرس المرفق فهارس مكونة من رقم واحد أو رقمين فقط ويرفض 100 أو أكثر، حتى على مضيف به معالجات قليلة. قارن الاكتشاف بمسح خام؛ راجع [خلل فهرس المعالج](https://github.com/kadupulhq/kadupul/issues/246). يقوم البرنامج النصي للمتوسط بجوب أحمال المعالجات بشكل مستقل ويحسب متوسط الصفوف المعادة.

يقرأ Device - Uptime و Device - Polling Time سجل الجهاز المخزن في Kadupul. يُعيد مساعد وقت التشغيل وقت تشغيل SNMP المخزن دون استقراء الوقت المنقضي؛ ويصف وقت الاستقصاء عمل تجميع Kadupul. القيمة القديمة المخزنة لا تثبت إمكانية الوصول الحالية. إذا توقف التجميع، فلن تُنشئ هذه المساعدات عينات جديدة.

## مشاكل الحساب

هذا هو الجزء الذي يجعل المحاكاة الافتراضية مختلفة عن الخادم الفعلي، ولا يتم حل أي منها بواسطة قالب رسم بياني.

**الضيوف يتحركون.** الضيف الذي ينتقل إلى مضيف آخر يختفي من جرد المضيف الأول ويظهر في جرد المضيف الثاني. قد تؤدي العينات الموقوتة بشكل مستقل إلى عد هذا الضيف مرتين مؤقتاً أو إغفاله. لا تثبت تغييرات التعداد وحدها حدوث انتقال: استخدم معرفات جرد برنامج مراقبة الأجهزة الافتراضية وأحداثه لتفسيرها.

**الموارد مشتركة، وبالتالي فإن التوزيع لكل ضيف هو مجرد تقدير.** يبلغ المضيف عن حمل المعالج الفعلي. ولا يبلغ عن الضيف الذي تسبب فيه. إن قسمة معالج المضيف على عدد الضيوف تنتج رقماً صحيحاً حسابياً ولا يجيب على أي سؤال طرحه أي شخص.

**الإفراط في التخصيص يجعل التخصيص والاستخدام كميتين مختلفتين.** يمكن أن تتجاوز المعالجات الافتراضية المعينة النوى الفعلية، ويمكن أن تتجاوز الذاكرة المعينة الذاكرة الفعلية عمداً. يصف الرسم البياني للموارد المعينة التخصيص بدلاً من الطلب المقاس. قارنه بالسعة الفعلية والحدود المكونة والاستخدام الفعلي.

**التنافس لا يظهر في هذه الجداول.** القياسات التي تخبرك بأن الضيف يعاني من نقص الموارد، والوقت الذي أمضاه في انتظار معالج فعلي، والذاكرة التي استعادها المضيف منه، ليست ضمن ما يجمعه هذا القالب. مضيف بنسبة 60 في المائة من المعالج مع ضيوف يتنافسون بشدة يبدو مطابقاً هنا لمضيف بنسبة 60 في المائة من المعالج مع ضيوف يعملون بسلاسة.

**قياسات الضيف والمضيف تجيب على أسئلة مختلفة.** قد لا يفسر استخدام الضيف وحده تأخيرات جدولة المضيف. اربط قياسات الضيف/التطبيق بمقاييس تنافس برنامج مراقبة الأجهزة الافتراضية بدلاً من اشتقاق التوزيع من حمل المضيف.

### ما يجب فعله بدلاً من ذلك

| السؤال | أين توجد الإجابة |
|---|---|
| هل المضيف متشبع | حمل معالج المضيف، من المضيف |
| هل الضيف متشبع | داخل الضيف، بالإضافة إلى مقياس تنافس يحتفظ به برنامج مراقبة الأجهزة الافتراضية |
| كم عدد الضيوف الذين يعملون | جرد ضيوف المضيف، كتعداد |
| هل البيئة تجاوزت سعتها | ليس من هذه الرسوم البيانية. يحتاج إلى بيانات تحديد المواقع التي لا يكشفها المضيف |
| هل انتقل الضيف | معرفات جرد برنامج مراقبة الأجهزة الافتراضية وأحداث الترحيل؛ خطوات الحساب وحدها غير كافية |

راقب الضيوف كأجهزة خاصة بهم لأي شيء يخص الضيف، وراقب المضيف لأي شيء يخص المضيف. قاوم إنشاء رسوم بيانية لكل ضيف من أرقام مستوى المضيف: فهي مشتقة، وتبدو موثوقة، وهي خاطئة بطرق لا يمكن لأحد اكتشافها لاحقاً.

## فخاخ في تعداد الضيوف المرفق

من المفيد فهم البرنامج النصي لجرد الضيوف قبل الاعتماد على مخرجاته.

**يجوب بـ SNMP الإصدار 1 وسلسلة المجتمع فقط.** تم إصلاح الإصدار في البرنامج النصي ولا يتم تمرير بيانات اعتماد v3 الموجودة على الجهاز. يمكن للجهاز المكون لـ v3 التجميع من خلال مسارات أخرى بينما يفشل تجميع الضيوف. قد ينجح تجميع الضيوف إذا قبل هذا العميل بشكل مستقل المجتمع المخزن عبر v1؛ تحديد v3 على الجهاز لا يحدد النتيجة بحد ذاته. يتم إرجاع عمليات فحص الضيوف الفارغة كأصفار. تحقق من عدم تطابق البروتوكول هذا دون خفض مستوى سياسة أمان العميل لاستيعاب المساعد.

**يأتي التعداد من جدول حالة الطاقة.** الرقم المبلغ عنه كإجمالي الضيوف هو عدد الإدخالات التي تم إرجاعها بواسطة مسح الشجرة الفرعية لحالة الطاقة، وليس من كائن جرد منفصل. لا يتم احتساب الضيف الذي يدرجه المضيف ولكن ليس لديه إدخال حالة طاقة.

**تتم مطابقة التشغيل على نص الحالة.** بعد الاقتطاع والتحويل إلى أحرف صغيرة، يؤدي `powered on` و `poweredon` فقط إلى زيادة عدد الأجهزة قيد التشغيل. التمثيلات الأخرى لا تفعل ذلك؛ قارن استجابة العميل الخام قبل تفسير الصفر.

**تصنيف أدوات الضيف به خلل مؤكد.** يتم احتساب النص الحرفي `not installed` على أنه قيد التشغيل لأن مطابقته تبدأ عند الإزاحة صفر. النص غير المعترف به يقع أيضاً تحت التشغيل. لا تعامل هذا التعداد كدليل على صحة الأدوات؛ راجع [خلل حالة الأدوات](https://github.com/kadupulhq/kadupul/issues/244).

**يقوم بالمسح ثلاث مرات في كل استدعاء.** يقرأ جدول حالة الطاقة مرتين، ثم جدول الأدوات، لذا حتى تعداداته الخاصة ليست لقطة جرد ذرية. على مضيف به العديد من الضيوف، قم بقياس تكلفة التجميع هذه. إذا كان المجمّع تحت ضغط، فهذا مرشح لفاصل زمني أطول قبل أن يكون مرشحاً لمزيد من الخيوط. راجع [توسيع نطاق المجمّع](/ar/guides/scale-the-poller/).

يُخرج البرنامج النصي عادةً جميع القيم الخمس المسماة، بما في ذلك الأصفار لعمليات المسح الفارغة. لذلك يمكن أن تسفر عملية المسح الفاشلة عن عينة كاملة من الناحية التركيبية ولكنها مضللة. بالنسبة للمخرجات غير المكتملة، يتحقق معالج مخرجات PHP من الحقول المطلوبة بواسطة مصدر البيانات المقترن ويحجب مجموعات الطوابع الزمنية غير المكتملة؛ ولا يتخلص منها بالضرورة على الفور. راجع [ذاكرة التخزين المؤقت للمجمّع](/ar/concepts/the-poller-cache/).

## فخاخ في الباقي

**متوسط المعالج يخفي عدم التوازن.** المضيف الذي يحتوي على نواة واحدة مستهلكة بالكامل و 63 نواة خاملة يكون متوسطه منخفضاً. احتفظ بالرسوم البيانية المعتمدة لكل معالج حيثما كان ذلك مهماً. يعيد مساعد المتوسط أيضاً `load:0` للمسح الفارغ، وهو ما لا يمكن تمييزه عن وحدة المعالجة المركزية الخاملة المقاسة؛ اربطه بحالة التجميع وخلل النتيجة الفارغة المعروف.

**فهارس المعالج موضعية.** يتم اكتشافها عن طريق جوب جدول المعالج. إذا تغيرت فهارس العميل، فتحقق من تعيينات الهوية قبل الوثوق بالاستمرارية. يعد القيد المرفق برقم واحد أو رقمين خللاً منفصلاً في الاكتشاف.

**إدخالات التخزين هي كل ما يطلق عليه العميل اسم التخزين.** توقع مخازن بيانات مختلطة بأشياء لم تكن تريدها، بوحدات تخصيص تحتاج إلى مضاعفة. هذا هو سلوك Host Resources، وليس أمراً غريباً خاصاً بـ ESXi. تحقق من وحدات التخصيص المخزنة مؤقتاً قبل تفسير وحدات البايت؛ يحتوي البرنامج النصي المشترك على [خلل تحويل معروف](https://github.com/kadupulhq/kadupul/issues/243) للعينات السالبة غير الصالحة أو المضاعفات المفقودة.

**أسماء الواجهات على برنامج مراقبة الأجهزة الافتراضية مستقرة حتى تتغير.** يمكن أن يؤدي تحديث برنامج التشغيل أو إعادة التكوين إلى إعادة ترقيمها. راجع [مراقبة محول الشبكة](/ar/guides/monitor-a-switch/) لمعرفة كيفية اختيار الفهرس وسبب أهميته.

**تعمل البرامج النصية على مضيف المجمّع.** تصل إلى برنامج مراقبة الأجهزة الافتراضية بنفسها، باستخدام معرف الجهاز الذي تم تمريره بواسطة الأمر المخزن مؤقتاً. يجلب مساعدو الضيف ومتوسط المعالج صف الجهاز الحالي في كل استدعاء؛ لا يتطلب تغيير المجتمع إعادة بناء وسيطات الأوامر تلك. قد يقوم جامعون آخرون بتضمين بيانات الاعتماد في عناصر عملهم. راجع [ذاكرة التخزين المؤقت للمجمّع](/ar/concepts/the-poller-cache/).
