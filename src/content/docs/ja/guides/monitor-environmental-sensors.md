温度、湿度、および瞬間電力は測定値であり、通常は `GAUGE` として保存されます。累積エネルギーやイベントの合計には、代わりにカウンタータイプが必要になる場合があります。テンプレートを選択する前に、各オブジェクトの単位、ID、およびセマンティクスを確認してください。

何かを作成する前に、すでに提供されているものを確認してください。

## 同梱されているもの

リポジトリ自身のクエリディレクトリには4つのデータクエリ定義しか存在せず、その中には環境センサー用のものはありません。

| 提供されている SNMP クエリ | カバー範囲 |
|---|---|
| `interface.xml` | ネットワークインターフェース |
| `host_disk.xml` | Host Resources ストレージ |
| `net-snmp_disk.xml` | UCD で宣言されたパーティション |
| `net-snmp_devio.xml` | UCD ブロックデバイス I/O |

センサーのサポートは、他の2つの方法で提供されます。

**Net-SNMP デバイスパッケージにバンドルされているスクリプトサーバークエリ。** `install/templates/NetSNMP_Device.xml.gz` をインポートして、`resource/script_server/` の下に3つの lmSensors クエリ XML ファイルをデプロイします。ヘルパースクリプト `scripts/ss_netsnmp_lmsensors.php` もソースチェックアウト内に存在します。

| クエリ | テーブル |
|---|---|
| Net-SNMP - Sensors - Get Thermal Sensors | `.1.3.6.1.4.1.2021.13.16.2.1` |
| Net-SNMP - Sensors - Get Fan Sensors | `.1.3.6.1.4.1.2021.13.16.3.1` |
| Net-SNMP - Sensors - Get Voltage Sensors | `.1.3.6.1.4.1.2021.13.16.4.1` |

ヘルパーはインデックス、名前、および読み取り値の列を使用します。クエリは数値の `sensorDevice` をインデックスとして使用します。`sensorName` は表示名を提供しますが、ヘルパーによって 18 文字に切り詰められます。名前が一意のセンサー識別子であることは保証されません。

通常の `get sensorReading` パスは生の値を返します。従来の温度オブジェクトの場合はミリ度、電圧の場合はミリボルト、ファンの場合は RPM です。温度グラフは `Divide by 1000` CDEF を適用します。電圧グラフには、Volts のラベルがあるにもかかわらず CDEF がなく、これは[確認済みのスケーリングの不具合](https://github.com/kadupulhq/kadupul/issues/247)です。

個別の `query sensorReading` パスは温度と電圧をスケーリングし、誤った定数 4294967294 を使用して符号付き電圧変換を試みます。また、[利用できない読み取り値に対して例外をスローする](https://github.com/kadupulhq/kadupul/issues/248)可能性もあります。この検出出力から保存単位を推測しないでください。

ヘルパーは依然として従来の温度列 `.2.1.3` を使用しています。現在の上流の [LM-SENSORS-MIB](https://raw.githubusercontent.com/net-snmp/net-snmp/master/mibs/LM-SENSORS-MIB.txt) では、その符号なしオブジェクトは非推奨とされ、符号付き列 `.2.1.4` が推奨されています。テンプレートを適応させる前に、実際のエージェントでサポート状況と負の温度の動作を確認してください。

**インポート可能なアーカイブとして提供されるデバイスパッケージ。** いくつかのパッケージは独自のクエリ XML を保持しており、インポート時にそれをクエリディレクトリに書き込みます。ここに関係するものは以下のとおりです。

| パッケージ | 提供内容 |
|---|---|
| SNMP UPS | UPS-MIB の入力および出力ラインのクエリ、さらにバッテリー、稼働時間、温度、およびアラーム用の固定 OID テンプレート |
| AKCP Device | 温度、湿度、気流、および 4-20 mA センサー用のスクリプトクエリ |
| APC InfraStruXure PDU | ブレーカーおよびフェーズ統計用のクエリ |
| APC InfraStruXure InRow CRAC | 温度、湿度、気流、およびファン速度を含むユニットおよびグループ統計用のクエリ |
| BayTech PDU | 電流、電圧、電力、および温度を備えたコンセントクエリおよび三相回路クエリ |

手作業でクエリを作成する前に、一致するパッケージを確認してください。[テンプレートのインポートとエクスポート](/ja/guides/import-and-export-templates/)に従い、ファイルのデプロイと検出を確認した上で、必要なグラフを明示的に作成してください。パッケージが存在するからといって、デバイスの互換性や正確なスケーリングが証明されるわけではありません。以下の UPS および lmSensors の不具合には注意が必要です。

## センサーがとる2つの形態

SNMP 収集では、スカラーオブジェクトとインデックス付きテーブルインスタンスを区別してください。

**固定 OID。** 1つのアドレスにある1つのスカラー値であり、そのタイプのすべてのデバイスで同じアドレスになります。バッテリー温度。総出力電力。固定 OID データソースを使用します。リテラル OID に対する SNMP get であり、読み取り値ごとに1つのデータソースとなります。

**テーブル。** デバイスごとに検出される未知の数の読み取り値です。ラックプローブ、コンセントタップ、相ごとの測定値。データクエリを使用します。これはテーブルを walk してインデックスを学習し、どの行をグラフにするかを選択できるようにします。

同梱の UPS パッケージは両方を使用しています。MIB のオブジェクト構造に従ってください。電流プローブが1つしかないデバイスでも、インデックス付きテーブル行として公開される場合があります。

| UPS 読み取り項目 | 形態 | OID |
|---|---|---|
| バッテリー温度 | 固定 | `.1.3.6.1.2.1.33.1.2.7.0` |
| 推定残り稼働時間 | 固定 | `.1.3.6.1.2.1.33.1.2.3.0` |
| バッテリー駆動時間 | 固定 | `.1.3.6.1.2.1.33.1.2.2.0` |
| バッテリー電圧 | 固定 | `.1.3.6.1.2.1.33.1.2.5.0` |
| 発生中のアラーム | 固定 | `.1.3.6.1.2.1.33.1.6.1.0` |
| 入力電圧、電流、電力、周波数 | クエリ | `.1.3.6.1.2.1.33.1.3.3.1` |
| 出力電圧、電流、電力、負荷 | クエリ | `.1.3.6.1.2.1.33.1.4.4.1` |

これらのデータソースはすべて `GAUGE` です。カウンターは1つもありません。同梱のテンプレートアーカイブは、ステップ 60 秒、ハートビート 600 秒、最小値 0、最大値なしを宣言していますが、温度には最小値がありません。インポートされたプロファイルと実際の RRD 設定を確認してください。これらの宣言は、稼働中のポーリング頻度を確定するものではありません。有効な負の読み取り値には、それを表示するグラフ軸も必要です。

## OID を見つける

何かを作成する前にデバイスを walk してください。探すべきものは3つあります。読み取り値のテーブル、ラベルの並行テーブル、ベンダーが選択した任意の乗数、さらに利用可能な場合は有効性/ステータスオブジェクトです。

```bash
snmpwalk -v2c -c public probe.example.net .1.3.6.1.2.1.33
# Replace this example enterprise number with the vendor's actual number.
vendor_oid='.1.3.6.1.4.1.318'
snmpwalk -v2c -c public probe.example.net "$vendor_oid"
```

サンプルのホストとコミュニティを設定値に置き換え、ポーラーからプローブを実行します。一致する MIB と依存関係をロードして、名前、単位、およびセマンティクスを確認します。ベンダーのオブジェクトドキュメントでも数値 OID を確認できます。近くにあるしきい値やステータスコードは測定値と交換可能ではありません。

```bash
snmptranslate -m +UPS-MIB -Td -OS .1.3.6.1.2.1.33.1.2.7
```

MIB 定義はスケーリングが文書化されている場所です。10分の1度を報告するベンダーは、オブジェクトの説明または単位句、および関連するベンダーのドキュメントにその旨を記載します。1回の読み取り値から推測すると、23.5 度が 235 度のグラフになってしまう可能性があります。

標準 MIB は予想以上に多くの範囲をカバーしています。`.1.3.6.1.2.1.33` の UPS-MIB はベンダー間で共通です。ENTITY-SENSOR-MIB は、センサー値とその横に独自のスケールおよび精度フィールドを提供します。エンタープライズサブツリーに頼る前に、これらを確認してください。

テスト環境で、代表的な再起動やプローブの交換前後における検出結果を比較してください。2回の変更されない walk だけではインデックスの安定性は証明されません。長期的なグラフを作成する前に、利用可能であれば安定したセンサー ID を記録してください。

## 固定 OID データソースを構築する

固定 OID センサーには、SNMP get データ入力を使用し、OID をリテラル値として設定し、その中に1つのデータソース項目を持つデータテンプレートが必要です。タイプを `GAUGE` に設定し、センサーが実際にその値を下回ることがない場合にのみ最小値に実際の値を設定し、ベンダーが上限を文書化していない限り最大値は未定義のままにします。

RRD データソースの範囲外の値は不明になります。これらの境界は、グラフの変換された単位ではなく、保存された生の単位で設定してください。そうしないと、表示 CDEF が適用される前に有効な測定値が失われる可能性があります。

## データクエリを構築する

クエリには、インデックス OID、walk された各 OID をインデックスに変換する方法、および必要な列ごとに1つのフィールドが必要です。

UPS 出力クエリは簡潔な実例です。これはラインテーブルにインデックスを付け、返された各 OID の末尾から正規表現でインデックスを解析し、インデックス用の1つの入力フィールドと、電圧、電流、電力、負荷用の4つの出力フィールドを宣言します。出力定義には、メソッド、ソース、方向、および列 OID が含まれます。列 OID は有効なインデックス走査ルートになり得ます。クエリのパーサーと実際に返された OID を一致させることが重要です。インデックスがどのように選択され保存されるかについては、[データクエリとインデックス](/ja/concepts/data-queries-and-indexes/)を参照してください。

再インデックス方法を意図的に選択してください。選択肢は、なし、稼働時間の巻き戻り時、インデックス数の変更時、およびすべてのフィールドの検証です。センサーテーブルは、より緩やかな方法が失敗する典型的な例です。ラックユニットからあるプローブを抜き、別のプローブを差し込むと、カウントは変わらないかもしれませんが、インデックスの背後にあるすべての読み取り値が別のセンサーのものになっている可能性があります。完全な検証には各サイクルで SNMP の処理コストがかかります。クエリがチェックできる識別フィールドを確認してください。変更されていない数値インデックスや重複/切り詰められたラベルでは、物理プローブが同一であることを証明できません。交換後は検出を更新し、グラフの関連付けを確認してください。

## 値をスケーリングする

どこで変換を行うかを決定し、1か所のみに配置してください。

| 場所 | 使用するタイミング |
|---|---|
| 収集スクリプト内 | 文書化されたコレクターの規約を使用する場合。lmSensors get は現在生の単位を返します |
| グラフ項目の CDEF 内 | 生の値を保存する価値があり、表示単位が表示の選択肢である場合 |

CDEF はベンダーの乗数に対する一般的な解決策です。同梱のパッケージには、現在のデータソース、`10`、および除算から構築された `Divide By 10` などの定義が含まれています。対応する生の単位を持つオブジェクトにのみ適用してください。

UPS パッケージには[不適切な電力および時間の CDEF](https://github.com/kadupulhq/kadupul/issues/249) があります。その On Battery 系列は秒を 60 ではなく 6000 で除算し、入力/出力 Watts 系列はワットを 10 で除算します。準拠したエージェントの場合、600 秒は 10 分として、1000 ワットは 1000 ワットとして表示される必要があります。バッテリー電圧とライン電流は 10 で除算する必要があります。推定残り稼働時間はすでに分単位です。[RFC 1628 の UPS オブジェクト単位](https://www.rfc-editor.org/rfc/rfc1628.html)を参照してください。

生の読み取り値を保存し、グラフ上で除算を行うことで、サンプルがデータソースの境界と保存期間を維持している限り、RRD ファイルの正確性を保ち、生の履歴を書き直すことなく表示乗数を修正できます。コレクター側での変換は保存単位を変更し、精度が失われる可能性があります。必ず文書化してください。説明のない生の読み取り値を、検証された工学単位として提示すべきではありません。

変換を2回適用しないでください。スクリプトがすでに値をスケーリングしているグラフ上の CDEF は、もっともらしく見えても誤った読み取り値を生成する可能性があります。

## 測定値に適したグラフ設定を適用する

トラフィックのデフォルトを盲目的にコピーするのではなく、測定値に応じた設定を選択してください。

| 設定 | トラフィック | センサー |
|---|---|---|
| データソースタイプ | `COUNTER` | `GAUGE` |
| ベース値 | 1000。軸が k や M で表示される | 同じく 1000 だが、度数に対して接頭辞は無意味 |
| オートスケール | 範囲が不明なため必要 | 範囲が既知のため通常は不要 |
| 上限と下限 | オートスケールモードに依存 | 有用な表示範囲を選択 |

明示的な上限と下限、および実際の単位を示す垂直ラベルを設定します。同梱の UPS 温度グラフはこのように設定されています。下限は 0、上限は 100、垂直ラベルは `C` です。

オートスケールオプションはスイッチではなく、選択肢のセットです。同梱の温度グラフが使用しているオプションは、`--alt-autoscale-max` で下限を渡します。保存されている上限 100 は渡しません。固定された境界がない場合、範囲外の読み取り値によって渡された制限が拡張される可能性があります。設定された制限は自動的に固定されるわけではありません。関心のある境界を維持するバリアントを選択してください。

| オプション | 効果 |
|---|---|
| 制限を無視するオートスケール | 両端が変動します。範囲がまったくわからない場合に使用します |
| 下限を受け入れるオートスケール | 下限を渡します。最大値はデータに従います |
| 上限を受け入れるオートスケール | 上限を渡します。最小値はデータに従います |
| 両方の制限を受け入れるオートスケール | 両方の制限を渡します。拡張は依然としてリジッドモードに依存します |

値が設定した制限外になった場合に軸の拡張を停止するリジッド境界オプションもあります。変動を確認することよりも固定された軸が重要な場合はこれをオンにし、そうでない場合はオフにしておきます。リジッドグラフは表示範囲外の変動をクリップする可能性があるためです。これによって保存されたサンプルが削除されることはありません。[RRDtool グラフ制限リファレンス](https://rrdtool.org/rrdtool/doc/rrdgraph.en.html)を参照してください。

SI 接頭辞が読者を混乱させるような度数やパーセンテージの場合は、単位指数を 0 に設定することを検討してください。ベース 1000 は接頭辞のステップを制御しますが、それ自体が接頭辞を無効にしたり測定単位を変換したりするわけではありません。

### ここではトラフィックよりも集約が重要になります

1時間にわたって平均化されたインターフェースカウンターは、何が起こったかを大まかに伝えてくれます。1時間にわたって平均化された温度は、重要であった10分間の変動を隠してしまいます。これらのデータソースの背後にあるストレージプロファイルが `MAX` アーカイブを保持していることを確認し、適切な `MAX` 集約を読み取るようにプロットされた系列を設定してください。`AVERAGE` 系列に対する凡例の最大値は、元のピークを復元しません。

MAX アーカイブであっても、収集されたサンプルに含まれるピークのみを保持します。ポーリング間の変動や保存前に拒否された値を復元することはできません。[データ保持の管理](/ja/guides/manage-data-retention/)および[データソースとアーカイブ](/ja/concepts/data-sources-and-rras/)を参照してください。

## 使用に値する MIB がない場合

多くの環境機器は Modbus、シリアルプロトコル、または HTTP API を使用しており、その SNMP エージェントは有用なものを何も公開していません。これらにはスクリプトデータ入力が必要です。スクリプトはデバイス上ではなくポーラーホスト上で実行され、デバイスへのアクセスはスクリプトの責務となります。出力の規約については、[データ収集スクリプトの作成](/ja/guides/write-a-data-collection-script/)を参照してください。

センサーが到達不能な場合は、`0` ではなく `U` を返してください。オフラインになったプローブは、0度を示しているプローブではありません。

## 障害モード

| 現象 | 一般的な原因 |
|---|---|
| 温度が10倍または100倍大きな数値としてグラフ化される | ベンダーの乗数が除算されていない |
| 温度が10倍小さな数値としてグラフ化される | スクリプト内と CDEF 内で2回除算されている |
| 電圧レールが数十億として読み取られる | 負の値を保持する符号なし SNMP 整数が修正されていない |
| プローブ交換後にセンサーグラフが平坦になる | テーブルが再インデックスされ、データソースが別のセンサーを指している |
| しきい値を超える読み取り値が欠落として表示される | データソースに最大値が設定されており、実際の値がそれを超えている |
| 度数の読み取り値で軸に k や M のラベルが付く | トラフィックテンプレートから継承されたベース値と単位設定 |
| 週間ビューで変動が見えない | 選択された集約、保持された解像度、ポーリング間隔、および拒否されたサンプルを確認する |
| クエリがインデックスを返さない | 返された OID、パーサーの一致、アクセス制限、およびオブジェクトのサポートを確認する。列ルートが有効な場合がある |
| Linux ホストで lmSensors クエリが何も見つけない | エージェントのサポート、アクセス権、公開されているセンサー行、および正確な SNMP エラーを確認する |
