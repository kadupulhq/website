먼저 장치 하나를 추가하고 응답을 확인한 뒤 다음 단계로 진행하세요. 모니터링 시스템에서 발생하는 대부분의 문제는 애초에 실제로 응답한 적이 없는 장치에서 비롯됩니다.

문제가 생겨도 괜찮은 장치를 선택하세요. 직접 소유하고 제어하는 네트워크에 있으며 SNMP가 이미 활성화된 스위치가 적합합니다. 다른 사람이 조회를 요청하고 있는 장치로 시작하지 마세요.

## 시작하기 전에

이 SNMP 예제에서는 장치가 지정된 수집기(collector)의 쿼리에 응답해야 합니다. 가능한 한 폴러(poller) 실행 사용자로 해당 수집기에서 검사를 실행하세요. 노트북에서 보낸 요청은 다른 방화벽 경로를 거칠 수 있습니다. 예제 주소와 커뮤니티 문자열을 장치에 구성된 읽기 전용 자격 증명으로 바꾸세요. 로컬 MIB 이름 파일이 설치되어 있지 않은 경우에도 아래의 숫자 OID로 작동합니다.

```bash
snmpget -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.1.1.0
```

이 명령이 설명 문자열을 반환하면 계속 진행하세요. 시간 초과가 발생하면 먼저 그 문제부터 해결해야 합니다. 웹 인터페이스에서 아무리 많은 설정을 변경해도 도달할 수 없는 장치가 응답하게 만들 수는 없습니다.

그런 다음 실제로 그래프로 그리려는 테이블을 확인하세요. 장치가 `sysDescr` 에는 응답하면서도 인터페이스 테이블 조회를 거부할 수 있기 때문입니다.

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.2.2.1.2
```

두 번째 OID는 `ifDescr` 열입니다. 노출된 인터페이스마다 한 행씩 반환되어야 합니다. 결과가 비어 있다면 제한된 SNMP 뷰나 지원되지 않는 테이블을 의미할 수 있으며, 권한 부여 오류는 자격 증명이나 액세스 정책 문제를 나타냅니다. 장치나 Kadupul 구성을 변경하기 전에 반환된 오류 내용을 조사하세요.

SNMP 버전에 관한 두 가지 사실이 이후 설정을 결정하므로 지금 확인해 두세요.

| 버전 | 의미 |
|---|---|
| v1 | Counter64 미지원. 고속 링크의 경우 폴링 간격 사이에 32비트 옥텟 카운터가 여러 번 래핑(오버플로)되어 계산된 전송률이 모호해질 수 있습니다 |
| v2c | 에이전트가 지원하는 경우 Counter64를 지원합니다. 커뮤니티 문자열은 일반 텍스트로 전송됩니다 |
| v3 | `authPriv` 를 통한 인증 및 암호화를 지원합니다. v3를 선택하는 것만으로 두 기능이 모두 자동 활성화되지는 않습니다 |

지원이 가능한 환경에서는 `authPriv` 가 적용된 v3를 사용하고, 격리된 관리 네트워크에서는 v2c를 선호하세요. SNMP 버전과 함께 64비트 인터페이스 그래프 유형을 선택하세요. 장치가 v1만 지원하는 경우 이 페이지 하단의 오류 표에서 폴링 간격과 트래픽 전송률을 고려하세요. [SNMP](/ko/reference/snmp/) 문서에서 자격 증명 필드를 자세히 다룹니다.

## 양식을 열기 전에 결정할 세 가지

**자격 증명.** 기본 포트가 아닌 경우 포트 번호를 포함하여 위에서 테스트한 자격 증명과 정확히 일치해야 합니다.

**가용성 확인 방식.** 이는 Kadupul이 장치의 가동 여부를 판단하는 방식으로, 데이터 수집 작동 여부와는 독립적입니다. 기본 제공되는 선택지는 없음(none), ping, SNMP 업타임, SNMP 설명, SNMP getNext, 그리고 ping과 SNMP 업타임의 두 가지 조합(둘 다 요구하는 방식과 둘 중 하나만 허용하는 방식)입니다.

SNMP로 폴링하는 장치에는 SNMP 방식을 선호하세요. 실제로 의존하는 대상을 직접 테스트하기 때문입니다. ICMP ping은 원시 소켓(raw socket)을 필요로 하며, 웹 및 폴러 사용자는 일반적으로 이 권한을 갖지 않습니다. 따라서 셸에서 `ping` 에 응답하는 장치라도 웹 인터페이스에서는 다운된 것으로 보고될 수 있습니다. 열려 있는 것으로 확인된 포트에 대한 TCP ping을 사용하면 이를 피할 수 있습니다.

**장치 템플릿.** 하드웨어와 일치하는 템플릿을 선택하세요.

## 장치 추가하기

1. 기존 **장치** 페이지(`host.php`)에서 **추가**를 선택합니다. Symfony 마이그레이션이 진행되는 동안에도 장치 생성 및 그래프 설정에는 이 페이지를 계속 사용합니다. 설명, 호스트 이름 또는 주소, 할당된 수집기, SNMP 버전 및 자격 증명을 입력합니다.
2. 선택한 가용성 확인 방식을 설정합니다.
3. 장치 템플릿을 선택합니다.
4. 저장하고 장치가 활성화되었는지 확인한 다음 가용성/SNMP 패널을 확인하세요. 데이터베이스에 레코드가 저장되었다는 사실 자체가 데이터 수집의 성공을 보장하지는 않습니다.

## 장치 템플릿이 결정하는 사항

장치 템플릿은 그래프 템플릿 및 데이터 쿼리를 장치와 연결합니다. 데이터 쿼리는 장치의 테이블(예: 인터페이스 목록)을 순회하여 행당 하나의 인덱스를 생성합니다. 템플릿을 적용하면 해당 데이터 쿼리도 함께 실행되어 이러한 인덱스를 채웁니다. 그래프 자동 생성이 비활성화된 경우 이러한 연결 자체만으로는 그래프가 생성되지 않습니다. 그래프 자동 생성이 활성화되어 있으면 템플릿/쿼리 훅이 일치하는 규칙에 따라 그래프를 생성할 수 있습니다. 복사본을 추가하기 전에 기존 그래프를 먼저 검토하세요.

템플릿을 변경하면 연결 상태가 바뀌고 이러한 훅이 다시 실행될 수 있습니다. 이는 기존 그래프나 데이터 소스를 초기화하는 작업이 아닙니다. 이미 이력이 누적된 장치에 템플릿을 적용하기 전에 선택한 템플릿과 쿼리된 인덱스를 확인하세요.

이러한 인덱스가 있기 때문에 OID를 직접 입력하지 않고도 목록에서 인터페이스를 선택할 수 있습니다. [템플릿](/ko/concepts/templates/) 및 [데이터 쿼리 및 인덱스](/ko/concepts/data-queries-and-indexes/) 문서에서 두 개념을 자세히 다룹니다.

## 상태 패널 확인하기

장치가 SNMP 가용성 확인 방식으로 저장되면 Kadupul은 세션을 열고 결과를 보고합니다. 이것이 가장 중요한 검사이며, 많은 사용자가 건너뛰는 부분이기도 합니다.

| 화면 표시 | 의미 |
|---|---|
| 시스템 및 업타임 쿼리 성공 | 패널이 기본 SNMP 메타데이터를 정상적으로 읽었습니다. 이것이 인터페이스 수집 성공을 입증하지는 않습니다 |
| 위치 또는 연락처가 비어 있음 | 이러한 선택적 메타데이터 필드는 설정되지 않았을 수 있습니다. 비어 있다는 것 자체가 수집 실패를 의미하지는 않습니다 |
| SNMP 사용 안 함 | 장치에 커뮤니티나 사용자 이름이 없거나 버전이 없음(none)으로 설정되어 있습니다 |
| SNMP 세션 오류 | 세션 설정에 실패했습니다. 표시된 오류, 자격 증명, 프로토콜 및 연결 설정을 검사하세요 |
| SNMP 시스템 오류 | `sysDescr` 읽기에 실패했습니다. 반환된 오류, 에이전트 뷰, 자격 증명 및 도달 가능성을 확인하세요 |
| SNMP 호스트 오류 | 설명과 업타임이 모두 반환되지 않았습니다 |
| 업타임이 `U`로 표시됨 | 업타임을 읽을 수 없었습니다. 일부 장치는 애초에 이를 보고하지 않습니다 |

가용성 확인 방식에 ping이 포함되어 있으면 아래에 별도의 ping 결과가 표시됩니다. 둘 다 확인하세요. 장치가 하나는 통과하고 다른 하나는 실패할 수 있으며, 실패한 항목을 통해 확인해야 할 지점을 알 수 있습니다.

시스템 설명이 비어 있다고 해서 데이터 수집이 실패한 것은 아닙니다. 코드에서는 설명이 비어 있어도 업타임이 유효한 에이전트를 지원합니다. 비활성화된 장치는 가용성 확인을 건너뛰며, 비 SNMP 가용성 확인 방식은 이 SNMP 패널을 표시하지 않습니다. 다음으로 실제 쿼리와 폴러 캐시를 확인하세요.

## 데이터 소스 및 그래프 생성하기

자동 생성된 그래프가 없는 새 장치의 경우 다음 단계는 그래프와 해당 데이터 소스를 생성하는 것입니다. 비어 있을 것이라고 단정하지 말고 장치 페이지에서 **데이터 소스 목록** 및 **폴러 캐시 보기**를 확인하세요.

장치 페이지에서 **이 장치에 대한 그래프 생성**을 선택합니다. 스위치의 경우 이는 인터페이스 데이터 쿼리를 실행하고 원하는 인터페이스를 선택한 다음 이에 대한 그래프 유형을 선택하는 것을 의미합니다. 48개 포트 전체가 아닌 2~3개의 인터페이스만 선택하세요. 경로가 정상 작동하는지 확인하는 것이 목적이며, 적은 수의 초기 배치가 다음 단계에서 확인하기 훨씬 수월합니다.

인덱싱된 그래프는 데이터 소스를 선택한 인터페이스와 연결하고 해당 폴러 캐시 항목을 준비합니다. 호환되는 기존 소스가 있다면 재사용될 수 있습니다. 그래프 생성 응답 화면이 폴링 실행을 증명하는 것은 아닙니다. 캐시에 예상된 장치, 인터페이스 OID 및 RRD 경로가 포함되어 있는지 확인하세요.

## 수집 작동 확인하기

예약된 수집 주기가 지날 때까지 기다린 후 타임스탬프와 값을 모두 확인하세요. 빈 그래프는 시작 정규화, 알 수 없는 값(unknown) 또는 수집 실패를 의미할 수 있습니다. 전송률을 계산하려면 카운터 판독값이 두 번 필요하지만, 두 번의 폴러 실행이 완료되고 유효한 아카이브 버킷을 항상 보장하는 것은 아닙니다.

다음 세 가지를 순서대로 확인하세요.

**폴러가 실행되었는지 확인합니다.** 구성된 로그에서 실행 완료 요약 메시지를 찾으세요. 요약이 없다면 일정 예약, 로그 대상 위치 및 권한, 폴러가 완료 전에 조기 종료되었는지 여부를 확인하세요. [로깅](/ko/reference/logging/) 문서를 참조하세요.

**파일이 존재하며 최근에 업데이트되었는지 확인합니다.** 호스트 이름에서 임의로 추측하지 말고 데이터 소스 또는 폴러 캐시에서 실제 RRD 경로를 복사하세요. 경로와 이름은 사용자 지정될 수 있습니다. [파일 배치](/ko/reference/file-layout/) 문서를 참조하세요. RRDtool에 파일이 마지막으로 기록된 시점을 확인하세요.

```bash
rrdtool last /path/to/rra/the_actual_file.rrd
rrdtool lastupdate /path/to/rra/the_actual_file.rrd
rrdtool fetch /path/to/rra/the_actual_file.rrd AVERAGE --start end-30m --end now
```

성공적으로 쓰기가 이루어지면 타임스탬프가 앞으로 진행되어야 합니다. 최근 타임스탬프라도 알 수 없는 값이 수반될 수 있으며, 버퍼링된 쓰기로 인해 디스크 타임스탬프 갱신이 지연될 수 있습니다. `rrdcached` 나 Boost를 사용하는 경우 해당 구성 요소의 플러시 상태도 함께 확인하세요.

**값이 알 수 없음(unknown)이 아닌지 확인합니다.** `lastupdate` 는 가장 최근에 제공된 값을 표시합니다. 카운터의 경우 이는 계산된 트래픽 전송률이 아니라 누적 카운터 값입니다. `fetch` 의 완료된 행에서 유한한 전송률이 나타나는지 살펴보세요. 시작 타이밍, 단계 정렬, 하트비트, 상하한 범위, 아카이브의 알 수 없는 데이터 임계값이 모두 유효한 행이 나타나는 시점에 영향을 미칩니다. 처음 두 행만으로 오류를 단정하지 마세요. 알 수 없는 값이 지속되면 수집된 값, 데이터 소스 유형, 하트비트 및 폴러 오류를 점검하세요.

## 초기에 자주 발생하는 문제

| 증상 | 주된 원인 |
|---|---|
| 저장은 되지만 시스템 설명 조회 시 오류 발생 | 자격 증명, 에이전트 뷰 및 수집기 도달 가능성을 확인하세요. 설명이 비어 있다는 것만으로는 충분한 증거가 되지 않습니다 |
| Kadupul에서는 SNMP 세션 오류가 나지만 노트북에서 `snmpget` 은 작동함 | 방화벽 경로가 다르거나 에이전트가 소스 IP 주소로 접근을 제한하고 있습니다 |
| 장치가 다운된 것으로 표시되지만 SNMP 데이터는 도착함 | 가용성이 원시 소켓을 열 수 없는 ICMP ping으로 설정되어 있습니다 |
| 설명은 나타나지만 데이터가 없음 | 폴러가 예약되어 있지 않거나 RRD 디렉터리에 쓸 수 없는 사용자로 실행 중입니다 |
| 데이터 쿼리가 인터페이스를 반환하지 않음 | 에이전트 뷰에서 인터페이스 테이블을 제외했거나 장치의 재인덱싱이 필요합니다 |
| 첫 번째 값이 알 수 없음이고 이후 정상화됨 | 카운터에서는 정상적인 동작입니다. 전송률을 계산하려면 두 번의 판독값이 필요합니다 |
| 알 수 없는 값이 계속 지속됨 | 수집 실패, 잘못된 값, 유형/범위 불일치, 하트비트 또는 아카이브 정규화 문제입니다 |
| 한동안 데이터가 나오다가 누락 발생 | 폴러 실행 시간이 간격보다 오래 걸리거나 장치에서 SNMP 요청 전송률을 제한하고 있습니다 |
| 카운터 전송률이 비현실적임 | 다중 32비트 래핑, 카운터 리셋, 단위 또는 데이터 소스 설정을 확인하세요. 고속 링크에는 지원되는 64비트 카운터를 사용하세요 |
| 재부팅 후 인터페이스 그래프가 잘못된 포트를 표시함 | 인덱스가 변경되었습니다. 데이터 쿼리에 변경 사항을 감지하는 재인덱싱 방식이 필요합니다 |

마지막 항목은 수백 대의 스위치를 관리하기 전에 반드시 이해해야 합니다. SNMP 인터페이스 인덱스는 재부팅이나 모듈 교체 후에도 안정적으로 유지된다는 보장이 없습니다. 데이터 쿼리의 재인덱싱 방식은 그래프가 동일한 물리적 포트를 계속 가리키도록 유지하는 역할을 합니다. [데이터 쿼리 및 인덱스](/ko/concepts/data-queries-and-indexes/) 문서에서 선택지를 설명합니다.
