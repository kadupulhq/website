テンプレートは、100台目のスイッチを追加するコストを2台目の追加と同じにするために存在します。4つの種類があり、階層的に積み重なっています。

実践的な手順については、[テンプレートの使用と検証](/ja/guides/template-workflow/)を参照してください。

**データテンプレート**は、収集対象とその保存方法を定義します。フィールド、その型、境界値、ストレージプロファイル、および数値をフェッチする入力方法が含まれます。オブジェクトごとのフィールドや既存のRRDファイルは現在のテンプレートと異なる場合があり、テンプレート自体が物理ファイルのレイアウトを保証するものではありません。

**グラフテンプレート**は、描画方法を定義します。どのアイテムを、どの順序で、どの色で、どの凡例行で、軸に何を記載するかを指定します。

**デバイステンプレート**は、ハードウェアのクラスに適したデータクエリとグラフテンプレートを束ねるため、デバイス追加時に適切なものを選択するだけで作業の大半が完了します。

**データクエリ**は、対象がいくつ存在するか事前にわからないケースを処理します。スイッチには探索によって検出される複数のポートがあり、データクエリはグラフ作成のためにインデックス付きの結果を記録します。検出処理単独では、固定された数のグラフやデータソースは作成されません。

## どのように積み重なるか

これら4つは同じものの4つの層ではありません。それぞれが下位の要素を指し示すことで構成されています。

| 種類 | 指し示す先 | 生成物 |
|---|---|---|
| デバイステンプレート | グラフテンプレートおよびデータクエリ | 直接的な生成物はなし。デバイスに提供する項目のリスト |
| データクエリ | インデックス付き結果のグラフ定義とマッピング | 検出された行。選択したグラフ作成によりデータソースの作成や再利用が可能 |
| グラフテンプレート | アイテムがデータを必要とするデータテンプレートフィールド | 複数のデータソースを参照できるグラフ |
| データテンプレート | 入力方法とストレージプロファイル | データソースのメタデータ。書き込みパスが必要とした時点でRRDを作成 |

データを保持するテンプレートアイテムはテンプレートフィールドを参照し、インスタンス化されたアイテムはローカルフィールドにマップされます。テキストや定数のアイテムはデータソースの参照を必要としません。グラフ作成時にこれらのマッピングが解決され、その後の再テンプレート化やアイテムの変更によっても変更される可能性があります。グラフ作成では、グラフごとに新しいファイルを作成する代わりに互換性のあるデータソースを再利用できます。

## テンプレート準拠かオブジェクトごと個別か

グラフおよびデータソースレベルの多くのフィールドには、テンプレート行に対応するフラグが用意されています。これらのフィールドでは、フラグがリンクされた子要素への通常のプッシュ動作を制御します。その他のフィールド、グラフアイテム、および入力マッピングには、個別の伝播ルールがあります。

| フラグ | 意味 | 保存時の動作 |
|---|---|---|
| クリア | フィールドはテンプレート準拠 | すべての子要素に書き込まれ、既存の設定を上書き |
| セット | フィールドはオブジェクト個別 | すべての子要素でそのまま保持 |

フラグはフィールドごとに設定されます。グラフテンプレートは軸ラベルをリンクされたグラフにプッシュする一方で、各グラフのタイトルや垂直限界値は作成者の設定に委ねることができます。このような組み合わせが通常の設定であり、例外ではありません。

この設計の2つの特性は、誤解を招きやすい点です。

フラグはテンプレート上に存在し、次の保存時に何を行うかのみを決定します。プッシュによってすでに平坦化された後にフィールドをオブジェクト個別に変更しても、何も復元されません。以前の個別設定値は失われており、フラグが保護するのは将来の変更のみです。

その逆はより危険です。何年もオブジェクト個別として運用されていたフィールドのフラグをクリアすると、1回の保存によってすべての子要素のフィールドがテンプレートの値で一斉に上書きされます。その値は未検証のプレースホルダーである場合が少なくありません。

### すべてのフィールドにフラグがあるわけではない

フィールドがこの伝播処理に関与するのは、フラグが存在する場合のみです。データソースレベルでは、4つのフィールドにフラグがあり、2つのフィールドには意図的にフラグがありません。

| フィールド | フラグ | 挙動 |
|---|---|---|
| 名前 | あり | テンプレート準拠またはオブジェクト個別 |
| 有効状態 | あり | テンプレート準拠またはオブジェクト個別 |
| ステップ | あり | テンプレート準拠またはオブジェクト個別 |
| ストレージプロファイル | あり | テンプレート準拠またはオブジェクト個別 |
| 入力方法 | なし（常にテンプレート準拠としてマーク） | テンプレートの保存ハンドラーがリンクされたデータソース行を明示的に更新 |
| RRDファイルへのパス | なし（決してテンプレート準拠にしないマーク） | 通常のテンプレートプッシュからは除外。再テンプレート化時も既存パスを維持 |

パスの維持は、通常のテンプレート変更時に履歴データとの既存の関連付けを保護します。これは他の管理操作によってパスを編集したり移動したりできないという意味ではありません。変更前にファイルの一意性を確認してください。

データソースアイテム上のフィールドにはすべてフラグがあります。フィールド名、型、ハートビート、最小値、最大値、およびデータを供給する入力フィールドが含まれます。

## グラフ入力は逆方向に作用する

グラフテンプレートは、複数のグラフアイテムを1つの編集可能フィールドに関連付ける名前付き入力を宣言できます。これにより、グラフ上の1つの値を編集するだけで、それを共有するすべてのアイテムが更新されます。これは、1つの色や凡例の設定で関連アイテムのグループを制御する仕組みです。

プッシュされる値はテンプレートの値ではありません。入力に属する他のアイテムから現在の値を読み取り、それをプッシュします。したがって、グラフ入力はテンプレートから下方に伝播するのではなく、グラフ自体のアイテム間で横方向に伝播します。そのため、入力を編集すると、テンプレートが直接触れていないグラフが変更されることがあります。

## 何がいつ伝播するか

| 変更内容 | 既存のオブジェクトに届くか | 方法 |
|---|---|---|
| グラフテンプレートフィールド（テンプレート準拠） | はい、保存時 | そのテンプレートに基づくすべてのグラフに書き込み |
| グラフテンプレートフィールド（オブジェクト個別） | いいえ | 子要素は自身の値を保持 |
| グラフアイテムの外観 | はい、保存時 | 色、透明度、アイテムタイプ、線幅、破線、CDEF、VDEF、シフト、統合関数、配置、テキストおよび凡例形式 |
| グラフアイテムの追加、削除、または別フィールドへの再指定 | 操作依存 | 一致、追加、削除、再マッピングは異なるパスを使用。結果として生じるローカルアイテムマッピングを確認 |
| データテンプレートフィールド（テンプレート準拠） | はい、保存时 | そのテンプレートに基づくすべてのデータソースに書き込み |
| データテンプレート入力フィールドの値 | テンプレート準拠の場合 | テンプレートと子要素の個別フラグ、クエリインデックスフィールド、ホストフィールドルールが伝播を制限 |
| データテンプレートのストレージプロファイル、ステップ、アーカイブ | データベースのみ | 既存の物理ファイルは作成時の構造を維持 |
| データテンプレートに追加されたフィールド | データベースのみ | 既存の物理ファイルにはそれらを格納する場所がない |
| デバイステンプレートの内容 | 個別の同期が必要 | 関連付けの編集だけでは既存のすべてのデバイスは同期されない |

データベースの伝播は、保存パスと上書きルールに依存します。テンプレートのメタデータを更新しても既存のRRDファイル自体は移行されません。ファイルの保守は個別の操作です。使用中のデータテンプレートエディタでは、一部の構造設定が読み取り専用になります。[カスタムテンプレートの作成](/ja/guides/create-custom-templates/)を参照してください。

## デバイステンプレートには明示的な同期パスがある

デバイステンプレートの関連付けを編集すると、新しいデバイスに提供される内容が変わります。既存のデバイスには、個別の再適用/同期操作を使用します。一括処理ヘルパーは、呼び出し元が停止中のデバイスを明示的に含めない限り、通常UpまたはRecovering状態のデバイスを選択します。すべてのデバイスが更新されたと想定する前に、操作の選択対象を確認してください。

同期処理は、不足しているグラフテンプレートの関連付けを追加し、選択したデータクエリを更新し、不要になった未使用のグラフテンプレート関連付けを削除できます。デバイステンプレートからテンプレートが削除されたという理由だけで、既存のグラフが直接削除されることはありません。また、自動化やプラグインのフックを呼び出すため、設定されたグラフ自動化ルールが実行される場合があります。

同期後に、結果として得られたデバイスの関連付けとグラフを確認してください。それらは、これまでに適用されたすべてのテンプレートバージョンの永続的な和集合であるとは限りません。

## インデックスとポートが移動する理由

データクエリは、検出されたどの項目が既存のどのデータソースに対応するかを決定する必要があります。それがインデックスです。ハードウェアや設定の変更後に数値インデックスが変更されることがあります。適切で安定したフィールドを使用すると一意性を維持するのに役立ちますが、インターフェース名も変更されたり再利用されたりする可能性があります。実際のデバイス上で一意性、永続性、再インデックス動作を確認してください。フィールド名単体で継続性が保証されるものはありません。

この決定は行う時点では些細に見えますが、誤った場合のコストは高くつきます。また、クエリ全体で一度ではなく、実行ごとにデバイス単位で行われるため、2台の同一スイッチが異なるフィールドをキーとしてインデックス付けされる可能性があります。フィールドの選択方法、インデックス消失時の挙動、リナンバリング検出のコストについては、[データクエリとインデックス](/ja/concepts/data-queries-and-indexes/)で解説しています。

## 後からテンプレートを変更する

グラフの変更は、該当する保存と伝播が完了した後のレンダリングに影響します。個別上書きや画像キャッシュが表示内容に影響を与える可能性があるため、すべてのグラフが即座に変更されると思い込まないでください。代表的な子グラフとそのアイテムマッピングを検査してください。[グラフの外観調整](/ja/guides/tune-graph-appearance/)を参照してください。

データテンプレートを保存しても、既存のRRDファイルは自動的に再構成されません。ファイルの実際のデータソース定義やアーカイブは、データベースプロファイルと一致しない場合があります。メンテナンス前に両方を検査してください。代替ファイルの作成は選択肢の1つに過ぎません。

変更内容に応じて、サポートされているRRDtoolの調整、アーカイブのリサイズ、または管理されたダンプ/リストア作業により、既存の履歴の一部または全部を保持できます。これらの操作には限界があり、バックアップと検証が必要です。一度も保存されなかったデータを再構築することはできません。ファイルを削除して再作成すると履歴が失われます。[データ保持の管理](/ja/guides/manage-data-retention/)および[データソースとラウンドロビンアーカイブ](/ja/concepts/data-sources-and-rras/)を参照してください。

## テンプレートと呼ばれるその他のもの

他に4つのオブジェクトがこの用語を使用していますが、上記の4つとは動作が異なります。カラーテンプレートはグラフアイテムに適用される名前付きパレットです。集約テンプレートは複数のグラフを1つに結合する方法を記述します。自動化テンプレートは検出されたデバイスをデバイステンプレートに一致させます。グラフプリセット定義は再利用可能な凡例形式を提供します。

これらはいずれもここで説明した階層構造には属していません。検索結果でテンプレートという言葉を見かけた際に、適切な種類として理解できるように把握しておくことが有用です。
