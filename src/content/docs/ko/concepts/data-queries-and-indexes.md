일반적인 데이터 소스는 구성하기 전에 무엇을 측정할지 미리 알고 있어야 합니다.
이 방식은 시스템 평균 부하 측정에는 잘 맞습니다. 그러나 스위치 포트, 디스크, 온도 센서,
가상 머신에는 적합하지 않습니다. 이러한 목록은 계속 변하며 사용자가 직접 통제할 수 없기 때문입니다.

데이터 쿼리는 사용 가능한 객체를 검색합니다. 수동으로 하든 구성된 자동화를 통해서든 그래프 생성
프로세스는 어떤 객체가 데이터 소스를 가질지 선택합니다. 쿼리를 한 번 실행했다고 해서 가능한 모든
그래프가 자동으로 생성되는 것은 아닙니다.

## 쿼리 정의에 포함되는 내용

데이터 쿼리는 세 부분으로 구성된 XML 설명입니다. 즉, 항목 목록이 있는 위치, 각 항목에 대해
읽어야 할 정보, 그리고 어떤 항목이 무엇인지 결정하는 방법입니다.

Kadupul과 함께 제공되는 인터페이스 쿼리가 대표적인 실무 예시입니다. 이 쿼리는 `.1.3.6.1.2.1.2.2.1.1`을
워크(walk)하여 인터페이스를 열거한 다음, 반환된 각 위치에서 명명된 필드 집합을 읽습니다. 각 필드는
방향(direction)을 선언합니다.

| 방향 | 의미 | 인터페이스 예시 |
|---|---|---|
| `input` | 식별 및 명명을 위해 읽음. 시간 경과에 따라 수집되지 않음 | `ifName`, `ifDescr`, `ifAlias`, `ifType`, `ifSpeed` |
| `output` | 매 주기마다 수집할 가치가 있는 값 | `ifHCInOctets`, `ifHCOutOctets` |
| `input-output` | 둘 다 해당 | `ifOperStatus`, `ifAdminStatus` |

필드는 값을 읽는 방식도 선언합니다. 대부분은 값을 있는 그대로 가져오지만, 일부는 정규식을 적용하여
SNMP 열거형에서 숫자를 추출하고, 일부는 원시 바이트 대신 텍스트로 디코딩하도록 요구합니다.

쿼리를 실행하면 인덱스당, 필드당 하나의 행이 저장됩니다. 즉 장치, 쿼리, 필드 이름, 값, 그리고 해당 값이
유래된 위치입니다. 이 테이블이 바로 "이 장치에 무엇이 있는가"에 대한 답변이며, 다음 실행 때까지
캐시됩니다. 그래프 선택은 이 캐시를 사용하지만, 그래프 생성 도구를 통해 쿼리를 연결하거나 다시
실행할 수도 있습니다. 그래프를 추가하기 전에 검색 결과를 검토하십시오.

## 인덱스는 식별성 문제이다

SNMP 테이블에서의 위치는 이름이 아닙니다. 에이전트가 부여하는 슬롯 번호일 뿐이며, 재부팅, 카드 재장착,
펌웨어 업그레이드, 또는 인터페이스를 제거하는 구성 변경 후에 에이전트는 슬롯 순서를 다시 매깁니다.
데이터 소스가 "슬롯 3"만을 기억하고 있다면, 슬롯 3이 다른 포트가 되는 날 3개월 치의 이력 데이터가
잘못된 대상에 조용히 묶이게 됩니다.

Kadupul은 인덱스 유형과 식별 값, 그리고 현재 확인된 SNMP 인덱스를 함께 저장합니다. 재인덱싱은 이
식별성을 사용하여 현재 테이블 위치를 조회하며, 수동으로 재정의된 인덱스 유형은 별도로 처리됩니다.

쿼리가 실행될 때마다 해당 필드 값에 대한 현재 슬롯을 조회합니다.

| 결과 | 발생하는 현상 |
|---|---|
| 동일한 슬롯 | 수행할 작업 없음 |
| 다른 슬롯 | 데이터 소스가 새 슬롯에 다시 매핑되고 관련 그래프가 이를 따름 |
| 값이 더 이상 존재하지 않음 | 고아(orphan) 처리는 쿼리와 코드 경로에 따라 달라짐. 수집이 중단되었다고 가정하지 말고 결과 플래그와 폴링 OID를 확인할 것 |

재인덱싱은 일반적으로 데이터 소스와 기존 이력을 보존합니다. `index_transient` 옵션은 누락된 식별성을
예상된 상태로 취급하고 일반적인 고아 표시를 건너뜁니다. `index_orphan_removal`은 영향을 받는 폴링 항목과
Boost 출력을 제거하지만, 데이터 소스나 RRD 파일 자체를 삭제하지는 않습니다.

현재의 고아 처리 방식에는 결함이 있습니다. 식별성이 사라지고 다른 어떤 소스도 인덱스를 변경하지 않는 경우,
변경 없음 분기가 이전 인덱스와 폴링 OID를 그대로 둔 채 고아 플래그를 다시 지워버릴 수 있습니다. 재사용된
포트 인덱스로부터의 수집을 방지하기 위해 자동 고아 마스킹에 의존하지 마십시오. 저장된 식별성을 검색 데이터와
대조하여 검증하고 문제가 해결될 때까지 영향을 받는 데이터 소스를 비활성화하십시오.

## 키로 사용할 필드 선택

모든 필드가 유용한 키가 될 수 있는 것은 아닙니다. 쿼리 정의는 우선순위가 지정된 선호 목록을 제공하며,
Kadupul은 이를 순회하면서 일련의 검사를 통과하는 첫 번째 후보를 채택합니다.

| 검사 항목 | 존재하는 이유 |
|---|---|
| 필드가 `input` 또는 `input-output`임 | 식별 필드는 검색 시 사용 가능해야 함 |
| 두 인덱스가 동일한 값을 공유하지 않음 | 중복된 키는 단일 행을 고유하게 식별할 수 없음 |
| 고유 값의 개수가 인덱스 개수와 일치함 | 후보의 불완전한 포괄 범위를 거부함 |

이러한 검사에는 예외가 있습니다. 선언된 단일 후보는 직접 반환되며 원시 인덱스 OID는 별도로 허용됩니다.
`index_type=nonunique`는 중복 거부를 건너뛰지만 고유 값 개수 검사는 건너뛰지 않습니다. 선택된 필드와
캐시된 값을 점검하십시오. XML 유형 라벨만으로는 유효성 검증의 증거가 되지 않습니다.

인터페이스 쿼리는 `ifName`, 그 다음 `ifDescr`, 그 다음 하드웨어 주소, 마지막으로 원시 인덱스를 선호합니다.
이 순서는 의도된 것입니다. `ifName`은 대부분의 플랫폼에서 짧고 안정적입니다. `ifDescr`는 안정적이지만
텍스트에 슬롯 번호가 포함되는 경우가 있어 본래 목적에 어긋납니다. 원시 인덱스가 마지막인 이유는 이를 키로
삼는 것이 키를 전혀 설정하지 않는 것과 거의 다를 바 없기 때문입니다.

이 부분이 사용자들을 종종 혼란스럽게 만드는 대목입니다. 선택은 장치별, 실행별로 해당 장치의 현재 데이터를
기반으로 이루어집니다. 캐시된 값의 누락이나 중복된 이름으로 인해 `ifName`이 부적합해져 `ifDescr`로
폴백될 수 있습니다. 빈 필드 자체만으로는 어떤 검사가 실패했는지 증명하지 못하므로 실제 검색 행을 확인해야 합니다.
동일한 스위치 두 대가 서로 다른 필드를 키로 삼게 될 수 있으며, 장치가 실행 간에 사용하는 필드를 변경할 수도
있습니다. 선택된 필드가 변경되면 재매핑 오류가 발생할 가능성이 열리므로 Kadupul은 경고 로그를 남깁니다.

선택된 필드는 일반적으로 이를 참조하는 제목 형식을 통해 그래프의 이름을 지정하는 데에도 사용됩니다.
보유 장비 전반에서 그래프 제목의 구성 형태가 달라진다면 정렬 필드를 살펴보아야 합니다.

## 재인덱싱이 필요한지 감지하기

매 주기마다 모든 장치에 대해 데이터 쿼리를 다시 실행하는 것은 비용이 많이 들고 대부분 무의미합니다. 대부분의
장치는 수년 동안 아무런 번호도 변경하지 않기 때문입니다. 대신 각 장치와 쿼리 쌍은 정상적인 수집 중에 검사되는
저렴한 어설션인 재인덱싱 방식을 갖습니다. 어설션이 실패하면 재인덱싱이 큐에 등록됩니다.

| 방식 | 검사 내용 | 한계 및 비용 |
|---|---|---|
| 없음 (None) | 자동 어설션 없음 | 쿼리 재실행은 수동 또는 다른 명시적 작업에서 비롯되어야 함 |
| 업타임 (Uptime) | 가동 시간이 거꾸로 가지 않았음 | 사용 가능한 SNMP가 필요함. 업타임 롤백이 없는 변경은 감지하지 못함 |
| 인덱스 개수 (Index Count) | 현재 개수가 캐시된 인덱스와 일치함 | 카운트 OID는 비용이 저렴할 수 있음. OID가 없으면 구현체가 워크나 스크립트 결과를 계산함. 개수가 동일한 변경은 놓칠 수 있음 |
| 모두 확인 (Verify All) | 알려진 키 값이 캐시된 인덱스에서 여전히 일치함 | 캐시된 크기에 따라 작업량이 증가함. 새로 추가된 인덱스나 해당 값을 유지하는 의미론적 변경의 감지는 보장하지 않음 |

"모두 확인"은 폴링 중에 어설션을 확인하며, 매 주기마다 전체 검색 쿼리를 무조건 다시 실행하지는 않습니다.
광범위하게 사용하기 전에 대표 장비에서 비용을 측정하십시오. 업타임은 일반적인 기본값이지만 SNMP가 비활성화되어
있으면 어설션을 제공하지 못합니다. 쿼리 정의에서 자체 업타임이나 카운트 소스를 제공할 수도 있습니다.

## 재인덱싱은 비동기로 수행된다

실패한 어설션이 그 자리에서 즉시 재인덱싱을 실행하지는 않습니다. 어설션은 명령을 기록하고, 수집 주기 이후의
별도 처리 단계에서 해당 명령을 가져와 쿼리를 다시 실행합니다. 그에 따른 실질적인 영향을 염두에 둘 필요가 있습니다.

감지 주기는 여전히 이전 캐시를 사용할 수 있으므로 재인덱싱이 완료되기 전에 값이 잘못된 시계열에 기록될 수
있습니다. 업타임 관련 스파이크 억제는 플래그가 설정되었을 때 단일 값 출력을 알 수 없음으로 대체하지만,
모든 다중 값 출력이나 모든 인덱스 변경에 대해 완벽하게 보장하는 것은 아닙니다.

다운되었거나 비활성화된 장치에 대해서는 재인덱싱이 실행되지 않습니다. 접근 불가능한 동안 번호가 다시 매겨진 장치는
다시 접근 가능해진 후에도 여전히 어설션이나 명시적인 재실행이 필요합니다. 첫 번째 폴링 성공만으로는 재매핑이
완료되었음을 증명하지 못합니다. `--force` 플래그도 다운/비활성화 검사를 무시하지 않습니다.

쿼리가 다시 실행되면 이동된 데이터 소스의 폴러 캐시 항목이 다시 작성되며, 이것이 실제로 수집 경로를 전환하는
역할을 합니다. 이 메커니즘이 바로 [폴러 캐시](/ko/concepts/the-poller-cache/)이며, 쿼리 재실행은 이를
자동으로 유지 관리하는 몇 안 되는 작업 중 하나입니다.

장치에 쿼리를 추가하고 결과를 확인하는 운영 절차에 대해서는 [스위치 모니터링](/ko/guides/monitor-a-switch/)을
참조하십시오.
