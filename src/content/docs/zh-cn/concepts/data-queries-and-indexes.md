普通数据源要求你在配置之前就知道要测量什么。这对系统平均负载很有效。
但对于交换机端口、磁盘、温度传感器或虚拟机则行不通，因为列表在变化且不受你控制。

数据查询用于发现可用对象。图表创建过程（无论是手动还是通过配置的自动化流程）
会选择哪些对象获得数据源；单次运行查询本身并不会创建所有可能的图表。

## 查询定义包含的内容

数据查询是一个包含三个部分的 XML 描述：对象列表所在位置、关于每个对象读取什么内容，
以及如何决定哪个对象是哪个。

Kadupul 随附的接口查询就是实际范例。它遍历 `.1.3.6.1.2.1.2.2.1.1` 以枚举接口，
然后在每个返回的位置读取一组命名字段。每个字段都会声明一个方向。

| 方向 | 含义 | 接口示例 |
|---|---|---|
| `input` | 用于标识和命名读取。不随时间收集 | `ifName`, `ifDescr`, `ifAlias`, `ifType`, `ifSpeed` |
| `output` | 每个周期都值得收集的值 | `ifHCInOctets`, `ifHCOutOctets` |
| `input-output` | 两者兼备 | `ifOperStatus`, `ifAdminStatus` |

字段还会声明如何读取该值。大多数按字面获取；有些应用正则表达式从 SNMP 枚举中提取数字，
有些则要求将值解码为文本而不是原始字节。

运行查询会按索引按字段存储一行：设备、查询、字段名称、值以及该值来源的位置。该表就是
“此设备拥有什么”的答案，缓存至下一次运行。图表选择使用该缓存，但图表创建工具也可以
附加或重新运行查询。在添加图表之前，请检查发现结果。

## 索引本质上是标识问题

SNMP 表中的位置并不是名称。它是代理分配的插槽编号，在重新引导、重新拔插线卡、固件升级
或删除接口的配置更改后，代理会重新排列插槽。如果数据源只记住“插槽 3”，那么一旦插槽 3
变成不同的端口，三个月的历史数据就会悄悄附着到错误的对象上。

Kadupul 存储索引类型和标识值，以及当前解析的 SNMP 索引。重新索引使用该标识来查找当前的
表位置；手动覆盖的索引类型有单独的处理方式。

在每次运行查询时，它都会查找该字段值对应的当前插槽。

| 结果 | 发生的情况 |
|---|---|
| 相同插槽 | 无需操作 |
| 不同插槽 | 数据源被重新映射到新插槽，其图表随之跟进 |
| 值不再存在 | 孤立项处理取决于查询和代码路径；请验证生成的标志和轮询 OID，而不是假定收集已停止 |

重新索引通常会保留数据源及其现有历史记录。`index_transient` 选项将缺失的标识视为预期情况，
并跳过常规的孤立项标记。`index_orphan_removal` 会删除受影响的轮询条目和 Boost 输出；
它不会删除数据源或 RRD 文件本身。

当前的孤立项处理存在一个缺陷：当一个标识消失且没有其他源更改索引时，无更改分支可以再次清除
孤立项标志，同时保留先前的索引和轮询 OID。不要依赖自动孤立项屏蔽来防止从重用的端口索引中收集数据。
根据发现数据验证存储的标识，并在解决之前禁用受影响的数据源。

## 选择作为键的字段

并非每个字段都可以作为可用的键。查询定义提供了一个有序的首选列表，Kadupul 会对其进行遍历
并选取第一个通过一组检查的候选字段。

| 检查项 | 存在的原因 |
|---|---|
| 字段为 `input` 或 `input-output` | 标识字段必须在发现中可用 |
| 没有两个索引共享相同的值 | 重复的键无法唯一标识单行 |
| 唯一值的计数等于索引的计数 | 拒绝候选覆盖不完整的情况 |

这些检查有例外情况：声明的单个候选字段会直接返回，原始索引 OID 会单独接受。
`index_type=nonunique` 会跳过重复项拒绝，但不会跳过唯一值计数检查。请检查所选字段和
缓存的值；XML 类型标签本身并不是验证的证据。

接口查询优先选择 `ifName`，然后是 `ifDescr`，接着是硬件地址，最后是原始索引。这种顺序
是经过深思熟虑的。`ifName` 在大多数平台上简短且稳定。`ifDescr` 很稳定，但有时在文本中
带有插槽编号，这违背了初衷。原始索引排在最后，因为以此为键几乎不比完全不使用键好多少。

这就是经常让人感到意外的部分。此选择是在每次运行时针对每个设备根据该设备的当前数据做出的。
缺少缓存值或重复名称可能会使 `ifName` 不适用并导致回退到 `ifDescr`。空白字段本身并不证明
哪项检查失败；请检查实际的发现行。两台相同的交换机最终可能基于不同的字段建立索引，并且设备
在两次运行之间可能会更改其使用的字段。当所选字段发生更改时，Kadupul 会记录一条警告，
因为此时重新映射错误变得可能发生。

所选字段通常还会通过引用它的标题格式来命名图表。如果你的图表标题在整个设备群中改变了风格，
排序字段就是需要排查的地方。

## 检测是否需要重新索引

在每个周期针对每个设备重新运行数据查询既昂贵又大多毫无意义，因为大多数设备多年都不会重新编号。
相反，每个设备和查询对都带有一个重新索引方法，这是在正常收集期间检查的廉价断言。当断言失败时，
重新索引将被排入队列。

| 方法 | 检查内容 | 限制与开销 |
|---|---|---|
| 无 | 无自动断言 | 查询重新运行必须来自手动或其他显式操作 |
| 运行时间 | 运行时间没有倒退 | 需要可用的 SNMP；会遗漏没有运行时间回滚的更改 |
| 索引计数 | 当前计数与缓存的索引匹配 | 计数 OID 可能开销很小；如果没有计数 OID，实现会对遍历或脚本结果进行计数。可能会遗漏计数相同的更改 |
| 验证全部 | 已知的键控值在其缓存的索引处仍然匹配 | 开销随缓存集增长；不保证检测到新添加的索引或保留这些值的语义更改 |

“验证全部”在轮询期间检查断言；它不会在每个周期无条件地重新运行整个发现查询。在广泛使用之前，
请在具有代表性的设备上测量其开销。运行时间是常用的默认值，但当 SNMP 处于禁用状态时它不提供
任何断言。查询定义可以提供自己的运行时间或计数来源。

## 重新索引是异步进行的

失败的断言不会当场执行重新索引。它会写入一条命令，收集周期之后的单独处理阶段会获取该命令
并重新运行查询。其实际效果值得牢记。

检测周期可能仍在使用旧缓存，因此在重新索引完成之前，某个值可能会落入错误的序列中。与运行时间
相关的尖峰抑制在设置其标志时会将单值输出替换为未知；它并不能保证适用于所有多值输出或每次索引更改。

对于处于关闭或禁用状态的设备，不会运行重新索引。在无法访问期间重新编号的设备在恢复可访问后仍需要
断言或显式重新运行。仅凭第一次成功的轮询并不能证明重新映射已完成。`--force` 不会覆盖关闭/禁用检查。

查询重新运行后，发生变动的数据源的轮询器缓存条目将被重写，这才是真正重定向收集的机制。该机制就是
[轮询器缓存](/zh-cn/concepts/the-poller-cache/)，而查询重新运行是少数能够自动维护它的操作之一。

有关操作层面（将查询添加到设备并读取结果），请参阅 [监控交换机](/zh-cn/guides/monitor-a-switch/)。
