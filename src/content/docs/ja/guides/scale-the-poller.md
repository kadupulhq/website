:::caution[使用前に検証してください]
ソースコードは公開されていますが、サポートされている Kadupul のリリースや移行
パスはまだ存在しません。本運用で依存する前に、バックアップを備えた隔離された
環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

ポーラーのスケーリングは、突き詰めれば1つの問いに行き着きます。すなわち「ある収集サイクルが、
次のサイクルが始まる前に完了しているか？」ということです。以下の内容はすべて、この問いに答え、
そして答えを確実に「はい」に戻すためのものです。

どのコンポーネントが収集を実行しているかが明確でない場合は、まず[アーキテクチャ](/ja/concepts/architecture/)を確認してください。

## 2つのクロック

システムには2種類の異なるインターバルが存在し、これらは同じ設定項目ではありません。

| | 概要 | 許容される値 |
|---|---|---|
| ランチャーインターバル | OS が cron または `cactid` サービスからコレクターを起動する頻度 | 60秒 または 300秒 |
| ポーラーインターバル | 基本となる収集周期。個々のデータソースステップはこれより長く設定可能 | 10、15、20、30、60、または 300秒 |

ポーラーインターバルがランチャーインターバルよりも短い場合、1回の起動でループ処理により
複数回の収集パスが実行されます。実行パス数は、ランチャーインターバルをポーラーインターバルで
割った値となります。

起動全体の許容時間予算は、これら2つの数値から導出されます。すなわち、パス数にポーラーインターバルを
掛けた値から2秒を引いたものです。これが、処理実行時間が比較される実際の壁時計時間（実測時間）となります。

## 実行時間が制限を超過した場合の挙動

3つの明確に異なる事象が発生し、ログに3種類の異なるメッセージが出力されます。

**処理が強制中断される。** 経過時間が時間予算を超過すると、ポーラーは最大実行時間を超えた旨をログに
記録し、統計情報を書き込んで終了します。サンプルの生成に至らなかった処理はデータ欠落（ギャップ）を残す
可能性があります。永続キューにすでに受け入れられたサンプルは、その後の正常な RRD 書き込みのために
保留されたまま維持されます。超過が発生したからといって、未フラッシュの測定値がすべて破棄されたことを
意味するわけではありません。グラフと並行してキューの深さとログを確認し、次の実行を正常に見せかけるためだけに
保持されている行を消去しないでください。

**次回の実行が前回の残骸を検知する。** 起動時、ポーラーは正常に終了しなかったプロセスの行数をカウントし、
ポーリングサイクルを超過したプロセスが検出された旨の警告を発します。未完了または古いプロセスレコード、
および実際に動作中の子プロセスを調査してください。警告表示単体ではボトルネックの根本原因は特定できません。

**クロックの同期が崩れる。** 前回の実行から時間予算で許容される以上の時間が経過している場合、ポーラーは
ランチャーとポーラーインターバルの同期が崩れている旨を警告します。この現象は通常ポーラーではなくランチャー側に
起因します。頻度が不適切な cron 設定、停止したサービス、またはスリープ状態になっていたホストなどが原因です。

これらの処理ルートは管理者通知ヘルパーを呼び出します。通知が届くかどうかは、設定された受信者、通知制御、
およびメール転送機構が機能しているかに依存します。ログに警告が記録されたからといって、メールが確実に届いたことの
証明にはなりません。[メール通知](/ja/guides/send-email-notifications/)を参照してください。

制限超過ではない第4のケースも存在します。ポーラーが想定より早いタイミングで再起動された場合、実行頻度が高すぎる
設定になっているとログに記録し、収集を行わずに終了します。`--force` オプションはこの時間チェックをバイパスします。
スケジュールされた起動や他の手動起動を停止させた制御下の診断時にのみ使用してください。このオプションは処理能力を
増強するものではなく、重複した収集を安全にするわけでもありません。

## 統計情報行

完了したすべての実行は、ログに統計情報を1行書き込みます。そこには経過時間、収集方式、プロセス数および
スレッド数、デバイス数、プロセスあたりのデバイス数、データソース数、処理された RRD ファイル数が含まれます。

経過時間、テールレイテンシ、キューの深さ、更新失敗の推移を監視してください。許容時間ぎりぎりの実行が
単発であってもデータの欠落を招いている場合は調査が必要です。継続的な増大傾向は、処理能力や収集動作を
見直すべき時期を特定する手がかりとなります。

## プロセスとスレッド

これらは異なる役割を担う2つの調整軸です。

| 調整軸 | 分割される作業単位 | 使用するコレクター |
|---|---|---|
| プロセス | デバイス（連続したデバイス ID の範囲に分割） | 両方 |
| スレッド | 単一デバイス内の各項目 | Spine のみ |

その結果、多くの運用者が陥りがちな落とし穴が生じます。すなわち、**プロセスにはデバイス全体が割り当てられる**
ということです。5,000個のデータソースを持つ1台のデバイスを複数のプロセスに分散させることはできません。
そのデバイスは1つのプロセスに割り当てられ、そのプロセスは完了に必要なだけの時間をすべて消費します。
プロセス数を増やしても、そのデバイスの処理時間は一切短縮されません。

両方の設定値はグローバルではなく、データコレクターごとに保持されます。設定ページの数値は、新しい
データコレクターを作成する際に適用されるプリセット値です。プリセットを変更しても、既存のコレクターの設定は変更されません。

また、デバイスごとのスレッド数設定も存在し、これによって単一の大規模デバイスが細分化されます。
この設定は C コレクターにのみ適用されます。

Balance Process Load は、累積アイテム数を利用してデバイス ID 順にデバイス全体の境界を決定します。
単一のデバイスを分割したりアイテム数を厳密に均等化したりするわけではなく、またアイテム数は実行時間と
一致しません。分離された代表的なワークロード環境で、有効化前後のプロセスごとの所要時間を比較検証してください。

## PHP コレクターと C コレクターの比較

PHP コレクターである `cmd.php` はアプリケーションに標準同梱されています。Kadupul では Spine のフォークを
保守する計画がありますが、そのソースの場所や検証済みビルドはまだ文書化されていません。十分な検証結果が得られる
までは PHP を使用してください。以下の Spine の比較、スレッド設定、およびコマンドは継承された仕様を説明するものであり、
利用可能またはサポートされている Kadupul の本番構成を示すものではありません。

| | PHP コレクター | Spine |
|---|---|---|
| 並列化 | プロセスのみ | プロセスおよびスレッド |
| スレッド設定 | 設定にかかわらず強制的に 1 | 設定を反映 |
| スクリプトサーバー | プロセスごとに1つ（変更不可） | プロセスごとに1〜15（設定可能） |
| スクリプトタイムアウト | 適用されない | 適用される（デフォルト25秒） |
| インストール | コードに標準同梱 | フォーク計画中（検証済みビルドの文書化なし） |

強制的なスレッド数の制限については明確にしておく必要があります。コレクターが PHP に設定されている場合、
ランタイムのスレッド変数は強制的に 1 に設定されます。ただし、これにより保存されているコレクターのスレッド設定値が
書き換えられるわけではありません。PHP コレクターをスケールさせるにはプロセス数を増やす必要がありますが、
ソースコード内のガイダンスでは、CPU コア数の2倍以下にとどめることが推奨されています。

Spine の設定とコマンドの動作は、評価対象となる実際のバイナリと照合して検証する必要があります。PHP アプリケーションの
ソースコード単体からでは、設定の探索順序、スレッドの挙動、または副作用を確定することはできません。

分離された Spine 評価用の継承されたコマンド例（検証済みの Kadupul コマンドではありません）：

```sh
spine --first=42 --last=42 --threads=1 --verbosity=HIGH --stdout
spine --hostlist='42,43,51' --readonly
```

`--readonly` は結果の書き込みを抑止することを目的としています。ただし、デバイスへの接続や収集スクリプトの
実行は依然として行われます。まずは分離されたテスト環境でその副作用を検証してください。

## データベース接続

スレッドは無償のリソースではありません。Spine の各スレッドはそれぞれ独自のデータベース接続を保持し、
各スクリプトサーバーも同様に接続を消費します。

```
estimated worker connections = processes * (threads + script_servers)
```

これはアプリケーションの設定ヘルプに記載されている推計式であり、測定された上限値ではありません。
すべてのコレクターでこの値を合算し、ポーラーの親プロセス、Web リクエスト、メンテナンス処理、その他の
クライアント用の余力を加算してください。データベースの接続上限を決定する前に、実際のピーク接続数と
拒否された接続数を測定してください。上限を引き上げることはシステムリソースの消費増にもつながります。

接続が枯渇すると測定値の欠落が発生する可能性がありますが、ローテーションするように発生するデータ欠落は
一意の診断基準にはなりません。データベースの接続メトリクスとアプリケーションのエラーログを照合して確認してください。

## 遅延 RRD 書き込み

ポーラーが毎回のパスで RRD ファイルに直接書き込むのを停止するモードが存在します。収集結果はまずデータベースの
テーブルに蓄積され、タイマー起動時またはグラフ描画時にファイルが要求されたタイミングでまとめてフラッシュされます。
これにより、多数の細かな書き込みが少数の大きな一括書き込みへと置き換えられます。

運用上極めて重要な2つの事実があります。

- リモートデータコレクターを使用している場合、このモードは必須となります。これは単なる推奨事項ではなく、
  ソフトウェアが要求する前提条件です。
- バッファテーブルはメモリ上ではなく永続化されているため、未フラッシュの測定データも再起動を生き残ります。
  これは同時に、RRD ファイルの更新状況がデータベースよりも遅れることを意味します。スナップショットを取得する前に、
  [バックアップと復元](/ja/guides/back-up-and-restore/)を確認してください。

本リビジョンでは、処理中の主キューである `poller_output` も InnoDB を使用します。ストレージの事前チェックでは
MEMORY キューは拒否されます。ヒープテーブルの上限を引き上げてもこの拒否は解消されません。データ生成プロセスを停止し、
整合性のあるバックアップを保持した状態で、継承された不適切なキューを明示的に変換し、各サービスアカウントでストレージを確認してください。

```sh
php cli/upgrade_database.php --migrate-poller-queue
php cli/upgrade_database.php --check-rrd-storage
```

これらは独立した操作です。未処理の行を保持し、行数だけでなくデータベースのディスク容量とキューの滞留時間を監視してください。
キューの選択、サービスアカウントの信頼確認、および再起動の前提条件については、[安全なアップグレード](/ja/guides/upgrade-safely/)を参照してください。

## リモートコレクターへの移行時期

リモートデータコレクターとは、異なるコレクター ID で同じコードを実行し、一部のデバイスをポーリングして収集結果を
中央データベースに書き戻す別のサーバーマシンです。

ボトルネックが保存側ではなく収集側に存在する場合は、リモートコレクターへの移行を検討してください。

- ポーラーホストの CPU が実行中に飽和し、実行間隔の間はアイドル状態になっている場合。
- 特定のデバイス群への往復レイテンシが実行時間の大半を占めており、そのグループが単一のリンク先にある場合。
- 直接ポーリングを行いたくない遠隔地の WAN の先に対象サイトが存在する場合。
- 隔離された拠点での収集が必要であり、本格運用前にオフラインバッファリングと復旧動作を検証済みである場合。

リモートコレクターを導入しても、中央データベースや RRD の書き込み制限が緩和されるわけではありません。
収集スループットを引き上げる前に、中央側での取り込みおよびフラッシュの処理能力を測定してください。
収集プロセスを増やすと、既存のバックログをさらに悪化させる恐れがあります。

各コレクターは独自のプロセス数とスレッド数、独自のデータベース認証情報、および同期インターバル（デフォルトは2時間）
を保持します。待機せずに完全同期を強制実行するためのコマンドラインツールも提供されています。

中央のインストール環境から Web サイトやプラグインのコードをリモートコレクターに複製し、自律的に更新させることができます。
コードを別の方法でデプロイしている場合は、この複製機能をオフにすることが可能です。

## どの制限に達したか

以下の表を使用して仮説を立て、ログと測定値を用いて検証してください。複数の制限が同時に発生する場合もあります。
なお、Spine の各オプションはここでは未検証のままです。

| 観察された現象 | 原因となる制限 | 変更・対処すべき項目 |
|---|---|---|
| ランチャーの非同期警告が出るが、ポーラー自体は高速 | スケジュールの遅延、前回の超過、またはホストの中断 | 起動履歴とプロセス状態を調査 |
| 実行時間は一定だが、特定のデバイスが常に遅延 | 応答遅延、高負荷なスクリプト、または作業の集中 | 入力方式の所要時間を測定しタイムアウト/再試行を見直し |
| 実行時間がデバイス数に比例して増加し、CPU が飽和 | コレクターの CPU 負荷過多 | プロセス追加が有効か測定。コレクター配置の分散を検討 |
| 実行時間がデバイス数に比例して増加するが、CPU はアイドル | ネットワーク、スクリプト、または DB の待機 | 並行度を変更する前に待機の原因を測定 |
| 複数のデバイスでローテーションするようにサンプルが欠落 | 接続数不足、タイムアウト、その他の収集エラー | エラーログ、接続メトリクス、保持キューを確認 |
| 実行時間は良好だが RRD 書き込みが遅く、ディスクが高負荷 | ストレージの I/O 不足 | 遅延 RRD 書き込みの採用、またはディスクの高速化 |
| Web インターフェースを含め全体的に動作が重い | データベースの処理能力不足 | バッファプールのサイズ拡大、次いで DB サーバーの強化 |

注意すべき2つの落とし穴。

**基本インターバルの変更は、すべてのデータソースステップの変更と同義ではありません。**
プロファイル、キャッシュされたアイテムステップ、RRD の heartbeat/step 定義の整合性を確認してください。
キャッシュを再構築しても、既存の RRD ファイルの構造そのものが変更されるわけではありません。
[データの保持期間](/ja/guides/manage-data-retention/)および[時間とインターバル](/ja/concepts/time-and-intervals/)を参照してください。

**インターバルを短縮すると、あらゆる負荷が乗算されます。** 300秒から60秒に変更しても、1回あたりの作業量が5分の1に
減るわけではありません。短縮された頻度に合わせて設定されたソースはより頻繁に収集されます。長いステップを維持している
ソースは毎回の基本パスで実行される必要はありません。毎回のパスが均等な負荷であると思い込まず、結果として生じる負荷を実際に測定してください。
