:::caution[사용 전 검증]
소스를 사용할 수 있지만 지원되는 Kadupul 릴리스 또는 마이그레이션 경로는 아직 없습니다. 시스템에 의존하기 전에 백업이 포함된 격리된 사본에서 이 절차를 테스트하세요. [프로젝트 상태](/ko/project/status/)를 참조하세요.
:::

완전한 Kadupul 복구 세트에는 세 가지 부분이 있습니다. 부분 백업으로 구성이나 측정값을 복구할 수는 있지만 전체 설치 환경을 재현할 수는 없습니다.

| 구성 요소 | 보관 내용 | 위치 |
|---|---|---|
| 데이터베이스 | 장치, 템플릿, 사용자, 권한, 폴러 캐시 및 모든 RRD 파일의 경로 | MySQL 또는 MariaDB |
| RRD 파일 | 보존된 측정값 및 통합 아카이브 | RRA 디렉터리(기본값은 설치 경로 하위의 `rra/`) |
| 구성 | 데이터베이스 자격 증명, 경로, 수집기 구성, 플러그인 및 스크립트 코드 | `include/config.php`, spine 구성 파일, `plugins/`, `scripts/`, `resource/` |

## 데이터베이스 전용 백업으로 복구할 수 있는 항목

데이터베이스는 그래프 정의와 모니터링 구성을 보관하는 반면, RRD 파일은 과거 그래프 아카이브를 보관합니다. Boost가 활성화된 경우 최근 측정값이 파일로 플러시될 때까지 데이터베이스 큐에 머무를 수도 있습니다. 데이터베이스 백업의 일부로 이러한 큐를 보존하세요. [아키텍처](/ko/concepts/architecture/)를 참조하세요.

데이터베이스만 복원하면 수백 대의 장치를 인식하고 모든 그래프가 정의되어 있지만, 그중 어느 것에도 데이터가 그려지지 않는 빈 시스템이 됩니다. 폴러를 시작하는 순간부터 다시 수집하기 시작하지만 이전 이력은 모두 사라집니다.

## RRD 전용 백업에서 누락되는 항목

RRD 파일에는 명명된 데이터 소스, 아카이브 정의 및 값이 포함되어 있지만, 이러한 값을 애플리케이션에 다시 연결하는 데 필요한 완전한 Kadupul 장치, 쿼리, 그래프 및 권한 메타데이터는 포함되어 있지 않습니다.

"스위치 12의 포트 3으로 들어오는 바이트 수"에서 디스크 경로로의 매핑은 데이터 소스의 한 열로서 데이터베이스에 존재합니다. 파일 트리만 복원하면 숫자로 가득 찬 수천 개의 파일을 갖게 되며, 직접 수작업으로 역공학을 수행하지 않고서는 어느 파일이 무엇인지 알아낼 방법이 없습니다.

이 두 가지는 하나의 백업입니다. 그렇게 취급하세요.

## 두 요소 간의 정합성

이 부분에서 대부분의 백업 절차가 은연중에 잘못됩니다.

폴러는 지속적으로 RRD 파일에 데이터를 기록합니다. 업데이트가 진행 중일 때 복사된 파일은 작성 도중에 캡처될 수 있습니다. 동시에 데이터베이스에도 데이터가 기록되고 있습니다. 02:00에 데이터베이스를 덤프하고 02:20에 파일 복사를 시작하면 두 결과물은 서로 다른 시점을 나타내며, 그 사이에 생성되거나 삭제된 모든 데이터 소스에서 불일치가 발생합니다.

지연된 RRD 쓰기는 상황을 더 까다롭고 흥미롭게 만듭니다. 이 모드에서 폴러는 매 패스마다 RRD 파일을 쓰지 않습니다. 결과는 지속성 있는 데이터베이스 테이블에 누적된 후 나중에 대량으로 플러시됩니다. 따라서 데이터베이스는 플러시 간격만큼 RRD 파일보다 합법적으로 앞서 있을 수 있으며, 디스크의 다른 어느 곳에도 없는 실제 측정값을 보유하게 됩니다.

선호도가 높은 순서대로 다음 중 하나를 선택하세요.

**조율된 스냅샷.** 데이터베이스 엔진에서 지원하는 백업 또는 정지 절차를 사용하고, 이를 모든 RRD 스토리지 및 애플리케이션 구성의 스냅샷과 조율합니다. 파일시스템 스냅샷만으로는 별도의 볼륨, 원격 수집기, 대기 중인 큐 또는 활성 데이터베이스 전반의 정합성을 확보할 수 없습니다.

**정지된 논리적 백업.** 예약된 실행기와 기타 생성기를 비활성화하고, 이미 실행 중인 수집기가 완료될 때까지 기다린 다음 지연된 쓰기를 플러시하고 플러시 워커가 끝날 때까지 대기합니다. 캡처가 진행되는 동안 구성 변경, 유지보수 작업 및 기타 RRD 작성자가 중지된 상태를 유지하세요. 수집 일시 중지로 인해 누락된 샘플이 발생할 수 있으며, 그 영향은 하트비트 및 통합 설정에 따라 다릅니다.

예제를 실행하기 전에 이러한 정지 단계를 완료하고 큐 및 워커 상태를 확인하세요. `poller_boost.php --force` 명령이 0을 반환했다는 사실만으로는 플러시가 완전히 완료되었다는 증거가 되지 않습니다. 이미 등록된 Boost 프로세스가 있으면 실제 작업을 수행하지 않고 종료될 수 있습니다. rrdcached 서비스나 원격 스토리지가 있다면 별도로 조율하세요.

이 Bash 예제는 로컬 스토리지, 비공개 클라이언트 옵션 파일에 구성된 데이터베이스 계정, 관리되는 모든 RRD가 포함된 RRA 디렉터리를 가정합니다. 모든 경로를 사용자 환경에 맞게 바꾸세요. 사용자 정의 절대 RRD 경로, 심볼릭 링크 대상, 외부 구성 및 원격 수집기 목록을 작성하여 별도로 캡처하세요.

```bash
set -euo pipefail
umask 077

APP=/path/to/kadupul
RRA=/path/to/kadupul/rra             # use the actual configured storage path
DEST=/var/backups/kadupul            # outside the served tree
MYSQL_CNF=/secure/path/backup-client.cnf
DB=$(php -r 'require $argv[1]; echo $database_default;' "$APP/include/config.php")
STAMP=$(date -u +%Y%m%dT%H%M%SZ)

install -d -m 0700 "$DEST"
STAGE=$(mktemp -d "$DEST/.partial-XXXXXXXX")
FINAL="$DEST/backup-$STAMP-${STAGE##*partial-}"

# All writers must already be stopped and deferred queues handled.
mysqldump --defaults-extra-file="$MYSQL_CNF" \
  --single-transaction --routines --events --triggers "$DB" > "$STAGE/db.sql"
tar -C "$RRA" -cf "$STAGE/rrd.tar" .
tar --exclude='./rra' --exclude='./log' --exclude='./cache' --exclude='./.git' \
  -C "$APP" -cf "$STAGE/application.tar" .

( cd "$STAGE"
  sha256sum db.sql rrd.tar application.tar > SHA256SUMS
  sha256sum --check SHA256SUMS )
test ! -e "$FINAL"
mv "$STAGE" "$FINAL"
```

애플리케이션 아카이브에는 구성과 일치하는 코드가 포함됩니다. 백업 세트와 함께 소스 리비전, 데이터베이스 및 RRDtool 버전, 실제 스토리지 경로 및 작성자 종료/플러시 상태를 기록하세요. 이 예제는 일반 로그, 캐시 및 Git 메타데이터를 제외하므로 해당 설치 환경에 맞게 이러한 제외 항목을 검토하세요.

성공적으로 캡처되고 체크섬이 확인된 세트만 최종 디렉터리 이름을 받습니다. 명령이 실패하더라도 `.partial-*` 내부에 잘린 파일이 남을 수 있습니다. `set -e`는 후속 명령을 중단하지만 이미 생성된 출력을 제거하지는 않습니다. 해당 디렉터리를 완료된 백업으로 승격하지 마세요. 체크섬은 사후 변경 사항을 감지할 뿐 논리적 완전성을 보장하지 않으므로 복원 테스트가 여전히 필요합니다.

`--single-transaction` 옵션은 트랜잭션 테이블을 다루며, 비트랜잭션 플러그인 테이블이나 동시 스키마 변경에 대한 일관된 스냅샷을 제공하지는 않습니다. 작성자와 스키마 변경을 중지된 상태로 유지하거나 엔진에 적합한 백업 방식을 사용하세요. 캡처가 완료되고 스토리지를 사용할 수 있음을 확인한 후에만 수집을 재개하세요. 트랜잭션 및 권한 요구 사항은 [mysqldump 문서](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)를 참조하세요. 초기 레시피의 누락 사항은 [website #12](https://github.com/kadupulhq/website/issues/12)에서 추적됩니다.

**시차를 인정하고 기록하세요.** 어느 쪽을 먼저 캡처하든 먼저 캡처한 쪽이 더 오래된 데이터가 되며, 어느 순서로 진행하더라도 라이브 상태의 쌍이 자체적으로 일치하게 되지는 않습니다. 시간 간격을 기록해 두세요. 그래야 결과를 복구할 수 있습니다.

데이터베이스를 먼저 덤프하고 파일을 나중에 복사하면 파일이 더 최신 상태가 됩니다. 해당 시간 간격 내에 삭제된 데이터 소스는 덤프에는 남아 있지만 파일은 사라져 폴러가 다시 생성할 참조가 남게 됩니다. 해당 시간 간격 내에 생성된 데이터 소스는 데이터베이스가 인식하지 못하는 파일로 존재하게 되어 작동하지 않습니다.

파일을 먼저 복사하고 데이터베이스를 나중에 덤프하면 데이터베이스가 더 최신 상태가 됩니다. 시간 간격 내에 생성된 데이터 소스는 덤프에 포함되지만 연결된 파일이 없으므로 폴러가 빈 상태로 다시 생성합니다.

어느 순서로 하든 필요한 파일이 복사되기 전에 삭제되면 이전 이력이 유실될 수 있습니다. 부분적으로 기록된 파일이나 일관되지 않은 큐 샘플이 캡처될 수도 있습니다. 시차를 기록하는 것은 한계를 문서화하는 것일 뿐 일치하지 않는 쌍을 완전하게 만들거나 복구 가능성을 보장하지는 않습니다.

## 백업에 포함되어 있지만 미처 생각하지 못한 내용

장치 자격 증명은 일반 텍스트 형태로 데이터베이스에 저장됩니다. 폴러 캐시에는 SNMP 커뮤니티 문자열과 SNMPv3 사용자 이름, 암호 및 패스프레이즈가 일반 열로 저장되는데, 수집기가 매 패스마다 이를 필요로 하기 때문입니다. 구성 파일에는 데이터베이스 암호가 포함되어 있습니다.

따라서 Kadupul 백업은 모니터링하는 모든 장치에 대한 자격 증명 저장소입니다. 유휴 상태에서 암호화하고, 읽을 수 있는 대상을 제한하며, 범용 파일 공유 공간에 푸시하지 마세요.

## 복원 순서

각 단계가 이전 단계에 의존하므로 순서가 중요합니다.

1. **구성을 먼저 복원하세요.** 데이터베이스 자격 증명과 RRA 경로가 없으면 다른 어떤 것도 확인할 수 없습니다. 다른 하드웨어로 복원하는 경우 나중이 아니라 지금 경로를 수정하세요.

2. **RRD 트리를 복원하세요.** 구성에 지정된 위치에 배치하세요. 소유권과 권한 모드를 확인하세요. 폴러는 폴러 사용자로 이러한 파일을 작성하고 웹 인터페이스는 웹 서버 사용자로 읽습니다. 내용은 보존하지만 소유권을 보존하지 않는 복원은 그래프는 문제없이 표시되지만 새로운 데이터는 전혀 수집하지 못하는 시스템을 만듭니다.

3. **데이터베이스를 복원하세요.** 덤프의 버전 테이블은 복원 대상 코드와 일치해야 합니다. 복원된 구성 요소를 함께 확인할 때까지 모든 실행기와 작성기를 비활성 상태로 유지하세요. 이전 릴리스의 덤프를 최신 코드에 복원하면 웹 인터페이스가 설치 프로그램으로 리디렉션되는데, 이는 올바른 동작이지만 복구 도중에 원하는 동작은 아닙니다. 먼저 일치하는 코드를 복원하세요.

4. **폴러 캐시를 다시 빌드하세요.** 캐시는 파생된 데이터이며 복원 직후는 캐시가 최신이 아닐 가능성이 가장 높은 상황입니다. 다시 빌드하는 데는 한 번의 실행만 필요하며 혼란스러운 여러 증상을 한 번에 해결할 수 있습니다.

5. **폴러를 시작한 다음 파일 하나를 확인하세요.** 첫 실행 후 RRD 파일의 최종 업데이트 시간이 이동하는지 확인하세요. 복원 시점까지는 그래프가 채워져 있다가 그 이후로 평평하게 유지된다면 수집 결과, 큐, 타임스탬프, 경로 및 권한을 점검하세요. 평평한 그래프 자체만으로는 원인을 파악할 수 없습니다.

## 주의해야 할 함정

**RRD 파일은 과거 시점의 업데이트를 거부합니다.** RRD 파일은 이미 보유하고 있는 타임스탬프 이전 또는 동일한 타임스탬프의 샘플을 허용하지 않습니다. 최신 데이터베이스에 대해 더 오래된 파일 세트를 복원한다고 해서 손실된 샘플이 자동으로 채워지지는 않습니다. 보존된 지연 큐나 다른 소스에 복구 가능한 측정값이 포함되어 있을 수 있지만, 이를 재생하려면 별도의 검증과 타임스탬프 순서 정렬이 필요합니다. 이러한 측정값이 없으면 수집은 공백을 둔 채 재개됩니다. 이것이 두 백업 간에 파일을 복사하여 병합할 수 없는 이유이기도 합니다.

**경로를 다시 작성하기 전에 저장된 경로가 토큰화되어 있는지 확인하세요.** 생성된 데이터 소스는 경로를 `<path_rra>/name.rrd` 형식으로 저장하며, 이 토큰은 읽기 시점에 RRD 경로 설정에서 확장됩니다. 이러한 데이터 소스의 경우 설치 위치를 옮기는 것은 설정을 변경하고 폴러 캐시를 다시 빌드하는 것을 의미하며 테이블의 행을 다시 작성하는 것이 아닙니다. 직접 수동으로 입력한 경로는 리터럴 형식으로 저장되므로 다시 작성해야 합니다. 전체 테이블에 걸쳐 업데이트를 실행하기 전에 확인하세요. 토큰화된 경로를 절대 경로로 다시 작성하면 다음 마이그레이션이 훨씬 더 어려워지기 때문입니다.

**원격 수집기에는 자체 구성 파일이 있습니다.** 각 원격 수집기는 자체 데이터베이스 자격 증명과 수집기 ID를 보유합니다. 이는 중앙 데이터베이스 백업에 포함되지 않으므로 호스트별로 별도 캡처해야 합니다.

**플러그인 데이터는 동일한 데이터베이스에 있습니다.** 플러그인은 설치 시 자체 테이블을 생성하므로 전체 데이터베이스 덤프로 포함할 수 있습니다. 하지만 플러그인 코드는 데이터베이스에 없습니다. 일치하는 `plugins/` 디렉터리 없이 데이터베이스를 복원하면 설치 환경에서 찾을 수 없는 플러그인을 비활성화합니다.

**복원해보지 않은 백업은 가설에 불과합니다.** 정기적으로 임시 테스트 인스턴스에 복원해 보세요. 이 방법을 통해 가장 자주 발견되는 실패 유형은 데이터 손상이 아니라 애초에 세 가지 요소 중 하나만 캡처하고 있던 불완전한 백업입니다.
