:::caution[继承的 RRDtool proxy 行为]
Kadupul 不支持 RRDtool proxy 部署。请使用本地 RRDtool 存储（`storage_location = 0`）。
本页中关于 proxy 设置、协议说明和工作流程的描述仅属于继承行为记录，并非受支持的部署或迁移路径。
参见 [RRDtool proxy](/zh-cn/reference/rrdproxy/)。
:::

:::caution[使用前请先验证]
源代码已公开，但目前尚无受支持的 Kadupul 发行版或迁移路径。在依赖这些步骤
之前，请在带有备份的隔离副本上进行测试。参见[项目状态](/zh-cn/project/status/)。
:::

系统迁移本质上是将备份恢复到一台与原备份来源不同的新机器上。[备份与恢复](/zh-cn/guides/back-up-and-restore/)
中的所有准则在此均完全适用；本页专门阐述因目标环境与源环境差异而引发的特殊考量。

主要涉及三个方面的环境差异，且各自伴随特定的失效模式。

| 环境差异 | 会引发的问题 |
|---|---|
| 文件路径不同 | 破坏存储在数据库和轮询器缓存中的文件路径引用 |
| 用户与用户组 ID 不同 | 文件读取权限及存储信任检查可能直接失败 |
| 运行时软件版本不同 | 扩展功能、数据库底层行为以及 RRD 兼容性可能出现分歧 |

## 在动手调整任何配置之前

首先搭建好目标服务器，并使其达到能够正常进行全新安装的状态：数据库服务正在运行、已安装所需的 PHP 扩展、
已安装 RRDtool、选定的采集器可正常调用、且 Web 服务器已配置就绪。此时请保持其轮询器、计划任务、远程复制
以及对外通知功能处于禁用状态。切勿运行安装向导。因为后续会全盘替换数据库，而诊断一个半安装状态的数据库架构
远比排查一个完全空白的环境要棘手得多。

务必使应用程序的版本号与依赖项完全保持一致，包括本地代码修改和各类插件。数据库的 `version` 表仅记录
架构版本号，并不代表每一次源码细节的变动；仅核对该版本号是远远不够的。被重定向至安装向导通常意味着数据库架构
不匹配或数据恢复不完整。请先在目标机上安装与源环境完全一致的代码，完成迁移并验证功能正常后，再按照
[安全升级](/zh-cn/guides/upgrade-safely/)的步骤作为独立任务进行版本升级。

请在当下就确定安装目录路径。若能在两台机器上保持完全相同的绝对路径，将免去下文涉及的大部分繁琐操作。
若无法做到路径一致，在正式动手前请务必仔细阅读路径章节。

## 操作步骤顺序

每一步操作都会验证其前一步的执行结果，因此严禁打乱先后顺序。

1. **停止源端和目标端上的所有数据生成者。** 停止所有计划的、远程的、Web 触发的以及手动的采集与维护任务；让正在执行的轮询平稳结束。只有在所有生成者完全停止之后，方可执行延迟写入刷新。将队列中未确认的行与匹配的数据库及 RRD 备份完整保存下来；切勿使用 truncate 清空。
2. **执行数据备份。** 将数据库、RRD 目录树和配置文件整体捕获。[备份与恢复](/zh-cn/guides/back-up-and-restore/)中强调的数据一致性原则是这一步的重中之重。
3. **迁移 RRD 目录树。** 具体方法详见下文。
4. **迁移数据库。**
5. **迁移源码、配置文件以及配置文件所指向的所有资源。** 这包括 `plugins/`、`scripts/`、`resource/` 以及数据输入方法调用的任何本地脚本文件。
6. **在完成最终数据恢复后重新应用目标机专属配置。** 修正文件路径、数据库连接端点、服务所属权以及数值型的存储信任设置。
7. **重建轮询器缓存。**
8. **以各个服务账户的身份分别运行存储检查，确认无误后仅在目标机上开启采集。** 重点监测代表性监控文件和残留队列深度。

## 搬迁 RRD 目录树

RRD 文件属于二进制文件，其内部数据排布取决于其生成时的底层系统环境。二进制直接复制要求两端具有完全兼容的系统架构和 RRDtool 格式；
单纯依靠相同的操作系统名称或系统字长并不能保证兼容。架构不兼容将直接导致读取错误。请务必使用目标机上的 RRDtool 验证已复制的文件。

如果您无法百分之百确定两端环境完全兼容，请采用数据转换而非直接复制。RRDtool 官方提供的 dump 与 restore 命令能够生成跨平台的
文本中间格式；Kadupul 内部在重构归档文件时也采用同样的方法。

在源服务器上，确保写入进程已停止，并使用全新的私有临时暂存目录：

```sh
set -eu
umask 077
rrdtool dump /path/to/source/file.rrd > /private/staging/file.xml.partial
mv /private/staging/file.xml.partial /private/staging/file.xml
```

通过加密信道安全传输生成的 XML 文件。在目标服务器上将其恢复为测试候选文件：

```sh
set -eu
umask 077
rrdtool restore /private/staging/file.xml /private/staging/file.candidate.rrd
rrdtool info /private/staging/file.candidate.rrd
```

对需要转换的每个文件重复此操作，并严密检查每条命令的退出状态。绝不要导入残缺的转储文件或未经验证的候选文件。
RRDtool 官方手册已明确将 XML 定义为[跨架构迁移的标准格式](https://oss.oetiker.ch/rrdtool/doc/rrddump.en.html)。

在全面投入这种耗时较长的转换方案前，请务必进行小规模试错验证。先复制单个文件，在目标机上对其执行 `rrdtool info`，
比对 step 步长、归档结构、最后更新时间以及数据源名称。同时，针对已知有数据的历史区间比对 `fetch` 查询输出。
在迁移整个目录树之前，针对代表性的归档布局重复上述测试，最后核对完整的文件清单。参见
[损坏 RRD 的恢复](/zh-cn/guides/recover-a-corrupted-rrd/)了解候选文件验证与归属权限规范。

无论采用何种传输方式，都必须原汁原味地保留原有目录层级结构。RRA 目录下的嵌套子目录绝不是随意组织的装饰；
每个文件的相对路径都是按数据源严格记录在库的，打平目录层级将导致所有数据源关联彻底损毁。

## 数据库迁移

标准的转储与导入流程。但在目标端有两个细节必须重点核查。

检查恢复后的数据表字符集、排序规则（collation）以及存储引擎，切勿只看数据库服务器的全局默认值。在正式切换前，
保留源端的所有表定义，并确认其与目标端数据库版本的兼容性。

**采集器队列绝不是可随时丢弃的临时缓存。** 当前版本的 `poller_output` 队列必须使用 InnoDB 引擎。存储预检会直接拒绝
MEMORY 队列。在采样数据确认落地之前，必须完整保留该表中的数据行以及 boost 和 realtime 队列；因为 RRD 备份中很可能
尚未涵盖这些最新数据。切勿认定恢复后的 MEMORY 表一定是空的：逻辑转储文件中可能包含重新填充该表的 insert 语句。

在数据写入已暂停且备份妥善留存的情况下，可以显式转换继承的非 InnoDB 队列：

```sh
php cli/upgrade_database.php --migrate-poller-queue
php cli/upgrade_database.php --check-rrd-storage
```

请分别以真实的 Web 用户和轮询器运行用户的身份执行存储检查。该命令会校验本地存储访问权限和选定的队列类型；仅在 root
身份下成功并不能证明后台服务也能顺利访问。正常在线的远程采集器通常以主队列为目标；只有在刻意调试本地队列时才使用 `--local`
参数。系统中的其他运行时缓存表也应当制定清晰的保留或重建计划。参见[存储与运行环境要求](/zh-cn/reference/requirements/)。

## 目标端路径调整

这是数据迁移中最容易出现纰漏的地方，因为大多数路径错误在首次采集运行之前都是完全静默且不可见的。

**RRA 路径。** 标准数据源路径使用 `<path_rra>` 占位符。在此版本中，启动引导逻辑通过应用程序目录追加 `/rra` 来推导
`$config['rra_path']`；它并不是一个允许随意指定本地路径的常规数据库设置项。在搬迁文件前，请核实该推导路径。
手动指定的自定义绝对路径必须逐一排查并手工修正。请完整保留多层嵌套的子目录结构。

**轮询器缓存中保存的是绝对路径。** 当轮询器缓存生成时，占位符会被展开，并将完整的绝对路径直接固化在缓存行中。
如果您更改了 RRA 存储目录，缓存行依然会固执地指向旧路径。轮询器会照常运转，但却不会在任何你能找到的地方留下数据。
请立即重建缓存：

```sh
php cli/rebuild_poller_cache.php
```

**数据库中保存的系统路径设置。** 这些配置项保存在数据库中，因此导入后它们全都指向原机器的系统目录布局。在首次运行前，
必须逐一审计：RRDtool 可执行程序路径、采集器二进制文件及其配置文件路径、PHP 解释器路径、SNMP 工具集路径、日志文件路径、
默认字体文件路径以及尖峰消除备份目录。同时，检查配置文件、系统服务单元文件、计划任务配置以及 Web 服务器中的路径和环境变量。

**数据输入方法中包含的命令行。** 它们使用占位符来代表安装根目录，因此如果新机器的安装路径与原先完全相同，则无需调整。
若安装路径发生了改变，则必须逐个核对这些命令定义。这一规则同样适用于数据查询底层的各类 resource XML 模板文件。

**远程采集器拥有独立的本地配置文件**，保存着各自的数据库凭据和采集器 ID。这些内容并不包含在中心库的转储文件中。
如果中心数据库的连接地址变动了，需要同步修改各个采集器的配置并测试连接连通性。完整的数据复制属于独立操作，
仅在系统中配置并启用了远程采集器时，才需要在主采集器上触发：

```sh
php cli/poller_replicate.php
```

在没有启用任何远程采集器的情况下执行该命令会直接报错退出。切勿将其列入单采集器单机迁移的必要成功校验步骤中。
在允许远程采集恢复前，务必先验证远程配置与数据复制链路。

## 所属权与文件权限

轮询器以运行它的系统账户身份写入 RRD 文件。Web 界面则以 Web 服务器账户身份读取这些文件。如果在 `/etc/passwd`
用户配置不同的两台机器之间直接复制文件，原样保留的数字用户 ID 将直接导致文件归属于完全错误的系统账户。

迁移后监控图表突然停止更新，可能是权限问题、路径失效、未触发采集、时间戳混乱或采样数据被拒所致。在实施修复前，
请仔细查阅轮询器日志和暂存队列；仅看图表断裂并不能准确定位问题根源。

除了检查抽样文件外，务必重点检查 RRA 根目录本身及其各个嵌套子目录的所属权。采集过程中会在这些目录中创建新的文件，
因此一个轮询器没有写入权限的目录，将直接导致迁移之后新添加的数据源采集失败，即便现有的历史文件读取正常也无济于事。
在 `include/config.php` 中将 `rrd_maintenance_trusted_uids` 和 `rrd_maintenance_trusted_gids` 重新映射到目标系统
真实的数字用户 ID，并核验受信任目录的父级链条。参见[存储与运行环境要求](/zh-cn/reference/requirements/)。

## 最小化数据丢失的割接流程

RRD 文件会断然拒绝任何时间戳早于或等于其最后更新时间的写入请求。这一机制给数据重放带来了硬性约束；但并不意味着每次迁移
都必然丢失采样。数据断层的时间跨度取决于采样周期、停机时长以及有多少队列中的暂存数据被完整保留。本方案采用单一采集权归属原则，
严禁将测试演练期间独立采集的数据混入最终的归档库中。

1. 提前一天使用当时的最新备份进行全流程沙盒演练。完整复制所有数据，校正每一处路径，并在禁用对外通知的前提下，针对隔离的测试设备进行更新测试。将目标环境所需的各项调整记录为可复现的标准操作文档。测试完成后立即停止演练环境的写入进程。
2. 保持演练环境绝对隔离。用最终割接时捕获的最新匹配备份彻底替换演练使用的数据库和 RRD 文件；绝不要将演练期间产生的数据行或队列混入正式恢复中。
3. 割接实施阶段：停止源环境的数据生成者，将未落地的采样彻底刷新或妥善暂存，随后捕获并传输最终的备份集。重新应用目标机专属配置：导入数据库会重新将源端旧路径写回 `settings` 表，覆盖配置文件也可能冲掉演练时配置的专用端点与信任参数。
4. 重建轮询器缓存，执行存储合规检查，核验完整的文件清单，唯有在上述所有检查均顺利通过之后，方可在目标机上正式开启数据采集。

评估沙盒演练的整体耗时，并为数据校验与潜在的回滚预留出充裕的时间窗口。在确认割接成功之前，必须保持源服务器处于停止状态；
若发生不可控故障，则可通过既定回滚方案重新将其指定为数据采集的唯一责任节点。

## 验证执行顺序

1. Web 界面能够正常打开，且绝不应出现跳转至安装向导的情况。若发生重定向，请重点排查源码与数据库版本不匹配、数据库连通性故障或数据恢复不完整。
2. 测试设备能够正常响应新一轮的数据采集；从备份恢复出来的 “up” 状态可能仅仅是停机前的静态假象。
3. 首轮采集完成后，RRD 文件的磁盘最后修改时间应当向前推进。请直接检查磁盘上的文件属性，而不是仅看图表刷新。
4. 渲染过去一小时的监控图表，应呈现为一条连贯的数据线条，而非空白断层。

如果第 3 步失败，请全面排查文件路径、系统权限、存储预检状态、队列深度以及 RRDtool 报错。如果第 4 步失败，请检查数据库中的
暂存数据、图表定义、选定的时间跨度以及 Web 服务账户的读取权限。单个文件的成功写入并不等同于所有设备、数据输入方法或远程采集器都处于正常状态。

## 常见陷阱

**严禁两台服务器同时对同一个 RRD 目录树进行并发写入。** 两个轮询器向同一套文件写入只会导致更新被拒和图表断层，绝不会合并数据。

**严禁将旧的 RRD 目录树恢复到较新的数据库之上。** RRD 文件无法进行历史追溯填充。采集只能从当前时刻恢复，两者之间的时间差
将变成永久性的数据断洞。

**备份数据中包含了明文的设备连接凭据。** 硬件迁移意味着这些高度敏感的凭据需要通过网络进行传输并同时留存于两台机器上。
严格限制备份文件的访问权限，并对传输通道全程加密。在业务验收完毕且符合数据保留政策允许销毁之前，妥善保管回滚备份；在割接期间切勿随意删除。

**插件的数据表存放在数据库中，但插件代码本身不在其中。** 如果在没有同步部署配套插件代码及其依赖项的情况下直接恢复数据库，
会导致插件页面报错、钩子（hook）中断或计划任务溃败。请逐一核验所有必需的插件代码。

**现存的 proxy 存储架构不在本迁移流程的支持范围内。** 系统不支持 proxy 模式部署。请定位并备份真实的底层 RRD 文件，然后在隔离环境中
单独验证向本地存储的迁移转换。本地残存的 `rra/` 目录中可能只是一些陈旧的历史废弃文件。

**原机器的下线退役应安排在最后一步，且绝不要安排在割接当天。** 保持原机器处于关机状态或全面禁用其所有采集任务，妥善保留其完整匹配的
系统备份，直到新系统的采集、绘图、远程同步及插件均经过充分的时间检验。根据实际业务负载与回滚要求合理设定观察周期；仅完成最短的一个
归档周期并不能证明所有子系统都在健康运转。
