자동화는 혼동하기 쉬운 두 개의 독립적인 메커니즘으로 구성됩니다. 검색(Discovery)은 주소 범위를 탐색하여 장치가 무엇인지 확인합니다. 규칙(Rules)은 장치가 존재하게 되면 해당 장치에 대해 무엇을 생성할지 결정합니다. 둘 중 하나만 실행할 수도 있지만, 자동화로 인해 발생하는 대부분의 문제는 두 가지를 한 번에 켜고 사후에 문제를 파악하는 데서 비롯됩니다.

## 범위 정의

네트워크 범위는 쉼표로 구분된 목록입니다. 각 항목은 다음 세 가지 형식 중 하나입니다.

| 형식 | 예시 | 참고 |
|---|---|---|
| CIDR | `192.168.1.0/24` | 점으로 구분된 마스크 `192.168.1.0/255.255.255.0`도 허용 |
| 와일드카드 | `192.168.*.*` | 내부적으로 동등한 CIDR로 변환됨 |
| 단일 주소 | `192.168.1.10` | 해당 주소만 정확히 스캔 |

`192.168.1.10-192.168.1.50`과 같이 작성된 시작-종료 범위는 오류와 함께 거부됩니다. 이는 지원되지 않습니다.

동시에 실행될 수 있는 네트워크 전반을 포함하여 겹치지 않는 범위를 사용하십시오. 작업 테이블에는 IP 주소에 대한 전역 고유 키가 있습니다. 중복이 발생하면 전체 삽입 배치가 거부되어 해당 배치의 다른 주소가 누락될 수 있습니다. [이슈 #207](https://github.com/kadupulhq/kadupul/issues/207)을 참조하십시오.

모든 것은 IPv4입니다. 범위 계산은 전반적으로 32비트 정수 변환을 사용하므로 여기에는 IPv6 경로가 없습니다.

네트워크 주소와 브로드캐스트 주소는 제외됩니다. `/24`는 `.1`부터 `.254`까지 254개의 주소를 스캔합니다. 단일 주소 항목은 하나를 스캔합니다. 마지막 옥텟이 255인 주소도 스캔 중에 건너뜁니다.

스캔이 시작되기 전에 범위 내의 모든 주소가 주소당 한 행씩 작업 테이블에 기록되며 스레드가 여기에서 행을 가져옵니다. `/16`은 첫 번째 ping 전에 65534개의 행을 기록합니다. 이는 실제 비용이며, 응답이 전혀 없을 때도 대규모 희소 범위의 스캔이 느린 이유입니다.

각 범위에 SNMP 옵션 세트를 연결하십시오. 마스터 모드는 오류를 기록하고 SNMP 세트 ID가 0인 범위를 건너뜁니다. 타겟 실행에는 동일한 가드가 적용되지 않습니다. 이를 직접 시작한다고 해서 누락된 SNMP 옵션을 사용할 수 있게 되는 것은 아닙니다.

## 스캔 속도 조절

| 설정 | 기능 | 기본값 |
|---|---|---|
| 검색 스레드 | 주소를 가져오는 병렬 워커 | 1 |
| 실행 제한 | 검색이 이 시간이 지난 후 종료됨 | 20분 |
| 일정 유형 | 수동, 매일, 매주, 매월 또는 특정 요일 | 수동 |
| Ping 방식 | ICMP, TCP, TCP closed, UDP 또는 SNMP | 전역 설정에서 가져옴 |
| Ping 재시도, 제한 시간 | 주소당 실패 비용 | 전역 설정에서 가져옴 |

스레드와 실행 제한을 신중하게 고려하지 않으면 서로 나쁜 영향을 미칩니다. 침입 탐지 시스템의 관점에서 볼 때 `/16`에 대한 50개 스레드는 포트 스캔입니다. 동일한 범위에 대해 1개 스레드로 실행하면 실행 제한에 도달하여 중간에 종료되어 완전한 결과처럼 보이는 부분적인 결과가 남게 됩니다.

네트워크가 감당할 수 있는 스레드 수에서 스캔이 제한 시간 내에 완료되도록 범위 크기를 조정하십시오. 각각 고유한 일정과 고유한 제한을 갖기 때문에 하나의 큰 범위보다 여러 개의 작은 범위가 더 낫습니다.

## 주소별 스캔 수행 작업

1. 이름을 확인합니다. 대체 DNS 서버는 공백으로 구분된 목록으로 제공될 수 있습니다. 설정되지 않은 경우 폴러 자체의 확인자가 사용됩니다. DNS가 아무것도 반환하지 않는 경우 NetBIOS 조회가 선택적 대체 수단이 됩니다.
2. 주소나 해당 이름이 이미 장치인지 확인합니다. 장치인 경우 해당 주소는 완료된 것으로 표시됩니다. 이는 해당 값을 통해 발견된 기존 장치를 억제합니다. 이는 동시 생성이나 다른 별칭에 대한 보장이 아닙니다.
3. 구성된 방식을 사용하여 ping을 실행합니다. SNMP 방식은 별도의 ping을 건너뜁니다.
4. ping에 응답이 있거나 SNMP 방식이 선택된 경우 SNMP를 시도하고 `sysDescr`, `sysObjectID`, `sysName`, `sysLocation`, `sysContact` 및 가동 시간을 수집합니다.
5. 수집된 시스템 데이터를 장치 규칙과 일치시킵니다.

ping에는 응답하지만 SNMP에는 응답하지 않는 주소는 발견되어 활성 상태인 것으로 기록됩니다. SNMP에는 응답하지만 어떤 장치 규칙과도 일치하지 않는 주소는 시스템 데이터와 함께 발견된 것으로 기록되며 아무것도 생성되지 않습니다. 둘 다 발견된 장치 목록에 표시됩니다.

중복 억제는 기본적으로 활성화되어 있습니다. 이 네트워크의 저장된 검색 레코드에서 다른 주소에 이미 `sysName`이 표시되었거나 다른 호스트 이름을 가진 장치에 존재하는 경우 해당 주소는 건너뜁니다. 이는 여러 인터페이스가 주소 지정된 라우터에는 올바른 기본값이지만 별도의 NAT 주소 뒤에 있는 동일한 어플라이언스에는 잘못된 기본값이며, 동일한 sysName 옵션은 이를 끄기 위해 존재합니다.

기존 장치는 스캔 중에 데이터 쿼리를 다시 실행할 수 있습니다. 이는 기본적으로 꺼져 있으며 가동 중이거나 복구 중으로 기록된 장치에 적용됩니다. 검색은 이 결정을 위해 저장된 상태를 사용하며 기존 장치를 새로 검색하지 않습니다.

## 장치 규칙에 따른 템플릿 결정

장치 규칙은 시스템 데이터를 장치 템플릿에 매핑합니다. 각 규칙에는 `sysDescr`, `sysObjectID` 및 `sysName`에 대한 패턴이 포함됩니다. 일치 프로세서는 장치가 비어 있지 않은 상태로 반환한 각 시스템 필드를 필터링합니다. 빈 규칙 패턴은 모든 값과 일치합니다. 규칙은 순서대로 평가되며 첫 번째 일치가 적용됩니다.

단순 리터럴 하위 문자열을 사용하고 검색 결과에서 선택한 템플릿을 확인하십시오. 현재 SQL 일치 프로세서는 정규식 패턴을 리터럴 `/` 문자로 래핑하므로 데이터베이스의 정규식 연산자가 직접 일치하더라도 `^Linux.*fixture$`와 같은 앵커된 패턴은 실패합니다. 하위 문자열 대체는 이 경우를 복구하지 못합니다. [이슈 #206](https://github.com/kadupulhq/kadupul/issues/206)을 참조하십시오. SQL `LIKE`도 `%`와 `_`를 와일드카드로 처리합니다.

일치하지 않으면 장치가 생성되지 않습니다. 주소는 수집된 모든 시스템 데이터와 함께 발견된 장치 목록에 기록되며, 해당 목록은 누락된 규칙을 작성하는 위치입니다.

일반적인 규칙 위에 구체적인 규칙을 배치하십시오. 공급업체 규칙 위에 하위 문자열 `Linux`와 일치하는 규칙을 배치하면 설명에 Linux가 언급된 모든 어플라이언스를 가져오게 됩니다.

## 생성을 활성화하기 전에 검색 미리보기

새 범위의 장치 생성 스위치는 기본적으로 꺼져 있습니다. 초기 단계에서는 꺼진 상태로 두고 기존 장치의 데이터 쿼리를 다시 실행하는 옵션을 비활성화하십시오. 이 단계에서도 검색 레코드, 스캔 통계 및 로그가 업데이트되며 구성된 알림을 보낼 수 있습니다. 그래프나 트리 규칙 실행은 미리 보지 않습니다.

스캔을 실행한 다음 발견된 장치 목록을 확인합니다. 여기에는 기록된 검색 결과, 수집된 SNMP 데이터, 사용 가능한 경우 일치하는 템플릿이 표시됩니다. 기존 장치, 억제된 중복 항목 및 건너뛴 주소는 여기에 표시될 필요가 없습니다. 목록뿐만 아니라 주소별 디버그 출력도 검토하십시오.

일정을 기다리지 않고 명령줄에서 강제로 스캔을 실행합니다.

```bash
php poller_automation.php --network=3 --force --debug
```

디버그 플래그는 주소별 결정이 발생할 때 이를 실시간으로 출력합니다. 일정이 도래한 활성화된 범위를 시작하는 마스터 프로세스는 별도의 모드입니다.

```bash
php poller_automation.php -M
```

타겟 `--force` 명령은 비활성화된 네트워크도 실행합니다. 마스터 모드에 `--force`를 추가하면 일정 확인을 건너뛰고 비활성화된 네트워크도 시작할 수 있습니다. 단일 범위를 검증할 때는 타겟 양식을 사용하십시오.

생성을 켜기 전에 결과에서 세 가지 사항을 확인하십시오.

- 장치 수가 예상한 것과 일치합니다. 자산 목록보다 훨씬 높은 수는 일반적으로 범위가 생각보다 넓다는 것을 의미합니다.
- 선택한 템플릿이 올바릅니다. 모든 항목에 동일한 일반 템플릿 열이 표시되는 것은 규칙이 일치하지 않음을 의미합니다.
- 중요한 것이 누락되지 않았습니다. 누락된 장치의 경우 범위 확장, 워커 완료, 기존 장치 및 중복 억제, ping 정책, SNMP 결과를 확인하십시오. 목록에 없다는 사실만으로는 도달할 수 없다는 것을 입증하지 못합니다.

## 그래프 및 트리 규칙

장치가 존재하게 되면 그래프 규칙과 트리 규칙이 해당 장치에 무엇을 구축할지 결정합니다. 검색은 장치를 생성한 후 이 자동화를 호출할 수 있으며, CLI는 이를 기존 장치에 적용할 수 있습니다. 개별 그래프 및 트리 규칙이 활성화되어 있어야 합니다. 전역 그래프/트리 자동화 스위치는 특정 생성 후크를 제어하며 명시적인 CLI 자동화를 전면 금지하는 것이 아닙니다.

그래프 규칙은 적용 대상 장치, 적용 대상 데이터 쿼리 내 발견된 인덱스, 생성할 그래프 유형의 세 부분으로 구성됩니다. 두 일치 부분 모두 규칙 항목으로 구성되며, 규칙 항목은 괄호로 묶인 `AND` 또는 `OR`로 결합된 필드, 연산자 및 패턴입니다.

| 연산자 그룹 | 멤버 |
|---|---|
| 부분 문자열 | contains, does not contain, begins with, does not begin with, ends with, does not end with |
| 일치 | matches, is not equal to |
| 숫자 | is less than, less than or equal, greater than, greater than or equal |
| 존재 여부 | is unknown, is not unknown, is empty, is not empty |
| 패턴 | matches regular expression, does not match regular expression |

이것들은 SQL `WHERE` 절이 됩니다. 정규식 연산자는 PCRE가 아닌 데이터베이스의 정규식 방언이므로 `preg_match`에서 작동하는 패턴이 여기에서 반드시 작동하는 것은 아닙니다. 숫자 패턴에 대한 숫자 비교는 따옴표 없이 전달되며, 그 외 모든 항목은 따옴표로 묶이고 데이터베이스는 해당 유형 변환 규칙을 적용합니다. 실제로 캐시된 값에 대해 숫자 필터를 테스트하십시오. 이러한 값은 일반적으로 텍스트로 저장됩니다. 부분 문자열 연산자는 SQL `LIKE`를 사용하며, 여기서 `%`와 `_`는 와일드카드 의미를 갖습니다.

아무 작업도 수행하지 않는 규칙을 디버깅하기 전에 알아두어야 할 두 가지 동작이 있습니다.

**빈 장치/개체 필터는 아무것도 일치하지 않지만, 빈 인덱스 필터는 캐시된 모든 인덱스와 일치합니다.** 장치 선택 필터는 일치 항목이 없을 때 false 조건으로 돌아갑니다. 그러나 그래프 규칙이 장치와 일치하면 모든 그래프 인덱스 조건을 제거해도 데이터 쿼리가 필터링되지 않은 상태로 남습니다. 예를 들어 `ifDescr = eth0` 조건을 제거하면 `lo`에 대한 그래프도 생성될 수 있습니다. 인덱스 조건을 편집하는 동안에는 규칙을 비활성화하십시오.

**장치가 검색하지 않은 필드를 참조하는 규칙은 취소됩니다.** 규칙이 해당 장치의 캐시에 없는 데이터 쿼리 필드를 필터링하는 경우, 실행 시 해당 필드를 언급하는 경고가 기록되고 해당 장치에 대한 해당 규칙 처리가 중지됩니다. 일반적인 원인은 하나의 데이터 쿼리에 대해 작성된 규칙이 다른 필드 세트를 반환한 장치에서 평가되기 때문입니다.

규칙 편집 페이지에는 후보 개체와 그래프가 나열됩니다. 규칙을 활성화하기 전과 편집한 후에 해당 목록을 검토하십시오. 이는 선택 미리보기일 뿐 전체 실행 드라이런이 아닙니다. 데이터 소스 확인, 기존 그래프 감지, 생성 후크 및 트리 삽입은 실행 중에 여전히 발생합니다. CLI에는 드라이런 옵션이 없습니다.

트리 규칙에는 별도의 장치 및 그래프 리프 유형과 선택한 대상 트리 및 상위 항목이 있습니다. 헤더 단계에서는 고정 문자열이나 장치/그래프 필드의 값을 사용할 수 있습니다. 필드에서 파생된 헤더는 대소문자를 구분하지 않는 PHP 정규식 대체를 적용합니다. 결과의 리터럴 `\n` 시퀀스는 이를 연속적인 중첩 헤더로 분할합니다. 이 대체 구문은 개체 일치에 사용되는 SQL 정규식과 다릅니다. 기존 헤더와 리프는 동일한 트리 및 상위 항목에서 재사용됩니다. 경로를 변경하면 이전 배치를 제거하지 않고 다른 배치를 추가할 수 있습니다.

## 이미 존재하는 장치에 규칙 적용

검색만이 유일한 방법은 아닙니다. ID, 호스트 이름 또는 설명으로 선택하여 시스템에 이미 있는 장치에 대해 규칙을 실행할 수 있습니다.

```bash
php cli/apply_automation_rules.php --ids="12 13 14" --debug
php cli/apply_automation_rules.php --hostname="^edge-" --debug
php cli/apply_automation_rules.php --description="branch office"
```

호스트 이름과 설명은 값이 유효할 때 정규식으로 일치하며 항상 부분 문자열로도 일치합니다. 세 가지 중 적어도 하나는 필수입니다. 선택기 없이 호출하면 오류와 함께 종료됩니다. 선택기가 결합되면 `AND`로 연결됩니다. 좁은 선택을 위해 공백으로 구분된 양수 장치 ID를 사용하십시오. 쉼표로 구분된 ID는 지원되지 않습니다. 패턴은 여전히 광범위할 수 있으며 SQL `LIKE` 대체는 `%`와 `_`를 와일드카드로 처리합니다.

선택기 쿼리는 비활성화된 장치를 자동으로 제외하지 않습니다. `--debug`는 진단을 추가하지만 여전히 생성을 수행합니다. 일치하는 장치가 없으면 성공적인 no-op이므로 종료 상태만으로는 아무것도 생성되었음을 입증하지 못합니다.

일치하는 각 장치에 대해 실행은 순서대로 세 가지 작업을 수행합니다.

1. 템플릿 적격성 및 데이터 소스 검사에 따라 장치에 그래프가 없는 연결된 그래프 템플릿에 대한 생성을 시도합니다.
2. 저장된 인덱스 캐시를 사용하여 연결된 데이터 쿼리에 대해 활성화된 그래프 규칙을 실행합니다. 이 단계 자체는 검색을 다시 실행하지 않습니다. 캐시가 누락되었거나 오래된 경우 먼저 데이터 쿼리를 새로 고치십시오.
3. 활성화된 장치 리프 트리 규칙을 적용합니다.

전역 트리 자동화가 활성화된 경우 새 그래프 생성이 그래프 리프 트리 규칙을 호출할 수 있습니다. CLI는 이미 생성된 그래프에 해당 규칙을 다시 적용하지 않습니다. 따라서 새롭거나 변경된 그래프 리프 규칙은 CLI가 다시 실행된다고 해서 기존 그래프를 소급 적용하지 않습니다. [이슈 #211](https://github.com/kadupulhq/kadupul/issues/211)을 참조하십시오. 배치를 별도로 확인하십시오. 단순히 생성 후크를 트리거하기 위해 과거 그래프를 삭제하고 다시 생성하지 마십시오.

반복 실행은 장치 및 그래프 템플릿별로 기존의 인덱스되지 않은 그래프를 억제합니다. 인덱스된 그래프는 장치, 데이터 쿼리, 그래프 유형 및 인덱스별로 확인됩니다. 이는 순차적 실행에서 중복 생성을 방지합니다. 이것이 동시성 보장은 아닙니다. 실행 후 건너뛴 그래프, 유효하지 않은 데이터 또는 생성 실패에 대한 `AUTOM8` 로그 메시지와 함께 그래프 목록과 트리를 확인하십시오.

혼란스러울 정도로 조용히 건너뛰는 한 가지 사항이 있습니다. 재정의 가능으로 표시되었지만 기본값이 없는 필드가 있는 그래프 템플릿은 자동화 대상이 아닙니다. 실행 시 재정의 가능한 필드에 기본값이 없어서 추가되지 않았다고 기록하고 넘어갑니다. 예상한 템플릿이 표시되지 않는 경우 가장 먼저 확인해야 할 사항입니다. 재정의 가능한 필드가 무엇인지에 대해서는 [템플릿](/ko/concepts/templates/)을 참조하십시오.

## 주의 사항

**규칙을 비활성화해도 작업이 취소되지는 않습니다.** 이미 생성된 그래프나 트리 항목은 제거되지 않습니다. 장치 삭제에는 별도의 그래프 및 데이터 소스 정리 동작이 있습니다. 장치를 제거하기 전에 삭제 옵션을 검토하십시오.

**중단된 스캔은 정상적인 스캔처럼 보입니다.** 실행 제한은 검색이 어디까지 진행되었든 간에 검색을 종료합니다. 기록된 총계는 완료된 작업의 총계이며 결과가 부분적이라는 표시는 없습니다. 스캔된 주소 수를 범위 크기와 비교하십시오.

**규칙은 장치가 아닌 데이터 쿼리 캐시에 대해 실행됩니다.** 아무것도 일치하지 않는 그래프 규칙은 종종 데이터 쿼리가 실행되지 않았거나 실행되었지만 인덱스를 찾지 못했음을 의미합니다. 규칙을 다시 작성하기 전에 발견된 인덱스 테이블을 확인하십시오.

**알림 메일에는 기존 검색 결과와 새 검색 결과가 모두 포함됩니다.** 범위 스캔이 완료되면 메일을 보낼 수 있으며, 각 IP가 스캔 전 스냅샷에 나타났는지 여부에 따라 기록된 검색 결과를 그룹화합니다. 이것이 요청된 모든 주소가 스캔되었다는 증거는 아닙니다.

## 오류 모드

| 증상 | 일반적인 원인 |
|---|---|
| 호스트가 있는 범위에서 스캔이 아무것도 찾지 못함 | Ping 차단, SNMP 오류, 제외 또는 중복 억제 |
| 범위 스캔이 거부되고 로그에 오류가 표시됨 | SNMP 옵션 세트가 연결되지 않음 |
| 장치가 발견되었지만 아무것도 생성되지 않음 | 생성 스위치가 꺼져 있거나 장치 규칙이 일치하지 않음 |
| 모든 장치에 동일한 일반 템플릿이 지정됨 | 규칙 순서 문제로, 일반 규칙이 특정 규칙 위에 있음 |
| 일부 주소만 스캔됨 | 실행 제한에 도달했거나 겹치는 범위로 인해 주소 배치가 거부됨 |
| 인터페이스당 하나가 아닌 라우터당 하나의 장치가 생성되거나 그 반대 | 동일한 sysName 중복 억제 설정 |
| 규칙이 아무것도 일치하지 않고 로그에서 열에 대해 경고함 | 규칙이 이 장치의 데이터 쿼리에서 반환하지 않은 필드를 필터링함 |
| 규칙에 의해 그래프 템플릿이 생성되지 않음 | 필수 기본값 누락, 유효하지 않은 데이터 소스 출력 또는 생성 실패 |
| 추가 인터페이스에 대한 예기치 않은 그래프 | 그래프 인덱스 필터가 비어 있거나 의도한 것보다 넓음 |
| 새 트리 규칙이 기존 그래프를 배치하지 않음 | CLI는 기존 그래프에 대해 그래프 리프 규칙을 소급 적용하지 않음 |
