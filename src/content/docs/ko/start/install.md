:::caution[사용 전 검증]
소스를 사용할 수 있지만 지원되는 Kadupul 릴리스 또는 마이그레이션 경로는 아직 없습니다. 시스템에 의존하기 전에 백업이 포함된 격리된 사본에서 이 절차를 테스트하세요. [프로젝트 상태](/ko/project/status/)를 참조하세요.
:::

순서대로 한 번 진행하세요. 각 단계는 점검으로 끝납니다. 다음 단계로 넘어가기 전에 점검을 수행하세요. 여기에 나열된 모든 문제는 지금 발견하면 해결 비용이 적게 들지만, 폴러가 일주일 동안 실행된 후 발견하면 해결 비용이 많이 듭니다.

## 시작하기 전에 필요한 사항

Kadupul은 MySQL 또는 MariaDB에 구성을 저장하고 디스크의 RRD 파일에 측정값을 저장하는 PHP 애플리케이션입니다. 이 페이지는 업그레이드나 보관된 LTS 계열이 아닌 현재 `main` 소스 기반의 새로운 메인 서버 설치를 설명합니다. 실행하기 전에 네 가지 구성 요소가 준비되어 있어야 합니다.

| 구성 요소 | 필요한 이유 |
|---|---|
| 보안 지원이 제공되는 릴리스의 PHP 8.4 이상 | 웹 인터페이스 및 폴러를 실행합니다 |
| MySQL 또는 MariaDB | 장치, 템플릿, 사용자 및 폴러 캐시를 보관합니다 |
| RRDtool | 라운드 로빈 아카이브를 생성 및 업데이트하고 그래프를 렌더링합니다 |
| net-snmp | 장치를 쿼리하는 데 사용되는 클라이언트 도구 및 라이브러리를 제공합니다 |

PHP에는 `pdo_mysql`, `gd`, `sockets`, `gmp`, `intl`, `ldap`, `mbstring`, `pcntl`, `posix` 및 `sqlite3`을 포함하여 [애플리케이션 매니페스트](https://github.com/kadupulhq/kadupul/blob/main/composer.json)에 필요한 확장도 있어야 합니다. 명령줄 및 웹 런타임 모두에 대해 이를 설치하세요. [요구 사항](/ko/reference/requirements/) 문서에서 Composer 요구 사항과 설치 프로그램의 별도 검사를 구분하여 설명합니다.

## 1단계: 런타임 설치

배포판 패키지에서 확장을 포함한 PHP, 데이터베이스 서버, RRDtool 및 net-snmp를 설치하세요.

**점검하세요.**

```bash
php -v
php -m | sort
rrdtool --version
snmpget --version
```

`php -m` 명령은 필요한 확장을 나열해야 합니다. PHP `snmp` 확장은 net-snmp 명령줄 도구를 사용할 수 있는 경우 선택 사항입니다. Composer는 종속성 설치 중에 자체 필수 확장을 확인하며, 웹 설치 프로그램에는 별도의 확장 확인이 있습니다. 런타임 대체가 Composer 요구 사항을 없애지는 않습니다.

명령줄과 웹 서버의 PHP 구성은 다를 수 있습니다. 둘 다 확인하세요. 설치 프로그램은 `memory_limit`을 최소 400M, `max_execution_time`을 최소 60초로 권장하며, 무제한 값(`-1` 및 `0`)도 허용합니다. 이러한 권장 사항보다 낮은 값은 경고를 생성하지만, 누락된 `date.timezone`은 오류입니다. `UTC`와 같이 명시적인 시간대를 설정하고 `php --ini`를 사용하여 명령줄 구성을 확인하세요.

## 2단계: 데이터베이스 및 사용자 생성

비어 있는 데이터베이스 하나와 해당 데이터베이스에 대한 권한이 있는 사용자 하나를 만드세요. 로컬 데이터베이스의 경우 데이터베이스 관리자 권한으로 이 SQL을 실행하고, 사용하기 전에 예제 암호를 변경하세요.

```sql
CREATE DATABASE kadupul CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kadupul'@'localhost' IDENTIFIED BY 'replace-with-a-unique-password';
GRANT ALL PRIVILEGES ON kadupul.* TO 'kadupul'@'localhost';
```

PHP가 다른 시스템에서 연결하는 경우 일치하는 데이터베이스 계정 호스트를 사용하세요.

또한 데이터베이스 서버에는 시간대 테이블이 채워져 있어야 하며, Kadupul 사용자는 `mysql` 데이터베이스의 해당 테이블에 대한 읽기 권한이 필요합니다. 이는 자체 스키마 외부의 유일한 권한 부여입니다. 모니터링 시스템에서 이를 당연히 요구할 것이라고 생각하기 어렵지만 필수 사항이며, 이 설정이 없으면 아래 점검이 실패합니다.

```bash
# Populate the tables, then grant the one extra read the installer needs.
mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root -p mysql
mysql -u root -p -e "GRANT SELECT ON mysql.time_zone_name TO 'kadupul'@'localhost';"
```

**점검하세요.** Kadupul 데이터베이스 사용자로 로그인하고 다음을 실행하세요.

```sql
SELECT COUNT(*) FROM mysql.time_zone_name;
```

권한 오류 없이 0이 아닌 개수가 반환되어야 정상입니다. 0은 테이블이 로드되지 않았음을 의미하고, 오류는 사용자가 해당 테이블을 읽을 수 없음을 의미합니다. 둘 다 설치 프로그램을 중단시킵니다.

서버 자체 설정 중 4가지는 지금 수정해야 할 만큼 중요합니다.

| 설정 | 권장값 | 이유 |
|---|---|---|
| `max_allowed_packet` | 16M 이상 | 메인 서버와 원격 수집기 간의 대규모 동기화 |
| `character_set_server`, `collation_server` | `utf8mb4`, `utf8mb4_unicode_ci` | 장치 설명에 멀티바이트 문자가 포함됨 |
| `innodb_file_per_table` | On | 테이블스페이스를 독립적이고 관리하기 쉽게 유지 |
| `innodb_buffer_pool_size` | 시스템 메모리의 약 4분의 1 | 작업 세트를 메모리에 유지 |

설치 프로그램은 이러한 설정을 자체적으로 확인하고 부족한 항목을 표시하므로 이 표를 무조건 신뢰할 필요는 없습니다. 부하가 발생하면 [데이터베이스 성능 튜닝](/ko/guides/tune-database-performance/) 문서에서 더 자세한 내용을 다룹니다.

## 3단계: 압축 해제, 소유권 수정 및 서비스 제공

웹 서버가 제공할 수 있는 위치에 애플리케이션을 배치한 다음 어떤 시스템 사용자가 소유할지 결정하세요. 그 결정은 위치보다 더 중요합니다. 웹 서버와 폴러를 예약하는 프로세스, 이 두 프로세스가 여기에 씁니다. 둘 다 동일한 사용자로 실행하세요. 폴러는 비특권 사용자로 실행하고 두 프로세스에 필요한 접근 권한을 부여하세요. 잘못된 소유권이나 권한 모드는 그래프가 렌더링되더라도 이후의 업데이트를 방해할 수 있습니다.

### 릴리스 압축을 푸는 대신 저장소를 복제한 경우

Git 체크아웃에는 PHP 종속성과 생성된 브라우저 자산이 모두 필요합니다. 저장소의 `mise.toml` 런타임이 설치된 상태에서 저장소 루트로부터 다음을 실행하세요.

```bash
mise exec -- php "$(command -v composer)" install --no-dev --optimize-autoloader
mise exec -- npm ci --ignore-scripts
mise exec -- npm run build
mise exec -- php bin/console about
```

Composer는 `include/vendor/`를 채우고 고정된 호환성 파일을 복원합니다. npm 빌드는 `include/js/`, `include/fa/` 및 `include/vendor/flag-icons/` 아래에 자산을 생성합니다. 소스 설치에는 Composer만으로는 충분하지 않습니다.

종속성이 완비된 오프라인 번들은 별도의 빌드 아티팩트입니다. 일반적인 GitHub 소스 아카이브는 해당 번들이 아닙니다. 대상 호스트에 인터넷 접근이 불가능한 경우 [오프라인 빌드 및 검증 절차](https://github.com/kadupulhq/kadupul/blob/main/docs/symfony-migration.md#offline-installation)를 따르세요.

종속성을 설치한 후 쓰기 가능한 경로를 준비하세요.

| 그룹 | 디렉터리 | 쓰기 가능 시점 |
|---|---|---|
| 설치 중 | `resource/snmp_queries`, `resource/script_server`, `resource/script_queries`, `scripts` | 설치 또는 업그레이드 중에만 |
| 설치 중 | `include/vendor/csrf/` 또는 구성된 `path_csrf_secret` 위치 | 설치 프로그램은 설치 고유의 비밀값을 생성해야 하며, 이후 이를 보존해야 합니다 |
| 항상 | `log`, `cache/boost`, `cache/mibcache`, `cache/purifier`, `cache/realtime`, `cache/spikekill`, 시스템 임시 디렉터리 | 설치가 유지되는 전체 기간 동안 |
| Symfony 런타임 | `var/cache`, 파일 로깅이 구성된 경우 `var/log` | PHP 런타임 및 캐시 워밍 사용자를 위해 |

RRD 디렉터리 역시 설치 수명 내내 쓰기가 가능해야 합니다. 이 디렉터리는 이력을 보관하므로 데이터베이스 디렉터리처럼 주의 깊게 관리하세요.

현재 마이그레이션에는 기존 로그인, 설치 프로그램 및 플러그인 라우트가 여전히 필요합니다. 이 결합된 설치의 경우 비공개 디렉터리, 구성, 종속성 및 런타임 상태에 대한 접근을 거부하는 명시적 규칙을 사용하여 저장소 루트를 서비스하세요. 전체 설치를 `public/`으로 전환하지 마세요. 그렇게 하면 아직 사용 중인 기존 라우트가 제거됩니다. Symfony의 별도 엔드포인트는 다른 라우팅을 사용합니다. [마이그레이션 지침](https://github.com/kadupulhq/kadupul/blob/main/docs/symfony-migration.md)을 참조하세요.

Nginx의 경우 저장소의 [Nginx 위치 규칙](https://github.com/kadupulhq/kadupul/blob/main/tests/e2e/nginx.conf)에서 시작하여 루트와 PHP-FPM 업스트림을 조정하세요. 일반적인 PHP 처리 앞에 거부 규칙을 유지하고 `/app.php/...`에 대해 PATH_INFO를 보존하세요. Nginx는 `.htaccess`를 읽지 않습니다. HTTP를 통해 RRD 파일, 로그 및 비밀값에 접근할 수 없도록 유지하세요. 파일 권한이 제공을 막는다고 가정하지 말고 실제 서버 구성을 확인하세요.

**점검하세요.** 폴러 사용자로 전환하여 항상 쓰기 그룹 디렉터리마다 파일을 작성한 다음 삭제하세요. `ls -l`에서 올바르게 보이는 권한이라도 SELinux나 AppArmor에 의해 거부될 수 있으며, 파일을 직접 쓰는 것이 이를 확인하는 유일한 검사입니다. 그런 다음 HTTP를 통해 로그 디렉터리 아래의 파일을 요청하세요. 거부 응답이 와야 합니다.

## 4단계: 구성 파일 작성

새 설치의 경우 배포된 구성 파일을 복사하세요.

```bash
cp include/config.php.dist include/config.php
```

기존 설치의 구성을 덮어쓰지 마세요. 2단계의 데이터베이스 호스트, 이름, 사용자 및 암호를 설정하세요. 처음 설치할 때 중요한 두 가지 다른 값이 있습니다. 애플리케이션이 앞뒤 슬래시와 함께 제공되는 경로인 `url_path`와, 메인 서버에서는 `1`이고 원격 수집기에서만 다른 값인 `poller_id`입니다.

원격 수집기 블록은 주석 처리된 상태로 두세요. 아직 만들지 않았으며, 만들 때가 되면 [원격 데이터 수집](/ko/concepts/remote-data-collection/) 문서에서 다룹니다. 다른 모든 설정에는 작동하는 기본값이 있으므로 설정을 변경하기 전에 [구성](/ko/reference/configuration/) 문서를 읽어보세요.

이를 사용하는 Symfony 기능을 위해 PHP 프로세스 환경에 배포 고유의 `APP_SECRET`을 구성하세요. 부트스트랩은 기본적으로 `APP_ENV=prod` 및 `APP_DEBUG=0`으로 설정되며 `.env` 파일을 로드하지 않습니다. 이는 레거시 설치 프로그램의 CSRF 비밀값과는 별개입니다.

**점검하세요.** 자격 증명을 표시하지 않고 구문을 확인하세요.

```bash
php -l include/config.php
```

브라우저에서 설치 프로그램을 열기 전에 다음 단계에서 스키마를 가져오세요.

## 5단계: 스키마 가져오기

설치 프로그램은 테이블이 이미 존재할 것으로 예상합니다. 생성한 데이터베이스에 제공된 스키마를 로드하세요.

```bash
mysql -u kadupul -p kadupul < cacti.sql
```

비어 있는 데이터베이스에 대해 이 작업을 한 번 수행하세요. 이것은 업그레이드 스크립트가 아닙니다. 이미 데이터가 채워진 데이터베이스로 가져오면 실패하거나 충돌 및 불완전한 데이터가 남을 수 있습니다.

## 6단계: 설치 프로그램 실행

브라우저에서 사이트를 열고 진행하세요. 설치 프로그램은 정해진 순서대로 진행되며 각 단계는 다음 단계의 관문 역할을 합니다.

1. 시작 및 라이선스.
2. 종속성 확인: PHP 버전 및 확장, 명령줄과 웹 서버 모두에 대한 1단계의 PHP 설정, 시간대 테이블, 2단계의 데이터베이스 설정. 오류는 다음 버튼을 차단합니다. 경고는 차단하지 않지만 내용을 읽어보세요.
3. 설치 유형: 새 메인 서버 또는 원격 수집기.
4. 권한 확인: 3단계의 디렉터리를 직접 써서 테스트합니다.
5. 바이너리 위치: PHP, RRDtool 및 net-snmp 도구의 경로.
6. 데이터 소스 프로필 및 론처 간격.
7. 템플릿 선택: 로드할 장치 템플릿.
8. 테이블 변환, 확인 및 설치 자체.

목록에서 6번 항목은 되돌리기 어려운 항목입니다. 선택한 프로필에 따라 이후 생성되는 모든 RRD 파일에 기록되는 스텝 및 아카이브 세트가 결정되며, 프로필을 편집해도 기존 파일이 마이그레이션되지는 않습니다. 보존 정책 변경에는 별도의 테스트된 마이그레이션이 필요하지만 항상 이력을 폐기해야 하는 것은 아닙니다. 피크 값이 중요하다면 프로필이 평균뿐만 아니라 최댓값도 유지하는지 확인하세요. 지나치기 전에 [데이터 소스 및 라운드 로빈 아카이브](/ko/concepts/data-sources-and-rras/) 문서를 읽어보세요. 그곳에서 제공되는 론처 간격은 1분 또는 5분입니다. 데이터 소스 프로필이 수집 간격을 설정하며, 론처와 프로필은 일관되게 구성되어야 합니다.

## 7단계: 기본 자격 증명 변경

제공된 스키마는 암호가 `admin`인 `admin`이라는 관리자 계정을 시드하며, 첫 로그인 시 변경을 강제하도록 플래그가 지정되어 있습니다. 또한 비활성화된 게스트 계정도 시드합니다. 다른 사용자가 인스턴스에 도달하기 전에, 즉 다른 사용자가 라우팅할 수 있는 네트워크에 인스턴스를 연결하기 전에 암호를 변경하세요.

## 8단계: 폴러 예약

폴러는 외부에서 시작되어야 합니다. 수집 간격과 론처 간격을 일관되게 구성하세요. 폴러는 1분 또는 5분의 론처 간격을 지원하며 일반 실행이 너무 일찍 도착하는 것을 방지하는 가드가 있습니다. 1분 론처의 경우 `php` 및 애플리케이션 경로를 절대 경로로 바꿔서 비특권 폴러 사용자의 crontab에 이 항목을 설치하세요.

```
* * * * * php -q /path/to/kadupul/poller.php > /dev/null 2>&1
```

또는 설치 경로와 비특권 사용자에 맞게 조정된 `service/cactid.service`를 사용하여 제공된 `cactid.php` 데몬을 실행하세요. 하나의 론처만 사용하세요. 데몬을 사용할 때는 cron 작업이나 타이머를 비활성화하세요.

실제 일정을 구성된 론처 간격과 일치시키세요. 1분 미만 수집 프로필의 경우 시작된 폴러가 해당 간격 내에서 수집 주기를 실행합니다. 이 cron 항목으로 1분 미만 주기를 표현하려고 하지 마세요.

**점검하세요.** 폴러 사용자로 수동으로 한 주기를 실행하세요.

```bash
php -q /path/to/kadupul/poller.php --force --debug
```

`--force`는 조기 실행 타이밍 가드를 건너뜁니다. 예약된 실행과 겹치지 않도록 스케줄러를 중지한 상태에서 이 수동 점검을 사용하세요. 다른 유지 관리나 안전 점검을 우회하지는 않습니다. 요약 행과 함께 깔끔하게 완료되어야 합니다. 그런 다음 스케줄러를 활성화하고 두 간격 동안 그대로 두어 사용자 개입 없이 다른 실행이 일어났는지 확인하세요.

## 발생하는 문제

첫 설치 시 실제로 마주치는 오류들입니다.

| 증상 | 원인 | 확인해야 할 곳 |
|---|---|---|
| 올바르게 보이는 PHP 설정에서 설치 프로그램이 중단됨 | 웹 서버와 명령줄이 서로 다른 `php.ini` 파일을 읽음 | `php --ini` 및 웹 SAPI가 보고하는 파일 |
| 시간대에서 설치 프로그램이 중단됨 | 시간대 테이블이 로드되지 않았거나 Kadupul 사용자가 읽을 수 없음 | `SELECT COUNT(*) FROM mysql.time_zone_name` |
| 쓰기 가능한 것처럼 보이는 디렉터리에서 권한 단계가 실패함 | 잘못된 소유자, 또는 SELinux 및 AppArmor | 폴러 사용자로 파일 작성 |
| 설치가 완료되었지만 데이터가 도착하지 않음 | 폴러가 예약되지 않음 | 수동으로 `poller.php --force --debug` 실행 |
| 몇 주기 동안 데이터가 나온 후 사라짐 | 폴러가 잘못된 사용자로 실행되어 웹 사용자가 업데이트할 수 없는 파일을 남김 | RRD 디렉터리 내 파일의 소유자 |
| 그래프에 작은 간격이 가득함 | 예약된 간격과 구성된 간격이 일치하지 않음 | crontab과 구성된 간격 비교 |
| Composer가 설치를 거부함 | PHP가 8.4 미만이거나 매니페스트 필수 확장이 누락됨 | `php -v`, `php -m` 및 Composer 오류 출력 |
| 폴러가 둘 이상의 프로세스를 실행할 수 없음 | `pcntl` 또는 `posix` 누락 | `php -m` |

[로깅](/ko/reference/logging/) 문서에서 각각이 자체 기록되는 위치를 다룹니다. [누락된 데이터 문제 해결](/ko/guides/troubleshoot-missing-data/) 문서에서는 설치는 정상이지만 단일 장치에 문제가 있는 경우를 다룹니다.

## 외부에 노출하기 전에

폴러는 시스템 사용자로 실행되며 RRDtool 및 수집 스크립트를 실행합니다. 명령을 실행하는 애플리케이션으로 설치를 취급하세요. 실제로 그렇게 동작하기 때문입니다.

- TLS를 통해 서비스하세요.
- 기본 관리자 암호를 잠시라도 그대로 두지 마세요.
- 데이터베이스 사용자를 자체 데이터베이스로 제한하세요.
- RRD 및 로그 디렉터리를 문서 루트 외부에 유지하세요.
- 별도로 결정하지 않는 한 게스트 계정을 비활성화 상태로 두세요.

[인터넷 연결 설치 보안](/ko/guides/secure-an-internet-facing-install/) 문서에서 나머지 내용을 다룹니다. 다음 단계: [첫 장치 추가](/ko/start/first-device/).
