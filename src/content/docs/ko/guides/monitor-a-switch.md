:::caution[사용 전 검증 필요]
소스 코드는 공개되어 있지만, 지원되는 Kadupul 릴리스나 마이그레이션 경로는 없습니다. 이를 신뢰하기 전에 백업이 준비된 격리된 사본에서 이러한 절차를 테스트하십시오. [프로젝트 상태](/ko/project/status/)를 참조하십시오.
:::

스위치는 데이터 쿼리의 전형적인 사용 사례입니다. 몇 개의 포트가 존재하는지 미리 알 수 없고, 개수가 변경될 수 있으며, 각 포트마다 고유한 데이터 소스가 필요합니다. 데이터 쿼리 작동 방식은 [템플릿](/ko/concepts/templates/)을 참조하십시오. 이 페이지에서는 올바른 설정에 대해 다룹니다.

## 시작하기 전에

가급적 폴러 사용자로 할당된 수집기에서 장치가 응답하는지 확인하십시오. 구성된 읽기 전용 자격 증명을 사용하십시오. 숫자 OID를 사용하면 로컬에 설치된 MIB 이름에 대한 종속성을 피할 수 있습니다.

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.31.1.1.1.1
```

SNMP v2c 또는 v3를 사용하십시오. 64비트 인터페이스 카운터는 SMIv2 개체이며 v1을 통해 쿼리할 수 없습니다. v1 장치는 32비트 카운터만 제공하며 다른 것은 제공하지 않습니다.

## 장치 템플릿 선택

장치 템플릿은 장치를 추가할 때 제공되는 데이터 쿼리와 그래프 템플릿을 결정합니다. Kadupul은 Cacti에서 제공하는 템플릿 세트를 상속받으며, 여기에는 일반 SNMP 장치 템플릿과 공급업체별 템플릿 세트가 포함됩니다.

어떤 것을 선택하든 포트 검색은 동일한 소스인 `resource/snmp_queries/interface.xml`에 정의된 인터페이스 데이터 쿼리에서 나옵니다. 하드웨어와 일치하는 템플릿이 없으면 일반 템플릿을 선택하고 인터페이스 쿼리를 연결하십시오.

## 데이터 쿼리 실행

쿼리는 `ifIndex`를 순회하여 포트를 찾고, `ifNumber`를 읽어 예상 개수를 확인합니다. 그런 다음 포트당 필드 세트를 수집합니다.

| 필드 | OID | 사용 용도 |
|---|---|---|
| `ifIndex` | `.1.3.6.1.2.1.2.2.1.1` | SNMP 테이블에서의 위치 |
| `ifName` | `.1.3.6.1.2.1.31.1.1.1.1` | 짧은 포트 이름, `Gi1/0/3` |
| `ifDescr` | `.1.3.6.1.2.1.2.2.1.2` | 자세한 설명 |
| `ifAlias` | `.1.3.6.1.2.1.31.1.1.1.18` | 사용자가 구성한 인터페이스 설명 |
| `ifHwAddr` | `.1.3.6.1.2.1.2.2.1.6` | 포트 MAC 주소 |
| `ifSpeed` | `.1.3.6.1.2.1.2.2.1.5` | 속도(bps), 32비트 |
| `ifHighSpeed` | `.1.3.6.1.2.1.31.1.1.1.15` | 속도(Mbps) |
| `ifOperStatus` | `.1.3.6.1.2.1.2.2.1.8` | Up 또는 Down |
| `ifInOctets` / `ifOutOctets` | `.1.3.6.1.2.1.2.2.1.10` / `.16` | 32비트 바이트 카운터 |
| `ifHCInOctets` / `ifHCOutOctets` | `.1.3.6.1.2.1.31.1.1.1.6` / `.10` | 64비트 바이트 카운터 |

장치에 대해 쿼리를 한 번 실행합니다. 검색된 포트 테이블이 반환됩니다. 그래프를 생성하기 전에 이 테이블을 읽으십시오. 이것이 이후의 모든 결정을 위한 기반이 됩니다.

## 64비트 카운터 선택

인터페이스 쿼리는 몇 가지 트래픽 그래프 템플릿을 제공합니다. 주요 항목:

| 그래프 템플릿 | 읽는 대상 |
|---|---|
| In/Out Bits | `ifInOctets`, `ifOutOctets` |
| In/Out Bits (64-bit) | `ifHCInOctets`, `ifHCOutOctets` |
| In/Out Bits (64-bit, 95th) | 동일, 95번째 백분위수 라인 포함 |
| In/Out Bits (64-bit, BW) | 동일, 인터페이스 속도에 상대적 |
| Status (Up/Down) | `ifOperStatus` |
| In/Out (Errors/Discards) | `ifInErrors`, `ifInDiscards`, `ifOutDiscards`, `ifOutErrors` |

특별한 이유가 없는 한 64비트 템플릿을 사용하십시오. 32비트 옥텟 카운터의 상한은 4294967295입니다. 최대 부하 상태의 기가비트 포트는 약 34초 만에 이를 채웁니다. 300초 간격의 스텝에서 폴러는 한 번의 오버플로와 일곱 번의 오버플로를 구별할 수 없으며, `COUNTER`는 두 샘플 사이의 단일 오버플로만 수정합니다. 그래프가 명백히 깨져 보이지는 않으며 지속적으로 너무 낮은 값만 표시됩니다.

수백 개의 그래프를 만들기 전에 카운터가 실제로 채워지고 있는지 확인하십시오.

```bash
snmpwalk -v2c -c 'your-read-only-community' switch.example.net .1.3.6.1.2.1.31.1.1.1.6
```

비어 있거나 실패한 walk는 조사가 필요합니다. 보고된 오류, 액세스 뷰 및 에이전트 지원을 확인하십시오.

## 속도 변경 후 저장된 최대값 확인

데이터 소스가 쿼리 속도를 기반으로 하는 최대값을 사용하는 경우 생성 시 캐시된 검색 데이터에서 속도를 가져옵니다. `ifHighSpeed`가 선호되고, 없으면 `ifSpeed`가 사용되며, 둘 다 0이면 구성된 기본값이 적용됩니다.

해당 값이 파일에 기록됩니다. 100Mbps로 검색된 후 나중에 더 높게 협상된 포트는 실제 트래픽보다 낮은 상한을 유지할 수 있으며 RRDtool은 해당 상한을 초과하는 속도를 unknown으로 기록합니다. 캐시된 속도, 데이터 소스 정의 및 실제 파일을 `rrdtool info`로 비교하십시오.

## 인덱스 결정

실수가 발생할 경우 기록이 손실되는 지점입니다.

각 데이터 소스는 포트에 대한 두 가지 정보를 저장합니다. 포트를 식별하는 필드(인덱스 유형)와 해당 필드의 값입니다. 재인덱싱할 때마다 현재 해당 필드에 해당 값을 가진 SNMP 인덱스를 쿼리하여 포트를 다시 찾습니다. 데이터 소스는 테이블 위치가 아니라 값을 따릅니다.

따라서 핵심 질문은 어떤 필드가 값을 전달하는가입니다.

인터페이스 쿼리는 선호 순서를 선언합니다. `ifName`, `ifDescr`, `ifHwAddr`, `ifIndex` 순입니다. Kadupul은 일반적으로 충분히 고유한 값을 가지고 중복이 없는 후보 중에서 선택합니다.

| 필드 | 생존 상황 | 실패 상황 |
|---|---|---|
| `ifName` | 재부팅, 카드 교체, 번호 재지정 | 에이전트가 비워 두거나 스택 멤버 간에 반복됨 |
| `ifDescr` | 스위치 하드웨어에서 일반적으로 안정적 | 서버에서는 변경되기 쉬운 커널 이름 |
| `ifHwAddr` | 재부팅 | 교체된 카드에 새 MAC이 할당되며, 이는 방지하고자 했던 바로 그 경우임 |
| `ifIndex` | 신뢰할 수 있는 것 없음 | 카드 교체, 재부팅 또는 펌웨어 변경으로 테이블 번호가 다시 매겨짐 |

쿼리가 `ifIndex`로 대체되는 경우 이를 정상적인 결과가 아닌 문제로 처리하십시오. 포트 기록은 스위치가 자유롭게 재할당할 수 있는 번호에 바인딩됩니다.

## 재인덱스 방법

장치별, 데이터 쿼리별로 설정됩니다. Kadupul이 인덱스 필드를 다시 읽는 시기를 결정합니다.

| 방법 | 트리거 조건 | 비용 |
|---|---|---|
| None | 없음. 수동 또는 스크립트 전용 | 없음 |
| Uptime | 장치 SNMP 가동 시간의 역행 | 주기당 한 번의 비교 |
| Index Count | 검색된 인덱스 수의 변경 | 주기당 한 번의 계수 |
| Verify All | 캐시된 ID 확인 실패 | 폴링 중 알려진 인덱스 쿼리 |

Uptime은 기본값이며 재부팅이 인덱스 번호를 다시 매기는 이벤트이므로 대부분의 스위치에 적합합니다. Index Count는 재부팅 없이 추가되거나 제거된 카드를 캡처합니다. Verify All은 알려진 인덱스에서 변경된 ID를 감지할 수 있지만 새 포트 검색을 보장하지는 않습니다.

선택한 장치 및 쿼리를 다시 실행하려면 두 ID를 모두 설치된 ID로 대체하십시오. 해당 장치에 대한 모든 쿼리를 다시 실행하려면 `--qid`를 생략하십시오.

```bash
php cli/poller_reindex_hosts.php --id=42 --qid=16
```

`--id=all`은 실행 범위를 활성화된 모든 장치로 확장합니다. 겹치는 재인덱스 실행을 피하십시오. `--force`는 프로세스 등록을 우회하고 제목 캐시를 새로 고칩니다.

## 포트가 사라졌을 때

포트가 누락되었다고 해서 수집이 자동으로 중지된다고 가정하지 마십시오. 현재 재인덱스 코드는 ID가 확인되지 않고 어떤 소스도 인덱스를 변경하지 않을 때 고아 플래그를 재설정하고 이전 폴링 OID를 유지할 수 있습니다. 저장된 ID를 새 검색 캐시와 비교하고 일치가 확인될 때까지 영향을 받는 소스를 비활성화하십시오. [데이터 쿼리 및 인덱스](/ko/concepts/data-queries-and-indexes/)를 참조하십시오.

## 대형 섀시

포트 수가 많아지면 장치당 두 가지 설정이 중요해집니다. SNMP 요청당 구성된 OID와 장치당 스레드 수를 확인하십시오. 일괄 처리 지원과 유효 병렬성은 수집기와 에이전트에 따라 다릅니다. PHP `cmd.php`와 Spine은 동일한 스레딩 동작을 제공하지 않습니다.

한 번에 하나의 설정만 변경하고 폴러 주기 지속 시간을 관찰하십시오.

## 실패 모드

| 증상 | 원인 |
|---|---|
| 그래프가 생성되었지만 모든 측정값이 unknown | 64비트 카운터가 구현되지 않았거나 장치가 SNMP v1 사용 |
| 카운터가 터무니없는 값으로 급증함 | 32비트 카운터가 단일 간격 내에 두 번 이상 오버플로됨 |
| 높은 부하에서만 간격 발생 | RRD 최대값이 오래된 검색 속도에 고정됨 |
| 유지 관리 후 포트 기록이 잘못된 포트에 할당됨 | 불안정한 ID, 오래된 매핑 또는 해결되지 않은 고아 처리 |
| 폴러가 유효하지 않은 SNMP 인덱스에 대한 경고 기록 | 인덱스 없이 남겨진 데이터 소스. 다시 색인화, 삭제 또는 비활성화 |
| 포트는 검색되었으나 아무것도 수집되지 않음 | 인덱스가 비어 있는 데이터 소스는 폴러 캐시 항목을 만들지 않음 |
