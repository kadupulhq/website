:::caution[使用前に検証してください]
ソースコードは公開されていますが、サポートされている Kadupul のリリースや移行パスはまだ存在しません。本運用で依存する前に、バックアップを備えた隔離された環境でこれらの手順をテストしてください。[プロジェクトのステータス](/ja/project/status/)を参照してください。
:::

完全な Kadupul のリカバリセットには3つの要素があります。部分的なバックアップでは設定や測定値を復旧できても、インストール環境全体を再現することはできません。

| 要素 | 保持する内容 | 格納場所 |
|---|---|---|
| データベース | デバイス、テンプレート、ユーザー、権限、ポーラーキャッシュ、およびすべての RRD ファイルのパス | MySQL または MariaDB |
| RRD ファイル | 保持された測定値と統合アーカイブ | RRA ディレクトリ（デフォルトではインストール環境下の `rra/`） |
| 設定 | データベース認証情報、パス、コレクター設定、プラグインおよびスクリプトコード | `include/config.php`、spine 設定ファイル、`plugins/`、`scripts/`、`resource/` |

## データベースのみのバックアップで復旧できるもの

データベースはグラフ定義と監視設定を保持し、RRD ファイルは履歴グラフアーカイブを保持します。Boost が有効になっている場合、最新の測定値はファイルにフラッシュされるまでデータベースのキューに保持されることもあります。データベースバックアップの一部として、これらのキューも必ず保護してください。[アーキテクチャ](/ja/concepts/architecture/)を参照してください。

データベースのみを復元した場合、400台のデバイスを認識し、すべてのグラフが定義されているものの、すべてのグラフが空で描画されるシステムになります。ポーラーを起動した瞬間から収集が再開されますが、過去の履歴は失われます。

## RRD のみのバックアップで欠落するもの

RRD ファイルには名前付きデータソース、アーカイブ定義、および値が含まれていますが、それらの値をアプリケーションに再接続するために必要な Kadupul のデバイス、クエリ、グラフ、権限などの完全なメタデータは含まれていません。

「スイッチ12のポート3の入力バイト数」からディスク上のパスへのマッピングは、データベース内のデータソースのカラムに保持されています。ファイルツリーのみを復元した場合、手動でリバースエンジニアリングしない限りどれがどれであるかを判別できない、数字で満たされた数千個のファイルが残るだけです。

この2つは揃って1つのバックアップです。そのように扱ってください。

## 両者の一致と整合性

こここそが、ほとんどのバックアップ手順が見過ごして誤りを犯しやすい点です。

ポーラーは RRD ファイルへ継続的に書き込みを行います。更新の実行中にコピーされたファイルは、書き込みの途中で取得されてしまう可能性があります。データベースも同時に書き込まれています。02:00 にデータベースをダンプし、02:20 にファイルのコピーを開始した場合、この2つの部分は異なる時点を表すことになり、その間に作成または削除されたデータソースはすべて不整合になります。

RRD の遅延書き込みは、この問題をさらに複雑で興味深いものにします。このモードでは、ポーラーは毎回の実行ごとに RRD ファイルへの書き込みを行いません。測定結果は耐久性のあるデータベーステーブルに蓄積され、後でまとめてフラッシュされます。したがって、データベースはフラッシュ間隔の分だけ RRD ファイルよりも正当に進んでいる状態になり、ディスク上の他の場所には存在しない実際の測定値を保持している可能性があります。

以下のいずれかの方法を選択してください（推奨度の高い順）：

**整合スナップショット。** データベースエンジンがサポートするバックアップまたは静止化（quiescing）手順を使用し、すべての RRD ストレージおよびアプリケーション設定のスナップショットと連携させます。ファイルシステムのスナップショット単体では、別々のボリューム、リモートコレクター、保留中キュー、または稼働中のデータベース全体で整合性を確立することはできません。

**静止化論理バックアップ。** スケジュールされたランチャーやその他のプロデューサーを無効化し、実行中のコレクターが完了するのを待ってから、遅延書き込みをフラッシュし、フラッシュワーカーの完了を待ちます。バックアップ取得中は、設定変更、メンテナンス、その他の RRD への書き込みをすべて停止した状態に保ちます。収集の中断によってサンプルの欠落が生じる場合がありますが、その現れ方はハートビートと統合設定に依存します。

例を実行する前に、これらの静止化手順を完了し、キューおよびワーカーの状態を確認してください。`poller_boost.php --force` が 0 を返したこと単体では、フラッシュが完了した証明にはなりません。すでに登録済みの Boost プロセスが存在すると、実際の作業を行わずに終了することがあります。rrdcached サービスやリモートストレージは別途連携させてください。

この Bash の例では、ローカルストレージ、プライベートクライアントオプションファイルで設定されたデータベースアカウント、および管理対象のすべての RRD を含む RRA ディレクトリを前提としています。すべてのパスを実際の環境に合わせて置き換えてください。カスタムの絶対 RRD パス、シンボリックリンク先、外部設定、およびリモートコレクターを洗い出し、それらも個別に取得してください。

```bash
set -euo pipefail
umask 077

APP=/path/to/kadupul
RRA=/path/to/kadupul/rra             # use the actual configured storage path
DEST=/var/backups/kadupul            # outside the served tree
MYSQL_CNF=/secure/path/backup-client.cnf
DB=$(php -r 'require $argv[1]; echo $database_default;' "$APP/include/config.php")
STAMP=$(date -u +%Y%m%dT%H%M%SZ)

install -d -m 0700 "$DEST"
STAGE=$(mktemp -d "$DEST/.partial-XXXXXXXX")
FINAL="$DEST/backup-$STAMP-${STAGE##*partial-}"

# All writers must already be stopped and deferred queues handled.
mysqldump --defaults-extra-file="$MYSQL_CNF" \
  --single-transaction --routines --events --triggers "$DB" > "$STAGE/db.sql"
tar -C "$RRA" -cf "$STAGE/rrd.tar" .
tar --exclude='./rra' --exclude='./log' --exclude='./cache' --exclude='./.git' \
  -C "$APP" -cf "$STAGE/application.tar" .

( cd "$STAGE"
  sha256sum db.sql rrd.tar application.tar > SHA256SUMS
  sha256sum --check SHA256SUMS )
test ! -e "$FINAL"
mv "$STAGE" "$FINAL"
```

アプリケーションアーカイブには設定と一致するコードが含まれます。ソースリビジョン、データベースおよび RRDtool のバージョン、実際のストレージパス、ライターのシャットダウン/フラッシュ状態をバックアップセットとともに記録してください。この例では通常のログ、キャッシュ、Git メタデータを除外しています。ご自身の環境に合わせてこれらの除外対象を確認してください。

正常に取得され、チェックサムが検証されたセットのみが最終的なディレクトリ名を受け取ります。失敗したコマンドによって `.partial-*` の内部に切り詰められたファイルが残る可能性があります。`set -e` は後続のコマンドを停止しますが、すでに作成された出力を削除することはありません。そのディレクトリを完了したバックアップとして扱わないでください。チェックサムは後からの変更を検出するものであり、論理的な完全性を保証するものではありません。復元テストは依然として不可欠です。

`--single-transaction` はトランザクションテーブルを対象としており、非トランザクションのプラグインテーブルや同時並行のスキーマ変更の一貫したスナップショットを保証するものではありません。書き込みとスキーマ変更を停止したままにするか、エンジンに適したバックアップ方法を使用してください。キャプチャが完了し、ストレージが使用可能であることを確認した後にのみ収集を再開してください。トランザクションおよび権限の要件については、[mysqldump documentation](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html) を参照してください。初期のスクリプトにあった欠落事項は [website #12](https://github.com/kadupulhq/website/issues/12) で追跡されています。

**時間差を受け入れ、記録する。** どちらの部分を先に取得しても、先に取得した方が古くなり、順序を変えただけで稼働中のペアの整合性が自然に取れるわけではありません。時間枠を記録してください。それこそが結果を復旧可能にする鍵です。

先にデータベースをダンプし、後からファイルをコピーした場合、ファイルの方が新しくなります。時間枠の間に削除されたデータソースはダンプ内に残りますが、そのファイルは消失しているため、ポーラーが再作成する参照が残ります。時間枠の間に作成されたデータソースは、データベースが認識しないファイルとして到着し、機能しません。

先にファイルをコピーし、後からデータベースをダンプした場合、データベースの方が新しくなります。時間枠の間に作成されたデータソースはダンプ内に存在しますが対応するファイルがないため、ポーラーはそれを空のファイルとして再作成します。

どちらの順序であっても、必要なファイルがコピーされる前に削除されると、時間枠より前の履歴が失われる可能性があります。また、書き込み途中のファイルや不整合なキュー内サンプルが取得される可能性もあります。時間差の記録は制約を文書化するものであり、不整合なペアを完全なものにしたり、復旧可能性を保証したりするものではありません。

## 思い至らないバックアップ内の情報

デバイスの認証情報はデータベース内に平文で保持されています。ポーラーキャッシュは、コレクターが毎回の実行で必要とするため、SNMP コミュニティ名や SNMPv3 のユーザー名、パスワード、パスフレーズを通常のカラムとして保持しています。設定ファイルにはデータベースのパスワードが含まれています。

したがって、Kadupul のバックアップは監視しているすべてのデバイスの認証情報ストアそのものです。保存時に暗号化し、読み取り権限を制限し、汎用のファイル共有に配置しないようにしてください。

## 復元の順序

各手順がその前の手順に依存しているため、順序が重要になります。

1. **最初に設定を復元する。** データベース認証情報と RRA パスがなければ、他の何も確認できません。別のハードウェアへの復元の場合は、後からではなく今すぐパスを修正してください。

2. **RRD ツリーを復元する。** 設定に記載されている場所に配置します。所有権とパーミッションを確認してください。ポーラーはこれらのファイルにポーラーユーザーとして書き込み、Web インターフェースは Web サーバーユーザーとして読み取ります。内容は保持されていても所有権が保持されていない復元を行うと、グラフは正常に描画されるものの何も収集されないシステムになります。

3. **データベースを復元する。** ダンプ内のバージョンテーブルは、復元先となるコードと一致していなければなりません。復元されたコンポーネントがまとめて確認されるまで、すべてのランチャーとライターを無効のままにしてください。古いリリースのダンプを新しいコード上に復元すると、Web インターフェースがインストーラーにリダイレクトされます。これは正しい動作ですが、復旧の最中に望む動作ではありません。まず一致するコードを復元してください。

4. **ポーラーキャッシュを再構築する。** キャッシュは派生データであり、復元作業はまさにキャッシュが古くなっている可能性が高い状況です。再構築にかかるコストは1回の実行だけであり、紛らわしい症状の大部分を未然に防ぐことができます。

5. **ポーラーを起動し、1つのファイルを確認する。** 初回実行後に RRD ファイルの最終更新日時が進むことを確認してください。グラフが復元ポイントまでは描画され、その後が平坦になっている場合は、収集結果、キュー、タイムスタンプ、パス、およびパーミッションを調査してください。平坦なグラフだけでは原因を特定できません。

## 落とし穴

**RRD ファイルは過去の更新を拒否します。** RRD ファイルは、すでに保持しているタイムスタンプ以前のサンプルを受け付けません。新しいデータベースに対して古いファイルセットを復元しても、それだけで失われたサンプルが埋め戻されるわけではありません。保持されていた遅延キューやその他のソースに復旧可能な測定値が含まれている可能性はありますが、再生には個別の検証とタイムスタンプ順の並べ替えが必要です。それらの測定値がなければ、収集はギャップを残したまま再開されます。これが、2つのバックアップ間でファイルをコピーしてマージすることができない理由でもあります。

**何かを書き換える前に、保存されているパスがトークン化されているか確認してください。** 自動生成されたデータソースはパスを `<path_rra>/name.rrd` として保存し、このトークンは読み取り時に RRD パス設定から展開されます。それらの場合、インストールの移行は設定を変更してポーラーキャッシュを再構築することを意味し、テーブルの行を書き換えることではありません。手動で入力されたパスはリテラルとして保存されているため、書き換えが必要です。テーブル全体の更新を実行する前に確認してください。トークン化されたパスを絶対パスに書き換えてしまうと、次回の移行がさらに困難になります。

**リモートコレクターには独自の設定ファイルがあります。** それぞれが独自のデータベース認証情報とコレクター ID を保持しています。それらは中央のデータベースバックアップには含まれていません。ホストごとに取得してください。

**プラグインのデータは同じデータベース内にあります。** プラグインはインストール時に独自のテーブルを作成するため、データベース全体のダンプでカバーされます。プラグインのコードはデータベース内にはありません。一致する `plugins/` ディレクトリなしでデータベースを復元すると、見つからない機能は無効化されます。

**復元したことのないバックアップは単なる仮説に過ぎません。** スケジュールに従ってテスト用のインスタンスに復元してください。これによって最も頻繁に発見される障害は、破損ではなく、3つの要素のうち1つしか取得していなかったバックアップです。
