:::caution[継承されたRRDtoolプロキシの動作]
KadupulではRRDtoolプロキシ構成はサポートされていません。ローカルRRDtoolストレージ（`storage_location = 0`）を使用してください。このページのプロキシ設定、プロトコルの説明、ワークフローは継承された動作を説明するものであり、サポートされている構成や移行パスではありません。[RRDtoolプロキシ](/ja/reference/rrdproxy/)を参照してください。
:::

KadupulのWebアプリケーション、データベース、スケジュール収集、RRDストレージはそれぞれ異なる役割を持ちますが、実行パスは重複しています。どの処理が失敗したかを把握することで調査範囲を絞り込めます。インターフェースが正常に表示されているからといって、収集が機能している証拠にはなりません。

**Webインターフェース**はPHPアプリケーションです。設定を管理し、キャッシュされたグラフの描画や配信を行います。リアルタイムグラフのリクエストなど、一部のWebアクションは収集処理も起動し、通常のグラフレポート要求が保留中のRRD更新をトリガーすることもあります。

**データベース**は設定、権限、稼働状態、ポーラーキャッシュ、測定キューを保持します。収集された値は、RRDへの書き込みや再試行を待つ間データベース内に留まることがあり、単なる設定保存場所ではありません。

**ポーラー**はスケジュールされた作業と子収集プロセスの実行を調整します。収集結果はデータベースキューを経由し、その後通常または遅延ライターがRRDファイルを更新します。

**RRDファイル**は期間が限定された時系列履歴データを保持します。通常、データソースにはそのフィールドを含む1つのRRDが割り当てられます。グラフ作成時に既存のソースを再利用することもでき、メタデータを作成したからといってファイルが既に存在するとは限りません。

## 各層の境界

| 境界 | 通過するデータ | 伝送手段 |
|---|---|---|
| インターフェースからデータベース | 設定、セッション、認可、キャッシュされた作業、運用データ | SQL（データベースはリモートホストでも可） |
| インターフェースからファイル | グラフ読み取り、キャッシュ画像、対象となるオンデマンドRRD更新または作成 | ファイルシステムおよびRRDtool |
| ポーラーからデータベース | 作業リスト、収集値、保持キュー、ステータス、カウントダウン | SQL |
| 収集プロセスからデバイス | SNMP、収集スクリプト、疎通確認 | ネットワークまたはローカルコマンド（Webトリガー収集も可） |
| ライターからファイル | グループ化されたサンプル（1回の更新に複数のタイムスタンプが含まれる場合あり） | RRDtoolコマンドおよび応答パイプ |
| データベースサーバーからRRDファイル | 通常のアプリケーションパスにおいてRRDへの直接更新はなし | アプリケーションのライターコードが2つのストレージを調整 |

データベースのレコードはデータソースをデバイスおよび設定されたファイルパスに関連付けます。RRDtoolファイルは時系列データとアーカイブを定義しますが、アプリケーション側のマッピングを置き換えるものではありません。ネットワークトラフィックはデバイスへのポーリングに限定されず、データベース接続、リモートコレクター、その他の連携機能もホスト間を通信します。

データベースの状態、保留中のサンプル、RRDファイルは常に整合性を保ってバックアップしてください。データベースのみの復元ではRRDの過去データは復元されず、ファイルのみの復元では設定や未フラッシュのサンプルが失われます。パスを整合させずにファイルを移動すると、ファイル未検出エラーや書き込み保留が発生する原因となり、必ずしも無言の収集障害になるとは限りません。[バックアップと復元](/ja/guides/back-up-and-restore/)および[新しいハードウェアへの移行](/ja/guides/migrate-to-new-hardware/)を参照してください。

## なぜ長期履歴にRRDファイルを使用するのか

長期的なグラフ履歴はRRDに保存されますが、測定キューはデータベース内に置かれます。本リビジョンにおける通常の処理中キューはInnoDBであり、遅延書き込みはBoostテーブル内にサンプルを保持します。書き込みの失敗やリモート配信の遅延により、これらのキューが増大することがあります。[大量書き込みの処理](/ja/concepts/high-volume-writes/)を参照してください。

RRDは選択された解像度ごとに決められた行数を割り当てます。通常の更新では履歴を無制限に追加するのではなく、その割り当て済み領域を循環再利用します。構成が変わらなければファイルサイズは一定に保たれますが、データソースの追加、構成の変更、リカバリ用コピーの保持、キューの蓄積によって総ストレージ要件は依然として増加します。

トレードオフとなるのは事前に決められた保持期間です。詳細な履歴の期限が切れるか統合されると、後から構成を変更しても破棄された詳細データを再現することはできません。[データソースとラウンドロビンアーカイブ](/ja/concepts/data-sources-and-rras/)を参照してください。

アプリケーションは共有更新とリレーショナルクエリを必要とするため、設定や運用状態の保存にはデータベースを使用します。これはすべての関係がデータベースの外部キーによって強制されていることや、テーブルが永続的に肥大化することを意味するものではなく、本アプリケーションの責任分担を表しています。

## 2つのパーツを共有する2つのパス

通常のページまたはグラフレクエストは一般に以下のパスをたどります。

1. ブラウザがリクエストを送信し、PHPが設定を読み込んでデータベースに接続します。
2. リクエストに対して認証および該当するレルム・オブジェクト認可が適用されます。
3. コンソール操作によって設定が読み取りまたは更新され、追加の処理が開始されることがあります。
4. グラフレクエストは保留中のBoostサンプルと画像キャッシュを確認するか、RRDtoolコマンドを組み立てて設定されたファイルを読み込みます。[グラフ描画の仕組み](/ja/concepts/how-graphs-are-drawn/)を参照してください。
5. リアルタイムグラフレクエストはリアルタイムコレクターを起動し、個別のテンポラリデータを使用することがあります。グラフが平坦であることだけでは、ファイルが空であることや収集・描画の成功を証明できません。

定期的なスケジュール収集は一般に以下のパスをたどります。

1. スケジューラーがポーラーを起動し、有効状態、タイミング、ストレージを確認します。
2. ポーラーキャッシュから実行すべき作業を選択し、子コレクタープロセスを起動します。
3. 子プロセスがデバイスに問い合わせるか収集スクリプトを実行し、結果をデータベースにステージングします。
4. 該当するライターがグループ化されたサンプルを処理し、設定されている場合は遅延キューを使用し、再試行可能な障害を保持します。
5. 稼働ステータスとスケジューリング状態がデータベース内で更新されます。

順序と障害処理の詳細については[ポーラーのライフサイクル](/ja/reference/poller-lifecycle/)を参照してください。これらのパスはデータベースとストレージのリソースを共有するため競合が発生する可能性があります。Webサーバーを再起動しても個別にスケジュールされたポーラーは修復されませんが、Webリクエストが収集や書き込みに関与することがあります。実際に障害を起こしているプロセスを特定してください。

## どのユーザー権限で何が実行されるか

| プロセス | 実行ユーザー | 起動元 |
|---|---|---|
| PHP Webアプリケーション | WebサーバーまたはPHP-FPMプールの実行アカウント | Webサーバー |
| スケジュールポーラー | スケジューラーの設定アカウント | cron、タスクスケジューラ、または設定済みサービス |
| RRDtool | 通常は起動元プロセスの実行アカウントを継承 | Web、ポーラー、または保守パス |
| 収集スクリプト | 通常はコレクターの実行アカウントを継承 | 定期収集またはWebトリガー収集 |

関与するすべての書き込みアカウントには、設定されたストレージへの適切なアクセス権が必要です。通常のデータソース作成ではメタデータのみが書き込まれ、RRDファイルはライターが必要とした時点で後から作成されることがあります。ファイルが存在しない場合、パス、信頼設定、権限、作成処理の失敗だけでなく、収集処理がその段階に到達していないことも考えられます。

root権限で実行される一部の作成パスでは、RRAディレクトリの所有者とグループを適用しようとします。これらの試行は失敗してエラーログを出力することがあり、サービスアカウントの適切な設定の代わりにはなりません。非rootの所有権はディレクトリのグループ継承やACLを含むOSの規則に従います。すべてのWebおよびポーラー書き込みアカウントにおいて、ストレージ権限と数値による信頼されたUID/GID設定を検証してください。[安全なアップグレード](/ja/guides/upgrade-safely/)を参照してください。

検証対象となったPHP ICMP実装はオペレーティングシステムのpingユーティリティを呼び出します。プローブを送信できるかどうかはそのユーティリティとOSポリシーに依存します。過去の実効UIDヘルパーが存在するからといって、各ICMPプローブがPHPをrootに昇格させるわけではありません。pingを有効にするためだけにアプリケーションをrootで実行しないでください。実際のコマンド、実行アカウント、エラー出力を確認してください。TCPとUDPのチェックでは到達性の意味合いが異なります。

## 作業リストは事前計算される

各実行時にテンプレート関係からすべてのコマンドを導出する負担を避けるため、ポーラーキャッシュには解決済みの収集作業が保存されます。設定変更操作によって該当するエントリが再構築され、必要に応じて明示的な再構築ツールも用意されています。

キャッシュされたフィールドに反映される変更は、収集処理が使用する前にそれらのエントリに届いている必要があります。他の設定は個別に読み込まれるため、すべての設定変更で手動のキャッシュ再構築が必要なわけではありません。単一の原因を決めつけず、キャッシュの内容、収集エラー、リモートレプリケーションの状態を確認してください。[ポーラーキャッシュ](/ja/concepts/the-poller-cache/)および[リモートデータ収集](/ja/concepts/remote-data-collection/)を参照してください。

## よく問題が発生する箇所

| 症状 | 有効な確認項目 |
|---|---|
| インターフェースは動作するがグラフが平坦 | スケジューラーの稼働、収集エラー、キュー、サンプルの鮮度、グラフの表示期間 |
| ポーラーは動作するがファイルが更新されない | ライターの応答確認/エラー、ストレージの信頼性と権限、遅延バックログ |
| 単一のデータソースのみ平坦 | デバイスの応答、キャッシュ行、ファイルマッピング、不明（unknown）サンプル、描画式 |
| 設定変更が反映されないように見える | 保存結果、テンプレートの上書き、対象キャッシュエントリ、レプリケーション |
| 定期的なデータ欠落 | タイミング、ハートビート、タイムアウト、デバイスの可用性、書き込み障害 |
| グラフの形状が想定と異なる | 生成されたコマンド、CDEF/CFの選択、実際のファイルデータ、画像キャッシュ、マッピング |
| ポートの履歴が別のインターフェースに紐付いている | クエリの識別情報、番号の再割り当て、再インデックスの結果 |
| アカウントでコンソールは見えるがグラフが表示されない | グラフページのレルム、オブジェクト認可、要求されたグラフの識別情報 |
| コレクター間でデータが一致しない | 割り当て、複製された設定、ローカルの上書き、接続状態 |
| システム全体が遅い | データベース待機、ライター/ストレージの競合、コレクターの実行時間、Web負荷 |
| データソースのメタデータはあるがファイルがない | 初回収集/書き込み、設定されたパス、信頼設定および作成エラー |

これらは調査の出発点であり、診断結果そのものではありません。該当する境界に沿って証拠を確認し、変更後に結果を検証してください。[欠落データのトラブルシューティング](/ja/guides/troubleshoot-missing-data/)を参照してください。
